# 第 52 章 容器与虚拟化

第 46-51 章把服务直接跑在系统上。真实项目里还有两种打包方式：**容器**（应用 + 依赖一起走）与**虚拟机**（完整操作系统）。本章讲在 Arch 与 WSL 上怎么用它们，以及各自会在哪里失灵——这一章的环境差异最大，凡是 WSL 做不到的都会明确标注。

> 本章目标：能说清容器与虚拟机的唯一关键差别及其后果；会用 Docker 或 Podman 运行、进入、看日志、挂载数据卷；能用 compose 描述多容器应用；知道 WSL 上跑容器的三个具体限制（内核、cgroups、网络）；了解 libvirt/QEMU 的定位与「WSL 里通常跑不了 KVM」的原因。
> 对应 Wiki：[Docker](https://wiki.archlinux.org/title/Docker)、[Podman](https://wiki.archlinux.org/title/Podman)、[Libvirt](https://wiki.archlinux.org/title/Libvirt)

## 容器与虚拟机：只差一件事

| 维度 | 容器 | 虚拟机 |
| --- | --- | --- |
| 内核 | **共享宿主内核** | 各自跑一个完整内核 |
| 隔离边界 | 命名空间 + cgroups + 安全模块 | 硬件虚拟化（VT-x/AMD-V） |
| 启动时间 | 毫秒到秒 | 数十秒 |
| 能跑的系统 | 与宿主同内核（Linux 跑 Linux） | 任意操作系统 |
| 内核相关操作 | 受限（模块、`sysctl`、部分特权） | 完全自由 |
| 典型用途 | 应用分发、环境一致 | 异构系统、内核实验、完整隔离 |

这一条差别解释了两类常见困惑：容器里 `uname -r` 显示的是宿主内核（不是镜像的）；容器里 `modprobe` 或改内核参数通常失败（不是权限没给对）。

## Docker：最普及的路径

（环境：WSL）

```bash
sudo pacman -S docker
sudo systemctl enable --now docker
sudo docker run --rm hello-world
```

日常命令只需六个：

```bash
docker ps -a                       # 容器列表（含已退出）
docker images                      # 镜像列表
docker run -d --name web -p 8080:80 nginx
docker logs -f web                 # 跟日志
docker exec -it web sh             # 进容器
docker rm -f web && docker rmi nginx
```

四个必须理解的参数：

- `-p 宿主端口:容器端口`：把容器端口映射出来。`-p 127.0.0.1:8080:80` 只绑回环，比 `-p 8080:80`（默认绑 `0.0.0.0`）安全；
- `-v 宿主路径:容器路径`：数据卷或绑定挂载。**容器删了，卷里的数据还在；没挂卷的数据跟着容器一起没**；
- `--name`：给容器起名，后续 `logs`/`exec`/`rm` 都用它；
- `-d`：后台运行（对应第 46 章讲的「容器内部不要再 daemonize」）。

`docker` 组等于 root：把用户加进 `docker` 组后，该用户能挂载宿主目录、能起特权容器——**这是提权，不是权限细化**。个人开发机可接受，多人机器应改用 rootless（下一节）。

## Podman：无守护进程的替代

Podman 的命令与 Docker 几乎一一对应，差别在架构：**没有常驻守护进程**，默认以普通用户 rootless 运行。

```bash
sudo pacman -S podman
podman run --rm hello-world
podman ps -a
```

三个好处：不需要 root 守护进程（攻击面小）、rootless 下容器内的 root 映射到宿主的普通用户、可以用 `podman generate systemd`（或更新的 Quadlet）把容器变成第 46 章那样的 systemd 单元。

代价也要知道：rootless 容器只能绑定 1024 以上的端口（要 80/443 得靠反代或 `net.ipv4.ip_unprivileged_port_start`）；部分存储驱动与网络模式需要额外配置；与 Docker 的 compose 文件虽基本通用，但总有边角差异。

## compose：多容器应用

一个 Web + 数据库的最小 `compose.yaml`：

```yaml
services:
  app:
    image: nginx:alpine
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: example
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

```bash
docker compose up -d      # 或 podman-compose up -d
docker compose ps
docker compose logs -f app
docker compose down       # 加 -v 会一并删除卷（数据没了）
```

`depends_on` 只保证**启动顺序**，不保证数据库就绪——应用要有重试或健康检查（`healthcheck`）。`down -v` 删卷是常见的数据丢失事故，执行前确认。

## WSL 上跑容器：三个限制

1. **内核是微软的**：容器共享 WSL 的内核，需要特定内核模块或内核版本的功能（如某些 eBPF、`nf_tables` 高级特性）可能不可用。
2. **cgroups 与 systemd**：rootless Podman 需要 cgroups v2 与 systemd 用户会话；WSL 里 systemd 未启用时（第 26 章）会直接失败。
3. **网络模式**：WSL2 默认 NAT，容器端口要经「容器 → WSL → Windows」两次转发；mirrored 模式下行为不同。`localhost` 在 Windows 侧能否访问容器端口，取决于模式与端口绑定地址。

另外，把宿主目录挂成 `/mnt/c/...` 的绑定挂载在 I/O 上很慢（跨文件系统），代码目录建议放在 WSL 的 ext4 里。

## libvirt/QEMU：完整虚拟化

（环境：真机或支持嵌套虚拟化的 VM；**WSL 通常跑不了 KVM**，因为拿不到 `/dev/kvm`）

```bash
sudo pacman -S libvirt qemu-full virt-manager
sudo systemctl enable --now libvirtd
sudo usermod -aG libvirt "$USER"     # 重新登录后生效
```

- **QEMU** 是模拟器/虚拟化器本体，`-enable-kvm` 才走向硬件加速；
- **libvirt** 是管理层（守护进程 + API + 存储/网络抽象），`virsh` 与图形化的 `virt-manager` 都通过它操作；
- 没有 `/dev/kvm` 时一切退化为纯软件模拟，慢到不可用——这是判断「能不能在这台机器上跑虚拟机」的第一条命令：

```bash
ls -l /dev/kvm
```

## 小结

- 容器与虚拟机只差「是否共享内核」；这条差别决定了启动速度、隔离强度与内核相关操作是否可用。
- Docker：`run/ps/logs/exec/rm` 六个命令覆盖日常；`-p` 绑定地址与 `-v` 数据卷是最容易出事的两个参数。
- `docker` 组等价 root；多人环境用 rootless Podman，并可交给 systemd 托管。
- compose 的 `depends_on` 只管顺序不管就绪；`down -v` 会删数据卷。
- WSL 跑容器的三个限制：微软内核、cgroups/systemd、双重 NAT；跨 `/mnt/c` 的绑定挂载很慢。
- libvirt/QEMU 需要 `/dev/kvm`；WSL 通常没有，虚拟机实验请在支持嵌套虚拟化的环境做。

## 练习

1. 最小容器（环境：WSL）：跑 `nginx:alpine`，用 `-p 127.0.0.1:8080:80` 绑定回环，`curl` 验证；再改成 `-p 8080:80`，用 `ss -tlnp` 看绑定地址的变化。
2. 数据持久化（环境：WSL）：用命名卷跑一次数据库，写入数据后 `rm -f` 容器，重新起一个挂同一卷，验证数据还在；再试不挂卷的版本，确认数据消失。
3. 进容器（环境：WSL）：`docker exec -it <容器> sh` 后运行 `uname -r` 与 `cat /etc/os-release`，解释为什么内核版本是宿主的、发行版是镜像的。
4. compose（环境：WSL）：用正文的 yaml 起两个容器，`docker compose logs` 观察启动顺序；把 `depends_on` 去掉再起一次，记录应用启动失败的报错（体现「顺序 ≠ 就绪」）。
5. 内核边界（环境：WSL）：在容器里尝试 `modprobe dummy` 与 `sysctl -w net.ipv4.ip_forward=1`，记录失败信息，并解释这是隔离设计还是权限问题。
6. 虚拟化能力检查（环境：VM/真机）：`ls -l /dev/kvm` 与 `egrep -c '(vmx|svm)' /proc/cpuinfo` 各是什么结果？据此判断这台机器能否跑硬件加速的虚拟机。
