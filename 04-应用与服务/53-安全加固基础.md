# 第 53 章 安全加固基础

安全不是一堆开关，而是一条顺序：**减少暴露面 → 限制权限 → 能看见异常 → 能快速更新**。这一章按这四步给出 Arch 上的最小加固集：SSH、防火墙、sudo 策略、AppArmor 概念、最小权限实践与更新机制。深度以「个人服务器 / 开发机」为准；面向公网的高价值系统还需要审计、入侵检测与备份演练。

> 环境前置：本章用到 `systemctl`/`journalctl`，需要 systemd 为 PID 1（`ps -p 1 -o comm=` 验证；WSL 未启用时按第 26 章启用）；防火墙与 sshd 实验在 VM 或真机做。

> 本章目标：能用 `sshd -T` 核对 SSH 的实际生效配置并安全地改成仅密钥登录；能用 nftables 写出一份默认拒绝的入站规则并持久化；能设计 sudo 授权（drop-in、超时、按命令）并识别 `NOPASSWD` 的风险；理解 AppArmor 的路径式访问控制与启用前提；能列出其余五条最小权限实践与两条更新机制（`arch-audit`、整系统升级）。
> 对应 Wiki：[Security](https://wiki.archlinux.org/title/Security)、[OpenSSH](https://wiki.archlinux.org/title/OpenSSH)、[Nftables](https://wiki.archlinux.org/title/Nftables)、[AppArmor](https://wiki.archlinux.org/title/AppArmor)

## 第一层：减少暴露面

先回答「这台机器需要对谁开放什么」。默认答案应该是：**只开必要的端口，只允许必要的人**。

```bash
ss -tulpn                 # 谁在监听；0.0.0.0 与 127.0.0.1 的区别（第 18 章）
sudo systemctl list-unit-files --state=enabled   # 开机自起了哪些服务
```

两条立刻能做的事：把只给本机用的服务绑到 `127.0.0.1`（数据库、Redis、开发服务器）；停掉并 `disable` 不用的服务。这比任何防火墙规则都有效——规则写错还能堵住，端口根本不听就没有被扫的风险。

## SSH：最该先加固的一项

第 18 章讲过密钥登录与 `sshd_config` 的四个关键项。这里补两个工程细节。

**一、用 `sshd -T` 核对实际生效值**：配置文件有 include、有默认值、有 drop-in（`/etc/ssh/sshd_config.d/*.conf`），肉眼看主文件不够：

```bash
sudo sshd -t            # 语法检查
sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|allowusers|port'
```

**二、改的时候留后路**（环境：VM/真机，**务必保留一个已登录的会话**）：

```bash
# 修改后先 reload，不要 restart
sudo systemctl reload sshd
# 新开一个终端验证能登录，再关旧会话
ssh -p 2222 deploy@host
```

如果新会话连不上，旧会话还在，可以改回去。**直接 `restart` + 关掉旧会话**是把自己锁在门外的最快方式。真锁死了只能进控制台或 Live 环境修（第 39、44 章）。

可选补充：`fail2ban`。它默认**所有 jail 都关闭**，只写端口与时长等于没启用；Arch 没有 rsyslog，sshd 日志只进 journal，还要指定 systemd 后端；本章防火墙用 nftables，封禁动作也要跟着换。最小可用配置（`/etc/fail2ban/jail.local`）：

```ini
[sshd]
enabled  = true
port     = 2222
backend  = systemd
banaction = nftables
bantime  = 1h
findtime = 10m
maxretry = 5
```

```bash
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd      # 确认 jail 已启用、能读出日志
```

缺 `enabled`/`backend`/`banaction` 任一项，都会得到「装了但没封」的假安全感。它是「缓解」不是「根治」——禁止密码登录之后，暴力破解的价值本来就大幅下降。

> **注意**：本章的最小策略只放行 SSH 与 ICMP。若这台机器还要跑 Web 服务（第 47–49 章），必须另行放行 80/443，否则站点外不可达，certbot 的 HTTP-01 验证也必然失败。

## 第二层：防火墙

Arch 默认推荐 nftables（第 18 章讲过表/链/规则模型）。一份可用的入站策略：

```bash
sudo pacman -S nftables
```

```text
# /etc/nftables.conf
destroy table inet filter   # 允许重复加载：先删旧表，表不存在也不报错
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif lo accept
    tcp dport 2222 accept   # 与 sshd_config 的 Port 保持一致，改端口必须同步改这里（第 18 章）
    icmp type echo-request accept
    icmpv6 type { echo-request, destination-unreachable, packet-too-big, time-exceeded, parameter-problem, nd-router-advert, nd-neighbor-solicit, nd-neighbor-advert } accept
  }
  chain forward { type filter hook forward priority 0; policy drop; }
  chain output  { type filter hook output  priority 0; policy accept; }
}
```

```bash
sudo nft -c -f /etc/nftables.conf    # 只读语法检查，不加载
sudo nft -f /etc/nftables.conf       # 确认无误再加载
sudo nft list ruleset                # 核对
sudo systemctl enable --now nftables # 开机自动加载
```

`nft -f` 是**追加**语义：文件里若只有 `table inet filter {...}`，第二次加载会因对象已存在而失败，所以首部先 `destroy table inet filter`。只想清空全部规则可改用 `flush ruleset`，但它会连同 Docker 等自建表一起清空，需谨慎。要点：`policy drop` 兜底；`established,related` 必须在前（否则回包被丢）；`iif lo` 放行回环；只开真正需要的端口。**`forward` 链也要设 `drop`**，否则这台机器可能被当成路由跳板。

> **危险**：在远程机器上改防火墙时，先 `nft -c -f` 检查语法，加载后立刻用另一个会话验证 SSH 仍可连。规则写错会让你和机器彻底失联。

## 第三层：sudo 策略

第 27 章讲了 `%wheel` 与 drop-in。这里补三条策略层面的取舍：

- **`NOPASSWD` 是提权后门**：任何能写你脚本/配置的人都能借此拿到 root。只在完全自动化且脚本本身受严格保护的场景使用（如 CI 里只允许一条 `systemctl restart app`）。
- **`timestamp_timeout`** 控制凭据缓存时长（默认 15 分钟）。共享机器上可调短，避免「你刚 sudo 完，别人接着用」。
- **按命令授权**优于整组全权，但要维护路径与参数；命令路径写错（`/usr/bin/systemctl` vs `/bin/systemctl`）会导致「明明授权了还是被拒」。

核对当前授权：

```bash
sudo -l          # 你自己能做什么
sudo -l -U app   # 某个用户能做什么
```

## 第四层：AppArmor

AppArmor 是**路径式**的强制访问控制：为每个程序定义它能读/写/执行哪些路径，即使程序被攻破也越不出这个笼子。它与 SELinux 的目标相同、模型不同——AppArmor 按路径、配置更易读；SELinux 按标签、更精细也更难。

Arch 上启用有三个前提：

1. 装 `apparmor` 包；
2. 内核启动参数里启用 LSM（如 `lsm=landlock,lockdown,yama,integrity,apparmor,bpf`——注意 LSM 名是 `yama`，别写成近似拼写；完整取值以 Wiki 为准；写在引导器配置里，第 41 章）；
3. `systemctl enable --now apparmor`，用 `aa-status` 确认已加载的 profile 数量。

```bash
sudo aa-status
ls /etc/apparmor.d/           # 可用的 profile
```

**概念比配置重要**：profile 定义「允许什么」，未列出的操作默认被拒；调试时看 `journalctl -k | grep -i apparmor` 的 `DENIED` 记录，再决定是补规则还是修程序。学习阶段不必为每个程序写 profile——把系统提供的装好、理解 `complain` 与 `enforce` 两种模式的差别即可。

## 最小权限：五条能立刻做的

1. **服务用专用用户**：绝不用 root 跑应用（第 46 章），配合 `NoNewPrivileges`、`ProtectSystem=strict`、`ReadWritePaths`、`PrivateTmp`（46 章的 unit 模板里都有）。
2. **敏感文件权限**：`stat -c '%a %U:%G' /etc/shadow` 确认普通用户读不到；密钥与 `EnvironmentFile` 用 `600`，目录 `700`。
3. **默认 umask 收紧**：需要私密的工作目录在 shell 配置里 `umask 077`，新建文件默认只有自己能读写。
4. **不在代码与配置里放密钥**：用 `EnvironmentFile`（`0600`）、系统密钥环或外部密钥管理；`.env` 不进 git。
5. **最小安装**：不需要的包与服务不装、不启用——每一个都是潜在漏洞面。

## 更新：唯一持续有效的防线

- **整系统升级**：`sudo pacman -Syu`（第 24、38 章）。长期不升级的系统，漏洞是叠加的。
- **安全公告**：`arch-audit` 会对照 Arch 安全团队的公告列出你系统里「有已知漏洞且已有修复」的包：

```bash
sudo pacman -S arch-audit
arch-audit            # 列出受影响的包与可用修复版本
arch-audit -u         # 只看已修复但未升级的
```

- **AUR 包要自己盯**：它们不在官方公告范围内，重建与升级都靠你（第 37 章）。
- **备份与演练**：加固的最后一条是「出事能恢复」。备份不演练等于没有备份（第 38 章）。

## 小结

- 顺序是：减少暴露面 → 限制权限 → 能看见异常 → 能快速更新。
- 最有效的动作往往不是防火墙，而是把服务绑回环、关掉不用的服务。
- SSH 改配置：`sshd -T` 核对、`reload` 生效、保留旧会话验证。
- nftables：`policy drop` + 先放 `established,related` + `forward` 也设 drop；远程改规则前先 `-c` 检查。
- sudo：`NOPASSWD` 是后门，`timestamp_timeout` 可缩短，按命令授权要注意路径。
- AppArmor 三前提：装包、内核参数启用 LSM、启用服务；`aa-status` 与 `DENIED` 日志是主要观察面。
- 五条最小权限 + 两条更新机制（整系统升级、`arch-audit`）构成日常防线。

## 练习

1. 暴露面盘点（环境：WSL）：`ss -tulpn` 列出所有监听，把 `0.0.0.0`/`[::]` 的项逐个标注「必要/可绑回环」；再列 `enabled` 服务，找出三个可以关掉的。
2. SSH 核对（环境：VM 或本地 sshd）：`sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication'`，对照 `/etc/ssh/sshd_config` 说明「实际生效值」与「文件内容」是否一致；改一个项后 `reload` 并用新会话验证。
3. nftables 演练（环境：VM，保留旧会话）：用正文的配置加载规则，`nft list ruleset` 核对；用 `nc -zv -w3` 验证 2222 通、其他端口长时间无响应（`policy drop` 是静默丢包，不是 RST 拒绝）；再加一条「临时全 drop」规则，观察 SSH 立刻断开后如何用控制台恢复。
4. sudo 审计（环境：WSL）：`sudo -l` 与 `/etc/sudoers.d/` 内容对照，指出哪些授权是整组全权、哪些按命令；尝试加一条 `NOPASSWD` 并解释它的风险。
5. AppArmor 观察（环境：VM）：装包、加内核参数、启用服务后跑 `aa-status`；触发一个被 profile 限制的操作，从 `journalctl -k | grep DENIED` 找到拒绝记录。
6. 漏洞自查（环境：WSL）：装 `arch-audit` 并运行，记录受影响的包数量；用 `pacman -Si` 核对其中一个包的可升级版本，写出你的处置步骤。
