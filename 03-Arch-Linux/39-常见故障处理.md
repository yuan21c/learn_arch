# 第 39 章 常见故障处理

Arch 的故障大多不是随机出现的，而是某次操作留下的状态：部分升级、错误配置、写满的磁盘、中断的事务。本章用“症状 / 诊断 / 修复 / 预防”四段式处理常见问题，原则是先取证，再动手。

> 本章目标：能根据报错定位常见故障的根因，选择风险最低的修复路径，并识别会扩大故障的命令。
> 对应 Wiki：[System maintenance](https://wiki.archlinux.org/title/System_maintenance)、[Pacman#Troubleshooting](https://wiki.archlinux.org/title/Pacman#Troubleshooting)

## 部分升级

**症状**：程序报 `error while loading shared libraries: libfoo.so.X`，pacman 报依赖无法满足；常发生在执行过 `pacman -Sy 包名`、长期使用 `IgnorePkg` 或手动装过旧包之后。

**诊断**：

```bash
tail -n 30 /var/log/pacman.log
ldd /usr/bin/程序名 | grep 'not found'
sudo pacman -Fy && pacman -F /usr/lib/libfoo.so.X
```

**修复**：先执行 `sudo pacman -Syu` 完成全系统升级。若库仍缺失，用 `pacman -F` 找到提供者并重装该包；若冲突来自第三方包，先移除冲突源再升级。

> **危险**：不要用 `--overwrite` 掩盖文件冲突，它只跳过文件冲突检查，不会修复依赖关系，损坏状态会继续累积。文件冲突的正确四步：`pacman -Qo <路径>` 查归属 → 确认哪个包该拥有它 → 修复/移除冲突源 → 必要时才用 `--overwrite <精确路径>`。本地数据库自检用 `pacman -Dk`（查依赖完整性）与 `pacman -Qk`（查文件完整性）。

**预防**：升级只用 `-Syu`；不长期压包；安装第三方包前确认依赖能在官方仓库满足。

## 密钥环与签名错误

**症状**：`invalid or corrupted package (PGP signature)`、`signature from ... is unknown trust`、`key ... could not be looked up`。

**诊断**：`timedatectl`、`pacman -Q archlinux-keyring`。

**修复**：先校正时间，再按 Wiki 的例外顺序更新密钥环：`sudo timedatectl set-ntp true`、`sudo pacman -Sy archlinux-keyring`、`sudo pacman -Su`，最后 `sudo pacman-key --refresh-keys`。缓存中的损坏包也要删除后重下。只有确认本地密钥环损坏时，才执行 `sudo pacman-key --init && sudo pacman-key --populate archlinux`；这会重置本地信任库并需重新填充。

**预防**：保持 keyring 随系统更新；时间错误的机器不要升级；长期未更新的镜像先完成一次完整升级。

## 依赖冲突

**症状**：`unable to satisfy dependency 'foo'`、`conflicting packages`、`failed to prepare transaction`。

**诊断**：

```bash
pacman -Qi 包名
pacman -Ss '^foo$'
```

**修复**：读清楚冲突双方是谁。缺依赖就安装提供者；两个包互斥就移除不再需要的那个；升级引入的冲突优先通过完整升级解决。

> **危险**：`--overwrite` 会强行覆盖文件归属，可能损坏另一个包。只有确认路径和归属、并接受后果时才用，且必须写出精确路径。

**预防**：不随意添加第三方仓库；安装 AUR 包前检查 `conflicts`/`provides`；关注 Arch News 中的包改名。

## 磁盘空间不足

**症状**：`error: not enough free disk space`、`failed to commit transaction (no space left on device)`，或下载到一半失败。

**诊断**：

```bash
df -h /
df -i /
```

**修复**：先清理可再生成的缓存与日志，保留最近版本以便回滚：`sudo paccache -rk1`、`sudo journalctl --vacuum-size=200M`、`sudo pacman -Sc`。最后一条会删除未安装包缓存，`pacman -Scc` 则清空全部缓存并失去降级能力。

> **危险**：空间不足时不要反复重试 `pacman -Syu`，半下载的包和未完成事务会让问题更复杂。

**预防**：定期 `sudo paccache -r`；给 journal 设上限；根分区不要放大文件；`df -i` 也要看，inode 耗尽同样表现为没空间。

## failed unit

**症状**：`systemctl is-system-running` 返回 `degraded`，或某个服务启动失败。

**诊断**：

```bash
systemctl status 单元名
journalctl -u 单元名 -b --no-pager
systemd-analyze verify /etc/systemd/system/单元名.service
```

**修复**：根据 `status` 的退出码和 `journalctl` 的首条错误修配置、路径或权限，然后执行 `sudo systemctl daemon-reload` 和 `sudo systemctl restart 单元名`。被 mask 的单元先 `systemctl unmask`；不需要的服务应 `disable`。

**预防**：自建单元先用 `systemd-analyze verify` 检查；改配置后必须 `daemon-reload`；不要把本机修改直接写进软件包提供的单元文件。

## pacman db.lck

**症状**：`failed to init transaction (unable to lock database)` 或 `could not lock database`。

**诊断**：

```bash
ps -eo pid,comm,args | grep '[p]acman'
sudo fuser -v /var/lib/pacman/db.lck
```

**修复**：有进程就等它结束。确认没有 pacman、paru、yay 在运行后，才删除锁文件并重新执行升级。

> **危险**：事务进行中删除 `/var/lib/pacman/db.lck` 会让两个 pacman 同时写数据库，可能损坏本地数据库。删锁前必须确认无相关进程；同样不要删除 `/var/lib/pacman/local` 来“重建数据库”，它保存已安装包的文件清单。

```bash
sudo rm /var/lib/pacman/db.lck
sudo pacman -Syu
```

**预防**：不要同时开多个包管理终端；不要在升级中途强制关闭 WSL 或杀进程；助手与 pacman 不要并行执行。

## DNS 失效

**症状**：`Could not resolve host`、pacman 无法下载，但 `ping 1.1.1.1` 正常。

**诊断**：

```bash
cat /etc/resolv.conf
resolvectl status
```

**修复**：确认 `/etc/resolv.conf` 由谁管理。使用 `systemd-resolved` 时检查服务并 `resolvectl query archlinux.org`；文件内容错误时写入可用 DNS。WSL 的自动生成逻辑见 [第 40 章 WSL 特有问题](40-WSL-特有问题.md)。

**预防**：不要在多个网络管理器之间来回切换；VPN 或代理变更后重新检查 DNS；不要硬编码 DNS 后忘记撤销。

## 时间漂移

**症状**：`signature is not yet valid`、TLS 证书报错、`timedatectl` 显示的时间与真实时间差很多。

**诊断**：

```bash
timedatectl
systemctl status systemd-timesyncd
```

**修复**：执行 `sudo timedatectl set-ntp true` 和 `sudo systemctl restart systemd-timesyncd`。WSL 在 Windows 休眠后漂移，通常要重启 WSL 让时间重新同步；虚拟机或真机可再用 `sudo hwclock --systohc`。WSL 没有可用的硬件时钟，不要照搬。

**预防**：保持 NTP 开启；休眠、挂起、时区变更后检查一次；不要用 `date -s` 手动拨时间代替同步。

## 救援与 chroot 的概念

系统无法启动或包管理器完全不可用时，需从外部环境挂载根分区，再用 `arch-chroot` 进入修复——分区与挂载见[第 43 章](43-安装准备与分区.md)，chroot 流程见[第 44 章](44-pacstrap-chroot-与引导器.md)。最小救援清单：Live ISO 启动 → `lsblk -f` 认盘 → `mount /dev/vda2 /mnt`（根）→ `mount --mkdir /dev/vda1 /mnt/boot`（ESP）→ `arch-chroot /mnt` → 修复（重装引导器/重建 initramfs/改 fstab）→ `exit`、`umount -R /mnt`、重启。

## 小结

- 顺序是取证、定位、最小修复、验证；不要从删文件或 `--overwrite` 开始。
- 部分升级用完整升级修复；密钥环问题先查时间，再更新 keyring。
- 依赖与文件冲突要读清双方，`--overwrite` 只能精确使用。
- 磁盘问题同时看容量与 inode；清理优先动缓存和日志。
- failed unit 看 `status` 与 `journalctl`；`db.lck` 只能在确认无进程后删除。
- 无法启动时从外部环境 `arch-chroot` 救援；WSL 用 `wsl -u root` 或导出备份，流程见 第 44 章 pacstrap、chroot 与引导器。

## 练习

1. 阅读 `/var/log/pacman.log`，找出最近一次升级的起止行。（环境：WSL）
2. 用 `pacman -F` 查找一个缺失库的提供者，写出重装命令。（环境：WSL）
3. 用 `systemd-analyze verify` 检查自建单元，故意写错 `ExecStart` 并修复。（环境：WSL）
4. 查看 `df -h`、`df -i` 与 pacman 缓存体积，制定一条清理命令。（环境：WSL）
