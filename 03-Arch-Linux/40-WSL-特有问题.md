# 第 40 章 WSL 特有问题

WSL 里的 Arch 运行在微软提供的内核和虚拟化层之上，很多“Arch 故障”其实是 WSL 的边界行为。本章只讲操作排障；能力边界的概念对照见 [第 24 章 WSL 的能力边界](24-WSL-的能力边界.md)，升级流程见 [第 38 章 升级流程与 Arch News](38-升级流程与-Arch-News.md)。

> 本章目标：能独立排查 systemd、挂载权限、DNS、时间、PATH、interop、网络和资源限制问题，并知道何时应改用虚拟机。
> 对应 Wiki：[WSL](https://wiki.archlinux.org/title/WSL)

## systemd 未启用

**检查**：`ps -p 1 -o comm=` 不是 `systemd`，或运行 `systemctl` 报 “System has not been booted with systemd”。

**修复**：在 `/etc/wsl.conf` 中启用 systemd，然后在 Windows 侧执行 `wsl --shutdown`：

```ini
[boot]
systemd=true
```

旧版 WSL 先执行 `wsl --update`。重新进入后用 `systemctl is-system-running` 验证。

**预防**：修改 `wsl.conf` 后必须 `wsl --shutdown`，只退出终端不会重新加载配置。

## /mnt/c 的权限与性能

**检查**：`mount | grep drvfs`、`stat -c '%a %U %G' /mnt/c/某文件`。若 `chmod +x` 无效，说明未启用 `metadata`。

**修复**：在 `/etc/wsl.conf` 的 `[automount]` 段写入 `options = "metadata,umask=22,fmask=11"`，然后 `wsl --shutdown`。

**预防**：代码仓库、数据库和构建目录放在 Linux 文件系统（`~/`）内，不要放在 `/mnt/c`；跨文件系统 I/O 慢，权限语义也不一致。

## /etc/resolv.conf 被自动生成

**检查**：`ls -l /etc/resolv.conf`，文件内容带有 “automatically generated by WSL” 注释；`resolvectl status` 可查看实际 DNS。

**修复**：若必须自行管理 DNS，在 `/etc/wsl.conf` 的 `[network]` 段写入 `generateResolvConf = false`，然后用 `sudo sh -c 'printf "nameserver 1.1.1.1\n" > /etc/resolv.conf'` 写入静态配置，最后重启 WSL。

较新的 WSL 可在 Windows 的 `.wslconfig` 中启用 DNS 隧道（`[wsl2] dnsTunneling=true`），对 VPN 场景更稳。

**预防**：不要用 `chattr +i` 锁死文件；先确认谁在管理 DNS，再改配置。VPN 切换后重新验证 `resolvectl query archlinux.org`。

## 时钟漂移

**检查**：`timedatectl`、`date -u`。Windows 休眠或长时间挂起后，WSL 时间可能落后，表现为签名或 TLS 错误。

**修复**：先重启 WSL 让它与 Windows 重新对时；仍偏差时在 WSL 内执行 `sudo timedatectl set-ntp true` 和 `sudo systemctl restart systemd-timesyncd`。

**预防**：Windows 侧保持时间服务正常；每次休眠恢复后检查一次 `timedatectl`。

## Windows PATH 干扰

**检查**：`echo "$PATH" | tr ':' '\n'` 出现 `/mnt/c/...`；`type -a python`、`which -a code` 显示多个来源。

**修复**：在 `/etc/wsl.conf` 的 `[interop]` 段写入 `appendWindowsPath = false`，重启 WSL。需要调用 Windows 程序时用完整路径或 `wslview`，不要依赖 PATH。

**预防**：保持 Linux 工具链在 PATH 中优先；不要把 Windows 的 Python、Node、Git 混进 Linux 项目。

## interop 调用 Windows 程序

**检查**：`cmd.exe /c ver`、`echo $WSL_INTEROP`、`ls /proc/sys/fs/binfmt_misc/ | grep -i wsl`。报 “cannot execute binary file” 通常是 interop 被关闭。

**修复**：在 `/etc/wsl.conf` 确认 `[interop] enabled=true`，然后 `wsl --shutdown`。路径转换用 `wslpath -w /home/arch/file`。

**预防**：interop 只用于必要的一次性调用；脚本中依赖 `cmd.exe` 会降低可移植性。

## 内核模块不可用

**检查**：`uname -r` 以 `-microsoft-standard-WSL2` 结尾；`ls /lib/modules/$(uname -r)` 可能为空，`modprobe 模块名` 失败。

**修复**：WSL 使用微软内核，不能按普通 Arch 方式加载任意模块。需要特定文件系统、网络或设备模块时，改用虚拟机；自定义 WSL 内核不在本书范围。

**预防**：不要把 `modprobe`、`dkms`、硬件驱动步骤当作 WSL 的常规操作；相关实验放到虚拟机。

## 没有引导器与“重启”

**检查**：WSL 由 Windows 启动，没有 GRUB/systemd-boot、ESP 或 initramfs 阶段；`systemctl reboot` 不等于重启 Windows。

**修复**：需要重启用户空间时，在 Windows 侧执行 `wsl --shutdown`，再重新进入。引导器实验见 第 44 章 pacstrap、chroot 与引导器。

**预防**：不要在 WSL 中练习 `grub-install`、`bootctl install` 或修改分区表。

## 端口转发

**检查**：Linux 内 `ss -tlnp` 确认服务监听；Windows 侧 `curl http://localhost:8000`。WSL2 默认通过 localhost 转发，但局域网访问需要额外配置。

**修复**：从局域网访问时，在管理员 PowerShell 添加 portproxy 与防火墙规则，目标地址用 `wsl hostname -I` 获取；WSL IP 会变化，重启后需更新。Windows 11 较新版本可改用 `.wslconfig` 的 `networkingMode=mirrored`。只转发必要端口，规则用完删除。

**预防**：开发服务默认绑定 `127.0.0.1`；确实需要局域网访问时再显式绑定 `0.0.0.0` 并限制来源。

## .wslconfig 内存限制

**检查**：WSL 内 `free -h`、`nproc`；Windows 侧查看 `%UserProfile%\.wslconfig`。默认 WSL2 可能占用较多内存。

**修复**：编辑 Windows 用户目录下的 `.wslconfig`，不是 Linux 内的 `/etc/wsl.conf`：

```ini
[wsl2]
memory=4GB
```

保存后 `wsl --shutdown` 生效。数值不要低于构建或服务所需。

**预防**：为 Windows 留足内存；构建大包时临时调高，不要长期把上限压得过低。

## 备份与恢复

**检查**：备份前 `wsl -l -v` 确认发行版名称与状态。

**修复**：先终止，再导出；导入时使用新名称和新目录，避免覆盖现有发行版：

```powershell
wsl --terminate Arch
wsl --export Arch D:\backup\arch-2026-10-27.tar
wsl --import Arch-test D:\wsl\arch-test D:\backup\arch-2026-10-27.tar
```

导入后默认用户通常是 root，用 `wsl -d Arch-test -u root` 进入并修改 `/etc/wsl.conf` 的 `[user] default=`。

> **危险**：`--import` 到已存在的发行版名称会失败或覆盖目标，先确认名称和目录；导出不包含 `/mnt/c` 等 Windows 挂载目录中的数据。

**预防**：大改动前导出；把备份放到另一块磁盘，定期做一次恢复演练。

## 何时放弃 WSL 转虚拟机

出现以下需求时，WSL 不是合适环境：加载自定义内核模块、编译或替换内核、练习分区/LUKS/文件系统、GRUB 或 systemd-boot、initramfs、直通硬件、完整的桌面与显示管理器、需要稳定 IP 或长期运行的服务。

这些场景使用 Hyper-V、VirtualBox 或 QEMU，按 第 43 章「安装准备与分区」 开始；判断标准是故障是否来自 WSL 本身，而不是“WSL 能不能凑合”。

## 小结

- WSL 的 systemd、挂载、DNS、时间、PATH、interop 都可以配置，但每次改 `wsl.conf` 都要 `wsl --shutdown`。
- `/mnt/c` 用于交换文件，不适合作为 Linux 项目或构建目录。
- DNS 与时间问题常伪装成网络或签名错误，先查 `resolv.conf` 和 `timedatectl`。
- 内核模块、引导器、分区与硬件直通超出 WSL 能力，应转到虚拟机。
- 备份用 `wsl --export`，恢复用 `wsl --import`；导入后检查默认用户。
- 端口转发和 `.wslconfig` 资源限制属于 Windows 侧配置，修改方式与 Linux 配置文件不同。

## 练习

1. 检查当前 PID 1、`/etc/wsl.conf` 和 `systemctl is-system-running`，记录 systemd 是否启用。
2. 在 `/mnt/c` 与 `~/` 各创建一个小文件，比较 `chmod` 行为与读写速度。
3. 查看 `/etc/resolv.conf` 的生成方式，写出关闭自动生成并重启 WSL 的步骤。
4. 用 `type -a python` 检查 PATH 来源，关闭 `appendWindowsPath` 后复测。
5. 导出一次 WSL，导入为测试发行版，修正默认用户后删除测试副本。
