# 第 41 章 启动深讲：内核、initramfs 与引导器

篇二第 20 章讲的是启动的通用五阶段，用的是「固件 → 引导器 → 内核 + initramfs → init → 用户空间」这套抽象。通用的内核参数表与引导故障表以第 20 章为准，本章只列 Arch 专属的文件与命令。本章把那套抽象落到 Arch 的具体文件与命令上：`/boot` 里到底躺着什么、`mkinitcpio` 做了什么、GRUB 与 systemd-boot 各自的配置写在哪、内核参数从哪来。读完这一章，你会知道 Arch 的引导链由哪些文件组成、改什么之后必须重建 initramfs；从零安装的完整步骤在第 43-44 章。

> 本章目标：能说出 Arch 启动链上每个文件的作用（`vmlinuz-linux`、`initramfs-linux.img`、`.efi` 引导程序、`grub.cfg`、loader entry）；会用 `mkinitcpio` 重建 initramfs 并解释 HOOKS 顺序的意义；能安装并配置 GRUB 或 systemd-boot，知道内核参数写在哪个文件；会管理内核模块与微码；能在引导失败时按阶段定位并进入救援目标。
> 对应 Wiki：[Arch boot process](https://wiki.archlinux.org/title/Arch_boot_process)、[Mkinitcpio](https://wiki.archlinux.org/title/Mkinitcpio)、[GRUB](https://wiki.archlinux.org/title/GRUB)、[Systemd-boot](https://wiki.archlinux.org/title/Systemd-boot)

## /boot 里到底有什么

Arch 的 ESP（EFI 系统分区）通常直接挂在 `/boot`，所以启动相关的东西都在一处（环境：VM，安装完成后）：

```bash
ls /boot
# EFI/  grub/  initramfs-linux.img  initramfs-linux-fallback.img  vmlinuz-linux
# intel-ucode.img（Intel CPU 时）
```

| 文件 | 作用 | 谁生成 |
| --- | --- | --- |
| `vmlinuz-linux` | 内核镜像 | 内核包 `linux` |
| `initramfs-linux.img` | 早期用户空间的压缩镜像 | `mkinitcpio` |
| `initramfs-linux-fallback.img` | 不含 autodetect 的完整备用镜像 | `mkinitcpio` |
| `intel-ucode.img` / `amd-ucode.img` | CPU 微码 | `intel-ucode` / `amd-ucode` 包 |
| `EFI/` | 引导程序本体 | 引导器安装时写入 |
| `grub/grub.cfg`（用 GRUB 时） | 引导菜单配置 | `grub-mkconfig` |

两个 initramfs 的区别很重要：正常镜像用 `autodetect` 钩子只带本机需要的模块，启动快；fallback 带全部模块，用于「换了硬件或正常镜像起不来」时兜底。引导器菜单里通常两项都列出来。

## mkinitcpio：为什么改了配置必须重建

内核自己不会挂载根文件系统——它需要驱动。这些驱动被打进 initramfs，由 `mkinitcpio` 按配置生成。配置文件是 `/etc/mkinitcpio.conf`，核心是 `HOOKS` 数组（顺序有意义）：

```text
HOOKS=(base systemd autodetect microcode modconf kms keyboard sd-vconsole block filesystems fsck)
```

读法：`base` 提供最基本的运行环境；`systemd`（旧版是 `udev`）负责设备发现与早期系统服务；`autodetect` 只保留本机硬件需要的模块；`microcode` 加载 CPU 微码；`block` 加存储相关模块；`filesystems` 加文件系统驱动；`fsck` 在挂载根之前检查。**顺序即依赖**——设备发现必须在 `autodetect` 之前，`filesystems` 必须在真正挂载根之前、并且排在 `block` 之后。你的机器上以 `/etc/mkinitcpio.conf` 的实际内容为准（新旧默认在这里差别最大）。

所以你改了这些就要重建（环境：VM，需 root）：

```bash
sudo mkinitcpio -P          # 按 /etc/mkinitcpio.d/*.preset 重建全部内核的 initramfs
sudo mkinitcpio -g /boot/initramfs-linux.img   # 只生成指定文件
```

什么时候必须重建：改 `HOOKS` 或 `MODULES`、加装加密/LVM/RAID 相关包、换文件系统、装微码包、内核升级（内核包的 pacman hook 会自动触发）。**忘了重建**的典型现象：换了磁盘控制器驱动后卡在 `Waiting for root device`，或加了 LUKS 却没有解锁提示。GRUB 菜单另有一条纪律：Arch 官方内核文件名固定（`/vmlinuz-linux`），升级**现有**内核一般不必重跑 `grub-mkconfig`；安装新内核或修改 `/etc/default/grub` 后才要重跑，也不要假设 pacman 会自动执行（用 `pacman -Ql grub | grep hook` 核对）。

## 内核参数：写在三个不同的地方

内核参数决定「怎么挂载根」「用哪个 target」「加载什么模块」。它写在哪取决于引导器：

| 引导器 | 参数位置 | 生效方式 |
| --- | --- | --- |
| GRUB | `/etc/default/grub` 的 `GRUB_CMDLINE_LINUX_DEFAULT` | `grub-mkconfig -o /boot/grub/grub.cfg` |
| systemd-boot | `/boot/loader/entries/*.conf` 的 `options` 行（或 `/etc/kernel/cmdline`） | 直接编辑，无需生成；`root=` 必须自己写，不会自动探测 |
| 临时（任一） | 引导菜单里按 `e` 编辑 | 仅本次启动生效 |

常用参数：

```text
root=UUID=xxxx            # 根文件系统（GRUB 的 grub-mkconfig 会自动探测；systemd-boot 要手写）
rw                        # 以读写挂载（有的预设默认 ro）
quiet                     # 少打印内核日志；排障时去掉
loglevel=3                # 控制台日志级别
nomodeset                 # 显卡驱动出问题时进图形
systemd.unit=rescue.target # 进救援目标
```

`nomodeset` 与 `systemd.unit=` 是最常用的两个救急参数：前者关闭内核图形模式设置，让显卡驱动出问题时至少能进低分辨率控制台；后者让你跳过图形与大部分服务直接进维护 shell。

## 安装引导器：GRUB 与 systemd-boot

两者的分工相同（加载内核与 initramfs、传参数），复杂度不同。**GRUB**（环境：VM，需 root）：

```bash
sudo pacman -S grub efibootmgr
sudo grub-install --target=x86_64-efi --efi-directory=/boot --bootloader-id=GRUB
sudo grub-mkconfig -o /boot/grub/grub.cfg
```

`grub-install` 往 ESP 写 `EFI/GRUB/grubx64.efi` 并在 NVRAM 建启动项；`grub-mkconfig` 扫描 `/boot` 里的内核，生成菜单。**每次内核升级或改 `/etc/default/grub` 后都要重跑 `grub-mkconfig`**——这是 GRUB 最常见的「改了没生效」原因。

**systemd-boot** 只支持 UEFI，配置就是几个文本文件（环境：VM，需 root）：

```bash
sudo bootctl install
```

然后手写一个入口（`/boot/loader/entries/arch.conf`）：

```text
title   Arch Linux
linux   /vmlinuz-linux
# 分支 A：HOOKS 已含 microcode —— 下面这行正常 initramfs 照常写；不要额外加独立微码行
initrd  /initramfs-linux.img
options root=UUID=xxxx rw
```

`initrd` 行可以有多个，微码必须在 initramfs **之前**加载。全局设置（默认项、超时）在 `/boot/loader/loader.conf`。systemd-boot 的优点是没有「生成」这一步，改完即生效。若你用固定文件名（`/vmlinuz-linux`、`/initramfs-linux.img`），内核升级不需要改入口；若改用 `kernel-install` 的版本化命名，入口就必须随内核版本更新。

## 内核、模块与微码

Arch 允许同时装多个内核，菜单里各占一项：

| 包 | 特点 |
| --- | --- |
| `linux` | 主线稳定版 |
| `linux-lts` | 长期支持，保守 |
| `linux-zen` | 面向桌面响应 |
| `linux-hardened` | 强化安全，牺牲部分兼容 |

装第二个内核是**最便宜的保险**：主线内核更新后出事，从菜单选 LTS 进去修。装内核时要同时装对应 `-headers`（DKMS 模块需要）。

模块的日常管理：

```bash
lsmod                      # 已加载模块
modinfo nvidia             # 看模块信息与参数
sudo modprobe -r 模块名    # 卸载
```

持久化配置分两个目录：`/etc/modules-load.d/*.conf` 写「开机自动加载哪些模块」，`/etc/modprobe.d/*.conf` 写「模块参数与黑名单」（`blacklist 模块名`）。后者常用于「开源驱动与专有驱动冲突」的场景。

微码（microcode）是 CPU 厂商发布的固件更新，必须在启动早期加载：Intel 装 `intel-ucode`、AMD 装 `amd-ucode`，然后在引导器里把 `initrd` 排在 initramfs 之前（GRUB 的 `grub-mkconfig` 会自动检测并插入）。

## 引导失败：按阶段定位

| 现象 | 检查 |
| --- | --- |
| 固件找不到启动项 | `efibootmgr -v` 看 NVRAM；ESP 里是否有 `.efi` |
| 进 `grub>` 提示符 | `grub.cfg` 是否生成、`/boot` 是否挂载 |
| 菜单后黑屏、无内核日志 | 内核参数、显卡（试 `nomodeset`） |
| `Waiting for root device` / kernel panic | `root=` 参数、initramfs 是否含存储驱动 |
| 卡在 job、进 emergency | `journalctl -xb` 找失败单元 |

救援入口有三个层次：引导菜单里临时加 `systemd.unit=rescue.target`（最小可用系统）、`emergency.target`（只有根与基本 shell）、以及从 live 环境 `arch-chroot` 进去修（第 34、44 章）。

## 小结

- `/boot` 里五类文件：内核、initramfs、fallback、微码、引导器；ESP 通常直接挂在 `/boot`。
- `mkinitcpio` 按 `HOOKS` 顺序生成 initramfs；改 HOOKS/模块/加密/文件系统后必须 `mkinitcpio -P`。
- 内核参数三处：GRUB 的 `/etc/default/grub`、systemd-boot 的 entry 文件、引导菜单临时编辑。
- GRUB 改完要 `grub-mkconfig`；systemd-boot 改完即生效，但内核升级不会自动更新入口。
- 多装一个内核（如 `linux-lts`）是最便宜的保险；模块持久化分 `modules-load.d` 与 `modprobe.d`。
- 微码必须在 initramfs 之前加载；引导失败按「固件 → 引导器 → 内核 + initramfs → init → 用户空间」逐段定位（排障时可把末两段合并看）。

## 练习

1. 盘点 `/boot`（环境：VM）：列出五个关键文件并各自说明由哪个包或命令生成；对比 `initramfs-linux.img` 与 `-fallback.img` 的体积，解释差异原因。
2. HOOKS 顺序（环境：VM，只读）：读 `/etc/mkinitcpio.conf` 的 `HOOKS` 行，指出如果去掉 `autodetect` 会发生什么、如果把 `filesystems` 放到 `block` 之前会怎样。
3. 重建并验证（环境：VM）：`sudo mkinitcpio -P`，观察输出里每个 preset 的生成过程；用 `ls -l /boot/initramfs-linux.img` 看时间戳变化。
4. 引导参数实验（环境：VM）：在菜单里临时加 `loglevel=7`，观察内核日志变多；重启恢复默认，确认没有写进配置文件。
5. 双内核保险（环境：VM）：安装 `linux-lts` 与对应 headers，`grub-mkconfig` 或补 systemd-boot entry，重启在菜单里选择 LTS 进入，`uname -r` 确认内核版本。
6. 救援目标（环境：VM）：用 `systemd.unit=rescue.target` 启动一次，`systemctl --failed` 与 `journalctl -xb -p err` 各看一次，再正常重启；说明 rescue 与 emergency 的差别。
