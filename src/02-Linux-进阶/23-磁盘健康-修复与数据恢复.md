# 第 23 章 磁盘健康、修复与数据恢复

第 18 章把 `fsck` 与 SMART 列为「维护三件」；第 21 章讲 RAID 只保可用、不保可恢复。这一章处理真正出事之后的顺序：盘开始报错、文件系统挂不上、误删了分区、机器已经起不来。核心原则只有一条——**先停止写入，再评估，再镜像，最后才修**。顺序做反了，本来能救的数据会被自己的操作覆盖掉。

> 本章目标：能读懂 SMART 的关键属性与自检结果，知道「PASSED」不等于健康；能区分硬件故障、文件系统损坏与逻辑误删三类问题；会用只读的 `badblocks`、`e2fsck -n`、`xfs_repair -n`、`btrfs check --readonly` 做无损评估；掌握 `ddrescue` 的镜像流程与 mapfile 用法；能判断什么时候该停手送专业恢复、什么时候该直接换盘。
> 对应 Wiki：[Smartmontools](https://wiki.archlinux.org/title/Smartmontools)、[Fsck](https://wiki.archlinux.org/title/Fsck)、[Data recovery](https://wiki.archlinux.org/title/Data_recovery)、[Btrfs](https://wiki.archlinux.org/title/Btrfs)

## 原理：三类故障，三套打法

「磁盘坏了」是一句含糊的话，实际至少分三类，处理方式完全不同：

| 类型 | 典型现象 | 首要动作 | 不该做什么 |
| ---------- | ------------------------------------ | -------------------------- | ---------------------------- |
| 硬件退化 | 读写报错、异响、SMART 计数上升 | 立即镜像，准备换盘 | 反复重试、长时间通电 |
| 文件系统损坏 | 挂载失败、`fsck` 报错、目录乱码 | 先只读检查，再在副本上修 | 对已挂载分区跑修复 |
| 逻辑误删 | 分区表丢了、文件被删、格式化误操作 | 停止写盘，用镜像做文件级恢复 | 往原盘写任何东西 |

三类的共同点是**原始介质是唯一证据**。任何修复工具都可能写入；一旦写入，后续恢复的难度会指数上升。所以顺序固定为：断电/停写 → 只读评估 → 整盘镜像 → 在镜像上尝试修复与提取。

### SMART：预测性指标，不是判决书

SMART 是硬盘固件自带的健康计数器。ATA 盘看属性（attribute），NVMe 盘看日志（log），字段名不同但思路一致：**用历史计数预测未来故障**。

| 属性（ATA） | 名称 | 含义 | 危险信号 |
| ------------------- | ------------------------ | ------------------------------ | ------------------------ |
| 5 | Reallocated_Sector_Ct | 已重映射的坏扇区数 | 非零且持续增长 |
| 187 | Reported_Uncorrect | 无法纠正的错误 | 非零 |
| 197 | Current_Pending_Sector | 等待重映射的扇区 | 非零，尤其持续增长 |
| 198 | Offline_Uncorrectable | 离线扫描中不可纠正 | 非零 |
| 199 | UDMA_CRC_Error_Count | 传输链路错误（线缆/接口） | 增长通常先查线缆 |

NVMe 没有「重映射扇区」概念，重点看 `Available Spare`（剩余备用块）、`Percentage Used`（寿命消耗）、`Media and Data Integrity Errors`（介质与数据完整性错误）。`smartctl -a /dev/nvme0` 会直接打印这些字段。

两条常被误解的事实：**`PASSED` 只表示「当前没超过厂商阈值」**，不表示盘不会明天坏；**属性值正常也不代表没有坏道**，因为待映射扇区可能还没触发阈值。SMART 的正确用法是看**趋势**：定期记录，比较两次之间的增量。

## 步骤：从体检到镜像

### 1. 先看 SMART（真机才有意义）

```bash
sudo smartctl -a /dev/sda # 总览：型号、容量、健康结论、属性表、错误日志
sudo smartctl -H /dev/sda # 只看总体健康结论
sudo smartctl -A /dev/sda # 只看属性表
sudo smartctl -t short /dev/sda # 启动短自检（约 1-2 分钟）
sudo smartctl -l selftest /dev/sda # 查看自检记录与结果
sudo smartctl -x /dev/nvme0 # NVMe 用 -x 看扩展日志
```

虚拟机里跑这几条通常会看到 `SMART support is: Unavailable - device lacks SMART capability.`——这是虚拟盘不暴露 SMART，不是命令用错。USB 硬盘盒常常挡住 SMART，需要 `-d sat` 指定协议（具体类型按 `smartctl -d help` 的列表逐个试）。真实硬盘上，`smartctl -t long` 会做一次全盘扫描，耗时随容量增长；扫描期间盘仍然可用，但性能下降。

要长期监控，启用 `smartd` 并配 `/etc/smartd.conf`（`DEVICESCAN` 可自动发现），让它把异常写进日志或发邮件。单次体检只能看到当下，趋势才有预测价值。

### 2. 只读扫描坏块

`badblocks` 默认是**只读**的，适合先摸底：

```bash
# 对 loop 设备演练；真机上把对象换成确认可丢弃的盘
mkdir -p /tmp/lab23 && truncate -s 64M /tmp/lab23/disk.img
LOOP=$(sudo losetup -f --show /tmp/lab23/disk.img)
sudo badblocks -sv -b 4096 "$LOOP" # -s 进度、-v 详细、-b 块大小；默认只读，不改数据
```

`-n` 是「非破坏性读写」：先读、再写测试模式、再恢复原内容。它比只读更彻底，但**中途断电或中断会留下被测试模式覆盖的数据**，只能在确认有备份或本来就是空盘时使用。`-w` 是破坏性写入测试，任何有数据的盘都不该用。三条模式的边界必须分清，很多事故来自把 `-n` 当成「安全」的同义词。

### 3. 文件系统检查：先只读

三类文件系统的检查工具不同，共同要求是**目标未挂载**：

```bash
sudo e2fsck -fn /dev/sdb1 # ext4：-n 只检查不修改（对「回答 no」），先看问题清单
sudo e2fsck -p /dev/sdb1 # ext4：preen 模式，只自动修「安全」的问题
sudo xfs_repair -n /dev/sdb1 # XFS：-n 只读检查，不改动
sudo btrfs check --readonly /dev/sdb1 # btrfs：只读检查
sudo btrfs scrub start -Bd /mnt/data # btrfs 在线校验（已挂载时用 scrub）
```

`e2fsck -n` 的退出码有含义：`0` 无错误、`1` 已修正、`4` 有未修正错误、`8` 操作错误。第一次一律用 `-n`，把输出里的「第一个错误」记下来，再决定是否允许修改。XFS 的 `xfs_repair` 与 btrfs 的 `check --repair` 都比 ext4 的修复激进；btrfs 官方建议优先用 `scrub` 与备份恢复，`check --repair` 只在明确需要时使用，且必须先有镜像。

### 4. 镜像：ddrescue 而不是 dd

`dd` 遇到坏扇区会反复重试甚至整盘卡住，`ddrescue` 专为坏盘设计：先快速跳过坏区把好数据抄出来，再回头慢慢抠坏区。Arch 上包名就是 `ddrescue`（extra 仓库，GNU ddrescue）；有另一个**不同**的工具名为 `dd_rescue`（A.I. Labs/garloff，命令同名），两者选项与 mapfile 格式不通用，不要混用。Debian/Ubuntu 系叫 `gddrescue`，那是跨发行版对照，**不是** Arch 的包名。

```bash
sudo pacman -S ddrescue
mkdir -p /tmp/lab23 && cd /tmp/lab23
sudo ddrescue -f -n /dev/sdb rescue.img rescue.map # 第一遍：不重试、不刮擦，尽快抄完好区
sudo ddrescue -d -r3 /dev/sdb rescue.img rescue.map # 第二遍：直接访问、每块重试 3 次
```

`mapfile` 是进度账本：它记录哪些区间已抄、哪些是坏区，中断后可以**接着跑**，不必从头再来。这也是它优于 `dd` 的关键。镜像文件要放在**另一块健康的盘**上，容量不小于源盘；如果源盘正在发出异响或 SMART 快速恶化，先断电再决定是否送专业恢复，反复通电可能让磁头刮伤盘片。

### 5. 在镜像上恢复文件

拿到镜像后，所有尝试都针对镜像：先 `mount -o ro,loop rescue.img /mnt/rescue` 看文件系统是否可读；不行再用 `testdisk` 找回分区表、用 `photorec` 按文件头提取文件（两者都在 `testdisk` 包里）。`photorec` 不依赖文件系统元数据，能捞回被删除或目录结构损坏的文件，但会丢失原文件名与目录层级——这是「先救内容、后救结构」的取舍。

## 失败模式

- **对已挂载分区跑 `fsck`**：工具会拒绝，强行绕过则可能在写入过程中破坏缓存中的元数据。必须先 `umount`，根分区则从 live 环境或 initramfs 里检查。
- **直接 `e2fsck -y`**：`-y` 对所有问题回答 yes，可能把「本来还能手工判断」的结构改成错误的方向。先 `-n` 看清单，确认是常见问题再修。
- **`xfs_repair -L` 清日志**：`-L` 会清零 XFS 日志，可能丢掉尚未落盘的元数据变更；只在日志损坏且已接受数据损失时使用。
- **对 btrfs 跑 `check --repair`**：它可能把损坏放大，官方文档明确要求先备份；能挂载时优先 `scrub`，能恢复时优先从快照恢复。
- **用 `dd` 救坏盘**：坏区会让 `dd` 长时间卡住，且没有 mapfile，中断后无法续传；应使用 `ddrescue`。
- **往原盘写东西**：包括「先格式化再恢复」「在原盘上装恢复软件」。每一次写入都可能覆盖待恢复的数据。
- **把 RAID 重建当修复**：重建只恢复冗余，不修复文件系统逻辑损坏，也不防误删；重建期间的高负载还可能加速另一块盘故障。
- **只看 SMART 结论**：`PASSED` 的盘仍可能随时失效；备份与镜像才是可恢复性的来源。
- **备份没做过恢复演练**：备份文件存在不等于能恢复，没验证过的备份只能算「希望」。

## 验证与回滚

| 操作 | 验证 | 回滚 |
| ------------------------- | ---------------------------------------------- | ------------------------------------------ |
| SMART 自检 | `smartctl -l selftest` 看完成后是 `Completed without error` 还是 `Completed: read failure` | 只读，无副作用 |
| 只读坏块扫描 | `badblocks -sv` 输出的错误块数；与上次比较 | 只读，无副作用 |
| 文件系统只读检查 | `e2fsck -fn`/`xfs_repair -n` 的退出码与首个错误 | 只读，无副作用 |
| 镜像 | `ddrescue` 的 mapfile 显示 rescued 比例；`cmp` 抽查已知文件 | 镜像文件即副本，源盘不动 |
| 文件系统修复 | 修完再跑一次只读检查，退出码应为 0 | 只能在镜像上修；原盘保持未改 |
| 恢复文件 | 打开文件、校验大小与哈希 | 从镜像重新提取，不碰原盘 |

一个可复现的「损坏 → 只读评估 → 修复 → 复检」闭环（在 `/tmp` 的镜像文件上做，安全）：

```bash
cd /tmp/lab23
truncate -s 64M broken.img
mkfs.ext4 -q broken.img
sudo dd if=/dev/zero of=broken.img bs=1 seek=1024 count=1024 conv=notrunc status=none # 毁掉主超级块
sudo e2fsck -fn broken.img # 预期：Bad magic number in super-block，随后尝试备份超级块；退出码非 0
mke2fs -n broken.img 2>&1 | tail -2 # 只打印布局（不改文件），给出备份超级块位置：8193、24577…
sudo e2fsck -fy -b 8193 broken.img # 用备份超级块修；预期退出码 1（已修正）
sudo e2fsck -fn broken.img # 复检；预期退出码 0
```

备份超级块的块号随文件系统大小变化，必须用 `mke2fs -n` 的实际输出，不能照抄 8193。这个演练同时说明两件事：ext4 的备份超级块是真实存在的救援路径；修复动作必须发生在副本上，且修完要复检，不能以「命令没报错」为成功标准。

## 取舍边界

- **修还是换**：SMART 出现持续增长的待映射/重映射计数、异响、读写大面积报错时，优先换盘并镜像，而不是反复修文件系统。文件系统错误反复出现，往往是底层介质在恶化。
- **自己救还是送专业**：磁头异响、盘片划伤、进水、摔过的盘，**不要再通电**。专业恢复的无尘室与备件成本高，但自行通电可能让原本可救的数据彻底报废。
- **镜像 vs 直接修**：有足够空间就一律先镜像。镜像让你可以反复试错；直接修只有一次机会。
- **RAID vs 备份**：RAID 能在坏一块时继续服务，但误删、勒索、文件系统损坏会同步到所有成员盘。可恢复性来自独立备份，不来自冗余。
- **本地 vs 异地 vs 云**：3-2-1 原则（3 份副本、2 种介质、1 份异地）解决的是「同一故障同时毁掉所有副本」。云备份便宜但受网络与账号安全影响；离线介质能防勒索，但需要人工轮换与验证。
- **监控频率**：SMART 每天一次足够看趋势，`scrub` 每月一次能发现静默损坏；频率再高只是增加 I/O，不会让坏盘变好。

## 小结

- 三类故障分开处理：硬件退化先镜像，文件系统损坏先只读检查，逻辑误删先停写。
- SMART 看趋势不看单次结论；ATA 关注 5/187/197/198/199，NVMe 关注备用块、寿命与介质错误。
- 虚拟机通常不暴露 SMART（实测显示 `Unavailable`），SMART 实验应在真机做。
- `badblocks` 默认只读，`-n` 是非破坏性读写但可中断留痕，`-w` 是破坏性；三者不能混用。
- 文件系统检查一律先 `-n`/`--readonly`，且必须未挂载；`xfs_repair -L` 与 `btrfs check --repair` 属于高风险操作。
- 坏盘用 `ddrescue`：先快速抄好区，再重试坏区，mapfile 支持续传。
- 所有修复与提取都在镜像上做；原盘只读、只镜像。
- 修复的验收标准是「复检通过」，不是「命令没报错」；备份的验收标准是「能恢复」。

## 练习

1. SMART 观察（真机）：`smartctl -a` 记下型号与五项关键属性；隔一天再记一次，算出增量。虚拟机里则记录 `SMART support is: Unavailable` 的输出，解释为什么虚拟盘没有这项能力。
2. 只读坏块扫描：在 `/tmp` 造一个 64 MiB 的空文件，挂成 loop 设备，用 `badblocks -sv -b 4096` 扫描；再用 `-n` 跑一次，比较耗时与「是否可能改数据」。
3. 超级块修复：按正文复现「清零前 1 KiB → `e2fsck -fn` 报错 → `mke2fs -n` 找备份块 → `e2fsck -fy -b <块号>` 修复 → 复检 rc=0」，记录三个退出码（预期：4、1、0）。
4. 镜像演练：对一个有数据的 loop 设备跑 `ddrescue -f -n` 拷贝到镜像，检查 mapfile 的 rescued 比例；中途 Ctrl-C 再续跑一次，证明 mapfile 能接着走。
5. XFS 与 btrfs 的只读检查：各建一个小文件系统，分别跑 `xfs_repair -n` 与 `btrfs check --readonly`，记录退出码；再说明为什么 btrfs 更推荐 `scrub`。
6. 取舍题：给出四个场景——(a) 盘有异响但仍能读；(b) 误删了分区表；(c) ext4 因断电损坏；(d) SSD 寿命显示 95% 但写入变慢。分别写出第一步动作，并说明为什么。
