# 第 27 章 DNS 与域名解析

第 24 章把「域名变地址」讲成了一条链：`nsswitch.conf` → `/etc/hosts` → `resolv.conf` 里的 DNS。但链上的每个角色各干什么、缓存在哪一层、TTL 为什么会让「改了记录却不生效」，都需要单独拆开。本章讲**解析的角色分工**（stub、递归、权威）、本机解析器的三种组织方式（NetworkManager、systemd-resolved、本地 dnsmasq/unbound），以及加密传输与分流（split DNS）的边界。

> 本章目标：能区分 stub resolver、递归解析器与权威服务器，并说出一次递归查询经过哪几步；理解 TTL 与负缓存为什么会造成「改了不生效」；会判断本机当前用的是哪套解析器（`resolv.conf`、`resolvectl`、`:53` 监听）；会用 `dig +trace` 观察递归、用 `+norecurse` 看权威应答；能配置 systemd-resolved 的 DoT 与按域分流；知道 dnsmasq/unbound 适合替代哪一层、不适合替代哪一层。
> 对应 Wiki：[Domain name resolution](https://wiki.archlinux.org/title/Domain_name_resolution)、[Systemd-resolved](https://wiki.archlinux.org/title/Systemd-resolved)、[Dnsmasq](https://wiki.archlinux.org/title/Dnsmasq)、[Unbound](https://wiki.archlinux.org/title/Unbound)

## 原理：三个角色，不是一台服务器

「DNS 服务器」是一个过度简化的说法。一次解析至少涉及三种角色：

| 角色 | 在哪 | 职责 | 典型实现 |
| ------------ | ---------------------- | ---------------------------------------- | ------------------------- |
| stub resolver | 你的机器 | 把程序的名字查询转给某个递归解析器 | libc、systemd-resolved stub |
| 递归解析器 | 本机或上游 | 从根开始逐级问，缓存结果 | systemd-resolved、dnsmasq、unbound、运营商 DNS |
| 权威服务器 | 域名拥有者 | 只回答自己 zone 内的记录 | BIND、NSD、Knot、云厂商 DNS |

程序（浏览器、`curl`、`ssh`）调用的是 **stub**，它自己不做递归。stub 只把查询发给 `/etc/resolv.conf` 里列出的某个递归解析器；真正「从根服务器一路问下来」的是递归解析器。这个分工解释了一个常见误解：**改 `/etc/resolv.conf` 不会让本机变成 DNS 服务器**，它只是换了一个「帮我查的人」。

一次冷缓存查询的路径：

```text
stub → 递归解析器（缓存未命中）
        → 根服务器：example.com 的 TLD 在哪？
        → .com 权威：example.com 的 NS 在哪？
        → example.com 权威：www 的 A 记录是什么？
      ← 逐级返回并缓存（受 TTL 约束）
stub ← 最终 IP
```

### TTL 与负缓存：为什么「改了不生效」

每条记录都带 TTL（秒），递归解析器只能在这个时间内缓存。TTL 到期前，即使权威端已经改了记录，递归解析器仍会返回旧值——这是设计行为，不是故障。排障时先看 `dig` 输出里的 TTL 剩余值，再决定是等、是 flush 缓存，还是改权威端。

负结果也会被缓存（RFC 2308）：查询一个不存在的名字得到 NXDOMAIN 后，递归解析器会在 SOA 规定的时间内记住「它不存在」。所以「刚建好的记录查不到」有时不是记录没生效，而是之前的 NXDOMAIN 还在负缓存里。

### 传输：UDP、TCP、DoT、DoH

传统 DNS 走 UDP 53，响应过大时截断并改用 TCP 53。加密方案有两种：**DoT**（DNS over TLS，853 端口，systemd-resolved 原生支持）与 **DoH**（DNS over HTTPS，443 端口，浏览器与专门客户端支持）。DoT 保护「stub 到递归」这一段，但递归到权威那段通常仍是明文；它解决的是「本地网络偷看你的查询」，不是端到端匿名。

## 步骤：先认清本机用的是哪套解析器

### 1. 三条命令定现状

```bash
readlink -f /etc/resolv.conf # 是普通文件还是指向 /run/... 的符号链接
cat /etc/resolv.conf # 当前 nameserver 与 search 域
resolvectl status # systemd-resolved 的全局与按链路状态
ss -lunp | grep ':53 ' # 本机谁在监听 53（stub 或本地解析器）
grep '^hosts' /etc/nsswitch.conf # 程序按什么顺序查名字
```

在本机实测（NetworkManager 管理、未启用 systemd-resolved）时：`/etc/resolv.conf` 是普通文件，首行注释 `Generated by NetworkManager`，`nameserver` 指向网关地址；`resolvectl status` 直接报 `Failed to connect to service /run/systemd/resolve/io.systemd.Resolve: No such file or directory`；`:53` 上没有本地监听。这三个现象同时出现，说明解析完全交给上游递归解析器，本机没有缓存层。

反过来，启用 systemd-resolved 的机器通常会看到：`/etc/resolv.conf` 指向 `/run/systemd/resolve/stub-resolv.conf`，里面是 `nameserver 127.0.0.53`；`ss` 显示 127.0.0.53:53 在监听；`resolvectl status` 列出每条链路的 DNS 服务器与 `DNSSEC`、`DNS over TLS` 状态。

### 2. 观察递归与权威

`dig` 默认走系统配置的递归解析器；加 `+trace` 则**绕过它**，自己从根开始逐级问：

```bash
dig +trace archlinux.org # 预期：依次出现根、.org、archlinux.org 的 NS 与最终 A
dig +norecurse @<权威服务器> archlinux.org A # 直接问权威，看 AA 标志与 TTL
dig @1.1.1.1 archlinux.org A # 指定递归解析器，用于对比本地结果
```

`+trace` 的输出是一串 referral（NS 记录），最后才是答案；它是理解「递归到底做了什么」的最直观材料。`+norecurse` 要求对方不递归，只有权威服务器才会给出带 `AA`（authoritative answer）标志的答案，递归解析器通常返回空答案或 referral。

### 3. systemd-resolved：stub、缓存与 DoT

resolved 在本机同时扮演 stub（127.0.0.53）与递归/缓存（转发到上游）。常用命令：

```bash
resolvectl query archlinux.org # 走 resolved，输出会注明 Data from: cache 或 network
resolvectl flush-caches # 清空 resolved 的缓存（不动上游）
resolvectl statistics # 命中/未命中计数，判断缓存是否在工作
resolvectl monitor # 实时打印解析事件，另一个终端触发查询即可观察
```

`/etc/resolv.conf` 指向哪个文件很关键：指向 `stub-resolv.conf` 时，程序走 resolved 的缓存与策略；指向 `resolv.conf`（无 stub 的那个）时，程序绕过 stub 直接问上游，resolved 的策略（DoT、分流）就管不到它。两种链接都合法，区别是「要不要缓存与统一策略」。

DoT 在 `/etc/systemd/resolved.conf` 里开启：

```text
[Resolve]
DNS=1.1.1.1 9.9.9.9
DNSOverTLS=yes
DNSSEC=yes
```

改完 `systemctl restart systemd-resolved`，再用 `resolvectl status` 确认对应链路显示 `+DNSOverTLS`。DoT 要求上游证书有效，遇到证书错误时解析会失败而不是降级——这是刻意的安全选择，但也意味着上游必须支持 853。

### 4. 本地缓存与分流：dnsmasq 的最小实验

需要本地缓存、DNS 过滤或「某个域名走指定上游」时，可以在本机跑一个递归/转发解析器。下面用 dnsmasq 在 **5353** 端口做一个不干扰系统 53 的实验（需在虚拟机中完成）：

```bash
sudo pacman -S dnsmasq
mkdir -p /tmp/lab27
cat > /tmp/lab27/dnsmasq.conf <<'EOF'
port=5353
listen-address=127.0.0.1
bind-interfaces
no-resolv
server=1.1.1.1
cache-size=1000
address=/lab.local/192.0.2.10
EOF
sudo dnsmasq --test --conf-file=/tmp/lab27/dnsmasq.conf # 预期：syntax check OK
sudo dnsmasq --conf-file=/tmp/lab27/dnsmasq.conf --pid-file=/tmp/lab27/dnsmasq.pid
dig @127.0.0.1 -p 5353 lab.local A # 预期：ANSWER 为 192.0.2.10（本地 address 规则）
dig @127.0.0.1 -p 5353 archlinux.org A # 预期：经 server=1.1.1.1 转发得到答案
sudo kill "$(sudo cat /tmp/lab27/dnsmasq.pid)"
```

`address=/lab.local/192.0.2.10` 是本地覆盖（任何 `*.lab.local` 都返回这个地址），`no-resolv` 阻止它读系统 `resolv.conf`，`server=` 指定上游。这个实验同时演示了本地解析器的两个用途：**本地名字覆盖**与**统一上游**。unbound 的定位类似，但它是完整递归解析器（自己从根走），配置与资源占用更大；dnsmasq 更轻，适合做转发+缓存。

### 5. split DNS：按域名选上游

VPN 与公司内网常见的需求是「公司域名走公司 DNS，其他走公共 DNS」。systemd-resolved 用「链路 + 域」表达：

```bash
resolvectl dns eth0 192.0.2.53 # 给 eth0 指定 DNS
resolvectl domain eth0 corp.example.com # 该域（及其子域）走 eth0 的 DNS
resolvectl status # 确认 DNS Domain 与对应服务器
```

`resolvectl domain` 里的域名会参与最长后缀匹配：`corp.example.com` 的查询走指定链路，其他查询仍走全局。把 `~.` 这样的域分配给某条链路则表示「所有查询都走它」。分流写错时最典型的现象是「内网域名解析到公网地址」或「外网域名被内网 DNS 拒绝」。

## 失败模式

- **手改 `/etc/resolv.conf` 被覆盖**：NetworkManager、resolved、DHCP 客户端都会重写它。持久配置应改对应管理者的配置（NM 的 `nmcli`/`conf.d`、resolved 的 `resolved.conf`），而不是改生成物。
- **两个解析器抢 53 端口**：dnsmasq、unbound、resolved stub 同时监听 127.0.0.1:53 会有一个启动失败或行为随机。用 `ss -lunp | grep :53` 先确认谁在监听，再决定关掉谁。
- **只清本地缓存，不清上游**：`resolvectl flush-caches` 只清本机；上游递归解析器仍缓存旧记录。要验证权威端是否已更新，用 `dig @<权威>` 直接问。
- **把 TTL 当成「生效时间」**：TTL 是「缓存最长时间」，不是「保证在该时间内生效」；改记录前先把 TTL 调小、等旧 TTL 过期，再改值，是标准操作。
- **NXDOMAIN 负缓存**：新记录查不到时先确认不是之前的负缓存；直接问权威服务器，或换一个没查过该名字的递归解析器对比。
- **`search` 域拼接意外**：`resolv.conf` 里的 `search` 会让短名字被拼成 `name.search域`；查询一个不存在的短名时，可能先命中一个奇怪的拼接结果。
- **DoT 证书失败就断网**：`DNSOverTLS=yes` 下上游证书不匹配会直接失败，不会回退明文。没有备用解析器时表现为「完全不能解析」。
- **DNSSEC 与上游不兼容**：开启 `DNSSEC=yes` 后，上游不支持或链路中间设备篡改会导致验证失败；要么换支持的上游，要么明确降级策略。
- **分流规则覆盖过宽**：把 `~.` 分配给 VPN 链路会把所有查询（包括公共域名）送进内网 DNS，常见于「连上 VPN 后上不了网」。
- **只看 `dig` 不看 `getent`**：`dig` 绕过 `nsswitch` 与 `/etc/hosts`，程序实际走的是 `getent` 那条链；两者不一致时问题在 nsswitch/hosts，不在 DNS 服务器。

## 验证与回滚

| 操作 | 验证 | 回滚 |
| ---------------------- | ------------------------------------------------ | ------------------------------------------ |
| 换上游 DNS | `dig @新上游` 与 `resolvectl query` 对比；`resolvectl status` | 改回原配置并重启对应服务 |
| 清缓存 | `resolvectl statistics` 命中数归零；再查一次看是否回源 | 缓存会自动重建，无需回滚 |
| 开 DoT | `resolvectl status` 出现 `+DNSOverTLS`；`resolvectl query` 成功 | 注释 `DNSOverTLS` 并重启 resolved |
| 配 split DNS | `resolvectl status` 的 DNS Domain；分别查内外网域名 | `resolvectl domain <链路>` 重置该链路的域列表 |
| 本地 dnsmasq | `dnsmasq --test`；`dig -p 5353` 两条查询 | `kill` 进程，删除临时配置 |
| 改 `/etc/resolv.conf` | `readlink -f` 确认还是符号链接；`getent hosts` 实测 | 恢复符号链接或让管理者重新生成 |

判断「解析到底走没走缓存」有一个简单办法：连续查两次同一域名，看 `resolvectl query` 的 `Data from:` 是否从 `network` 变成 `cache`；或在 `resolvectl monitor` 里看两次事件。缓存没命中时，问题可能在 TTL 太短、上游拒绝缓存，或程序用了绕过 resolved 的路径。

## 取舍边界

- **NetworkManager 管理 vs systemd-resolved**：NM 直接写 `resolv.conf` 简单、依赖少，但没有本地缓存与统一策略；resolved 提供 stub、缓存、DoT、分流，代价是多一个守护进程与一套 `resolvectl` 语义。桌面/笔记本常用 resolved，服务器常直接交给 NM 或静态配置。
- **dnsmasq vs unbound**：dnsmasq 轻量、转发+缓存+本地覆盖，适合家用/小网络；unbound 是完整递归解析器，能独立从根解析、支持 DNSSEC 验证，适合不想依赖上游的场合，代价是配置与资源更高。
- **递归解析器自建 vs 用上游**：自建递归能减少对运营商的依赖、统一缓存与策略，但要把「递归放大攻击」「DNSSEC 验证」「上游根列表维护」算进成本；多数场景用可信上游更省事。
- **DoT vs DoH**：DoT 是系统级、端口固定、易被网络策略识别；DoH 混在 443 里更难被阻断，但把信任交给浏览器/客户端，且排障更隐蔽。系统级加密优先 DoT，浏览器隐私需求用 DoH。
- **TTL 长 vs 短**：长 TTL 减少查询、加快解析，但改记录后生效慢；短 TTL 灵活，代价是更多查询与更高负载。切换服务商/迁移前先调短 TTL，是变更管理的一部分。
- **权威自建 vs 托管 DNS**：自建权威（BIND/NSD/Knot）控制力强，但要自己处理冗余、DDoS、DNSSEC 签名轮换；托管 DNS 把这些打包成服务，代价是依赖厂商。解析器（递归）与权威是两套软件，不要混为一谈。

## 小结

- 三个角色：stub（本机）、递归解析器（缓存与逐级查询）、权威（只答自己 zone）；改 `resolv.conf` 只是换递归解析器。
- 一次冷查询从根走到权威，逐级返回并按 TTL 缓存；负结果也会缓存。
- 先认清本机：`readlink -f /etc/resolv.conf`、`resolvectl status`、`ss -lunp | grep :53`、`nsswitch.conf` 的 `hosts` 行。
- `dig +trace` 看递归，`+norecurse` 看权威，`@server` 做对比；`dig` 与 `getent` 走的不是同一条链。
- resolved 提供 stub（127.0.0.53）、缓存、DoT 与 split DNS；`/etc/resolv.conf` 指向哪个文件决定程序是否经过它。
- 本地 dnsmasq 适合做转发、缓存与本地覆盖；unbound 适合完整递归。两者都不要和系统 stub 抢 53。
- 改记录前先调小 TTL，排查时先分清「权威没改」「上游缓存」「本地缓存」「nsswitch/hosts」四层。

## 练习

1. 现状盘点（只读）：运行 `readlink -f /etc/resolv.conf`、`cat /etc/resolv.conf`、`resolvectl status`、`ss -lunp | grep ':53 '`，判断本机是「NM 直连上游」还是「resolved stub + 缓存」，并说明依据（预期：能看到 `Generated by NetworkManager` 或 `127.0.0.53` 之一）。
2. 递归观察（需联网，安装 `bind` 提供 `dig`）：对同一域名分别跑 `dig +short`、`dig +trace`、`dig +norecurse @<权威>`，标出哪一步是递归、哪一步带 `AA` 标志。
3. 缓存与 TTL：连续两次 `resolvectl query archlinux.org`，记录 `Data from:` 的变化；再 `resolvectl flush-caches` 后查一次，说明缓存层在哪。
4. 本地解析器（需在虚拟机中完成）：按正文用 dnsmasq 在 5353 端口提供 `lab.local → 192.0.2.10`，用 `dig -p 5353` 验证本地覆盖与转发两条路径，然后结束进程。
5. split DNS 设计题：给「公司域名 `corp.example.com` 走 192.0.2.53，其余走 1.1.1.1」写出 `resolvectl dns` 与 `resolvectl domain` 两条命令，并说明 `resolvectl status` 里该看哪两行确认生效。
6. 故障判断：给出四个现象——(a) 改了 A 记录，本地仍返回旧 IP；(b) `dig` 正常但 `curl` 报无法解析；(c) 开启 DoT 后完全不能解析；(d) 连上 VPN 后公共网站打不开。分别写出第一层该查什么。
