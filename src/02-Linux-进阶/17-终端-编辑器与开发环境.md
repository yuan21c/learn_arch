# 第 17 章 终端、编辑器与开发环境

日常操作的入口只有三个：一个能敲命令的**终端**、一个能改文件的**编辑器**、一套能编译运行与版本管理的**工具链**。三者都可以用最朴素的方式工作，也都能配置得很复杂。这一章不教命令（第 2 章已讲），也不教权限（第 4 章已讲），只回答一个工程问题：**远程、断线、多任务、多语言并存时，最小可用的环境应该由哪几层组成，各自的边界在哪里。**

> 本章目标：能说清终端模拟器、伪终端、TTY 与 `$TERM` 各自是什么；会用 tmux 建立可断线重连的会话；知道服务器上为什么必须会一个终端编辑器，并能用 vim 的生存键位完成基本编辑；理解 shell 提示符与补全的配置边界；能搭出一个不依赖图形界面的最小开发环境（版本控制、构建、运行、语言服务）。
> 对应 Wiki：[Terminal emulator](https://wiki.archlinux.org/title/Terminal_emulator)、[Tmux](https://wiki.archlinux.org/title/Tmux)、[Vim](https://wiki.archlinux.org/title/Vim)、[Git](https://wiki.archlinux.org/title/Git)

## 四层结构：从键盘到进程

一次按键到达程序，中间经过四层，出问题时每一层都可能成为原因：

| 层 | 是什么 | 观察方式 | 典型故障 |
| ---------- | -------------------------------------- | ---------------------------- | ------------------------------ |
| 终端模拟器 | 图形程序（如 kitty、GNOME Terminal） | 就是你在用的窗口 | 字体、配色、快捷键冲突 |
| 伪终端 (pty) | 内核提供的一对主/从设备，模拟终端行为 | `ls -l /dev/pts` | 程序读不到输入、窗口大小错 |
| 会话与 TTY | 登录会话、控制终端 | `tty`、`who` | 「不是终端」导致交互程序失败 |
| `$TERM` | 终端能力描述的名字 | `echo $TERM`、`infocmp` | 方向键乱码、颜色异常 |

`tty` 回答「我现在的控制终端是哪个」：图形终端里通常输出 `/dev/pts/N`，SSH 会话也是 `/dev/pts/N`，而 `cron`、systemd 单元里输出 `not a tty`——这解释了很多交互式命令（需要确认、需要全屏）在定时任务里失败的原因。需要伪终端时用 `script` 或 `ssh -t` 分配一个。

`$TERM` 不是一个装饰性的环境变量，而是 `terminfo` 数据库的键。全屏程序（vim、tmux、top）靠它查「这个终端支持哪些能力、方向键发什么序列」。两边不一致时现象很具体：

```bash
echo "$TERM" # 常见：xterm-256color
infocmp "$TERM" | head -5 # 看这个终端的能力定义
infocmp xterm-256color tmux-256color | head # 对比两种终端的差异
```

如果 SSH 进去后方向键变成 `A`、`B` 这样的字符，或 tmux 里颜色不对，先查 `$TERM` 是否与 `terminfo` 里的条目匹配，而不是重装软件。`TERM=unknown` 时全屏程序会拒绝启动或退化成行模式。

## tmux：让会话脱离窗口

SSH 断开时，终端里前台进程会收到 `SIGHUP`（第 13 章），正在跑的编译、训练、长任务随之中断。tmux 解决的正是这个问题：它作为一个**服务端进程**持有伪终端与子进程，你的窗口只是「连上去看」的客户端，断开窗口不影响服务端。

```bash
tmux new -s work # 新建名为 work 的会话
tmux ls # 列出会话
tmux attach -t work # 重新连上（断线后重连就是用这条）
tmux detach # 默认前缀 Ctrl-b 后按 d：脱离，会话继续跑
tmux kill-session -t work # 结束会话及其中的所有进程
```

窗口与窗格是最小够用的多任务能力：`Ctrl-b c` 新建窗口、`Ctrl-b n/p` 切换、`Ctrl-b %` 左右分屏、`Ctrl-b "` 上下分屏、`Ctrl-b 方向键` 在窗格间移动、`Ctrl-b z` 最大化当前窗格。前缀键可以改，但**改之前先确认没有和编辑器快捷键冲突**——这是最常见的「配了 tmux 之后 vim 不听话」的来源。

三个必须知道的边界：

- tmux 服务端是**普通用户进程**，不是系统服务；机器重启后会话全没，要开机自启得靠 systemd 用户单元（第 46 章）。
- 会话里的进程继承 tmux 服务端的环境变量，**不是**你 attach 时的环境；改了 `PATH` 要重开会话或在会话内改。
- 嵌套 tmux（本地 tmux 里 SSH 到远端再开 tmux）会让前缀键冲突，需要给内层换前缀键（`set -g prefix C-a`）。

## 编辑器：服务器上必须会一个终端编辑器

图形编辑器依赖 X/Wayland 与桌面环境；SSH 会话、救援模式、容器里只有终端。**至少要能在一个不熟的环境里改一个配置文件并保存退出**，这是运维底线。选型不是信仰问题，而是场景问题：

| 编辑器 | 学习成本 | 适用场景 | 不该用的场景 |
| -------- | -------- | ------------------------------ | -------------------- |
| vim / neovim | 中 | 服务器、远程、快速改配置 | 需要大量图形化重构 |
| nano | 低 | 应急改一行、给新人用 | 长期主力编辑 |
| emacs | 高 | 深度定制、 org 工作流 | 只改配置文件 |

vim 的**生存键位**只需记这一组，足以完成「打开、改、存、退」：

```text
i 进入插入模式    Esc 回到普通模式    :w 保存    :q 退出    :wq 保存退出    :q! 放弃退出
dd 删一行    yy 复制一行    p 粘贴    /关键词 搜索    :set number 显示行号
```

崩溃或断线后，vim 会留 `.swp` 交换文件。再次打开同一文件时提示 `Swap file ... already exists`，处理方式只有三种：确认原会话已死就删 `.swp`（`rm 文件名.swp`）、或用 `:recover` 恢复内容、或 `:q!` 放弃。**不要盲目删 `.swp`**——它可能是你唯一没保存的修改。

## shell 提示符、补全与配置的边界

提示符（`PS1`）与补全（completion）属于「体验层」，配得好省时间，配得重会拖慢每个新终端：

- `PS1` 应包含「用户@主机、当前目录、git 分支、上条命令退出码」这几项就够；每多一次外部命令调用（如每次渲染都跑 `git status`），打开终端就多一次等待。
- bash 补全靠 `bash-completion` 包 + `/usr/share/bash-completion/completions/`；zsh 用 `compinit`。补全脚本来自各软件的打包，**不是 shell 自带**，装新工具后补全不生效先查它有没有提供补全文件。
- 提示符与别名写进 `~/.bashrc`（交互式非登录）或 `~/.bash_profile`（登录）；写错文件会出现「SSH 进去不生效、本地生效」这类差异，原因是两者加载路径不同（第 10 章）。

配置的第一原则是**可回退**：改之前 `cp ~/.bashrc ~/.bashrc.bak`，改完新开一个终端验证，而不是在唯一会话里 `source` 改坏的文件——那样连提示符都没有，只能靠 `bash --noprofile --norc` 救回来。

## 最小开发环境：不依赖图形界面

一个能在纯终端里完成「拉代码、改、编译、跑、提交」的环境，只需要五样东西：

```bash
git --version # 版本控制
gcc --version # 或 clang、go、rustc，按语言选
make --version # 构建编排（多数项目已有 Makefile）
gdb --version # 或 lldb，调试
strace --version # 系统调用观察，排障用
```

语言服务（LSP）不是必需品，但决定了「在终端里能不能有补全与跳转」。它在编辑器与编译器之间起桥接作用：编辑器的 LSP 客户端通过标准输入输出与语言服务器通信，服务器负责索引与语义分析。边界在于：**LSP 只提供编辑体验，不参与构建**；构建失败的原因仍要回到编译器和构建日志。

```bash
git init /tmp/lab17 && cd /tmp/lab17
printf 'int main(void){return 0;}\n' > main.c
gcc -Wall -Wextra -o main main.c && ./main; echo "exit=$?" # 编译并运行
```

## 失败模式

- **`$TERM` 不匹配**：SSH 或 tmux 里方向键乱、颜色错、vim 报 `Terminal entry not found`；先 `echo $TERM` 与 `infocmp` 对照，再改配置，不要先重装。
- **断线即中断**：长任务没放进 tmux，SSH 一断就收 `SIGHUP`；任务已经在跑时无法补救，只能重跑。
- **环境不继承**：在 tmux 里启动的服务读的是 tmux 服务端的环境，不是当前窗口的；`PATH`、代理变量常因此失效。
- **交换文件误删**：`.swp` 里可能是未保存内容，删之前先 `:recover` 看一眼。
- **配置改坏**：在唯一会话里 `source` 语法错误的 `~/.bashrc`，新命令全失败；用 `bash --noprofile --norc` 或另一个已开会话恢复。
- **locale 缺失**：中文文件名显示成问号或乱码，查 `locale` 与 `locale -a` 是否生成了对应 locale，而不是换终端。

## 验证与回滚

| 操作 | 验证 | 回滚 |
| ------------------ | ------------------------------------ | -------------------------- |
| 改 `$TERM` | `infocmp "$TERM"` 无报错、全屏程序正常 | 改回原值，或 `unset TERM` 后重开 |
| 改 tmux 配置 | 新开会话验证前缀键与分屏 | 保留 `~/.tmux.conf.bak`，删配置即回默认 |
| 改 shell 配置 | 新开终端，不 `source` 当前会话 | `.bak` 覆盖回去，或 `--noprofile --norc` |
| 编辑器崩溃 | `:recover` 检查内容 | 保留 `.swp` 直到确认内容已保存 |

一条通用判据：**任何影响「能不能登录、能不能敲命令」的配置，都要保留一个不加载它的入口**（另一个会话、`--norc`、控制台）。否则回滚动作本身都执行不了。

## 取舍边界

- **tmux vs screen vs 直接后台**：tmux 功能全、社区活跃；screen 更老但到处都有；`nohup`/`&` 只解决「不被挂断」，不提供重连与窗口管理。远端长任务用 tmux，一次性的短命令用 `&` 即可。
- **终端编辑器 vs 图形 IDE**：远程与救援场景必须会终端编辑器；本地大型项目用 IDE 提效没有问题。两者不冲突，**别把「只会 IDE」带进 SSH 会话**。
- **重配置 vs 默认配置**：默认配置换机器就能用，重配置换机器要迁移。个人机器可以深配，生产跳板机保持接近默认，降低维护面。
- **LSP/插件 vs 纯编辑器**：插件提升体验也增加启动时间与故障面；排障环境下用 `vim -u NONE` 启动一个干净实例，能快速判断「是配置问题还是系统问题」。

## 小结

- 四层结构：终端模拟器 → 伪终端 → 会话/TTY → `$TERM`；`not a tty` 解释了交互命令在定时任务里失败。
- tmux 的价值是「会话脱离窗口」：服务端持有进程，客户端断开不影响任务；环境变量继承自服务端。
- 服务器底线是会用 vim 的生存键位；`.swp` 可能含未保存内容，先 `:recover` 再决定删不删。
- 提示符与补全属体验层，配置要能回退；登录与非登录 shell 的加载文件不同。
- 最小开发环境 = 版本控制 + 编译器 + 构建 + 调试 + `strace`；LSP 只管编辑体验，不管构建。
- 排障先对照 `$TERM` 与 `infocmp`，再动配置；影响登录的改动必须留备用入口。

## 练习

1. 终端层次（只读）：在图形终端与 SSH 会话里分别运行 `tty`、`who`、`echo $TERM`、`ps -o tty= -p $$`，把输出对应到四层结构，并解释 `cron` 任务里为什么是 `not a tty`。
2. 断线重连（`/tmp` 演练）：`tmux new -s lab17` 里跑 `while :; do date; sleep 2; done`，`Ctrl-b d` 脱离后 `tmux ls` 看会话仍在，再 `attach` 回去；最后 `kill-session` 清理。
3. `$TERM` 对照：`infocmp xterm-256color tmux-256color | head` 找出两者能力差异；在 tmux 内外各 `echo $TERM`，解释为什么 tmux 会改写它。
4. 编辑器生存（`/tmp` 演练）：用 vim 打开一个文件，练习 `i`、`Esc`、`:wq`；再故意不保存直接杀进程，重开时用 `:recover` 恢复内容，记录提示文字。
5. 配置回滚：备份 `~/.bashrc` 后写入一行故意错误的语法，新开终端观察报错；用 `bash --noprofile --norc` 进入干净 shell，把 `.bak` 恢复回去。
6. 最小工具链（`/tmp` 演练）：按正文编译 `main.c`，分别用 `gcc -Wall -Wextra` 与不带警告的版本编译，比较输出；再用 `strace -f -e trace=openat ./main` 观察它打开了哪些文件。
