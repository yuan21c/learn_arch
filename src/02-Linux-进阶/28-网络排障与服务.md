# 第 28 章 网络排障与服务

第 24 章讲的是网络「怎么配」：地址、路由、DNS、SSH、防火墙。这一章讲「不通时怎么查」。网络排障的难点不是命令太少，而是**证据太多且各层互相甩锅**：应用说网络不通，网络说端口没开，端口说 DNS 解析错，DNS 说上游超时。有效的方法只有一个——先用最小成本的证据把故障范围切成两半，再逐层缩小，而不是一上来就 `tcpdump` 抓全量包。

> 本章目标：能按「本机 → 网关 → 出口 → 目标 → 应用」的顺序切分故障范围；读懂 `ss` 的连接状态（`SYN-SENT`、`TIME-WAIT`、`CLOSE-WAIT`）并判断是网络问题还是应用问题；会用 `tcpdump` 的捕获过滤器抓一段可读的包；理解 conntrack 与 NAT/有状态防火墙的关系；会用 `mtr` 与 `curl -w` 区分「丢包」「DNS 慢」「TLS 慢」；能识别 MTU 黑洞这一经典误判。
> 对应 Wiki：[Network troubleshooting](https://wiki.archlinux.org/title/Network_troubleshooting)、[Nftables](https://wiki.archlinux.org/title/Nftables)、[Conntrack](https://wiki.archlinux.org/title/Conntrack)

## 原理：先切范围，再选工具

排障的第一动作不是敲命令，而是回答「坏在哪一段」。把路径切成五段，每段用最便宜的证据验证：

| 段 | 问题 | 最小证据 |
| ---------- | ------------------------------ | -------------------------------------- |
| 本机 | 网卡起来了吗、地址有吗、路由选对了吗 | `ip -s link`、`ip addr`、`ip route get` |
| 局域网 | 网关通吗、ARP/邻居表正常吗 | `ping 网关`、`ip neigh` |
| 出口 | 能到公网 IP 吗、丢包在哪 | `ping 公网 IP`、`mtr` |
| 目标 | 端口开吗、TCP 握手完成吗 | `nc -vz`、`ss`、`tcpdump` |
| 应用 | DNS 慢、TLS 慢、服务端慢 | `curl -w`、应用日志 |

这条顺序的价值在于**每一步都能证伪一个假设**。如果 `ping 公网 IP` 通、`ping 域名` 不通，问题几乎一定在 DNS；如果 IP 与端口都通、`curl` 仍失败，问题在 TLS 或 HTTP 层。反之，跳过前面直接抓包，往往抓到一堆看不懂的包，还得回头补基础证据。

### 连接状态：`ss` 是最便宜的证据

`ss` 不只是「看谁在监听」，它的状态字段能直接区分故障类型：

| 状态 | 含义 | 常见原因 |
| ---------------- | ---------------------------------------- | -------------------------------------- |
| `LISTEN` | 服务在等连接 | 正常；注意绑定地址是 `0.0.0.0` 还是 `127.0.0.1` |
| `SYN-SENT` | 客户端发了 SYN，等回应 | 防火墙 `drop`、目标不可达、路由错 |
| `SYN-RECV` | 服务端收到 SYN，半开连接 | 大量出现可能是 SYN Flood 或回包路径断 |
| `ESTAB` | 双向连接建立 | 正常 |
| `FIN-WAIT-1/2` | 本端已发 FIN，等对方关闭 | 正常关闭过程；长期停留说明对方不回 FIN |
| `TIME-WAIT` | 本端主动关闭后等待 2MSL | **正常**，不是泄漏 |
| `CLOSE-WAIT` | 对方已关闭，本端应用没关 | **应用 bug**：没调用 `close()` |

`TIME-WAIT` 常被误当成「端口耗尽」的元凶。它持续约 60 秒（2MSL），是 TCP 保证旧连接残包不污染新连接的必要机制；大量短连接会堆积 `TIME-WAIT`，但通常可以通过连接复用（keep-alive）缓解，而不是改内核参数。真正要查的是 `CLOSE-WAIT`：它说明程序收到了对方的 FIN 却没关闭自己的句柄，数量会一直涨。

```bash
ss -s # 汇总：总连接数、各状态计数
ss -tanp state time-wait | head # 只看 TIME_WAIT
ss -tanp state close-wait | head # 只看 CLOSE_WAIT（应用问题）
ss -ti # 每条连接的 rtt、重传、拥塞窗口
ss -lntp # 监听端口与绑定地址
```

`ss -ti` 里的 `retrans`、`rtt`、`cwnd` 是判断「链路丢包」与「应用慢」的分界线：重传率高说明包真的丢了；重传为零但 `time_starttransfer` 很大，问题更可能在服务端处理或 DNS/TLS。

## 步骤：抓一段能读的包

### 1. 本地起一个服务，抓回环流量

最安全的实验是在本机回环上做，不经过任何网络设备：

```bash
sudo pacman -S tcpdump # 未安装时先装
python3 -m http.server 8080 --bind 127.0.0.1 &
SERV=$! # 记住服务进程，结束后只杀它
sudo tcpdump -ni lo -c 20 'tcp port 8080' & # -n 不解析名字，-c 抓 20 个包后退出
TCAP=$!
sleep 1
ss -lntp | grep 8080 # 预期：LISTEN 在 127.0.0.1:8080
curl -s http://127.0.0.1:8080/ >/dev/null
wait "$TCAP" # 只等抓包进程；直接 wait 会卡在常驻的 HTTP 服务上
kill "$SERV"
```

预期能看到 `SYN → SYN-ACK → ACK` 三次握手、HTTP 请求与响应、以及关闭时的 `FIN` 序列。这条实验把「TCP 连接长什么样」变成可观察的事实，也练习了捕获过滤器 `tcp port 8080` 的写法——过滤器在**内核里**生效，只把你关心的包送进用户态，比抓全量再 `grep` 高效得多。

### 2. 捕获过滤器的常用组合

```bash
sudo tcpdump -ni eth0 host 203.0.113.10 and port 443 # 某目标某端口
sudo tcpdump -ni eth0 'tcp[tcpflags] & tcp-syn != 0' # 只看 SYN
sudo tcpdump -ni eth0 -s 0 -w /tmp/lab28.pcap # 全尺寸写文件，供 Wireshark 分析
sudo tcpdump -ni eth0 -r /tmp/lab28.pcap -c 10 # 读回文件，不重新抓
```

`-s 0` 表示不截断（老版本默认只抓前几十字节，看不到 payload）；`-w` 写 pcap 后应尽快 `-r` 读回或拷走，避免在生产机上长期占用磁盘。生产环境抓包要同时考虑**隐私**（包里有凭据、明文协议）与**性能**（高流量下抓包本身会丢包），优先用「短时间、强过滤、写文件」而不是前台滚动输出。

### 3. conntrack：NAT 与有状态防火墙的账本

netfilter 的 conntrack 记录每条连接的状态。NAT、`ct state` 匹配、`masquerade` 都依赖它：

```bash
sudo pacman -S conntrack-tools
sudo conntrack -C # 当前条目数
sudo conntrack -L | head # 列出连接（含 NAT 前后的地址）
sudo conntrack -S # 按 CPU 的统计与错误计数
```

两条排障事实：**`ct state established,related accept` 放行的是 conntrack 眼中的已建立连接**，不是「TCP 状态为 ESTAB」；**NAT 只在第一个包做改写，后续包靠 conntrack 还原**。所以防火墙规则顺序错、conntrack 表满、或中间设备清了状态，都会出现「握手成功、后续包被丢」的怪现象。内核日志出现 `nf_conntrack: table full, dropping packet` 时，先查 `nf_conntrack_count` 与 `nf_conntrack_max`，再判断是连接数异常还是上限太小。

### 4. mtr：丢包在哪一跳

```bash
sudo pacman -S mtr
mtr -n -c 10 1.1.1.1 # -n 不解析名字，-c 发 10 轮
mtr -n -r -c 10 archlinux.org # -r 输出报告，适合贴进工单
```

`mtr` 同时显示每一跳的丢包率与延迟。关键判读规则：**中间跳的丢包率不等于端到端丢包**。路由器常对 ICMP 限速或直接不回应（显示 `???`），只要**最后一跳**丢包低，中间跳的红色数字多半是控制面限速，不代表转发路径真的丢包。反过来，最后一跳持续丢包、且延迟随跳数递增，才说明路径上有真实问题。

### 5. MTU 黑洞：小包通、大包死

这是最容易被误判成「应用 bug」的网络问题。用 DF（Don't Fragment）位探测：

```bash
ping -M do -s 1472 1.1.1.1 # IPv4/1500 MTU：20 IP + 8 ICMP + 1472 = 1500，预期通
ping -M do -s 1473 1.1.1.1 # 预期失败（本机报 message too long，或远端返回 fragmentation needed）
tracepath 1.1.1.1 # 逐跳探测路径 MTU
```

`-M do` 禁止分片；`-s` 是 ICMP 载荷大小。IPv6 的头部是 40 字节，1500 MTU 对应载荷 1452。典型症状：`ping` 小包正常、SSH 能连上但一执行命令就卡住、TLS 握手在中途停住、网页小请求正常但大文件失败——因为握手后的大包被静默丢弃，而 ICMP `Fragmentation Needed` 又被中间防火墙挡了（PMTUD 黑洞）。缓解手段是在出口做 **TCP MSS 钳制**（把 SYN 里的 MSS 改小），而不是在每台客户端上调 MTU。

### 6. 用 `curl -w` 拆开「慢」

```bash
curl -o /dev/null -s -w \
  'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  https://archlinux.org
```

五个时间点对应四段：`time_namelookup` 是 DNS，`time_connect` 是 TCP 握手，`time_appconnect` 是 TLS 握手，`time_starttransfer` 是首字节（含服务端处理），`time_total` 是整体。哪一段占比异常，就去查哪一层：DNS 大而 connect 小 → 解析慢；connect 大 → 网络/防火墙；appconnect 大 → TLS/证书/中间设备；starttransfer 大 → 服务端或后端。**不要用「网站慢」直接归因于网络**，多数「慢」停在服务端或 DNS 上。

## 失败模式

- **抓错网卡**：容器、VPN、多网卡机器上，流量可能走 `tun0`、`docker0` 或 `br0`，在 `eth0` 上抓不到。先 `ip route get <目标>` 看出口设备，再决定 `-i`。
- **过滤器写错**：`port 443` 只匹配 TCP/UDP 端口，不区分方向；要区分用 `src port`/`dst port`。过滤器语法错时 `tcpdump` 直接报错退出，不会「抓了但抓错」。
- **`-s` 截断**：默认 snaplen 在老版本上会截掉 payload，误以为「没有数据」；用 `-s 0`。
- **把 `TIME-WAIT` 当故障**：它是正常的主动关闭等待；真正的问题是 `CLOSE-WAIT` 堆积或短连接过多。前者修应用，后者用连接复用。
- **conntrack 表满**：高并发 NAT/防火墙设备上出现 `table full, dropping packet`，表现为随机丢包；应调 `nf_conntrack_max` 并排查连接泄漏，而不是只调大上限。
- **只看 `ss` 不看防火墙**：`ss` 显示 `LISTEN` 只说明进程绑定了地址，不代表包能到达；`policy drop` 下监听仍在，但外部连不上。
- **绑定地址误判**：服务监听 `127.0.0.1:8080`，从另一台机器访问必然失败；`ss -lntp` 的地址列要看清是 `127.0.0.1`、`0.0.0.0` 还是 `[::]`。
- **mtr 中间跳误判**：中间跳 ICMP 限速造成的丢包不是转发丢包；以最后一跳为准。
- **MTU 黑洞**：小包通、大包不通时，先怀疑 MTU/PMTUD，而不是应用；`ping -M do` 是最快的验证。
- **DNS 与网络混为一谈**：`ping 域名` 失败可能是 DNS，也可能是 ICMP 被禁；用 `getent hosts` 与 `ping IP` 分开验证。

## 验证与回滚

| 操作 | 验证 | 回滚 |
| -------------------- | ------------------------------------------------ | ------------------------------------------ |
| 抓包 | `-c` 限数量、`-w` 写文件后 `-r` 读回；确认抓到握手 | 停止进程，删除 pcap（可能含敏感数据） |
| 改 conntrack 上限 | `conntrack -C` 与 `dmesg` 不再出现 table full | `sysctl -w` 改回；持久化文件删除对应行 |
| 调 MTU/MSS | `ping -M do` 逐级加 `-s`；`tracepath` 看路径 MTU | 恢复原 MTU/MSS 配置 |
| 防火墙变更 | 保留会话 + `nft -c -f` + 限时回滚（第 25 章） | 恢复规则文件 |
| 改 DNS | `curl -w` 的 `time_namelookup` 对比；`resolvectl query` | 恢复解析器配置 |

排障本身也要留证据：把「操作前」的 `ip route get`、`ss -s`、`conntrack -C`、`curl -w` 输出存一份，改完再对比。没有基线的「好像好了」无法判断是修好了还是暂时被缓存掩盖。

## 取舍边界

- **先看状态还是先抓包**：`ss`、`ip route get`、`curl -w` 是零成本证据，先做；tcpdump 信息量大但成本高、可能涉密，放在「已经缩小到某条连接」之后。
- **抓全量还是强过滤**：生产环境优先强过滤 + 短时间 + 写文件；全量抓包只在隔离环境或明确需要复盘时使用。
- **conntrack 调大还是查泄漏**：调大上限能缓解症状，但如果连接数持续增长，根因是应用没关连接或短连接风暴；先查 `ss` 状态分布，再决定。
- **调 MTU 还是钳 MSS**：端到端调 MTU 要改所有设备；在出口钳 MSS 只改一处，适合 PPPoE/VPN/隧道场景。代价是钳制值过小会降低吞吐。
- **mtr 还是 traceroute**：`mtr` 连续采样、统计更可靠；`traceroute` 单次、适合快速看路径。两者都受 ICMP 限速影响，判读规则相同。
- **在故障机上调还是先隔离**：能在测试环境复现就先隔离；生产上直接改内核参数或防火墙，风险远高于先抓一段证据。

## 小结

- 排障先切五段：本机 → 局域网 → 出口 → 目标 → 应用；每段用最便宜的证据证伪一个假设。
- `ss` 的状态能直接分类：`SYN-SENT` 多为被丢/不可达，`TIME-WAIT` 正常，`CLOSE-WAIT` 是应用没关连接。
- `ss -ti` 的重传与 RTT 区分「链路丢包」与「应用慢」。
- `tcpdump` 用强过滤 + `-c`/`-w`，抓完 `-r` 读回；先 `ip route get` 确认网卡。
- conntrack 是 NAT 与 `ct state` 的账本；表满会随机丢包，先查连接分布再调上限。
- `mtr` 只看最后一跳的丢包；中间跳的红色多为 ICMP 限速。
- MTU 黑洞的典型症状是「小包通、大包死」，用 `ping -M do -s` 与 `tracepath` 验证，出口钳 MSS。
- `curl -w` 把「慢」拆成 DNS、TCP、TLS、首字节四段，避免把服务端问题归因于网络。

## 练习

1. 连接状态观察（需在虚拟机中完成）：起一个本地 HTTP 服务，用 `curl` 连续请求，同时用 `ss -tanp state time-wait` 与 `ss -s` 观察 `TIME_WAIT` 的产生与消退；再用一个故意不关连接的小脚本制造 `CLOSE_WAIT`（提示：客户端读完后不 `close()`），说明两种状态的区别。
2. 回环抓包（需在虚拟机中完成）：按正文用 `tcpdump -ni lo -c 20 'tcp port 8080'` 抓一次 `curl`，在输出里指出 SYN、SYN-ACK、ACK、HTTP 请求、FIN 各是哪几行。
3. 过滤器练习：写出三条过滤器——只看某目标的 SYN、只看某网段的 443、排除 SSH 端口；用 `tcpdump -d '<过滤器>'` 只看编译结果而不抓包，验证语法。
4. conntrack（需在虚拟机中完成）：安装 `conntrack-tools`，在有 NAT 或本地服务连接时运行 `conntrack -C` 与 `conntrack -L`，找一条连接，说明它在 NAT 前后的地址如何对应。
5. MTU 探测（需联网）：用 `ping -M do -s 1472` 与 `-s 1473` 找出口 MTU 的临界值，再用 `tracepath` 对比；解释为什么 `-s 1473` 的失败信息可能来自本机而不是远端。
6. 慢在哪一段（需联网）：用 `curl -w` 的五段时间测三个站点，指出每个站点的主要耗时段；再用 `dig +stats` 单独测 DNS，验证你的判断。
7. 误判分析：某服务「能连上但一发大文件就断」，`ss` 显示 `ESTAB`，`ping` 小包正常。写出你的排查顺序与最可能的结论。
