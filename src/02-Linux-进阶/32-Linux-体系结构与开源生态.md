# 第 32 章 Linux 体系结构与开源生态

前 31 章都在「怎么用」：进程、存储、网络、服务。这一章退后一步，给出一张**地图**：内核与用户空间怎么分界、发行版到底做了什么、一个 bug 或补丁在生态里经过谁的手、许可证如何约束分发与修改。这些内容不会让你多会一条命令，但会决定你遇到问题时**找谁、看哪份文档、改哪一层**。

> 本章目标：能画出「硬件 → 内核 → 用户空间」的分层与系统调用这条唯一稳定接口；理解「Linux 内核」与「一个 Linux 发行版」不是同一件事；能说出上游（upstream）、发行版打包者、用户三者各自的职责；能区分 GPL、LGPL 与 MIT/BSD 的义务边界；知道内核 ABI 承诺覆盖什么、不覆盖什么；遇到问题时能判断该报给上游还是发行版。
> 对应 Wiki：[Arch Linux](https://wiki.archlinux.org/title/Arch_Linux)、[Kernel](https://wiki.archlinux.org/title/Kernel)、[Getting involved](https://wiki.archlinux.org/title/Getting_involved)、[Arch packaging standards](https://wiki.archlinux.org/title/Arch_packaging_standards)

## 原理：三层结构，一条接口

Linux 系统的稳定结构只有三层：

```text
硬件（CPU、内存、磁盘、网卡）
        ↑ 驱动、中断、DMA
内核（进程调度、内存管理、文件系统、网络栈、安全模块）
        ↑ 系统调用（syscall）：read/write/open/ioctl/…
用户空间（libc、shell、服务、应用）
```

**内核运行在特权态**，能直接操作硬件与特权指令；**用户空间运行在非特权态**，只能通过系统调用请求内核办事。这条边界是 Linux 稳定的根本：内核内部可以随意重构，只要系统调用的语义不变，用户空间的程序就不用改。`/proc` 与 `/sys` 是内核暴露给用户空间的视图（进程信息、设备与调参），不是普通文件系统；`ioctl` 是设备相关的「万能入口」，不同设备语义完全不同。

内核代码有两种存在方式：**builtin**（编译进内核镜像）与**可加载模块**（`.ko`）。发行版的内核配置决定哪个驱动是哪种形态——在本机实测，`modinfo ext4` 的 `filename` 显示 `(builtin)`，说明 ext4 被编进了内核而不是模块。模块必须与**当前内核版本**匹配，升级内核后第三方模块（如 NVIDIA、VirtualBox）需要重新编译，这正是 DKMS 存在的理由。

### 内核 ABI：承诺给用户空间，不承诺给模块

Linux 内核有一条著名原则：**不破坏用户空间**（we do not break userspace）。它保证的是「用户空间程序依赖的系统调用与接口」长期稳定，不保证内核内部函数、结构体布局、模块接口稳定。因此：

| 对象 | 稳定性 | 含义 |
| ------------------ | ------------------------ | ---------------------------------------- |
| 系统调用与用户空间 ABI | 长期稳定 | 旧程序在新内核上仍应能跑 |
| 内核内部 API/ABI | 不保证 | 模块源码要随内核版本适配 |
| 第三方模块二进制 | 不保证 | 换内核就要重编（DKMS 自动化这件事） |
| 发行版包版本 | 取决于发行版 | 滚动发行版会持续升级 |

这也解释了「为什么编译好的驱动换个内核就不能用」，以及「为什么上游说能跑、发行版上却不行」——中间隔着一层内核配置与补丁集。

### 发行版不是内核

严格说，Linux 只是内核。一个「Linux 发行版」= 内核 + 用户空间（libc、shell、工具、服务）+ 包管理器 + 默认配置 + 维护政策。同一份内核源码，不同发行版会给出不同的：

- **内核配置**（哪些驱动 builtin、哪些是模块、开不开某项特性）；
- **补丁集**（上游未合并的修复、硬件支持、发行版特调）；
- **用户空间**（glibc 还是 musl、systemd 还是其他 init、包管理器）；
- **版本策略**（滚动升级还是固定版本 + 安全回补）。

所以「Arch 上能跑、Debian 上不能跑」往往不是内核 bug，而是配置、版本或打包差异。判断问题时，先确认「这是上游行为、发行版补丁，还是本地配置」。

### 生态角色：上游、发行版、用户

| 角色 | 做什么 | 出问题时 |
| ------------ | ------------------------------------------ | -------------------------------------- |
| 上游 | 维护源码、review 补丁、发版本 | 通用 bug、功能缺失、设计问题报上游 |
| 发行版 | 打包、打补丁、签名、集成、安全通告 | 包安装/升级/配置问题报发行版 |
| 用户 | 使用、反馈、贡献补丁/文档/翻译 | 提供可复现信息，先搜 issue 再报 |

上游与发行版之间不是「总部与分部」，而是两条独立的维护链：发行版可以把上游补丁回移（backport），也可以携带自己的补丁。一个 bug 可能只存在于「某发行版的内核配置 + 某个版本组合」里，这时报给上游会被要求先复现于主线。

贡献并不神秘，路径是分层的：报告 bug（版本、复现步骤、日志）→ 参与讨论（邮件列表/issue）→ 提交补丁（`git format-patch` + `git send-email`，内核要求 `Signed-off-by`）→ 接受 review → 合并。文档、翻译、打包、测试同样是贡献，不必从写内核代码开始。

### 许可证：copyleft 与 permissive 的边界

开源许可证不是「免费」的同义词，而是一组**分发与修改的规则**。常见三类：

| 许可证 | 典型项目（本机实测） | 核心义务 | 边界 |
| --------------- | ------------------------------------ | -------------------------------- | ---------------------------------------- |
| GPL-2.0-only | Linux 内核（`pacman -Qi linux`） | 分发衍生作品须提供源码、同样许可 | 内核整体采用 GPL-2.0-only |
| GPL-3.0-or-later | bash | 同上，并含专利与反规避条款 | 衍生作品必须整体 GPL-3 |
| LGPL-2.1-or-later | glibc（同时有 GPL-2.0-or-later） | 允许动态链接而不污染调用方 | 修改库本身仍受 LGPL 约束 |
| MIT / BSD | 大量库与工具 | 保留版权声明与免责声明 | 允许闭源分发，义务很轻 |
| Apache-2.0 | 部分工具与云原生项目 | 保留声明、专利授权、变更说明 | 与 GPL-2 的兼容性需逐案确认 |

三条实务边界：**GPL 约束的是「分发」而不是「使用」**，内部使用不触发源码义务；**「衍生作品」的判定依赖链接方式与法律解释**，动态链接闭源程序到 glibc 通常被认为不构成衍生（LGPL 的设计目的），但静态链接与内核模块是另一回事；**许可证不提供担保**，MIT/BSD 的免责声明意味着出了问题作者不负责。以上是工程常识，不构成法律意见，商业分发应咨询法务。

内核还有一个特殊点：部分符号用 `EXPORT_SYMBOL_GPL` 导出，只有 GPL 兼容模块能使用；闭源模块加载会让内核标记为 `tainted`，这不违法，但会影响上游对 bug 报告的受理。

## 步骤：给一台机器做「生态考古」

下面这组命令不改变系统，只回答「这台机器由谁组装、每个文件归谁、边界在哪」。以下输出均来自本机实测：

```bash
uname -r # 7.2.11-arch1-1：内核版本带发行版后缀
pacman -Qi linux | grep -E '^(Name|Version|Licenses|Packager)'
# Name: linux / Version: 7.2.11.arch1-1 / Licenses: GPL-2.0-only
# Packager: Jan Alexander Steffens (heftig) <heftig@archlinux.org>
pacman -Qo /usr/bin/bash # /usr/bin/bash is owned by bash 5.3.20-1
pacman -Qi bash | grep '^Licenses' # GPL-3.0-or-later
pacman -Qi glibc | grep '^Licenses' # GPL-2.0-or-later  LGPL-2.1-or-later
modinfo ext4 | grep -E '^(filename|license|description)'
# filename: (builtin) / license: GPL / description: Fourth Extended Filesystem
lsmod | head # 当前加载的模块；builtin 的驱动不会出现在这里
ldd /usr/bin/bash # bash 依赖的共享库：libc、libtinfo 等
```

这六条命令分别回答六个问题：内核是哪个版本、内核包由谁打包、某个文件属于哪个包、包的许可证是什么、某个驱动是内置还是模块、用户空间程序依赖哪些库。`pacman -Qo` 是「文件 → 包」的反查，遇到「这个文件是哪来的」时最有用；`ldd` 展示用户空间与库的链接关系，也是判断「动态链接还是静态链接」的入口。

再看一眼系统调用边界（需安装 `strace`）：

```bash
sudo pacman -S strace
strace -c ls /tmp # 统计 ls 这次执行用到的系统调用与耗时
strace -f -e trace=openat,read,write ls /tmp # 只看文件相关调用
```

`strace -c` 的输出是一张「用户空间程序向内核请求了什么」的账单。它直观地展示了本章的核心事实：用户空间程序不直接碰硬件，所有资源操作都要经过系统调用。

## 失败模式

- **把「Linux」当成一个公司/一个系统**：内核由社区维护，发行版各自独立；「Linux 官方」这种说法会误导问题归属。
- **报错报错地方**：上游 bug 报到发行版 issue，会被转回上游；发行版打包问题报到上游，会被要求先找发行版。判断依据是「能否在主线/其他发行版复现」。
- **忽略内核配置**：同一个驱动在某发行版是 builtin，在另一个是模块或根本没编进去；「驱动不存在」可能只是配置差异。
- **把 AUR 当官方仓库**：AUR 是用户提交的构建脚本，不经过官方二进制审核；信任与维护责任在提交者。第 29 章讲过包管理概念，这里只强调「来源等级」。
- **许可证误解**：以为 GPL 项目不能商用（可以商用，义务在分发时触发）；以为 MIT 没有任何义务（必须保留版权与许可声明）。
- **忽略供应链**：不校验签名、不使用可信镜像、不关注安全通告，等于把「包从哪来」交给运气。`pacman-key` 的签名链与官方镜像公告是这条链的一环。
- **只看版本号不看补丁集**：发行版可能 backport 了修复但版本号没变；判断漏洞是否存在要看发行版的安全通告，而不是只看 upstream 版本。
- **把 systemd 当成 Linux 本身**：init/服务管理是可替换组件；Alpine 用 OpenRC、一些嵌入式系统用 busybox init，内核仍是 Linux。

## 验证与回滚

| 操作 | 验证 | 回滚 |
| ------------------- | ------------------------------------------------ | ------------------------------------------ |
| 确认包来源 | `pacman -Qi <包>` 的 Packager/URL；`pacman -Qo <文件>` | 卸载或重装对应包 |
| 确认许可证 | `pacman -Qi` 的 Licenses 字段；上游 LICENSE 文件 | 无需回滚，属于信息核对 |
| 确认驱动形态 | `modinfo <模块>` 的 filename；`lsmod` 是否出现 | 换内核或改配置后重启 |
| 升级内核/驱动 | 记录升级前 `uname -r` 与关键模块；保留旧内核与 initramfs | 引导旧内核；回滚包版本 |
| 判断 bug 归属 | 在主线/其他发行版复现；查 upstream issue 与发行版通告 | 无需回滚，属于定位 |

「记录升级前状态」是生态层面的回滚基础：知道旧内核版本、旧包版本、旧模块列表，才能在升级出问题时退回一个确定可用的组合。第 30 章的启动链与第 29 章的包管理提供了具体手段，本章只强调**先留证据再变更**。

## 取舍边界

- **滚动 vs 固定发行版**：滚动（Arch）拿到最新上游、配置透明，代价是持续维护与偶发回归；固定（Debian stable）稳定、可预测，代价是软件版本旧。选择取决于「你要最新特性还是最少变更」。
- **上游源码 vs 发行版包**：源码给你完全控制与最新代码，代价是自己处理依赖、补丁、升级与安全通告；发行版包把这些打包，代价是版本与配置受制于打包者。生产环境通常优先发行版包，特殊需求才自建。
- **glibc vs musl**：glibc 功能全、兼容性广，体积大；musl 轻量、适合容器与嵌入式，但部分软件兼容性需验证。Alpine 的差异很大一部分来自这个选择。
- **systemd vs 其他 init**：systemd 集成服务、日志、网络、定时器，学习曲线与耦合度高；OpenRC/runit 更小、更贴近传统脚本，但生态工具少。它们都不改变「内核 + 用户空间」这条边界。
- **贡献代码 vs 贡献其他**：写内核补丁门槛高、周期长；报告高质量 bug、补文档、做打包、写测试同样影响生态。选择自己能持续投入的方式，而不是只看「是否算核心贡献」。
- **自建 vs 托管**：自建给你控制权与责任，托管把运维与安全更新外包。边界是「你是否有能力持续维护」，而不是「自建是否更酷」。

## 小结

- 三层结构：硬件 → 内核 → 用户空间；系统调用是唯一稳定接口，`/proc`、`/sys`、`ioctl` 是内核暴露的视图与入口。
- 驱动有 builtin 与模块两种形态；模块与内核版本绑定，第三方模块需随内核重编。
- 内核承诺用户空间 ABI 稳定，不承诺内部 API/模块 ABI；「不破坏用户空间」是这条边界的政策表达。
- 发行版 = 内核 + 用户空间 + 包管理 + 配置 + 政策；发行版差异常来自内核配置、补丁集与版本策略。
- 生态三角：上游维护源码，发行版负责打包集成，用户反馈与贡献；报 bug 前先判断归属。
- 许可证分 copyleft（GPL/LGPL）与 permissive（MIT/BSD/Apache）；义务在分发时触发，具体边界需按项目与法务确认。
- `pacman -Qi`、`pacman -Qo`、`modinfo`、`ldd`、`strace` 是给机器做「生态考古」的五件工具。

## 练习

1. 生态考古（只读）：在本机运行正文的六条命令，记录内核版本、内核包打包者、bash 所属包、bash 与 glibc 的许可证、ext4 是 builtin 还是模块。预期：内核许可证为 `GPL-2.0-only`，bash 为 `GPL-3.0-or-later`。
2. 文件归属（只读）：用 `pacman -Qo` 反查 `/usr/bin/ls`、`/usr/lib/libc.so`、`/etc/pacman.conf` 分别属于哪个包；再解释为什么「知道文件属于哪个包」对排障有价值。
3. 系统调用账单（需在虚拟机中完成）：安装 `strace`，对 `ls` 与 `cat` 各跑一次 `strace -c`，比较两者系统调用分布的差异，指出哪些调用属于文件 I/O、哪些属于内存管理。
4. 许可证对照：列出本机三个包的 Licenses 字段（一个 GPL、一个 LGPL、一个 MIT/BSD），分别写出「闭源分发时要不要提供源码」「能不能静态链接进闭源程序」的初步判断，并标注需法务确认的部分。
5. 归属判断：给出四个问题——(a) 某驱动在 Arch 能用、Debian 不能用；(b) `pacman` 升级时文件冲突；(c) 内核主线已修复但本机仍有漏洞；(d) AUR 包编译失败。分别判断该找上游、发行版还是包提交者，并写出理由。
6. 版本地图：用 `uname -r`、`pacman -Qi linux`、`pacman -Si linux` 收集内核的版本、仓库、打包者与描述，画出一张「上游版本 → 发行版版本 → 本机版本」的对应关系。
