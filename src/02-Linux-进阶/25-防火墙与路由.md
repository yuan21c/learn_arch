# 第 25 章 防火墙与路由

第 24 章给了 nftables 的最小入站规则集，也讲了 `ip route` 的基本读法。这一章补两块最容易出事、也最容易被跳过的东西：**包到底按什么规则选路**，以及**防火墙怎样在转发与 NAT 场景下工作**。前者决定「流量走哪张网卡」，后者决定「内网能不能出去、外面能不能进来」。两者写错的表现很像——「网断了」——但排查入口完全不同。

> 本章目标：理解最长前缀匹配与 metric 的作用范围，会用 `ip route get` 验证选路；理解策略路由（`ip rule` → 独立路由表）的适用场景；能说出 netfilter 五个钩子与 DNAT/SNAT 各自发生在哪一步；会写带集合（set）的 nftables 规则并持久化；掌握「先预检、再限时回滚、最后收紧」的防锁死流程。
> 对应 Wiki：[Network configuration](https://wiki.archlinux.org/title/Network_configuration)、[Nftables](https://wiki.archlinux.org/title/Nftables)、[Router](https://wiki.archlinux.org/title/Router)

## 原理：选路与过滤是两个独立阶段

一个包离开主机或经过主机时，先做**路由决策**（去哪），再做**过滤/NAT**（允不允许、要不要改地址）。两条链路各自有成体系的规则，混在一起排查就会迷路。

### 路由：最长前缀优先，metric 只做同前缀的平局

内核的路由表（FIB）按「前缀长度」匹配：目标地址同时落在 `10.0.0.0/8` 与 `10.1.0.0/16` 时，选 `/16`，因为它的前缀更长、更具体。**metric 不参与不同前缀的比较**——它只在同一前缀的多条候选之间做取舍。这一点解释了为什么「加了一条 metric 更低的默认路由，却没盖住已有的 `/24` 路由」。

```bash
ip route # 主路由表：default、各网段、直连
ip route show table all # 所有表（含 local、策略路由表）
ip route get 203.0.113.10 # 最关键的一条：内核实际会选哪条路
ip route get 1.1.1.1 # 预期输出含 via、dev、src 三个字段
```

`ip route get` 是唯一能直接回答「这个目标走哪」的命令，比人眼比对路由表可靠。它的输出还带 `src`，说明源地址是怎么选的——多网卡机器上「回包源地址不对」的问题，先用它确认。

### 策略路由：按来源、标记选不同的表

默认只有一张主表，规则是「谁离得近走谁」。当需要「来自 A 网段的流量走 B 线路」「带某个防火墙标记的包走 VPN」时，就用策略路由：

```text
包 → 按优先级遍历 ip rule → 命中某条规则 → 查该规则指定的表 → 找到路由
```

`ip rule` 的默认三条（实测）：`0: from all lookup local`、`32766: from all lookup main`、`32767: from all lookup default`。自定义规则通常插在 32766 之前：

```bash
sudo ip rule add from 192.168.50.0/24 table 100
sudo ip route add default via 192.168.50.1 table 100
sudo ip route add 192.168.50.0/24 dev <iface> table 100 # 回程也要有，否则「出得去、回不来」；<iface> 用 ip -br link 查
ip rule list
ip route get 1.1.1.1 # 若源地址在 192.168.50.0/24，预期显示 table 100 的网关
```

策略路由最常见的故障是**只有去程没有回程**：只给表 100 加了默认路由，没加该网段的直连路由，包出去后回不来。验证时必须同时看 `ip route get`（去程）与目标端的回程路由。

### netfilter：五个钩子，两个 NAT 位置

nftables 的链挂在 netfilter 的钩子上，包经过的路径固定：

| 钩子 | 时机 | 典型用途 |
| ------------ | ---------------------- | ---------------------------- |
| prerouting | 刚进主机，路由决策之前 | DNAT、目的地址改写 |
| input | 路由判定「发给本机」 | 本机服务防火墙 |
| forward | 路由判定「路过本机」 | 路由器/网关的转发过滤 |
| output | 本机发出之前 | 本机出站策略 |
| postrouting | 即将离开网卡 | SNAT、masquerade |

两条硬事实：**DNAT 必须在 prerouting**（路由决策前改目的地址，内核才会按新地址转发）；**SNAT/masquerade 必须在 postrouting**（出口网卡确定后才能选源地址）。NAT 只对连接的第一个包做改写，后续包靠 conntrack 还原，所以 `ct state established,related accept` 要放在链的前部，否则回包会被当成新连接处理。

### drop 与 reject：静默还是明确

`drop` 直接丢包，发起方看到的是超时；`reject` 回一个错误（如 `icmp port-unreachable`），发起方立刻知道被拒。对内部服务用 `reject` 更容易排障；对公网暴露的端口用 `drop` 可以减少信息泄露。这是策略选择，不是对错问题。

## 步骤：可回滚的防火墙与转发配置

### 1. 先读基线，再动规则

任何修改前先保存当前规则，出问题时这就是回滚依据：

```bash
mkdir -p /tmp/lab25
sudo nft list ruleset > /tmp/lab25/ruleset.before # 备份当前规则
sudo nft list tables
ip route show table all > /tmp/lab25/routes.before
```

### 2. 带集合的入站规则

把允许的源地址放进命名集合，规则本身保持不变，增删地址只改集合。**端口变量与第 24 章一致**：那里的 `SSH_PORT=2222` 改过端口，这里就必须跟同一个值，只改一处是「重启后 SSH 断连」的常见原因。示例先在当前 shell 定义变量（`nft` 命令里由 shell 展开，写进文件时则直接替换成数字）：

```bash
SSH_PORT=2222 # 与第 24 章一致；仍用默认端口时写 22
sudo nft add table inet filter
sudo nft add set inet filter ssh_allow '{ type ipv4_addr; flags interval; }'
sudo nft add element inet filter ssh_allow '{ 192.0.2.0/24, 203.0.113.7 }'
sudo nft add chain inet filter input '{ type filter hook input priority 0; policy accept; }' # 先 accept，最后再收紧
sudo nft add rule inet filter input ct state established,related accept
sudo nft add rule inet filter input iif lo accept
sudo nft add rule inet filter input tcp dport "$SSH_PORT" ip saddr @ssh_allow accept
```

建链时就用 `policy accept`，是为了让后面的规则逐条加上时不至于立刻断掉现成连接；等规则齐了、在另一个会话验证过，再改成 `drop`（见本节第 4 步）。

`flags interval` 让集合能装 CIDR 段，不加就只能装单个地址。集合的价值在于**规则数量不随地址数量增长**：一千个白名单地址仍是一条规则，匹配是哈希/区间查找，不是线性扫描。

### 3. 转发与 NAT（把主机当路由器）

先开转发，再放行 forward，最后做源地址伪装。示例假定 **`<wan_iface>` 是外网出口、`<lan_iface>` 是内网入口**（示例值 `eth1`/`eth0`）；先用 `ip -br link` 查你的网卡名——现代 Arch 用可预测命名（`enp*`、`wlan*`），照抄 `eth0` 会匹配不到任何接口，规则看似成功却全部失效：

```bash
ip -br link # 先确认网卡名，再替换下面命令里的 <wan_iface> / <lan_iface>
sudo sysctl -w net.ipv4.ip_forward=1 # 临时生效；持久化写 /etc/sysctl.d/99-forward.conf
sudo nft add chain inet filter forward '{ type filter hook forward priority 0; policy drop; }'
sudo nft add rule inet filter forward ct state established,related accept
sudo nft add rule inet filter forward iifname "<lan_iface>" oifname "<wan_iface>" accept
sudo nft add table inet nat
sudo nft add chain inet nat postrouting '{ type nat hook postrouting priority srcnat; policy accept; }'
sudo nft add rule inet nat postrouting oifname "<wan_iface>" masquerade
```

`masquerade` 用出口网卡的当前地址做源地址，适合家宽这类地址会变的场景；固定公网地址可用 `snat ip to <地址>`。只开 `ip_forward` 不放行 forward，包会在 forward 链被默认策略丢掉；只放行 forward 不开 `ip_forward`，内核根本不做转发——两个条件缺一不可。

端口映射（DNAT）写在 prerouting。注意 `inet` 表同时管 IPv4/IPv6，`dnat to` 会有歧义，必须写 `dnat ip to`（本书验证环境实测：不加 `ip` 会报 *specify `dnat ip' or `dnat ip6'*）：

```bash
sudo nft add chain inet nat prerouting '{ type nat hook prerouting priority dstnat; policy accept; }'
sudo nft add rule inet nat prerouting tcp dport 8080 iifname "<wan_iface>" dnat ip to 192.168.50.10:80 # 从外网进来的 8080 转到内网主机
```

### 4. 持久化：文件、预检、原子加载

交互式 `nft add` 的规则重启即消失。持久做法是整份写进 `/etc/nftables.conf`，**开头先 `flush ruleset`** 保证可重复加载：

```text
#!/usr/sbin/nft -f
flush ruleset
define SSH_PORT = 2222

table inet filter {
  set ssh_allow { type ipv4_addr; flags interval; }
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif lo accept
    tcp dport $SSH_PORT ip saddr @ssh_allow accept
    tcp dport $SSH_PORT reject with icmp type port-unreachable
  }
  chain forward {
    type filter hook forward priority 0; policy drop;
    ct state established,related accept
    iifname "<lan_iface>" oifname "<wan_iface>" accept
  }
}
table inet nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "<wan_iface>" masquerade
  }
}
```

**加载前必须把 `<lan_iface>`/`<wan_iface>` 换成 `ip -br link` 查到的真实网卡名**——尖括号占位符不是 nft 语法，`nft -c -f` 会直接报语法错。文件里用的是 nft 自己的符号变量（`define SSH_PORT = 2222`，引用写 `$SSH_PORT`），和 shell 变量是两套机制，但值必须与第 24 章统一。**下面这份是「已收紧」的最终形态（两处 `policy drop`）**，首次加载时先不要直接用它，按下面四步走：

```bash
# ① 首次：把 input 与 forward 两处的 policy drop 先改成 accept
sudo nft -c -f /etc/nftables.conf # 预检：语法、钩子、集合类型
sudo nft -f /etc/nftables.conf # 原子加载：整份文件作为一个事务
# ② 在另一个会话验证 SSH 仍可登录（不要在唯一的远程会话里做收紧）
ssh -p 2222 <user>@<host> 'echo ok'
# ③ 改回 policy drop 之前，先安排限时回滚：180 秒后自动清空规则
sudo systemd-run --on-active=180 --unit=nft-rollback /usr/bin/nft flush ruleset
# ④ 把两处 policy accept 改回 drop，预检并重新加载
sudo nft -c -f /etc/nftables.conf && sudo nft -f /etc/nftables.conf
# ⑤ 确认仍能登录后取消定时器，否则三分钟后规则会被清空
sudo systemctl stop nft-rollback.timer
sudo systemctl enable nftables # 开机自启；Arch 的 nftables.service 读取该文件
```

`nft -f` 是事务性的：文件里任何一条语法错，整份都不会部分生效，这比逐条 `nft add` 安全得多。`policy drop` 生效的瞬间，正在握手的 SSH 连接可能被丢掉，所以「宽松加载 → 另一会话验证 → 限时回滚 → 收紧」这四步不能省。

## 失败模式

- **把自己锁在门外**：`policy drop` 生效的瞬间，正在进行的 SSH 回包可能被丢。必须保留一个已登录会话、控制台或快照；更稳的是先设 `policy accept`，规则齐了再收紧。
- **持久化了一份坏配置**：交互式试错没问题，但把坏规则 `nft list ruleset > /etc/nftables.conf` 并启用服务后，重启会继续锁死。保存前先 `nft -c -f`，并保留上一版文件。
- **只开转发不放行**：`ip_forward=1` 但 forward 链 `policy drop`，现象是「能连上本机、内网出不去」。反过来只放行不转发，包在协议栈里就停了。
- **NAT 只做一半**：只配了 masquerade，没配 forward 放行；或只配 DNAT，没开 `ip_forward`，端口映射看起来「规则在但不通」。
- **策略路由缺回程**：自定义表只有默认路由，没有直连网段，包出得去回不来；`ip route get` 只验证了去程，必须同时看回程。
- **规则顺序错**：`drop` 写在 `accept` 前面，后面的放行永远不生效；`ct state` 放行放在链尾，回包已被前面的规则处理。
- **同时在用 iptables 与 nft**：Arch 的 `iptables-nft` 只是兼容层，底层仍是 nftables；混用两套命令容易产生「`iptables -L` 看到的和 `nft list ruleset` 不一致」的困惑。选定一套，另一套不要手工写。
- **IPv6 邻居发现被丢**：只放行 ICMPv4，忘了 ICMPv6 的 ND 类型，表现为 IPv6 时通时不通（第 24 章的最小集已包含这条）。

## 验证与回滚

| 操作 | 验证 | 回滚 |
| ---------------------- | ------------------------------------------------ | ------------------------------------------ |
| 改路由 | `ip route get <目标>` 看 via/dev/src；再验证回程 | `ip route del` 删掉新增条目 |
| 加策略规则 | `ip rule list` 的顺序；`ip route get` 命中预期表 | `ip rule del` 按优先级删除 |
| 改防火墙 | `nft list ruleset` 与基线 diff；`nft -c -f` 预检 | `nft -f` 重新加载备份文件 |
| 开转发 | `sysctl net.ipv4.ip_forward`；从另一台机器实测 | `sysctl -w net.ipv4.ip_forward=0` |
| 持久化 | 重启后 `nft list ruleset` 与服务状态 | 控制台进入，恢复 `/etc/nftables.conf.bak` |

**限时回滚**是把「锁死」风险降到最低的做法：应用新规则前，先安排一条几分钟后自动清空规则的定时任务；如果新规则把你锁在外面，等它执行即可恢复。

```bash
sudo systemd-run --on-active=180 --unit=nft-rollback /usr/bin/nft flush ruleset
# 180 秒后自动执行；确认新规则没问题后，取消它：
sudo systemctl stop nft-rollback.timer
```

这条命令用 systemd 的定时器，不依赖当前 shell 会话（用 `sh -c 'sleep 180; nft flush ruleset' &` 在退出登录时可能被 SIGHUP 带走）。验证新规则可用后一定要取消定时器，否则三分钟后规则会莫名其妙消失。

## 取舍边界

- **nftables vs iptables**：新系统统一用 nftables；只有在维护旧脚本、旧文档时才用 `iptables-nft` 兼容层。不要为了「命令眼熟」而放弃集合、事务加载这些实际优势。
- **drop vs reject**：对外端口用 `drop` 少泄露信息；对内网与调试用 `reject` 让错误立刻可见。混用时按「公网 drop、内网 reject」划界。
- **主机防火墙 vs 网络防火墙**：主机防火墙随机器走、能按进程/用户做细粒度控制；网络防火墙集中管理、在流量到达主机前就拦住。两者不是替代关系，云环境通常两层都有。
- **NAT vs 纯路由**：NAT 让内网共享一个出口地址，代价是外部无法主动发起连接、排障时看不到真实源地址；纯路由保留端到端地址，但需要可路由的地址段与回程配置。家宽/实验环境用 NAT，机房与 IPv6 环境优先纯路由。
- **策略路由的复杂度**：每多一张表，就多一套「去程/回程/规则优先级」要维护。没有「多线路选路」「按标记分流」的真实需求时，不要引入策略路由。

## 小结

- 路由先于过滤：最长前缀决定走哪，metric 只在同前缀间做平局；`ip route get` 是验证选路的唯一可靠方式。
- 策略路由 = `ip rule` 按优先级选表 + 表内有完整去程与回程；只加默认路由必然「出得去回不来」。
- netfilter 五钩子：DNAT 在 prerouting，SNAT/masquerade 在 postrouting，本机流量走 input/output，路过流量走 forward。
- 转发需要两个条件同时满足：`ip_forward=1` 与 forward 链放行。
- 集合（`flags interval`）让白名单不随地址数量膨胀；`nft -c -f` 预检 + `nft -f` 事务加载是持久化的正确姿势。
- 防锁死三板斧：保留会话、先宽松后收紧、限时自动 `flush ruleset`。
- `inet` 表里做 DNAT 必须写 `dnat ip to`，否则语法检查就会报歧义。

## 练习

1. 选路验证（只读）：运行 `ip route show table all`、`ip rule list`、`ip route get 1.1.1.1`，画出「目标 → 命中哪张表 → 哪条路由 → 哪个源地址」的链条；再给 `203.0.113.0/24` 临时加一条经默认网关的路由，用 `ip route get` 验证后删除（预期：删除后恢复原选路）。
2. 最长前缀（实验网段）：在实验网段内同时加 `10.0.0.0/8` 与 `10.1.0.0/16` 两条路由（指向不同的假网关），用 `ip route get 10.1.2.3` 与 `ip route get 10.2.2.3` 观察命中差异，说明 metric 为什么没有参与决策。
3. 策略路由（至少两张网卡）：为 `192.168.50.0/24` 建表 100，加入默认路由与直连路由，用 `ip rule list` 与 `ip route get` 验证；再故意删掉直连路由，观察「回程缺失」在 `ip route get` 里如何表现。只有一块网卡时，用 `ip route get` 输出解释建表与规则的作用即可。
4. 集合与规则：建一个 `flags interval` 的集合，加入两个 CIDR，写一条引用集合的 SSH 放行规则；用 `nft list ruleset` 确认规则里显示的是 `@集合名` 而不是展开后的地址。
5. 转发与 NAT（两台 VM 或一台双网卡 VM；没有就用 `ip route get` 与 `nft list ruleset` 解释数据流）：按正文开 `ip_forward`、建 forward 链与 masquerade，从内网侧 `ping` 外网并用 `nft list ruleset` 看计数器；再关掉 `ip_forward`，确认现象变化。
6. 限时回滚（**会锁死 SSH**：只在可丢弃环境做，或严格按正文先安排 `systemd-run --on-active=180` 再加载规则）：用 `systemd-run --on-active=180` 安排一次 `nft flush ruleset`，然后加载一份会锁死 SSH 的规则（例如把 `policy` 设为 `drop` 且不放行 22），等待定时器触发，确认会话恢复；记录「规则生效到自动回滚」的时间。
