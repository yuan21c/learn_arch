# 第 54 章 维护与排障总则

前面各章给的是单点知识：怎么装、怎么升级、怎么修某个具体故障。真正维护一台长期运行的机器，还需要一套稳定的方法：什么时候做什么、出事时先看什么、什么算「修好了」、哪些操作会把小问题变成大问题。本章不引入新工具，只把维护节奏与排障顺序固定下来。

> 本章目标：能制定日/周/月/季度的维护清单；按「现象 → 时间线 → 范围 → 假设 → 最小验证」排查问题；按风险从只读到可逆再到破坏性逐级操作；为每次变更准备验证与回滚；知道哪些「修好了」其实只是掩盖症状。
> 对应 Wiki：[System maintenance](https://wiki.archlinux.org/title/System_maintenance)、[General troubleshooting](https://wiki.archlinux.org/title/General_troubleshooting)

## 维护不是「有空再升级」

维护分四个节奏，每个节奏只做该做的事，避免把所有动作堆到一次：

| 节奏 | 动作 | 目的 |
| ------ | ------------------------------------------------------------ | -------------------------- |
| 日常 | 看 `systemctl --failed`、磁盘余量、备份是否按计划完成 | 早发现退化，不等用户报障 |
| 每周 | `pacman -Syu`、读 Arch News、处理新出现的 `.pacnew` | 小步升级，减少单次变更面 |
| 每月 | 检查 journal 体积、缓存版本数、证书/域名到期、`pacman -Qm` | 清理可再生成数据，确认非官方包可重建 |
| 每季度 | 恢复演练、固件/内核策略复核、账号与密钥清理、容量趋势 | 验证备份真的可用，处理长期风险 |

节奏的意义在于「可预期」：升级前知道要备份、要读 News；恢复演练放在没有故障的时候做，才不会在事故中第一次使用备份。

## 排障五步：先取证，再动手

排障最容易犯的错是「看到症状就开始改」。固定顺序能减少变量：

1. **现象**：用一句话写清「谁、在什么操作下、看到什么」。不要写「坏了」。
2. **时间线**：最近改了什么、升级了什么、重启过没有、故障是持续还是间歇。`pacman.log` 与 `journalctl` 是时间线的第一手材料。
3. **范围**：单用户还是全系统、单服务还是全网络、单文件还是整个分区。范围决定 blast radius。
4. **假设**：列出最可能的两个原因，并写出「如果假设成立，哪条只读命令能看到证据」。
5. **最小验证**：先跑只读命令，再考虑可逆操作；一次只改一个变量，改完立即验证。

若第 5 步失败，回到第 4 步换假设，而不是叠加更多改动。多个变更叠在一起时，无法判断哪个生效、哪个引入新问题。

## 风险阶梯：只读 → 可逆 → 破坏

| 级别 | 例子 | 使用条件 |
| ---------- | ---------------------------------------------------------- | ------------------------------ |
| 只读 | `systemctl status`、`journalctl`、`pacman -Qi`、`df`、`ss` | 任何时候先做 |
| 可逆 | 改 `/etc` 前备份、临时 unit、`systemctl disable`、降级单包 | 已定位到具体对象，且有回滚步骤 |
| 破坏性 | 分区、格式化、`enroll-keys`、删缓存、`--overwrite`、重装 | 有快照/备份，且确认无更低风险路径 |

「可逆」不是口头判断：改配置前 `cp` 备份、卸载前记录包清单、降级前确认缓存里有旧版本，才叫可逆。没有回滚步骤的「小改动」也属于破坏性。

## 变更管理：一次只动一件事

任何有风险的变更都按同一模板执行：

```text
目标 → 现状取证 → 备份/快照 → 变更 → 验证 → 记录（含回滚命令）
```

- **目标**要可验证，例如「让 sshd 监听 2222」，而不是「优化 SSH」。
- **现状取证**先保存输出：`systemctl cat`、`ss -tlnp`、配置文件副本。
- **备份/快照**是回滚的前提；没有它就不要开始。
- **验证**要覆盖「预期行为」与「没有破坏其他功能」两面。
- **记录**写清改了什么、为什么、怎么回滚；下次排障时这就是时间线。

## 记录与交接

排障记录不是写给自己看的日记，而是让下一个人（或三个月后的你）能复现判断。最小记录包含五项：

```text
时间：
现象（一句话）：
最近变更：
已执行命令与关键输出：
结论与下一步：
```

三条纪律：

- **命令原文保留**：不要只写「检查了磁盘」，要写 `df -i` 的输出；参数、路径、版本都可能影响结论。
- **区分事实与推测**：输出是事实，「可能是驱动问题」是假设；假设要标注，不能混进结论。
- **写清回滚点**：改了哪个文件、备份在哪、怎么恢复；没有回滚点的变更不算完成。

交接时把「未完成事项」与「已知风险」单独列出：例如「第 39 章 `.pacnew` 待合并」「备份保留两代，容量接近上限」。口头交接容易漏，文字记录能让下一位维护者直接接手。

一条合格记录的示例：

```text
时间：2026-11-04 10:20
现象：sshd 无法启动，登录超时
最近变更：昨晚升级 openssh
已执行：systemctl status sshd（exit 1）；journalctl -xeu sshd（Host key 权限 0644）
结论：升级后主机密钥权限被改；下一步按记录修正为 0600 并重启验证
回滚点：/etc/ssh 已备份到 /etc/ssh.bak-20261104
```

## 失败模式

- **一次改多个变量**：升级、改配置、换驱动同时做，出问题无法归因；一次只动一件事。
- **没有时间线就猜根因**：不看 `pacman.log`/`journalctl`，把「上次重启后坏了」当成「硬件坏了」。
- **从破坏性操作开始**：先删缓存、先 `--overwrite`、先重装，现场被毁，根因再也查不到。
- **把「服务起来了」当修好**：没有验证依赖功能、日志与重启后行为；问题在下次启动时回来。
- **维护全靠记忆**：备份、清理、证书续期没有清单，漏一次就可能在最坏时间暴露。
- **恢复演练留到事故时**：第一次用备份就发现缺文件、缺密钥、权限不对。
- **只看单机不看趋势**：磁盘、inode、日志体积持续增长，直到某次升级写满分区。

## 验证与回滚

维护与排障的验证可以固化成一组只读基线，定期保存并对比：

```bash
systemctl --failed --no-pager
df -h / && df -i /
du -sh /var/cache/pacman/pkg /var/log/journal
pacman -Qm
journalctl -p err -b --no-pager | tail -n 10
ss -s
```

实验：为「服务失败」做一次可逆演练——用 `systemd-run --unit=demo54 --on-active=5s /bin/false` 创建一个注定失败的一次性单元，等它结束后用 `systemctl status demo54` 与 `journalctl -u demo54` 取证，再 `systemctl reset-failed demo54` 清理。全程不改系统服务，可复现。回滚按层级：配置用 `.bak`，单包用缓存/ALA，整机用快照/备份；破坏性修复前先保存现场日志。

## 取舍边界

- **预防性维护 vs 故障后修复**：定期升级与演练占时间，但把事故成本前移；完全不做维护省事，直到一次故障代价更大。
- **最小修复 vs 彻底重装**：能定位到单点就最小修复，保留现场；大面积损坏或根因不可查才重装。
- **自动化 vs 手工**：重复且可验证的动作适合自动化；涉及判断与不可逆操作的步骤保留人工确认。
- **快速恢复 vs 找到根因**：生产环境先恢复服务、后查根因；但必须保留现场，否则同类问题会重复。
- **严格变更窗口 vs 随时小步**：小步变更风险低但需要纪律；大窗口变更影响面大，必须配完整回滚。

## 小结

- 维护按日/周/月/季度分层，升级、清理、演练各归其位。
- 排障固定五步：现象、时间线、范围、假设、最小验证；失败就换假设，不叠加改动。
- 操作按风险分级：只读优先，可逆其次，破坏性最后且有快照/备份。
- 每次变更都写「目标、取证、备份、变更、验证、记录」，一次只动一件事。
- 「服务起来了」不等于修好；要验证功能、日志与重启后的行为。
- 备份与恢复演练要在平时完成，事故中才用第一次是高风险。

## 练习

1. 为自己的机器写一份日/周/月/季度维护清单，每项配一条只读验证命令。
2. 用 `journalctl --list-boots` 与 `tail /var/log/pacman.log` 还原最近一次变更的时间线（只读）。
3. 完成本章的 `systemd-run` 失败单元演练，记录 `status` 与 `journalctl` 的首条错误，最后清理该单元。
4. 选一个你改过的配置，写出「备份、验证、回滚」三条具体命令；检查回滚命令是否真的可执行。
5. 把一次历史故障按五步重写：当时看到什么、改了什么、哪一步本应先做只读检查。
6. 对比「最小修复」与「重装」的触发条件，写出三条必须重装的判据。
