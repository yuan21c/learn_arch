# 第 43 章 缓存、降级与密钥环

升级通常向前走，但维护系统时需要两条退路：缓存里保留的旧版本，以及能重新建立信任的密钥环。缓存策略决定你能不能快速回滚单个包；密钥环决定 pacman 是否愿意安装任何包。两者都不该等到出事才临时研究。

> 本章目标：制定缓存清理策略，能用缓存或 Arch Linux Archive 降级单个包，并独立走完一次签名错误的排查流程。
> 对应 Wiki：[Pacman#Cleaning the package cache](https://wiki.archlinux.org/title/Pacman#Cleaning_the_package_cache)、[Downgrading packages](https://wiki.archlinux.org/title/Downgrading_packages)、[Pacman/Package signing](https://wiki.archlinux.org/title/Pacman/Package_signing)

> 本章的缓存删除、降级与密钥环重建**未实测**；可复现练习先用 `paccache -d`、`pacman -Qi`、`pacman-key --list-keys` 等只读命令，删除与重建只在快照中做。

## 缓存策略

pacman 下载的包默认留在 `/var/cache/pacman/pkg/`，不会自动删除。缓存既是离线重装的来源，也是降级时的第一选择，因此不能一删了之。

```bash
du -sh /var/cache/pacman/pkg
# 3.8G /var/cache/pacman/pkg

sudo paccache -d # 只列出将被删除的版本，不实际删除
sudo paccache -r # 每个包保留最近 3 个版本
sudo paccache -rk1 # 每个包只保留最近 1 个版本
sudo paccache -ruk0 # 删除所有已卸载包的缓存
```

`-r` 适合日常，`-rk1` 更激进，只在磁盘紧张时使用；`-d` 永远先跑一遍，确认删除列表。`paccache` 来自 `pacman-contrib`，未安装时先 `sudo pacman -S pacman-contrib`。

`pacman -Sc` 与 `paccache` 的删除范围不同，别混用：

| 命令 | 删除范围 | 典型用途 |
| -------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------- |
| `pacman -Sc` | 只删「已不在本地数据库（已卸载）」的包缓存，并清理不再使用的同步数据库；默认 `CleanMethod = KeepInstalled` 会保留已安装包的全部缓存（含旧版本） | 回收已卸载包的磁盘 |
| `pacman -Scc` | 清空整个缓存（含已安装包的全部版本） | 确定不需要离线回滚时 |
| `paccache -r` | 已安装包保留最近 3 个版本；`-ruk0` 删除已卸载包 | 日常控制缓存体积 |

> **危险**：`pacman -Scc` 会清空整个缓存，执行后无法离线重装或降级任何包，只能去 Arch Linux Archive 重新下载；先确认没有离线回滚需求。`pacman -Sc` 默认只清已卸载包，但仍会删除旧同步数据库，下次 `-Syu` 需要重新下载。

磁盘告警时按顺序处理：先 `sudo paccache -d` 预览，再 `sudo paccache -rk1`；只有确认不需要历史版本时才考虑 `pacman -Scc`。

## 从缓存降级

```bash
ls /var/cache/pacman/pkg/ | grep '^firefox-'
# firefox-142.0-1-x86_64.pkg.tar.zst
# firefox-143.0-1-x86_64.pkg.tar.zst

sudo pacman -U /var/cache/pacman/pkg/firefox-142.0-1-x86_64.pkg.tar.zst
# loading packages...
# resolving dependencies...
# looking for conflicting packages...
# :: Proceed with installation? [Y/n]
```

`pacman -U` 安装本地包并更新本地数据库，但仍会检查依赖。若旧版本要求旧依赖，pacman 会报依赖不满足；此时需要一并降级相关依赖，而不是用 `-d` 强行绕过。

降级后立即检查：

```bash
pacman -Qi firefox | grep -E 'Version|Depends On|Required By'
sudo pacman -Syu
# 观察输出中是否又要把 firefox 升回去
```

单包降级只是临时措施。只要仓库里的新版本存在，下次 `-Syu` 就会把它升回去；如果新版本确实有问题，应关注上游与 Arch News，而不是长期冻结。

### Arch Linux Archive

缓存里没有旧版本时，用 ALA 下载。**包文件与它的 `.sig` 要一起下载到同一目录**：

```bash
curl -O https://archive.archlinux.org/packages/f/firefox/firefox-142.0-1-x86_64.pkg.tar.zst
curl -O https://archive.archlinux.org/packages/f/firefox/firefox-142.0-1-x86_64.pkg.tar.zst.sig
sudo pacman-key -v firefox-142.0-1-x86_64.pkg.tar.zst.sig # 或 gpg --verify；预期显示 Good signature
sudo pacman -U firefox-142.0-1-x86_64.pkg.tar.zst
```

路径规则是 `包名首字母/包名/文件名`。ALA 同时提供按日期的仓库快照，网址见 [Arch Linux Archive](https://wiki.archlinux.org/title/Arch_Linux_Archive)。

**为什么必须单独验签**：Arch 默认 `LocalFileSigLevel = Optional`（`pacman.conf` 里常被注释为示例），本地包**缺少 `.sig` 时 `pacman -U` 只给 warning，不失败**；把「安装成功」当成「签名通过」是常见误判。想强制检查，可临时用 `pacman -U --siglevel Required 包文件`，缺签名会直接失败。任何情况下都不要用 `SigLevel = Never` 之类的方式跳过错误。

## 为什么不要长期 IgnorePkg

```ini
[options]
IgnorePkg = firefox
```

`IgnorePkg` 让 pacman 在 `-Syu` 时跳过指定包。短期看它阻止了「坏版本」进入系统，长期看它制造了一个持续的部分升级状态：其余包继续升级，被忽略的包仍链接旧库、依赖旧 ABI，直到某天启动失败或依赖冲突。

如果只是等上游修复，记录待办并在修复后删除该行；如果确实需要旧版本，优先用 ALA 加明确的降级流程，并接受「每次升级都要重新处理」的成本。以 Wiki 的 [System maintenance](https://wiki.archlinux.org/title/System_maintenance) 为准。

## 密钥环

Arch 包带 PGP 签名，pacman 用 `/etc/pacman.d/gnupg` 下的**本地信任库**验证。日常维护只需要先更新 **`archlinux-keyring` 包**（它的 install 脚本会自动 populate 密钥）；只有本地密钥环损坏、需要重建时，才删掉 `/etc/pacman.d/gnupg` 后重新初始化并 populate。

```bash
sudo pacman -S --needed archlinux-keyring # 日常：更新包，install 脚本自动 populate
sudo pacman-key --list-keys | head -n 5

# 仅在密钥环损坏、需要重建时（危险，先读下文提示）：
sudo mv /etc/pacman.d/gnupg /etc/pacman.d/gnupg.bak # 先改名备份，不要直接删
sudo pacman-key --init
sudo pacman-key --populate archlinux
```

`--init` 创建本地 GPG 目录，`--populate archlinux` 导入 Arch 官方密钥，`archlinux-keyring` 包则持续更新这些密钥。正常升级会自动带上它，不需要每次手动执行。重建会丢失本地信任；若本机有自建签名密钥，删除后无法恢复，因此用 `mv` 备份而不是 `rm -rf`，确认新密钥环工作正常后再删备份。

密钥过期或缺失时刷新：

```bash
sudo pacman-key --refresh-keys
```

该命令从密钥服务器拉取更新，可能耗时数分钟；网络受限时先确认 keyserver 可达。需要更换 keyserver 时编辑 `/etc/pacman.d/gnupg/gpg.conf`，具体字段以 Wiki 为准。

系统时间也会影响验签。时间严重偏差时，密钥可能显示「尚未生效」或签名无效：

```bash
timedatectl
# System clock synchronized: yes
sudo timedatectl set-ntp true
```

虚拟机从挂起或快照恢复后也容易出现时钟漂移：虚拟 RTC 只在启动时同步一次，长时间挂起后系统时间会落后。遇到偏差时先看 `timedatectl` 的 `System clock synchronized`，再执行 `sudo timedatectl set-ntp true` 让它重新对时；仍不准时检查虚拟机管理器是否向客户机同步物理机时间。真机上则多由 RTC 电池或 NTP 配置引起，可用 `sudo hwclock --systohc` 把系统时间写回硬件时钟。

## 签名错误的标准处理

典型报错：

```text
error: firefox: signature from "..." is invalid
:: File /var/cache/pacman/pkg/firefox-143.0-1-x86_64.pkg.tar.zst is corrupted
 (invalid or corrupted package (PGP signature)).
```

按顺序处理，不要一上来就删密钥环：

1. `timedatectl` 确认时间同步。
2. 按第 38/39 章的 keyring 引导流程：`sudo pacman -Sy --needed archlinux-keyring && sudo pacman -Su`（适用于密钥环过旧、常规 `-Syu` 因 unknown trust 中止）；若 keyring 包本身验签失败，先从缓存或 ALA 用 `pacman -U` 安装新版 `archlinux-keyring`。
3. `sudo pacman-key --refresh-keys`，再重试 `sudo pacman -Syu`。
4. 若只有某个包报错，删除该包缓存后重下：`sudo rm /var/cache/pacman/pkg/包名-*.pkg.tar.zst`，再升级。
5. 仍失败时换镜像源（`reflector` 或手改 mirrorlist），排除镜像同步损坏。
6. 验证密钥环：`sudo pacman-key --list-keys` 能看到 Arch 主密钥，并让一次 `sudo pacman -Syu` 成功。`pacman -Qkk archlinux-keyring` 只核对包内文件（`/usr/share/pacman/keyrings/...`），不覆盖 `/etc/pacman.d/gnupg`，不能当作密钥环健康证明。

> **危险**：不要用 `SigLevel = Never` 或任何跳过校验的选项绕过验签。那等于关闭整个包体系的信任链。重建 `/etc/pacman.d/gnupg` 也会丢失本地信任，只在没有自定义密钥时考虑。

## 失败模式

- **直接 `pacman -Scc`**：清空整个缓存后无法离线重装或降级，只能重新下载；先确认没有回滚需求。
- **`paccache -rk1` 当日常策略**：每个包只留一个版本，出问题当天就没有旧版可退；空间不紧张时保留 3 个更稳。
- **长期 `IgnorePkg` 代替降级**：冻结一个包等于持续部分升级，依赖它的包会先坏；临时降级也要记录恢复计划。
- **用 `SigLevel = Never` 绕过验签**：等于关闭整条信任链；签名错误应查时间、密钥环与镜像，而不是关校验。
- **直接 `rm -rf /etc/pacman.d/gnupg`**：会丢失本地信任与自建密钥；若必须重建，先 `mv` 成备份。
- **忽略系统时间**：时间偏差会让密钥「尚未生效」或签名无效，表现为莫名其妙的验签失败。
- **只降级主包不降依赖**：旧版主包要求旧 ABI 的库，pacman 报依赖不满足；此时要一并处理相关依赖，而不是 `-d` 强装。

## 验证与回滚

```bash
du -sh /var/cache/pacman/pkg # 缓存体积
sudo paccache -d # 只预览将被删除的版本，不删除
pacman -Qi 包名 | grep -E 'Version|Depends On'
sudo pacman-key --list-keys | head -n 5 # 能看到 Arch 主密钥
timedatectl # System clock synchronized: yes
```

`paccache -d` 是最安全的验证：它列出删除清单但不落盘。降级前用 `pacman -Qi` 记录当前版本与依赖，降级后用同一条命令对照；回滚就是重新 `pacman -U` 新版本或 `pacman -Syu`。密钥环的验证是 `--list-keys` 能看到主密钥且一次升级成功；若改动过 `/etc/pacman.d/gnupg`，把它 `mv` 回原名的备份即可恢复旧信任库（**未实测**，操作前停 pacman）。

## 取舍边界

- **保留 1 个 vs 3 个版本**：磁盘充足保留 3 个，给回滚留窗口；磁盘紧张才降到 1 个，并接受「坏版本当天无退路」。
- **`paccache` vs `pacman -Sc`**：前者按版本数精细控制；后者只清已卸载包。两者目标不同，不要用 `-Scc` 图省事。
- **缓存降级 vs ALA**：缓存快但只覆盖下载过的版本；ALA 全但依赖网络与归档可用性。
- **更新密钥环 vs 重建密钥环**：先更新 `archlinux-keyring` 包；只有本地信任库损坏才重建，重建会丢自定义信任。
- **刷新密钥 vs 换镜像**：`--refresh-keys` 解决密钥过期；多个包同时验签失败更像镜像同步损坏，先换源。

## 小结

- 缓存是降级与离线重装的第一来源，清理前先用 `paccache -d` 预览。
- `paccache -r` 保留 3 个版本，`-rk1` 只留 1 个；`pacman -Sc` 默认只清已卸载包的缓存，`pacman -Scc` 清空全部缓存（先确认无离线回滚需求）。
- 降级用 `pacman -U` 安装缓存或 ALA 中的旧包，并检查依赖是否匹配。
- `IgnorePkg` 长期冻结等于持续部分升级，只适合短期等待修复。
- 密钥环由 `archlinux-keyring` 维护，签名错误先查时间、再更新密钥环、最后换镜像。
- 永远不要关闭签名校验来「解决」问题。

## 练习

1. 用 `du -sh` 记录缓存大小，执行 `paccache -d` 并解释删除列表。
2. 安装一个包，从缓存降级到上一版本，再 `pacman -Syu` 升回，记录每一步输出（前提：缓存里要有旧版本——没有就先用旧版换新版制造一个，或从 ALA 下载）。
3. 用 `pacman -Qi` 检查降级包的依赖，判断是否还需要降级其他包。
4. 运行 `sudo pacman-key --list-keys`，找出 `archlinux` 主密钥的创建日期（预期：输出含 pub 条目；不加 sudo 会 Permission denied）。
5. 改时间观察签名失效（**危险**，时间错乱会波及 TLS 与日志；只在可丢弃环境+快照里做）：前置——虚拟机快照 + 备份 `/etc/pacman.d/gnupg`；把系统时间调错后 `pacman -Syu` 观察签名错误，恢复时间后重试验证修复。
