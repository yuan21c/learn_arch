# 第 56 章 文件恢复与恢复后处理

误删文件后，最关键的几分钟决定能否恢复：继续写入、重新挂载、在源盘上安装恢复工具，都会让被删数据被覆盖。恢复不是「运行一个工具」，而是一套顺序：先停止写入、再对介质做镜像、在镜像上尝试恢复、最后验证并清理。恢复出来的文件也不能直接用——权限、属主、完整性和依赖都要重新核对。

> 本章目标：理解删除在 ext4 与 btrfs 上的不同后果；按「停写 → 镜像 → 恢复 → 验证」顺序处理；知道 `ddrescue`、`testdisk`/`photorec`、`debugfs`、btrfs 恢复工具的适用边界；能在恢复后核对权限、校验和、包依赖与服务状态。
> 对应 Wiki：[File recovery](https://wiki.archlinux.org/title/File_recovery)、[Disk caching](https://wiki.archlinux.org/title/Disk_caching)、[Btrfs#Recovery](https://wiki.archlinux.org/title/Btrfs#Recovery)

## 删除之后发生了什么

- **ext4**：删除文件会把 inode 标记为空闲、数据块归还分配器；数据本身不会立刻清零，但后续写入会复用这些块。时间越久、写入越多，可恢复率越低。
- **btrfs**：写时复制，旧数据块可能仍被快照引用；若没有快照，删除后同样可能被新数据覆盖。`btrfs restore` 从文件系统层面扫描，不等同于「撤销删除」。
- **SSD/TRIM**：删除后控制器可能很快回收块，恢复窗口比机械盘更短；TRIM 开启时不要对恢复抱太高期望。
- **日志型文件系统**：日志保证元数据一致性，不保证文件内容可恢复；`fsck` 修复的是结构，不是数据。

因此第一条纪律是：**发现误删后立即停止对源介质的写入**。能卸载就卸载，不能卸载就把系统切到只读或停机，从另一台机器操作。

## 恢复顺序：镜像优先

不要直接在源盘上跑恢复工具。正确顺序：

1. **停写**：卸载分区，或让机器停机；不要在源盘上安装工具、下载文件。
2. **镜像**：用 `ddrescue` 对介质做逐块镜像，失败区域记录在 map 文件里。
3. **在镜像上恢复**：所有扫描、 carving、修复都针对镜像文件，源盘保持只读。
4. **恢复到另一块盘**：恢复出的文件写到第三块盘，绝不写回镜像或源盘。
5. **验证**：校验和、文件类型、权限、属主、依赖、服务逐项检查。

```bash
# 镜像落点确认（必须在执行 ddrescue 前完成）
lsblk -f                              # 选定一块剩余空间大于源分区的独立磁盘
sudo mount /dev/disk/by-uuid/<UUID> /mnt/backup   # 或用 udisksctl mount -b /dev/sdX1
findmnt /mnt/backup                   # 确认已挂载且非 tmpfs
df -h /mnt/backup                     # 确认剩余空间 > 源分区大小（镜像 ≈ 源分区大小）

sudo ddrescue -d -r3 /dev/vda2 <backup-mount>/vda2.img <backup-mount>/vda2.map
```

`<backup-mount>` 表示已挂载到非 tmpfs 目录的备份目录，如 `/mnt/backup`；镜像文件大小约等于源分区大小，目标必须是剩余空间大于源分区的**独立磁盘**，不要写入 tmpfs（`/run`、`/dev/shm`）或同一块源盘。

`-d` 直接访问设备，`-r3` 对坏区重试三轮；`map` 文件记录哪些块成功、哪些失败。镜像完成后先 `sha256sum` 记录，再复制一份工作副本——所有恢复实验只动副本。

## 工具与适用边界

| 工具 | 适用对象 | 能做什么 | 不能做什么 |
| ---------------- | ------------------------ | -------------------------------- | ------------------------------ |
| `debugfs` | ext2/3/4 | 查看 inode、`lsdel` 列出已删 inode | 不保证内容完整，不自动重建文件名 |
| `extundelete` | ext3/ext4 | 按 inode 或路径恢复 | 对已覆盖块无能为力；新版 ext4 支持有限 |
| `testdisk` | 分区表、引导扇区 | 重建分区表、找回丢失分区 | 不恢复分区内所有文件内容 |
| `photorec` | 多种文件系统 | 按文件签名 carving，忽略目录结构 | 文件名、路径、时间戳大概率丢失 |
| `btrfs restore` | btrfs | 从损坏/误操作的文件系统复制文件 | 需要可挂载或可读取的文件系统 |
| `ddrescue` | 任何块设备 | 对故障介质做镜像 | 不解析文件系统 |

选择顺序：文件系统结构还在，先用 `debugfs`/`extundelete` 按 inode 恢复；结构损坏或分区丢失，用 `testdisk`；只想要内容、不介意文件名，用 `photorec`；btrfs 用 `btrfs restore`；介质本身有坏道，先 `ddrescue` 再做前面任何一步。

> 本章的 `ddrescue`、`extundelete`、`testdisk`、`photorec`、`btrfs restore` 与任何写入恢复均**未实测**；可复现练习只做「镜像 + 校验和 + 只读检查」，不执行真实恢复。

## 恢复后的处理

恢复出的文件默认不可信，按四层核对：

```bash
file 恢复文件 # 真实类型，不信扩展名
sha256sum 恢复文件 # 与备份/原文件比对（若留有校验和）
stat 恢复文件 # 权限、属主、时间戳
diff -r 恢复目录 备份目录 # 目录级对照（若有备份）
```

1. **完整性**：`file` 识别真实类型，`sha256sum` 对照旧校验和；carving 出的文件常被截断。
2. **权限与属主**：恢复工具常以当前用户写文件，`root` 拥有的配置会变成普通用户；用 `chown`/`chmod` 按原记录修正。
3. **依赖与包**：恢复的是数据文件时，确认对应软件已安装且版本匹配；恢复的是程序时，优先重装包而不是直接放回 `/usr`。
4. **服务状态**：数据库文件恢复后要做一致性检查（`PRAGMA integrity_check`、`pg_dump` 验证），再启动服务。

恢复完成后，把镜像与 map 文件保留一段时间，确认无遗漏再清理；同时复查磁盘健康，误删可能只是坏盘的前兆。

建议保留一张恢复记录：

| 字段 | 记录内容 |
| ---------- | ------------------------------ |
| 源介质 | 设备名、容量、SMART 结论 |
| 镜像 | 路径、`sha256sum`、map 文件位置 |
| 工具与步骤 | 使用的工具、关键参数、失败区域 |
| 恢复结果 | 文件数、校验和对照、缺失清单 |
| 处置 | 源盘是否只读、镜像保留到何时、是否转专业机构 |

## 分区、RAID 与加密层的恢复

文件恢复之前要先恢复「容器」；容器不对，文件系统工具看到的是空白或乱码：

- **分区表丢失**：`testdisk` 扫描旧分区表并写回；写回前先备份当前扇区，确认分区边界后再保存。
- **RAID 掉盘**：`mdadm --examine` 查看成员盘的角色与事件计数，`--assemble` 重新组装；不要对成员盘单独 `mkfs`。
- **LUKS 头损坏**：若有头备份，用 `cryptsetup luksHeaderRestore` 恢复；没有备份时恢复难度极高，优先找专业机构。
- **LVM 元数据损坏**：`vgcfgrestore` 从 `/etc/lvm/backup` 恢复卷组配置；先确认备份与当前 PV 一致。
- **btrfs 多设备**：缺设备时先只读挂载（`-o degraded,ro`）抢救数据，再考虑替换设备与重新平衡。

这些操作都会写元数据，属于破坏性修复，本章**未实测**；顺序永远是「先镜像、再在副本上尝试、最后才动源盘」。

## 失败模式

- **继续在源盘上操作**：下载工具、解压、安装都在覆盖被删块；应先停写并从另一台机器操作。
- **直接在源盘上跑恢复工具**：工具可能写入临时文件或修复元数据；一律先镜像。
- **恢复到源盘或镜像**：把恢复结果写回正在恢复的介质，覆盖尚未扫描的区域。
- **对 SSD 期待机械盘的恢复率**：TRIM 已回收的块无法恢复；越早停写越好。
- **用错文件系统工具**：对 btrfs 跑 ext4 工具，或对 LUKS 内层直接扫描；先确认层与文件系统。
- **只恢复内容不看元数据**：文件名、路径、权限、属主丢失，直接放回系统会造成权限与依赖问题。
- **把 carving 结果当完整文件**：`photorec` 按签名截取，长文件可能只恢复前段；必须逐个验证。
- **恢复后不查磁盘健康**：坏道导致的读错误被当成「误删」，下一次故障会更大。

## 验证与回滚

恢复流程的验证重点是「镜像可靠、结果可核对、源盘未被污染」：

```bash
sha256sum /run/media/backup/vda2.img
cmp /run/media/backup/vda2.img /run/media/backup/vda2-work.img
sudo fsck -n /dev/vda2 # 只读检查，不修复
sudo smartctl -a /dev/vda # 若设备支持 SMART
```

`cmp` 确认工作副本与镜像一致；`fsck -n` 只报告不写入；SMART 判断是「误删」还是「介质故障」。回滚：恢复失败时源盘仍保持只读，可换工具在镜像副本上重试；已恢复到工作盘的错误结果删除即可，不影响源盘。实验可在 `/tmp` 建一个小镜像，用 `cp` 做副本、`sha256sum`/`cmp` 验证流程，不执行真实删除与恢复。

## 取舍边界

- **自己恢复 vs 专业数据恢复**：介质有异响、SMART 大量重映射、RAID 掉盘时，继续通电可能扩大损坏；这类情况应交专业机构。
- **inode 恢复 vs carving**：结构完好时按 inode 恢复保留文件名与路径；结构损坏才用 carving，接受元数据丢失。
- **镜像整盘 vs 只镜像分区**：整盘保留分区表与引导，适合分区丢失；只镜像分区更快，适合单分区文件恢复。
- **恢复到原盘 vs 另一块盘**：永远选另一块盘；原盘只读是恢复的前提。
- **保留镜像 vs 立即清理**：镜像占空间但可重复尝试；至少保留到数据核对完成，敏感数据还要考虑加密与销毁。

## 小结

- 误删后第一动作是停写，第二动作是对介质做镜像，恢复只在镜像副本上做。
- ext4 删除后数据块可被复用，btrfs 依赖快照与写时复制，SSD/TRIM 会显著缩短恢复窗口。
- 工具按场景选择：`debugfs`/`extundelete`、`testdisk`、`photorec`、`btrfs restore`、`ddrescue`。
- 恢复结果要核对类型、校验和、权限属主、依赖与服务，不能直接放回系统。
- 介质异常时优先保护现场，必要时交给专业恢复。
- 本章的真实恢复步骤未实测；镜像、校验和与只读检查是安全等价路径。
