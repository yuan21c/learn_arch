# 第 53 章 常见故障处理

Arch 的故障大多不是随机出现的，而是某次操作留下的状态：部分升级、错误配置、写满的磁盘、中断的事务。本章用「症状 / 诊断 / 修复 / 预防」四段式处理常见问题，原则是先取证，再动手。

> 本章目标：能根据报错定位常见故障的根因，选择风险最低的修复路径，并识别会扩大故障的命令。
> 对应 Wiki：[System maintenance](https://wiki.archlinux.org/title/System_maintenance)、[Pacman#Troubleshooting](https://wiki.archlinux.org/title/Pacman#Troubleshooting)

## 部分升级

**症状**：程序报 `error while loading shared libraries: libfoo.so.X`，pacman 报依赖无法满足；常发生在执行过 `pacman -Sy 包名`、长期使用 `IgnorePkg` 或手动装过旧包之后。

**诊断**：

```bash
tail -n 30 /var/log/pacman.log
ldd /usr/bin/程序名 | grep 'not found'
sudo pacman -Fy && pacman -F /usr/lib/libfoo.so.X
```

**修复**：先执行 `sudo pacman -Syu` 完成全系统升级。若库仍缺失，用 `pacman -F` 找到提供者并重装该包；若冲突来自第三方包，先移除冲突源再升级。

> **危险**：不要用 `--overwrite` 掩盖文件冲突，它只跳过文件冲突检查，不会修复依赖关系，损坏状态会继续累积。文件冲突的正确四步：`pacman -Qo <路径>` 查归属 → 确认哪个包该拥有它 → 修复/移除冲突源 → 必要时才用 `--overwrite <精确路径>`。本地数据库自检用 `pacman -Dk`（查依赖完整性）与 `pacman -Qk`（查文件完整性）。

**预防**：升级只用 `-Syu`；不长期压包；安装第三方包前确认依赖能在官方仓库满足。

## 密钥环与签名错误

**症状**：`invalid or corrupted package (PGP signature)`、`signature from ... is unknown trust`、`key ... could not be looked up`。

**诊断**：`timedatectl`、`pacman -Q archlinux-keyring`。

**修复**：先校正时间，再按 Wiki 的例外顺序更新密钥环：`sudo timedatectl set-ntp true`、`sudo pacman -Sy --needed archlinux-keyring && sudo pacman -Su`，最后 `sudo pacman-key --refresh-keys`。缓存中的损坏包也要删除后重下。先区分两件事：`pacman-key --init` 只在密钥环**不存在**时创建 `/etc/pacman.d/gnupg`，不会清空已有的信任库。确认本地密钥环损坏、需要**重建**时，才先 `sudo mv /etc/pacman.d/gnupg{,.bak}` 备份（保留自建密钥），再执行 `sudo pacman-key --init && sudo pacman-key --populate archlinux`。

**预防**：保持 keyring 随系统更新；时间错误的机器不要升级；长期未更新的镜像先完成一次完整升级。

## 依赖冲突

**症状**：`unable to satisfy dependency 'foo'`、`conflicting packages`、`failed to prepare transaction`。

**诊断**：

```bash
pacman -Qi 包名
pacman -Ss '^foo$'
```

**修复**：读清楚冲突双方是谁。缺依赖就安装提供者；两个包互斥就移除不再需要的那个；升级引入的冲突优先通过完整升级解决。

> **危险**：`--overwrite` 会强行覆盖文件归属，可能损坏另一个包。只有确认路径和归属、并接受后果时才用，且必须写出精确路径。不要用 `-Rdd`/`-Sdd` 绕过依赖；它会把「装不上」变成「运行时崩」。

**预防**：不随意添加第三方仓库；安装 AUR 包前检查 `conflicts`/`provides`；关注 Arch News 中的包改名。

## 磁盘空间不足

**症状**：`error: not enough free disk space`、`failed to commit transaction (no space left on device)`，或下载到一半失败。

**诊断**：

```bash
df -h /
df -i /
```

**修复**：先清理可再生成的缓存与日志，保留最近版本以便回滚：`sudo paccache -rk1`、`sudo journalctl --vacuum-size=200M`、`sudo pacman -Sc`。最后一条会删除未安装包缓存，`pacman -Scc` 则清空全部缓存并失去降级能力。

> **危险**：空间不足时不要反复重试 `pacman -Syu`，半下载的包和未完成事务会让问题更复杂。

**预防**：定期 `sudo paccache -r`；给 journal 设上限；根分区不要放大文件；`df -i` 也要看，inode 耗尽同样表现为没空间。

## failed unit

**症状**：`systemctl is-system-running` 返回 `degraded`，或某个服务启动失败。

**诊断**：

```bash
systemctl status 单元名
journalctl -u 单元名 -b --no-pager
systemd-analyze verify /etc/systemd/system/单元名.service
```

**修复**：根据 `status` 的退出码和 `journalctl` 的首条错误修配置、路径或权限，然后执行 `sudo systemctl daemon-reload` 和 `sudo systemctl restart 单元名`。被 mask 的单元先 `systemctl unmask`；不需要的服务应 `disable`。

**预防**：自建单元先用 `systemd-analyze verify` 检查；改配置后必须 `daemon-reload`；不要把本机修改直接写进软件包提供的单元文件。

## pacman db.lck

**症状**：`failed to init transaction (unable to lock database)` 或 `could not lock database`。

**诊断**：

```bash
ps -eo pid,comm,args | grep -E '[p]acman|[p]aru|[y]ay'
sudo fuser -v /var/lib/pacman/db.lck
sudo lsof /var/lib/pacman/db.lck 2>/dev/null # 没有 lsof 可跳过
```

**修复**：有进程就等它结束。确认没有 pacman、paru、yay 在运行后，才删除锁文件并重新执行升级。

> **危险**：事务进行中删除 `/var/lib/pacman/db.lck` 会让两个 pacman 同时写数据库，可能损坏本地数据库。删锁前必须确认无相关进程；同样不要删除 `/var/lib/pacman/local` 来「重建数据库」，它保存已安装包的文件清单。

```bash
sudo rm /var/lib/pacman/db.lck
sudo pacman -Syu
```

**预防**：不要同时开多个包管理终端；不要在升级中途强制关机或杀进程；助手与 pacman 不要并行执行。

## DNS 失效

**症状**：`Could not resolve host`、pacman 无法下载，但 `ping 1.1.1.1` 正常。

**诊断**：

```bash
cat /etc/resolv.conf
resolvectl status
```

**修复**：确认 `/etc/resolv.conf` 由谁管理。使用 `systemd-resolved` 时检查服务并 `resolvectl query archlinux.org`；文件内容错误时写入可用 DNS。DNS 解析链的通用原理见第 24 章，接管方式以 Wiki 的 `resolv.conf` 条目为准。

**预防**：不要在多个网络管理器之间来回切换；VPN 或代理变更后重新检查 DNS；不要硬编码 DNS 后忘记撤销。

## 时间漂移

**症状**：`signature is not yet valid`、TLS 证书报错、`timedatectl` 显示的时间与真实时间差很多。

**诊断**：

```bash
timedatectl
systemctl status systemd-timesyncd
```

**修复**：执行 `sudo timedatectl set-ntp true` 和 `sudo systemctl restart systemd-timesyncd`。虚拟机从挂起恢复后虚拟 RTC 可能落后，先让 NTP 重新同步；真机若同步后仍偏差，再用 `sudo hwclock --systohc` 写回硬件时钟。

**预防**：保持 NTP 开启；休眠、挂起、时区变更后检查一次；不要用 `date -s` 手动拨时间代替同步。

## 虚拟机内的端口与资源问题

**本机能连、外部不通**：先在客户机内用 `ss -tlnp` 看监听地址——绑定 `127.0.0.1` 时只有本机可访问，需要外部访问再改绑并限制来源；然后确认虚拟机网络模式，NAT 需要端口转发，桥接则直接出现在局域网。端口与服务可达性的实验见第 66 章，网络原理见第 24 章。

**资源不足**：`free -h`、`nproc`、`df -h` 分别对照虚拟机配置的内存、CPU、磁盘上限。CPU 与内存在关机后才能调整；磁盘扩容后还要在客户机内扩展分区与文件系统（第 18 章）。给物理机留足资源，构建大包时临时调高即可。

**内核模块对不上**：`uname -r` 与 `/lib/modules/$(uname -r)` 必须匹配。升级内核后没有重启时，`modprobe` 会找不到模块目录，重启即可（第 52 章）。实验性模块操作前先打快照。

## 救援与 chroot 的概念

系统无法启动或包管理器完全不可用时，需从外部环境挂载根分区，再用 `arch-chroot` 进入修复——分区与挂载见[第 35 章](35-安装准备与分区.md)，chroot 流程见[第 36 章](36-pacstrap-chroot-与引导器.md)。最小救援清单：Live ISO 启动 → `lsblk -f` 认盘 → `mount /dev/vda2 /mnt`（根）→ `mount --mkdir /dev/vda1 /mnt/boot`（ESP）→ `arch-chroot /mnt` → 修复（重装引导器/重建 initramfs/改 fstab）→ `exit`、`umount -R /mnt`、重启。

## 失败模式

- **看到 `db.lck` 就删**：没有确认进程，两个 pacman 并发写数据库；破坏的是本地包记录，不是锁文件。
- **用 `--overwrite` 大范围跳过冲突**：只跳过文件检查，不修复依赖；损坏状态继续累积。
- **用 `-Rdd`/`-Sdd` 绕过依赖**：把「装不上」变成「运行时崩」，故障从安装期推迟到启动期。
- **事件中执行 `paccache -rk1`**：正要回滚时把唯一旧版本删掉；排障期间先保留缓存。
- **不看 inode**：`df -h` 还有空间但 `df -i` 已耗尽，表现为「没空间」却找不到大文件。
- **反复 `pacman-key --init`**：密钥环已存在时它不会修复问题；签名错误应先查时间与 keyring 版本。
- **把 DNS 故障当 pacman 故障**：`Could not resolve host` 时反复重装 pacman 无用，先用 `resolvectl` 与 `ping` 分层定位。
- **一遇故障就重装系统**：多数问题可在 Live 环境修 fstab、引导器或包数据库；重装会丢失现场，也无法解释根因。

## 验证与回滚

本章的通用顺序是「取证 → 定位 → 最小修复 → 验证」，取证命令都不改系统：

```bash
tail -n 30 /var/log/pacman.log
ps -eo pid,comm,args | grep -E '[p]acman|[p]aru|[y]ay'
sudo fuser -v /var/lib/pacman/db.lck
systemctl --failed --no-pager
journalctl -xeu 单元名 -b --no-pager | tail -n 20
df -h / && df -i /
resolvectl status | head -n 10
timedatectl
```

判读：`pacman.log` 给出最近事务；进程列表决定能否安全删锁；`journalctl` 的首条错误比末尾堆栈更有用；容量与 inode 要同时看；DNS 先确认「能否解析」再谈「能否下载」。回滚：虚拟机快照；`/etc` 逐文件恢复；单包降级用缓存/ALA；引导或 fstab 问题从 Live 环境修复（**未实测**）。本章的删除锁、`--overwrite`、重装与 chroot 修复均**未实测**，抽检以只读命令为准。

## 取舍边界

- **最小修复 vs 重装**：能定位到单包/单配置就最小修复；分区或数据库大面积损坏才重装。
- **`--overwrite` 精确路径 vs 大范围**：只在确认归属、接受后果时写精确路径；永远不要用通配符一把覆盖。
- **清缓存 vs 留回退**：故障中先保缓存；空间实在不足时只清已卸载包，并记录删了哪些版本。
- **快照回滚 vs 原地修复**：能回滚就先回滚，保留现场另存；无法回滚再从 Live 环境修。
- **等进程结束 vs 杀进程**：pacman 事务应等它结束；确认卡死且无写入时才考虑终止，并准备恢复数据库。

## 小结

- 顺序是取证、定位、最小修复、验证；不要从删文件或 `--overwrite` 开始。
- 部分升级用完整升级修复；密钥环问题先查时间，再更新 keyring。
- 依赖与文件冲突要读清双方，`--overwrite` 只能精确使用。
- 磁盘问题同时看容量与 inode；清理优先动缓存和日志。
- failed unit 看 `status` 与 `journalctl`；`db.lck` 只能在确认无进程后删除。
- 无法启动时从 Live ISO 挂载根分区并 `arch-chroot` 救援；虚拟机可先尝试回滚快照，流程见[第 36 章](36-pacstrap-chroot-与引导器.md)。

## 练习

1. 阅读 `/var/log/pacman.log`，找出最近一次升级的起止行。
2. 用 `pacman -F` 查找一个缺失库的提供者，写出重装命令。
3. 用 `systemd-analyze verify` 检查自建单元，故意写错 `ExecStart` 并修复。
4. 查看 `df -h`、`df -i` 与 pacman 缓存体积，制定一条清理命令。
