# 第 57 章 性能分析与系统观测

「卡」是最模糊的故障描述。CPU 忙、内存不足、磁盘排队、网络重传、应用自己阻塞，都会表现为「慢」，但修法完全不同。性能分析的核心不是记住更多工具，而是按资源分层定位：先用低开销的整体指标判断瓶颈在哪一层，再用 per-process 与 tracing 工具回答「是谁」。

> 本章目标：能用 `uptime`、`vmstat`、`free`、`/proc/pressure`、`ss` 做低开销初筛；理解 load average、CPU 利用率、内存可用量、I/O 等待与 PSI 的含义；能按「整体 → 进程 → 调用」三层缩小范围；知道采样与追踪的开销和适用边界。
> 对应 Wiki：[System monitoring](https://wiki.archlinux.org/title/System_monitoring)、[Improving performance](https://wiki.archlinux.org/title/Improving_performance)、[Performance analysis](https://wiki.archlinux.org/title/Performance_analysis)

## 先定义「慢」在哪一层

把系统资源分成五层，逐层问一个只读问题：

| 层 | 关键问题 | 初筛工具 |
| -------- | ------------------------------------ | ------------------------------ |
| CPU | 是否持续跑满？是用户态还是内核态？ | `uptime`、`vmstat`、`mpstat` |
| 内存 | 可用内存是否不足？是否在换页？ | `free`、`vmstat`、`/proc/pressure/memory` |
| 磁盘 I/O | 设备是否饱和？谁在排队？ | `iostat -xz`、`/proc/pressure/io` |
| 网络 | 是否丢包、TCP 重传、连接耗尽？ | `ss -s`、`nstat -az TcpRetransSegs`、`ip -s link` |
| 应用 | 是否锁等待、GC、串行处理？ | 应用日志、`strace`、`perf` |

顺序很重要：先看整体饱和，再看单个进程；先看「等待在哪」，再看「谁在等」。直接对某个进程 `strace`，可能错过真正的瓶颈设备。

## CPU：load average 不是 CPU 使用率

`uptime` 的三个数字是 1/5/15 分钟平均负载，统计的是「可运行 + 不可中断睡眠（D 状态）」的任务数。它不等于 CPU 百分比：

- 4 核机器 load 4.0 表示平均有 4 个任务在跑或等，刚好打满；load 8.0 表示明显排队。
- load 高但 CPU 空闲，通常是 D 状态任务在等 I/O 或锁；此时加 CPU 无用。
- 容器/虚拟机里 load 可能包含宿主影响，要和 `%steal` 一起看。

```bash
uptime
vmstat 1 5 # r 列是可运行任务，b 列是不可中断睡眠
nproc
```

`vmstat` 的 `r` 持续大于核数、`us`+`sy` 高，才是 CPU 饱和；`b` 高而 `wa` 高，指向 I/O 或存储。

## 内存：看 available，不看 free

Linux 会用空闲内存做缓存，`free` 第一列很小是正常的。判断是否真的不足看 `available` 与换页：

```bash
free -h
vmstat 1 5 # si/so 非 0 表示换页
cat /proc/pressure/memory
```

`available` 是「不换出也能给新进程用」的估计；`si/so` 持续非 0 说明已经在换页，延迟会显著上升。PSI 的 `some`/`full` 给出「有多少时间被内存压力阻塞」，比单一剩余量更贴近体验。

## 磁盘 I/O：利用率与排队

```bash
iostat -xz 1 3 # 需安装 sysstat；看 %util、await、aqu-sz
cat /proc/pressure/io
pidstat -d 1 3 # 需安装 sysstat；按进程看读写
```

`%util` 接近 100% 表示设备忙，但 SSD/RAID 上不一定线性；`await` 是平均等待时间，`aqu-sz` 是队列长度。三者一起看：队列长、等待高，才是真饱和。`iostat` 第一次输出是自启动以来的平均值，要从第二次开始看瞬时值。

## 网络：连接与重传

```bash
ss -s # 总连接数、TIME_WAIT 等
ss -tlnp # 监听端口与进程
nstat -az TcpRetransSegs # 主机累计 TCP 重传段计数
ss -ti # 查看具体 TCP 连接的传输与重传信息
ip -s link # 网卡层收发错误、丢弃等接口统计
```

`ip -s link` 是网卡接口层统计，不能用来代表 TCP 重传。`nstat -az TcpRetransSegs` 读取主机累计的 TCP 重传段计数；比较两个时间点的值才能观察增量，它不是按单条连接或网卡拆分的重传率。需要定位具体连接时再看 `ss -ti`。连接数暴涨、`TIME_WAIT` 堆积、重传增加，都会让应用「慢」但 CPU 不高。先分清是「连不上」「连得慢」还是「吞吐低」，再看是应用、协议栈还是链路。

## 进程与调用层

整体定位到某一层后，再回答「是谁」：

```bash
ps -eo pid,ppid,stat,%cpu,%mem,etimes,comm --sort=-%cpu | head
pidstat -u -r -d 1 3 # 需 sysstat
strace -c -p PID # 统计系统调用耗时，有开销
perf top # 采样热点，需 perf 与符号
```

`ps` 的 `STAT` 里 `D` 表示不可中断睡眠，常与 I/O 或内核锁相关；`R` 表示可运行。`strace -c` 按调用聚合，适合看「卡在哪个 syscall」，但会显著拖慢目标；`perf` 采样开销低，适合找 CPU 热点，但需要调试符号才能看到函数名。

## 失败模式

- **把 load average 当 CPU 使用率**：load 高可能是 D 状态等 I/O；按 CPU 扩容或调线程只会更糟。
- **只看 `free` 第一列**：把缓存当「内存不足」，反复清缓存；应看 `available` 与 `si/so`。
- **只采一个样本**：瞬时峰值或刚好空闲，结论完全相反；至少连续采样 3–5 次。
- **看 `iostat` 第一行**：那是自启动以来的平均，不是当前值；从第二次输出开始读。
- **在虚拟机里忽略 `%steal`**：宿主抢走 CPU 时间，客体内部怎么优化都没用。
- **直接 `strace` 生产进程**：开销可能放大延迟；先采样，再对可疑进程短时追踪。
- **没有基线**：不知道「正常」是什么样，就无法判断「变慢」；基线要在健康时记录。
- **把应用锁等待当系统瓶颈**：CPU、内存、磁盘都空闲但请求排队，问题在应用内部并发模型。

## 验证与回滚

性能观测本身应低开销、可重复。下面一组命令可以在任意时刻安全执行：

```bash
uptime
free -h
vmstat 1 5
cat /proc/pressure/cpu /proc/pressure/io /proc/pressure/memory
ss -s
ps -eo pid,stat,%cpu,%mem,comm --sort=-%cpu | head -n 6
```

判读顺序：load 与 `r/b` → `available` 与 `si/so` → PSI 的 `some/full` → 连接与错误。把同一组命令在「正常时」与「变慢时」各跑一次，差异就是证据。回滚：观测命令不改系统；若为排障临时调整了内核参数或服务配置，先恢复 `.bak` 并重启对应服务；压测或 tracing 造成的负载要立即停止，避免把观测变成故障。

## 取舍边界

- **采样 vs 追踪**：采样开销低、能长期开；追踪信息细、开销高，只对短窗口使用。
- **整体指标 vs per-process**：整体判断「哪层饱和」，per-process 判断「谁贡献」；顺序不能反。
- **短窗口 vs 长窗口**：短窗口看尖峰，长窗口看趋势；两者都要，单看一个会误判。
- **清缓存 vs 不动缓存**：缓存是性能的一部分，除非确认内存压力，否则不要手工清。
- **扩容 vs 优化**：CPU 饱和先看是否可并行/降算法；I/O 饱和先看是否可批量/换存储；直接扩容可能只是把瓶颈后移。
- **生产观测 vs 复现环境**：生产只做低开销采样；重负载 tracing 在复现环境做。

## 小结

- 「慢」要分层：CPU、内存、磁盘、网络、应用，先整体后进程。
- load average 包含 D 状态任务，不等于 CPU 使用率；要配 `vmstat` 的 `r/b` 看。
- 内存看 `available` 与 `si/so`，PSI 比单一剩余量更贴近卡顿体验。
- 磁盘看 `%util`、`await`、`aqu-sz`，且从 `iostat` 第二次输出读瞬时值。
- 进程层用 `ps` 看状态，`strace`/`perf` 按需短时使用，注意开销。
- 健康时留基线，故障时才有对照；观测命令本身不改系统。

## 练习

1. 连续执行 `vmstat 1 5`，记录 `r`、`b`、`si`、`so`、`wa` 五列，解释每个值的含义。
2. 对比 `free -h` 的 `free` 与 `available`，说明为什么不能因第一列小就判定内存不足。
3. 读 `/proc/pressure/cpu`、`io`、`memory` 的 `some`/`full`，写出各自衡量的等待类型。
4. 用 `ss -s` 与 `ss -tlnp` 记录当前连接与监听端口，指出哪个进程占用的连接最多（只读）。
5. 对同一个进程分别用 `ps` 与 `pidstat` 观察 3 秒，比较两者给出的 CPU/内存字段差异（`pidstat` 需安装 sysstat）。
6. 设计一次「CPU 高」与「I/O 高」的判别流程，各写出三条先后执行的命令与判据。
