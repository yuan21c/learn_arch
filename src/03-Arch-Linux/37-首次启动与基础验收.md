# 第 37 章 首次启动与基础验收

第一次从硬盘进入 Arch，先不要急着装软件。安装过程是否真的成功，要靠一组可以复现的检查来回答：发行版对不对、内核从哪来、PID 1 是谁、引导模式是什么、系统有没有带故障运行。本章把这些检查固定成「五项自检」，再完成首次全量更新与基础工具安装。

> 本章目标：完成首次启动的五项自检并解释每项输出；判断系统是从硬盘还是从 ISO 启动；完成首次全量更新并安装基础工具；遇到常见启动失败时能定位方向。
> 对应 Wiki：[General recommendations](https://wiki.archlinux.org/title/General_recommendations)｜[System maintenance](https://wiki.archlinux.org/title/System_maintenance)

## 五项自检

```bash
cat /etc/os-release
uname -r
ps -p 1 -o comm=
systemctl is-system-running
cat /sys/firmware/efi/fw_platform_size
```

| 命令 | 期望 | 异常含义 |
| --------------------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| `cat /etc/os-release` | `NAME="Arch Linux"` | 装错发行版，或仍停留在 Live 环境 |
| `uname -r` | 本地安装的内核版本，如 `7.2.11-arch1-1` | 与 pacstrap 装的内核不符，或根文件系统仍是 squashfs/overlay（见下方 Live 判据），说明没真正从硬盘启动 |
| `ps -p 1 -o comm=` | `systemd` | PID 1 不是 systemd，启动链缺了关键一环 |
| `systemctl is-system-running` | `running` 或 `degraded` | 直接报错=systemd 未作为 PID 1；`degraded`=在跑但有 failed 单元 |
| `cat /sys/firmware/efi/fw_platform_size` | `64` | `32`=32 位 UEFI；文件不存在=BIOS/CSM 启动 |

`uname -r` 只反映内核版本，**不含发行版/环境信息**，不要用「输出里有没有 `iso` 字样」判断是否还在 Live 环境（正式安装的内核同样可能是 `arch1-1`）。Live 环境的判据是这三条：

```bash
findmnt -n -o FSTYPE / # Live ISO：squashfs 或 overlay；装到硬盘后：ext4/btrfs/xfs
test -d /run/archiso && echo "仍在 Live 环境"
journalctl -b --no-pager | grep -i -m1 archiso
```

三条里任一命中，就说明还在 ISO 里，此时五项自检的「通过」没有意义。

`degraded` 不是失败，而是「系统起来了但有单元没起来」，用 `systemctl --failed` 列出具体单元再逐个处理。

## 确认引导来源

五项自检只能证明「现在这套系统能跑」，还要确认固件菜单里的条目指向硬盘上的引导器，而不是 Live ISO：

```bash
efibootmgr -v # GRUB 安装时看这里
bootctl status # systemd-boot 安装时看这里
```

按第 36 章实际安装的引导器选一条执行。条目存在且路径指向 ESP 上的 loader（GRUB 为 `grubx64.efi`，systemd-boot 为 `systemd-bootx64.efi`）才算装对。若固件菜单仍优先启动 ISO，关机后在虚拟机设置里移除 ISO 再启动。

## 网络、时间与磁盘

```bash
nmcli device status
ping -c 3 archlinux.org
timedatectl
lsblk -f
findmnt /
findmnt /boot
```

`nmcli` 显示 `connected` 且 `ping` 能解析域名，才谈得上更新。有线网络在虚拟机中通常自动拿到 DHCP；无线网络用 `nmcli device wifi list` 与 `nmcli device wifi connect "SSID" password "密码"`。`timedatectl` 要看到时区正确、`System clock synchronized: yes`——时间偏差会直接表现为包签名错误。最后两条 `findmnt` 确认根分区与 ESP 都挂在实际分区上，而不是根分区里的普通目录。

## 首次全量更新

安装时同步的数据库在生成后就开始老化，先装包可能遇到 404，或装到与本地库不匹配的版本；因此首次进入先做一次全量升级，这也与第 41 章「禁止部分升级」一致。

```bash
pacman -Syu # root 直用；普通用户写 sudo pacman -Syu
```

第一次更新要完整读输出，尤其是 `:: Proceed with installation?` 之前的包列表和提示。

官方镜像通常已初始化密钥环。若 `pacman -Syu` 报签名错误，不要反复执行 `pacman-key --init`；按第 43 章的密钥环流程处理（先更新 `archlinux-keyring`，再视情况重建）。

若你在安装阶段已经先装过包，补一次 `pacman -Syu` 即可回到一致状态。

## 安装基础工具（含 sudo）

此时仍是 root 登录（普通用户的创建与 sudo 授权在第 38 章完成）：下面命令在 root 下**省略 `sudo`**，普通用户执行时才保留——别在装好 `sudo` 之前使用它。

```bash
pacman -S --needed base-devel git sudo reflector pacman-contrib
```

| 包 | 用途 |
| ---------------- | ----------------------------------------- |
| `base-devel` | 元包：依赖拉入构建 AUR 包所需的完整工具链 |
| `git` | 拉取 AUR 仓库与源码 |
| `sudo` | 提权执行（本步装好后才能用 `sudo`） |
| `reflector` | 生成镜像列表 |
| `pacman-contrib` | 提供 `checkupdates`、`paccache` 等工具 |

`--needed` 的语义是「**已是最新版本的包跳过**」——装过但版本旧的包仍会升级，不是「装过就不再动」。编辑器与手册页在第 39 章的基础工具一节补装，不必现在一次装全。

## 常见启动失败

| 现象 | 可能原因 | 排查方向 |
| ---------------------------------------------------------- | --------------------------- | ----------------------------------------------------------------- |
| 停在 `emergency mode` 或 `You are in emergency mode` | fstab 条目错误或重复 | Live ISO 挂载根分区 + `arch-chroot`，核对 UUID 与 fstab（第 36 章） |
| `systemctl` 报 "System has not been booted with systemd" | 不是从硬盘正常启动 | 确认固件启动顺序与引导条目，排除仍在跑 Live 环境 |
| 固件菜单没有 Arch 条目 | 引导器未写入 ESP 或 NVRAM | `efibootmgr -v`、`bootctl status`，必要时 `arch-chroot` 重装引导器 |
| `Unable to mount root fs` | `root=UUID` 错误或 initramfs 缺失 | 核对 `blkid`，`mkinitcpio -P` 重建 |
| 提示 `db.lck` 已存在 | pacman 上次异常退出 | 先确认没有 pacman 进程，再删锁文件 |
| `pacman -Syu` 大量 404 或超时 | 镜像源不可用 | 更换镜像源，见 [安装后配置与镜像源备份](39-安装后配置与镜像源备份.md) |
| 已联网但域名解析失败 | DNS 未配置 | 检查 `/etc/resolv.conf` 与 NetworkManager 连接配置 |

`db.lck` 的处理要谨慎，先确认进程：

```bash
ps aux | grep '[p]acman'
```

> **危险**：只有在确认没有 pacman 进程运行时，才可以删除 `/var/lib/pacman/db.lck`。误删正在使用的锁会导致数据库损坏。

## 失败模式

- **还在 ISO 环境里验收**：根文件系统是 squashfs/overlay、`/run/archiso` 存在，或本次启动日志里有 archiso 字样，说明没有真正从硬盘启动。`uname -r` 不承担这个判据——它只是内核版本。
- **把 `degraded` 当成功**：系统起来了但有 failed unit，表面可用、功能缺失；必须 `systemctl --failed` 逐条处理。
- **先装软件再做首次更新**：安装时的同步数据库已老化，容易 404 或装到与本地库不匹配的版本；先 `pacman -Syu`。
- **反复 `pacman-key --init`**：签名错误通常不是密钥环「没初始化」，而是过期或时间错误；重复初始化不会修复，反而增加变量。
- **误删 `db.lck`**：未确认进程就删锁，两个 pacman 并发写本地数据库会造成真实损坏。
- **固件仍优先启动 ISO**：条目存在但顺序不对，重启又回到 Live；先移除 ISO 或调整启动顺序再验证。
- **时间未同步**：TLS 与包签名失败，日志里表现为「证书/签名无效」，根因却是时钟。

## 验证与回滚

五项自检本身就是验证脚本，逐条记录输出即可复现：

```bash
cat /etc/os-release | head -3
uname -r
ps -p 1 -o comm=
systemctl is-system-running
cat /sys/firmware/efi/fw_platform_size
systemctl --failed --no-pager
journalctl -p err -b --no-pager | tail -n 8
```

判读顺序：先确认发行版与内核来源，再确认 PID 1，最后看失败单元与错误日志。若 `uname -r` 与 pacstrap 装的内核不符，先解决启动来源，不要继续调服务。回滚手段：虚拟机快照回滚；仍在 ISO 时移除 ISO 后重启；引导条目错误则从 Live 环境修正（属于破坏性修复，**未实测**，见第 36 章）。`db.lck` 只在 `pgrep -a pacman` 无输出时才处理。

## 取舍边界

- **`running` vs `degraded`**：`running` 只表示没有失败单元，不代表所有功能都配好；`degraded` 必须查清，不能忽略。
- **首次全量更新 vs 先装常用软件**：先更新保证数据库一致；先装包只适合明确知道镜像仍同步、且马上会完整升级的场景。
- **`systemctl is-system-running` vs `systemctl --failed`**：前者给总体状态，后者给具体单元；排障以后者为准。
- **重装 vs 修复**：能从 Live 环境修正 fstab/引导器就修复；只有分区或数据库大面积损坏才重装。

## 小结

- 五项自检回答五个问题：发行版、内核来源、PID 1、systemd 状态、引导模式。
- `degraded` 表示系统在跑但有失败单元，用 `systemctl --failed` 查，不要当成启动成功。
- 引导条目要指向硬盘上的 loader；还从 ISO 启动说明固件顺序或介质没处理干净。
- 首次更新用 `pacman -Syu`，密钥环只在报错时处理；`--needed` 是「最新才跳过」。
- 启动失败先分四类：fstab、引导器、initramfs、锁文件/网络。

## 练习

1. 完成五项自检并把完整输出记到笔记（预期：五项均与表格期望一致）。
2. 用 `efibootmgr -v` 或 `bootctl status` 核对引导条目，说明它指向 ESP 上的哪个文件（预期：路径以 `.efi` 结尾且位于 ESP）。
3. 执行一次 `pacman -Syu`，记录升级了多少个包、耗时多久（预期：事务完整结束无 error）。
4. 用 `systemctl --failed` 列出失败单元，逐条说明原因；没有失败项就说明为什么 `degraded` 未出现（预期：0 units 或可解释的失败项）。
5. 用 `journalctl -p err -b` 找出本次启动的错误日志，判断哪些是硬件或固件噪音、哪些需要处理（预期：能区分噪音与真实故障）。
