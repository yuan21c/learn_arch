# 第 51 章 构建进阶、多版本与数据库修复

单个包能构建之后，现实问题会变成三类：一个源码树要产出多个包、同一软件要并行保留多个版本、本地包数据库被写坏后如何恢复。本章把这三件事放在一起，因为它们都围绕「包的身份与版本」：拆分包决定包名边界，`epoch` 与 `pkgrel` 决定版本比较，本地数据库记录最终结果。

> 本章目标：能写拆分包与 VCS 包的 PKGBUILD；理解 `epoch`、`pkgrel`、`provides`/`conflicts` 如何支持多版本共存；能读懂 `/var/lib/pacman/local` 的结构并用只读命令判断数据库损坏；知道哪些修复必须重装、哪些只能从备份恢复。
> 对应 Wiki：[PKGBUILD#Packaging](https://wiki.archlinux.org/title/PKGBUILD#Packaging)、[VCS package guidelines](https://wiki.archlinux.org/title/VCS_package_guidelines)、[Pacman#Troubleshooting](https://wiki.archlinux.org/title/Pacman#Troubleshooting)

## 拆分包：一个源码树，多个包

拆分包用 `pkgbase` 表示总名，`pkgname` 写成数组，每个子包对应一个 `package_子包名()`：

```bash
pkgbase=mytools
pkgname=(mytools-cli mytools-doc mytools-lib)
pkgver=2.1.0
pkgrel=1
arch=('x86_64')
depends=('glibc')
makedepends=('cmake')

package_mytools-lib() {
  depends=('glibc')
  install -Dm644 build/libmytools.so "$pkgdir/usr/lib/libmytools.so"
}

package_mytools-cli() {
  depends=('glibc' 'mytools-lib')
  install -Dm755 build/mytools "$pkgdir/usr/bin/mytools"
}

package_mytools-doc() {
  arch=('any')
  install -Dm644 doc/mytools.1 "$pkgdir/usr/share/man/man1/mytools.1"
}
```

三条纪律：子包函数名必须与 `pkgname` 成员完全一致；每个子包可以单独覆盖 `depends`、`arch`、`pkgdesc`；共享的源码下载与编译只做一次，`prepare()`/`build()` 在总包层面执行。拆分不是越多越好——只有「用户会单独安装其中一个」时才有价值，否则只是增加索引与依赖解析的复杂度。

## 版本比较：epoch、pkgver、pkgrel

pacman 的版本比较顺序是 `epoch` → `pkgver` → `pkgrel`。完整版本写作 `epoch:pkgver-pkgrel`，省略 epoch 时视为 0。

| 场景 | 做法 | 说明 |
| ---------------------------- | ------------------------------ | ------------------------------------------ |
| 只改打包方式（补丁、依赖、路径） | `pkgrel` 加 1 | 上游版本没变，但包内容变了 |
| 上游发布新版本 | `pkgver` 更新，`pkgrel` 归 1 | 版本字符串不能含 `-` |
| 上游版本号「倒退」 | 提高 `epoch` | 例如从 `2024.10` 改为 `2.0`，靠 epoch 保证新包优先 |
| 同一软件并行两个大版本 | 不同 `pkgname` + `conflicts`/`provides` | 例如 `foo2` 与 `foo3`，不要靠 epoch 伪装 |

`epoch` 是单向门：一旦发布过 `epoch=1`，后续所有版本都必须带至少相同的 epoch，否则客户端会认为新包更旧。不要把 epoch 当「强制重装」的捷径；强制重装应递增 `pkgrel`。

## VCS 包与动态版本

`-git` 包的 `pkgver` 由仓库状态生成，构建前调用 `pkgver()`：

```bash
pkgname=mytool-git
pkgver=r120.abcdef1
pkgrel=1
source=('git+https://example.com/mytool.git#commit=abcdef1')
sha256sums=('SKIP')

pkgver() {
  cd mytool
  printf 'r%s.%s' "$(git rev-list --count HEAD)" "$(git rev-parse --short HEAD)"
}
```

`#commit=` 把源码钉在某个提交；不写就跟随默认分支，构建结果随时间变化。`pkgver()` 的输出必须单调递增，否则助手会认为「没有更新」。VCS 包用 `SKIP` 是标准做法，但审查时要看 `#commit=` 与 `pkgver()`，不能只看到 `SKIP` 就放行。

## 多版本共存与替换

同一软件的两个大版本通常用不同包名共存：

```bash
pkgname=foo3
provides=('foo=3.2.1')
conflicts=('foo2')
```

`provides` 让依赖 `foo` 的包接受 `foo3`；`conflicts` 阻止与旧版同时安装。若确实需要同时安装，两个包都不能声明互斥，且文件路径、配置目录、服务名必须彼此隔离——这通常意味着上游本身支持并行安装，而不是打包者硬拆。

`replaces` 用于「新包接管旧包」：安装新包时提示删除旧包。它不自动迁移配置，也不保证旧包的数据被清理。

## 本地包数据库的结构

pacman 的本地数据库在 `/var/lib/pacman/local/`，每个已安装包一个目录：

```text
/var/lib/pacman/local/bash-5.3.20-1/
├── desc    # 包名、版本、依赖、安装原因、校验和
├── files   # 包内文件清单
└── mtree   # 文件元数据（权限、属主、大小、校验和）
```

`desc` 缺失或写坏时，`pacman -Q` 可能仍能列出目录名，但 `-Qi` 报字段缺失，升级时依赖解析失败。`files` 与 `mtree` 用于 `-Qk`/`-Qkk` 的文件核对。

只读诊断命令：

```bash
pacman -Dk # 检查本地数据库的依赖完整性
pacman -Qk bash # 检查该包的文件是否都存在
pacman -Qkk bash # 进一步核对文件属性（类型、权限、大小、时间戳等），不校验内容哈希
pacman -Qi bash # 读取 desc 的字段
```

`-Dk` 报 missing dependency 说明数据库记录的依赖关系不完整，常见于手工删过包目录或中断的事务；`-Qk`/`-Qkk` 报缺失文件说明磁盘内容与数据库不一致，这两类问题性质不同。注意 `-Qkk` 只比对 `mtree` 里的**文件属性**，不做内容哈希校验（`pacman -Qk --help` 写的是 `-kk for file properties`）；要验证内容是否被改，只能重装该包或与包文件里的哈希对照。

## 数据库损坏的修复路径

修复原则：**能用重装解决，就不要手改数据库**。重装同一个包会让 pacman 重写该包的 `desc`/`files`/`mtree`：

```bash
sudo pacman -S 包名 # 重装，覆盖该包的本地记录与文件
```

若整个 `/var/lib/pacman/local` 损坏，优先从备份恢复（第 40 章）；没有备份时，只能按已安装清单逐个重装，代价高且容易漏掉 AUR 包。直接编辑 `desc` 或用脚本「重建数据库」不是官方支持路径，字段格式随 pacman 版本变化，写错会让后续事务全部失败。

> 本章的数据库修复、重装与 `pacman-db-upgrade` 均**未实测**；只读诊断与 `/tmp` 构建演练是安全等价路径。

## 失败模式

- **拆分包函数名与 `pkgname` 不一致**：`makepkg` 报找不到 `package_*`，或产出的包缺内容；名字必须逐字对应。
- **子包依赖写成总包依赖**：`depends` 在子包函数里被覆盖，总包层面的依赖不会自动继承；每个子包都要写清自己的运行时依赖。
- **`pkgver` 含连字符**：pacman 解析失败；版本字符串只能用字母、数字、`.`、`_`、`+`。
- **用 `epoch` 代替 `pkgrel`**：epoch 一旦提高就不能回退，后续版本管理会被锁死。
- **VCS 包不钉 `#commit=`**：同一 PKGBUILD 今天和明天构建出不同内容，无法复现。
- **手工编辑 `/var/lib/pacman/local`**：字段缺失或格式错误会让升级事务失败；应重装包或从备份恢复。
- **删除整个 `local` 目录「重建」**：等于丢失所有已安装包的记录，之后无法正常升级或卸载。
- **把 `-Qk` 的文件缺失当成数据库损坏**：前者是磁盘内容问题，后者是记录问题；修复方式不同。

## 验证与回滚

拆分包可以在 `/tmp` 完整演练，不安装到系统：

```bash
mkdir -p /tmp/split51 && cd /tmp/split51
# 写入本章的 PKGBUILD 与最小源码后：
makepkg --printsrcinfo > .SRCINFO
makepkg -f
ls -1 *.pkg.tar.zst
for p in *.pkg.tar.zst; do pacman -Qkp "$p"; done
```

`pacman -Qkp` 读取每个产物的包名、版本与依赖，能直接发现「子包没生成」或「依赖写错」；`tar -tf` 可进一步核对文件落点。数据库侧只用只读命令：

```bash
pacman -Dk
pacman -Qk bash
pacman -Qkk bash
ls /var/lib/pacman/local/bash-*/ | head
```

回滚：拆分包构建失败删掉 `src/`、`pkg/` 与产物重来；多版本共存装错时 `pacman -Rns 错误包名`（**未实测**）；数据库记录损坏时重装对应包（**未实测**），整库损坏从第 40 章的备份恢复。任何写数据库的操作前先 `cp -a /var/lib/pacman/local /var/lib/pacman/local.bak`。

## 取舍边界

- **拆分包 vs 多个独立 PKGBUILD**：同一源码、共享编译时拆分包省时间；源码与版本独立的项目应各自建包，避免一个 PKGBUILD 承担过多职责。
- **`epoch` vs `pkgrel`**：只改打包用 `pkgrel`；上游版本号语义倒退才用 `epoch`，且要接受不可逆。
- **VCS 包 vs 发布 tarball**：需要跟踪上游最新提交用 VCS；要可复现、可审计的发布用固定 tarball 与真实校验和。
- **`provides` vs 改依赖名**：能改依赖声明时优先改名；`provides` 适合过渡期兼容，长期使用会让依赖关系变模糊。
- **重装修复 vs 手工修数据库**：重装可预测但耗时；手改数据库快但不受支持，只应作为最后手段。
- **多版本共存 vs 单一版本**：共存给迁移窗口，但配置、服务名、文件路径都要隔离；无法隔离时不如只保留一个版本。

## 小结

- 拆分包用 `pkgbase` + `pkgname` 数组 + `package_子包名()`，函数名必须与包名一致。
- 版本比较顺序是 epoch → pkgver → pkgrel；`pkgrel` 管打包变化，`epoch` 管版本倒退。
- VCS 包用 `pkgver()` 生成版本，用 `#commit=` 钉住源码；`SKIP` 不等于已校验。
- 多版本共存靠不同包名 + `provides`/`conflicts`，不是靠 epoch 伪装。
- 本地数据库在 `/var/lib/pacman/local`，`-Dk` 查依赖完整性，`-Qk`/`-Qkk` 查文件一致性。
- 数据库损坏优先重装对应包或从备份恢复，不要手改 `desc`、更不要删整个 `local`。

## 练习

1. 在 `/tmp` 写一个两子包的 PKGBUILD，构建后用 `pacman -Qkp` 核对两个产物的包名与依赖，记录输出。
2. 给同一个包只改 `pkgdesc` 并递增 `pkgrel`，解释为什么不能只改内容不升版本。
3. 读一个 VCS 包的 `PKGBUILD`，指出 `pkgver()` 如何生成版本、`#commit=` 是否钉住提交；没有钉住时写出复现风险。
4. 用 `pacman -Dk`、`pacman -Qk bash`、`pacman -Qkk bash` 各执行一次，说明三条命令分别检查什么（只读）。
5. 列出 `/var/lib/pacman/local/bash-*/` 下的文件，解释 `desc`、`files`、`mtree` 各自记录什么。
6. 设计一个「数据库损坏」的恢复顺序：从只读诊断、单包重装、整库备份恢复到重装系统的触发条件，写成四步。
