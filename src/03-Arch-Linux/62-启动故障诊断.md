# 第 62 章 启动故障诊断

启动故障看起来都像「开不了机」，实际发生在不同阶段：固件找不到引导项、引导器加载失败、内核起不来、initramfs 挂不到根、systemd 进了 emergency、服务起不来导致登录循环。每个阶段的证据来源不同，修法也不同。诊断的第一步不是修，而是判断「停在哪一阶段」。

> 本章目标：建立「固件 → 引导器 → 内核/initramfs → 根挂载 → systemd → 用户空间」的阶段模型；能按屏幕症状判断停点；会用 `journalctl --list-boots`、`-b -1`、`systemd-analyze critical-chain` 收集证据；知道 rescue/emergency 目标与临时内核参数怎么用；能区分「引导问题」与「服务问题」。
> 对应 Wiki：[General troubleshooting](https://wiki.archlinux.org/title/General_troubleshooting)、[Boot debugging](https://wiki.archlinux.org/title/Boot_debugging)、[Systemd#Diagnosing_boot_problems](https://wiki.archlinux.org/title/Systemd#Diagnosing_boot_problems)

## 阶段模型

| 阶段 | 正常表现 | 失败表现 | 主要证据 |
| ------------ | ---------------------------- | -------------------------------- | ------------------------------ |
| 固件 | 厂商 logo、启动菜单 | 无输出、直接进固件设置 | 固件设置、`efibootmgr -v` |
| 引导器 | GRUB/systemd-boot 菜单 | `grub>`、`Failed to load kernel` | 引导器配置、ESP 文件 |
| 内核 | 内核日志滚动 | `Kernel panic`、无输出 | 屏幕、`journalctl -b -1` |
| initramfs | 解锁、挂载根 | `Waiting for root device`、LUKS 失败 | `lsinitcpio`、`/proc/cmdline` |
| systemd | 服务并行启动 | `emergency mode`、`degraded` | `journalctl -xb`、`systemctl --failed` |
| 用户空间 | 登录界面/桌面 | 黑屏、登录循环、服务崩溃 | 服务日志、显示管理器日志 |

停点判断比具体错误更重要：如果连引导菜单都没出现，先查固件与 NVRAM；如果菜单出现但选后立即重启，查引导器与内核；如果内核日志后停住，查 initramfs 与根挂载。

## 取证：先保存，再重启

启动故障最常见的问题是「一重启证据就没了」。优先做三件事：

1. **拍照/录屏**：屏幕上的最后几行往往就是根因。
2. **保存上一次启动日志**：`journalctl -b -1` 读取上一次启动；前提是 journal 已持久化（`/var/log/journal` 存在）。
3. **记录改动**：最近升级了什么、改了什么配置、是否换过硬件。

```bash
journalctl --list-boots
journalctl -b -1 -p err --no-pager | tail -n 30
journalctl -b -1 -u 失败单元 --no-pager
cat /proc/cmdline
systemd-analyze critical-chain
systemd-analyze blame | head -n 10
```

`--list-boots` 给出启动编号与时间，`-1` 是上一次；`critical-chain` 显示启动关键路径上的耗时，`blame` 是各单元耗时排行。若 journal 未持久化，`-b -1` 可能不可用，只能依赖屏幕与 Live 环境。

## 按停点分流

**停在固件/无引导菜单**

- 检查启动模式是否被改成 CSM/Legacy；UEFI 安装需要 UEFI 模式。
- `efibootmgr -v` 看条目是否还在、顺序是否被改；必要时从 Live 环境重建条目。
- ESP 是否还在、`EFI/BOOT/BOOTX64.EFI` 是否存在；分区 GUID 变化会让旧条目失效。

**进入 `grub>` 或引导器报错**

- `ls` 找分区，`set root=`、`linux /boot/vmlinuz-linux`、`initrd /boot/initramfs-linux.img` 手工试引导。
- 引导器配置里的 `root=` UUID 是否与 `blkid` 一致；内核与 initramfs 是否还在 `/boot`。
- 能进系统后用 `grub-mkconfig` 或 `bootctl install` 重建（**未实测**）。

**内核 panic 或停在 `Waiting for root device`**

- 临时在引导菜单编辑内核参数，加 `loglevel=7` 看更多输出。
- 检查 `root=`、存储控制器驱动、LUKS 解锁、RAID/LVM 是否在 initramfs 里。
- 用 Live 环境 `lsinitcpio` 检查镜像内容，必要时重建 initramfs。

**进入 emergency mode**

- 屏幕会提示 root 已挂载为只读或某个挂载失败；`journalctl -xb` 找 failed unit。
- 常见原因是 `/etc/fstab` 的 UUID 错、某个分区不存在、systemd 单元依赖失败。
- 在 emergency shell 里先只读检查，再决定修 fstab 还是屏蔽故障单元。

**能启动但服务/桌面失败**

- `systemctl --failed` 看失败单元，`journalctl -xeu 单元名` 看原因。
- 显示管理器失败可能只是显卡驱动或会话配置；先切到 TTY（`Ctrl+Alt+F3`）确认系统本身可用。
- 登录循环通常是家目录权限、shell、会话启动脚本或磁盘满。

## 临时内核参数与救援目标

在引导菜单里按 `e`（GRUB）或 `e`（systemd-boot）临时编辑，只对本次启动生效：

- `systemd.unit=rescue.target`：启动到基本系统，多数服务不启动。
- `systemd.unit=emergency.target`：只挂根，最小 shell，适合修 fstab。
- `loglevel=7`：提高内核日志级别，看到更多初始化信息。
- `nomodeset`：绕过显卡 KMS，用于黑屏排查。
- `root=/dev/分区`：临时指定根，验证 UUID 是否是问题。
- `break=premount`：仅在 initramfs 含 `break` hook 时可用，停在挂载根之前。

这些参数用于「进入系统取证」，不是修复本身；进入后要找到根因并改配置，而不是每次启动都靠临时参数。

> 本章的引导器重建、fstab 修改、initramfs 重建与 rescue/emergency 启动均**未实测**；可复现练习只做日志与启动耗时读取。

## 失败模式

- **重启前不取证**：屏幕信息与上一次启动日志丢失，只能猜；先拍照、先 `journalctl -b -1`。
- **journal 未持久化**：重启后没有 `-1`，无法回看；关键机器应启用持久日志。
- **同时改多个内核参数**：无法判断哪个生效；一次只加一个。
- **把服务失败当引导失败**：系统已进多用户，只是某个 unit 失败；应查 `systemctl --failed`，不是重装引导。
- **在 emergency 里直接改 fstab 不备份**：改错后下次更起不来；先 `cp`。
- **忽略 `critical-chain` 的等待点**：只看到总时长，没看到哪个单元在等；关键路径上的 `@` 时间才是线索。
- **用重装代替诊断**：现场丢失，同类问题会重复；先按阶段定位。
- **不看硬件变化**：换内存、加硬盘、改 BIOS 后启动失败，优先查固件与内核参数，而不是配置。

## 验证与回滚

```bash
journalctl --list-boots
journalctl -b -1 -p err --no-pager | tail -n 20
systemd-analyze critical-chain
systemd-analyze blame | head -n 8
systemctl --failed --no-pager
cat /proc/cmdline
ls -l /boot
efibootmgr -v
```

判读：`critical-chain` 的 `@` 值表示该单元开始时间，箭头指向它等待的单元；`blame` 的高耗时单元不一定是根因，可能是被上游阻塞；`/proc/cmdline` 是本次真实参数；`/boot` 文件时间能看出内核/initramfs 是否刚更新。回滚：临时参数重启即失效；配置改动用 `.bak` 恢复；引导器与 fstab 修复前保存 `efibootmgr -v` 与文件副本；整机故障用快照或 Live 环境修复（**未实测**）。

## 取舍边界

- **现场诊断 vs 快速重装**：生产环境先恢复服务并保留日志/镜像，再离线分析；个人机器时间紧可重装，但要接受根因未知。
- **持久日志 vs 内存日志**：持久化便于 `-b -1`，占磁盘；小存储设备可只保留最近几次。
- **rescue vs emergency**：rescue 启动更多服务、便于网络排障；emergency 更小、更适合改 fstab。
- **修原引导器 vs 换引导器**：配置错优先修；反复出问题且系统简单，可换 systemd-boot 降低配置面。
- **临时参数 vs 永久修改**：临时参数用于取证；确认根因后再写进配置，避免把调试状态留在生产。
- **单内核 vs 多内核**：保留旧内核是最低成本的启动退路；代价是菜单与 initramfs 维护。

## 小结

- 启动分六段：固件、引导器、内核、initramfs、systemd、用户空间；先判断停点。
- 取证优先：拍照、`journalctl -b -1`、`--list-boots`、`critical-chain`，再重启。
- 无引导菜单查固件/NVRAM/ESP；有菜单但立即失败查引导器与内核；内核日志后停住查 initramfs 与根挂载。
- emergency 里先只读检查，再改 fstab 或屏蔽故障单元。
- 临时内核参数只用于取证，不是长期修复。
- 本章的修复动作未实测；日志与耗时读取是安全等价路径。
