# 第 50 章 自定义仓库与发布

当同一批自建包要装到多台机器，或者内网机器不能访问外网时，继续用「拷 `.pkg.tar.zst` 再 `pacman -U`」会迅速失控：版本对不上、依赖要手工补、卸载没有记录。自定义仓库把二进制包和一份索引放在一起，让 pacman 像使用官方仓库一样解析依赖、比较版本、记录安装来源。

> 本章目标：说清自定义仓库与 AUR 的区别；能用 `repo-add` 建立索引并在 `/tmp` 中用独立 `--dbpath` 验证；知道数据库与包的签名怎么做、客户端如何信任；能把仓库发布到文件路径或 HTTP，并处理优先级与保留策略。
> 对应 Wiki：[Pacman/Tips and tricks#Custom local repository](https://wiki.archlinux.org/title/Pacman/Tips_and_tricks#Custom_local_repository)、[Pacman package signing](https://wiki.archlinux.org/title/Pacman_package_signing)、[Creating packages](https://wiki.archlinux.org/title/Creating_packages)

## 三种分发方式的边界

| 方式 | 交付物 | 谁负责构建 | 适合场景 |
| ---------- | ---------------------- | -------------- | ------------------------------ |
| 官方仓库 | 官方签名的二进制包 | 发行版打包者 | 绝大多数软件 |
| AUR | `PKGBUILD` 构建材料 | 使用者自己 | 官方没有、愿意审查脚本 |
| 自定义仓库 | 自建二进制包 + 索引 | 你或你的团队 | 多机统一版本、内网、私有软件 |

自定义仓库不改变「包从哪来」的信任问题，只是把构建结果集中分发。它适合「同一版本要装到十台机器」，不适合「只在一台机器上用一次」——后者直接 `makepkg -si` 更省事。

## 仓库目录与索引

一个仓库目录至少包含两类东西：

```text
/srv/repo/x86_64/
├── hello-arch-1.0.0-1-any.pkg.tar.zst
├── hello-arch-1.0.0-1-any.pkg.tar.zst.sig   # 可选，包签名
├── custom.db -> custom.db.tar.gz             # 索引，repo-add 维护
├── custom.db.tar.gz
├── custom.files -> custom.files.tar.gz       # 文件清单，供 -F 使用
└── custom.files.tar.gz
```

`custom.db` 是 pacman 读取的索引，记录包名、版本、依赖、校验和与文件名；`custom.files` 记录每个包包含哪些路径。`repo-add` 从包内元数据生成索引，`repo-remove` 删除条目。索引文件名（`custom`）就是客户端 `pacman.conf` 里的仓库名。

## 建仓与更新索引

先在 `/tmp` 用第 47–48 章构建出的包演练，不碰系统仓库：

```bash
mkdir -p /tmp/repo50/x86_64
cp ~/build/hello-arch/hello-arch-1.0.0-1-any.pkg.tar.zst /tmp/repo50/x86_64/
cd /tmp/repo50/x86_64
repo-add custom.db.tar.gz hello-arch-1.0.0-1-any.pkg.tar.zst
repo-add -n -R custom.db.tar.gz ./*.pkg.tar.zst
ls -l
```

`-n` 只加入索引里没有的包，`-R` 删除索引中已不存在于目录的旧条目。日常发布顺序是「先复制新包，再 `repo-add -n -R` 全量刷新」，这样删掉旧包文件后索引不会留下死条目。`repo-add` 默认拒绝覆盖同版本条目；重建同版本包时应先 `repo-remove` 或提高 `pkgrel`。

`repo-add` 只更新索引，不移动包文件；索引与包必须在同一目录（或客户端能按 `Server` 路径找到的相对位置）。

## 签名：数据库与包

未签名的仓库等于「谁都能往里放包」。签名分两层：

```bash
# 数据库签名（repo-add 调用 gpg）
repo-add -s -k <你的密钥ID> custom.db.tar.gz ./*.pkg.tar.zst
# 包签名（makepkg 构建时签，或事后补签）
gpg --detach-sign --use-agent hello-arch-1.0.0-1-any.pkg.tar.zst
```

`repo-add -s` 会生成 `custom.db.tar.gz.sig`；客户端必须信任对应公钥，否则 `SigLevel` 校验失败。把公钥分发给客户端并本地签入信任库：

```bash
sudo pacman-key --add /path/to/repo-public.key
sudo pacman-key --lsign-key <密钥ID>
```

客户端 `pacman.conf` 的 `SigLevel` 决定严格程度：`Required DatabaseOptional` 要求数据库签名、包签名可选；`Required` 两者都要求。正式内网仓库建议数据库与包都签，并把公钥通过独立渠道分发，避免「从仓库下载公钥再信任它」的循环。

> 本章的签名、发布与写入客户端 `pacman.conf` 均**未实测**；`/tmp` 建索引与 `--dbpath` 查询是安全等价路径。

## 发布：文件路径与 HTTP

`Server` 支持 `file://` 与 `http(s)://`。小规模内网可以先挂静态目录：

```bash
cd /tmp/repo50
python3 -m http.server 8000 # 仅测试；生产用 nginx/Caddy 并限制访问
```

客户端配置：

```ini
[custom]
SigLevel = Required DatabaseOptional
Server = http://127.0.0.1:8000/x86_64
```

`Server` 的路径必须正好指向「包含 `custom.db` 与包文件」的目录；多架构仓库用 `$arch` 变量，例如 `Server = https://repo.example.com/$repo/$arch`。仓库段的位置决定同名包的优先级：pacman 按 `pacman.conf` 中出现的顺序选包，不看版本高低。自定义仓库应放在官方仓库之后，除非你明确要覆盖官方包。

权限上，HTTP 服务只需读权限；不要把仓库目录设成可写，也不要把索引与包分散到不同路径。

## 客户端验证与升级

```bash
sudo pacman -Syu # 先正常同步
pacman -Sl custom # 列出该仓库可见包（需先同步）
pacman -Si custom/hello-arch # 看版本、依赖与描述
pacman -Sp custom/hello-arch # 只打印将下载的 URL，不安装
```

`-Sl` 为空通常是索引没同步、`Server` 路径错或仓库名与索引名不一致；`-Sp` 能直接暴露 URL 404。安装后 `pacman -Qi hello-arch` 会记录仓库来源，`pacman -Qm` 不再把它列为外来包（因为它来自已配置仓库）。

## 失败模式

- **只复制包、不更新索引**：客户端看不到新版本，报 `target not found`；每次发布都要重跑 `repo-add -n -R`。
- **索引与包不在同一目录**：`Server` 能找到索引却找不到包，安装时 404。
- **`repo-add` 在错误目录执行**：索引记录的文件名是相对的，目录变了就全部失效。
- **数据库签了但客户端没有公钥**：报 `unknown trust`；先 `pacman-key --add` 与 `--lsign-key`。
- **把自定义仓库放在官方仓库前面**：同名包被自定义版本覆盖，可能连带替换依赖；除非有意，否则放后面。
- **删除旧包却保留旧索引**：客户端仍解析到已不存在的文件；用 `-R` 刷新或手工 `repo-remove`。
- **同版本重建不升 `pkgrel`**：客户端认为已是最新，不会重装；改包内容必须递增 `pkgrel`。
- **HTTP 目录可写或可列目录**：任何人都能替换包；发布目录只读，索引更新走构建机。

## 验证与回滚

安全演练不需要动系统仓库：用独立 `--dbpath`、`--config`、`--cachedir` 在 `/tmp` 建一套隔离环境（`-Sy` 需要 root，但只写 `/tmp`）。

```bash
mkdir -p /tmp/repo50/db /tmp/repo50/cache
cat > /tmp/repo50/pacman-test.conf <<'EOF'
[options]
DBPath = /tmp/repo50/db
CacheDir = /tmp/repo50/cache

[custom]
SigLevel = Never
Server = file:///tmp/repo50/x86_64
EOF
sudo pacman -Sy --config /tmp/repo50/pacman-test.conf
pacman -Sl custom --config /tmp/repo50/pacman-test.conf
```

`-Sl` 能看到 `hello-arch` 说明索引与路径正确；若为空，先查 `Server` 尾部是否少了 `/x86_64`。这套环境与系统数据库隔离，删除 `/tmp/repo50` 即完成回滚。正式仓库的回滚靠保留旧包：客户端可用 `pacman -U /path/旧版本.pkg.tar.zst` 降级，或把仓库索引恢复到上一版；发布前先备份 `custom.db.tar.gz`。

## 取舍边界

- **自定义仓库 vs AUR**：AUR 分发构建脚本、每次本机编译；自定义仓库分发二进制、版本统一。团队多机选仓库，个人单机选 AUR/本地构建。
- **`file://` vs HTTP**：同机或挂载盘用 `file://`，零服务；跨机用 HTTP，需考虑 TLS、鉴权与可用性。
- **签名 vs 不签**：内网实验可不签；一旦仓库能被非受信人员写入，就必须签数据库与包。
- **单一仓库 vs 每包一仓**：一个仓库管理简单，但索引变大、耦合强；按团队或产品拆分仓库便于独立发布与授权。
- **无限保留 vs 定期清理**：保留旧版本是回滚能力，但占空间；至少保留每个包最近一个可用版本，清理前确认客户端不依赖旧版。
- **覆盖官方包 vs 只补缺**：覆盖官方包会接管其升级责任；优先使用不同包名，确需覆盖时隔离仓库并写清维护责任。

## 小结

- 自定义仓库 = 二进制包 + `repo-add` 维护的索引；它分发构建结果，不分发 `PKGBUILD`。
- `repo-add -n -R` 是日常刷新索引的命令；包与索引必须在同一目录。
- 数据库签名与包签名是两层，客户端要信任公钥；`SigLevel` 决定严格程度。
- `Server` 路径必须指向索引所在目录；仓库顺序决定同名包优先级，自定义仓库通常放后面。
- 用独立 `--dbpath/--config/--cachedir` 可在 `/tmp` 完整验证仓库，不动系统。
- 保留旧版本才能回滚；发布目录只读，更新由构建机完成。
