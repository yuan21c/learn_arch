# 第 46 章 文件层次与包所有权

篇一第 5 章讲过 FHS 的通用目录职责，篇一第 6–7 章讲透了权限与 ACL。本章只补 Arch 特有的那一层：**哪些文件是包管理器放的、哪些是你放的、升级时它们各自会怎样**。把这条边界弄清楚，就不会出现「升级把配置冲掉」或「重装把程序覆盖」这类事故。

> 本章目标：能说出 Arch 上 `/usr`、`/etc`、`/var`、`/usr/local`、`/opt` 的分工与「谁管理」；理解 merged-usr（`/bin`→`/usr/bin`）的现状；会用 `pacman -Qo` 查文件归属、`pacman -Qkk` 核对包文件状态；知道 `/etc` 修改与 `.pacnew` 的关系，以及为什么不建议手工往 `/usr` 放文件。
> 对应 Wiki：[Arch filesystem hierarchy](https://wiki.archlinux.org/title/Arch_filesystem_hierarchy)、[Pacman](https://wiki.archlinux.org/title/Pacman)

## 谁管理哪一块

FHS 在 Arch 上的落地可以用一张「所有权」表概括——它比通用 FHS 表多一列关键信息：

| 路径 | 放什么 | 谁管理 | 升级时会怎样 |
| -------------- | -------------------------------- | ------------- | -------------------------------------------------------------- |
| `/usr` | 发行版提供的程序、库、文档 | **包管理器** | 被新版本替换 |
| `/etc` | 系统与软件配置 | 管理员 | `backup=()` 内的文件保留你的版本并生成 `.pacnew`，其余会被覆盖 |
| `/var` | 日志、缓存、数据库等可变数据 | 服务与管理员 | 不受影响 |
| `/usr/local` | 管理员自己编译/安装的软件 | **你** | 不受影响 |
| `/opt` | 自包含的第三方软件（整目录分发） | 供应商/管理员 | 不受影响 |
| `/home` | 用户数据 | 用户 | 不受影响 |
| `/tmp`、`/run` | 临时与运行时状态 | 系统 | 重启清空 |

判断规则只有一条：**文件在不在包管理器的数据库里**。在，就由 pacman 负责；不在，就是你（或某个安装脚本）负责。

## merged-usr：`/bin` 已经是符号链接

传统 FHS 里 `/bin`、`/sbin`、`/lib` 是与 `/usr` 平级的目录。现代发行版（含 Arch）已经完成 **usr 合并**：

```bash
ls -ld /bin /sbin /lib /lib64
# lrwxrwxrwx ... /bin -> usr/bin
# lrwxrwxrwx ... /sbin -> usr/bin
# lrwxrwxrwx ... /lib -> usr/lib
# lrwxrwxrwx ... /lib64 -> usr/lib
```

含义有三点：所有可执行文件实际都在 `/usr/bin`（`/sbin` 也指向 `/usr/bin`，不再单独区分系统管理命令）；`/lib` 指向 `/usr/lib`；**不要**再往 `/bin` 或 `/sbin` 里放东西——那等于往 `/usr/bin` 里放。篇一第 5 章说过 sbin 的合并目标因发行版而异，Arch 是 `/usr/bin`。

## `/usr/local` 与 `/opt`：两个「不属于包管理器」的地方

自己编译的软件按惯例装到 `/usr/local`（第 29 章讲的 `--prefix=/usr/local`）：

```text
/usr/local/bin 自己装的命令（在默认 PATH 中，优先于 /usr/bin）
/usr/local/lib 自己装的库
/usr/local/share 文档与数据
```

`/opt` 则留给「整目录分发」的第三方软件（如某些商业软件、游戏平台），一个软件一个子目录，自带全部依赖。

两者都不是 pacman 的地盘，因此也不会有升级与卸载记录。**优先级**上，`/usr/local/bin` 在默认 `PATH` 里排在 `/usr/bin` 之前（第 10 章），这既方便也危险：自己装的旧版本会默默盖住系统的新版本。

## 查归属：pacman -Qo

怀疑某个文件「不知道从哪来的」，就查归属：

```bash
pacman -Qo /usr/bin/bash
# /usr/bin/bash is owned by bash 5.3.3-1
pacman -Qo /etc/ssh/sshd_config
# /etc/ssh/sshd_config is owned by openssh 10.2p1-1
pacman -Qo /usr/local/bin/mytool
# error: No package owns /usr/local/bin/mytool
```

最后一条报错不是失败，而是**有用的信息**：该文件不属于任何包，由你或某个脚本放置。这条命令也是排查「命令行为与文档不一致」的第一步——先确认你运行的那个二进制到底属于哪个包、哪个版本。

## 校验完整性：pacman -Qkk

包数据库里记录了每个包安装的文件清单（来自包内 mtree）。`-Qkk` 逐项核对：

```bash
sudo pacman -Qkk bash
# bash: 148 total files, 0 altered files
```

`-k` 只查文件是否存在；`-kk` 进一步比对权限、大小与修改时间。对 `backup=()` 标记的配置文件，内容变化会以 `backup file mismatch` 提示，但 `altered files` 仍可能是 0；只有非 backup 文件的属性被改才计入 altered。它也不是校验和比对——内容被改但属性未变时不会报 altered。

输出里的 `altered files` 非 0 说明有文件被改动过——常见原因是手工编辑（`/etc` 下是正常的）或某个安装脚本覆盖了文件（`/usr` 下就是问题）。重装单个包即可恢复。

`-Qkk` 只检查**包拥有的文件**：手工放进 `/usr` 的文件不在任何包清单里，`-Qkk` 看不到；升级遇到同名文件会以 `exists in filesystem` 中止事务，需要先移走或确认归属。

```bash
sudo pacman -S bash # 已安装时即重装
```

## `/etc` 的修改与 `.pacnew`

`/etc` 是唯一「包提供但你应该改」的地方。默认两个文件相同；你改过之后，包升级带来新版本，pacman 不会覆盖你的文件，而是把新版本存为 `配置文件名.pacnew`——**但这只对该文件在包的 `backup=()` 列表里生效**（PKGBUILD，第 48 章）；没被 `backup=()` 标记的 `/etc` 文件升级时会被直接覆盖：

```text
/etc/ssh/sshd_config ← 你的版本（保留）
/etc/ssh/sshd_config.pacnew ← 包里的新版本
```

合并工具是 `pacdiff`（来自 `pacman-contrib`），它逐个把差异摆出来让你决定。**长期不处理 `.pacnew` 的后果**是：你的配置停留在旧版本，新版本的默认值、安全修复都没生效，而表面上一切正常。第 52 章的升级流程会把这一步固定成动作。

反过来，删除一个被修改过的配置文件时，pacman 会留 `.pacsave`，防止你的配置随卸载消失。

> **危险**：不要为了「让命令可用」而手工 `cp` 程序到 `/usr/bin` 或 `/bin`。这些位置由包管理器拥有，升级会被覆盖、`-Qkk` 会报 altered，且没有任何卸载记录。要装软件就走包（第 41–43 章）或 `/usr/local`。

## 一次「文件从哪来」的排查

遇到一个陌生文件，按这个顺序问四句：

1. `pacman -Qo <路径>` —— 有归属吗？属于哪个包、哪个版本？
2. 没有归属 → 是不是在 `/usr/local`、`/opt`、`/home`？那是「人放的」，去找安装记录。
3. 有归属但被改过 → `pacman -Qkk <包名>` 看改动范围，判断是配置（正常的）还是程序（异常的）。
4. 需要恢复 → `/etc` 手工合并 `.pacnew`；`/usr` 直接重装包。

## 失败模式

- **手工把文件放进 `/usr`**：包升级会覆盖同路径文件，冲突时 pacman 直接拒绝升级；本地内容放 `/usr/local` 或 `/opt`。
- **忽略 `.pacnew`**：配置长期停留在旧版本，上游安全修复没有生效，但服务表面仍正常。
- **把 `-Qkk` 的「altered」全当成损坏**：`/etc` 下改过的配置文件本来就与包内版本不同；要结合 `pacman -Qii` 与备份判断。
- **用 `-Ql` 查未安装包**：只能列已安装包的文件；仓库包用 `-F` 或 `pacman -S --print-format`。
- **在合并 `/usr` 系统里假设 `/bin` 是独立目录**：`/bin`、`/sbin`、`/lib` 都是符号链接；按旧文档创建真实目录会破坏兼容。
- **删除「看起来重复」的文件**：同内容不同路径可能被不同包或程序依赖；先用 `pacman -Qo` 查归属。
- **升级失败后直接删冲突文件**：可能删掉另一个包的文件；先看 pacman 报出的冲突路径与所属包。

## 验证与回滚

```bash
ls -ld /bin /sbin /lib /lib64 # 合并 /usr 后应为符号链接
pacman -Qo /usr/bin/bash
pacman -Ql bash | grep -E '^bash /usr/bin'
pacman -Qii bash # 含备份文件与安装/修改时间
pacman -Qkk bash # 文件状态核对
```

判读：`-Qo` 的归属为空，说明文件不属于任何包，可能是手工放置或残留；`-Qii` 的 `Backup Files` 列出 pacman 会保留 `.pacsave` 的配置；`-Qkk` 报 altered 时先看是不是 `/etc` 下的配置。回滚：包文件被覆盖时重装该包（`pacman -S 包名`，**未实测**）；本地文件被误删从备份恢复；`.pacnew` 合并前先备份原文件，合并后用 `diff` 复核。实验以只读查询为主，可完整复现。

## 取舍边界

- **`/usr` vs `/usr/local` vs `/opt`**：包管理内容放 `/usr`；自编译或本地脚本放 `/usr/local`；第三方整套应用放 `/opt`，三者升级边界清楚。
- **包管理器 vs 手工安装**：能用包就用包，升级与卸载可追踪；手工安装要自己记录版本、依赖与卸载步骤。
- **`.pacnew` 立即合并 vs 延后**：安全相关配置立即处理；不影响运行且需要停机窗口的，登记到维护清单，不能无限延后。
- **`-Qkk` 全量扫描 vs 定点检查**：全量耗时长且噪声多；排障时先定点查可疑包，定期再抽查。
- **合并 `/usr` vs 传统布局**：现代 Arch 已是合并布局，按符号链接理解；不要为兼容旧脚本重建真实目录。

## 小结

- 判断文件归谁的唯一标准：在不在 pacman 数据库里（`pacman -Qo`）。
- 所有权四分区：`/usr` 归包管理器、`/etc` 归你但与包协商、`/var` 归服务、`/usr/local` 与 `/opt` 归你。
- Arch 已完成 merged-usr：`/bin`、`/sbin` 都指向 `/usr/bin`，不要再往里放文件。
- `pacman -Qkk` 核对包文件的存在性、权限/大小/时间（非校验和），`altered files` 非 0 要区分「配置被改」与「程序被改/覆盖」。
- `/etc` 的升级冲突表现为 `.pacnew`，用 `pacdiff` 合并；删配置会留 `.pacsave`。
- 陌生文件排查四步：查归属 → 判断来源 → 校验改动 → 决定恢复方式。

## 练习

1. 所有权侦察：对 `/usr/bin/bash`、`/etc/passwd`、`/etc/hostname`、`/usr/local`（若存在文件）各跑一次 `pacman -Qo`，把结果按「有归属/无归属」二分归类；再单独回答：其中哪些是配置文件？
2. merged-usr 验证：`ls -ld /bin /sbin /lib`，再用 `readlink -f /bin/ls` 看真实路径；解释为什么 `pacman -Qo /bin/bash` 与 `pacman -Qo /usr/bin/bash` 给出同一个包。
3. 文件状态核对（需 root）：对一个小包（如 `bash` 或 `less`）跑 `pacman -Qkk`，记录总文件数与 altered 数；再用 `pacman -Ql` 查出该包中某个文件的真实路径，故意 `touch` 它（**演练后重装恢复**），重跑观察 altered 数的变化。
4. `.pacnew` 演练（`/tmp` 外勿动真配置）：从一个包中找一个 `/etc` 下的小配置文件，复制一份并改名 `.pacnew`，用 `pacdiff` 或 `diff` 观察两者差异，说明合并时该保留什么。
5. 陌生文件排查：用 `find /usr/local -type f | head` 找出一批无归属文件，对其中一个执行完整的四步排查，写出结论。
6. 边界判断：四件事分别该放哪、由谁管理——自己编译的工具、nginx 的站点配置、PostgreSQL 的数据目录、某商业 IDE 的整套安装目录。
