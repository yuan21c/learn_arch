# 第 90 章 视频与编解码

第 88 章讲声音怎么从声卡出来；这一章讲**视频为什么能播、为什么卡、为什么颜色不对**。视频问题几乎都能拆成四层：容器、编码、解码路径、色彩。分不清这四层，就会把「封装不支持」当成「编码坏了」，或把「硬解没生效」当成「文件损坏」。

> 本章目标：能区分容器与编码，并解释 remux 与 transcode 的差别；知道 H.264/H.265/AV1/VP9 与 AAC/Opus 的适用场景；理解 VA-API/NVDEC 硬解路径与 `hwdec` 模式；会用 `ffprobe` 读出流信息、用 `ffmpeg` 做无损重封装与转码；知道 HDR 与色彩空间的基本概念；能识别「硬解黑屏」「像素格式不支持」「音画不同步」三类问题。
> 对应 Wiki：[Codec](https://wiki.archlinux.org/title/Codec)、[Mpv](https://wiki.archlinux.org/title/Mpv)、[VLC media player](https://wiki.archlinux.org/title/VLC_media_player)、[FFmpeg](https://wiki.archlinux.org/title/FFmpeg)

## 容器与编码：两层别混

| 层 | 例子 | 决定什么 | 换层代价 |
| ---------- | ------------------------------ | ------------------------------ | ------------------------------ |
| 容器 | MP4、MKV、WebM、TS | 怎么装流、字幕、章节、索引 | remux 很快、几乎无损 |
| 视频编码 | H.264、H.265/HEVC、AV1、VP9 | 像素怎么压缩、解码器要求 | transcode 慢、有画质损失 |
| 音频编码 | AAC、Opus、FLAC、AC-3 | 声音怎么压缩、声道布局 | 可单独转码 |
| 字幕 | SRT、ASS、PGS | 文本或图形字幕 | 文本可转，图形字幕多需重封装 |

- **remux**（`-c copy`）：只换容器，不重编码；「MKV 播不了但 MP4 能播」常靠这一步解决。
- **transcode**：重新编码，兼容性最好但耗时且有损；只在目标设备确实不支持原编码时做。
- 文件名后缀不等于容器真相：`.mp4` 里放 AV1 也能存在，老设备却可能不认；**以 `ffprobe` 的输出为准**。

## 编码选型

| 编码 | 压缩效率 | 兼容性 | 硬件支持 | 适用 |
| ---------- | -------- | -------- | ---------------------- | ------------------------------ |
| H.264/AVC | 基准 | 最广 | 几乎所有 GPU | 通用分发、老设备 |
| H.265/HEVC | 高 | 较广 | 较新 GPU | 4K、存储受限 |
| AV1 | 很高 | 增长中 | 新 GPU 硬解/硬编 | 长期归档、流媒体 |
| VP9 | 高 | WebM/浏览器好 | 部分 GPU | 网页视频 |
| AAC | 基准 | 最广 | 不涉及 | 通用音频 |
| Opus | 很高 | 现代浏览器/播放器 | 不涉及 | 低码率语音、WebM |

选择原则：**目标设备能硬解什么就用什么**；归档追求体积选 AV1/H.265，但要接受编码慢、老设备播不了。

## mpv、VLC 与 ffmpeg

| 工具 | 定位 | 优点 | 代价 |
| ---------- | ------------------------------ | ------------------------------ | ------------------------------ |
| mpv | 配置驱动的播放器 | 画质与色彩管线强、脚本化 | 默认无 GUI，要学配置 |
| VLC | 全能 GUI 播放器 | 开箱即用、格式多、跨平台 | 高级色彩/硬解控制较弱 |
| ffmpeg | 命令行处理工具 | 转码/重封装/分析的事实标准 | 参数多，误用会毁画质 |

三个代表用法：

```bash
mpv --hwdec=auto-safe video.mkv # 自动选择安全的硬解路径
vlc --avcodec-hw=any video.mkv # VLC 的硬解开关
ffmpeg -i in.mkv -c copy out.mp4 # 无损重封装
```

`auto-safe` 只在确认稳定的硬解路径上启用，避免某些驱动下的黑屏；`-c copy` 不重编码，速度取决于磁盘而不是 CPU。

## 硬解：VA-API 与 NVDEC

硬解把解码工作交给 GPU 的固定功能单元，省 CPU 与电量：

```bash
vainfo 2>&1 | head -12 # Intel/AMD：列出支持的 profile
ffmpeg -hwaccels # 列出 ffmpeg 支持的硬解后端
mpv --hwdec=auto-safe --vo=gpu-next video.mkv
```

- Intel/AMD 走 VA-API（第 82 章的 `intel-media-driver` 或 Mesa `radeonsi`）；NVIDIA 走 NVDEC。
- 硬解链路要求「解码器 → 色彩转换 → 渲染」都支持该像素格式；10-bit/HDR 文件在只支持 8-bit 的路径上会失败或回退软解。
- 硬解不是万能：某些编码档次（如 4:4:4、特殊 profile）没有硬件支持，回退软解才是正确行为。

## 可复现实验：读流信息与无损重封装

在 `/tmp` 生成一段测试视频并探测（本机已实测通过）：

```bash
ffmpeg -hide_banner -loglevel error \
  -f lavfi -i testsrc=duration=2:size=640x360:rate=25 \
  -f lavfi -i sine=frequency=440:duration=2 \
  -c:v libx264 -pix_fmt yuv420p -c:a aac /tmp/b6-test.mp4 -y

ffprobe -hide_banner \
  -show_entries stream=index,codec_name,codec_type,width,height,pix_fmt \
  -show_entries format=duration,size,format_name \
  -of default=noprint_wrappers=1 /tmp/b6-test.mp4

ffmpeg -hide_banner -loglevel error -i /tmp/b6-test.mp4 -c copy /tmp/b6-test.mkv -y
ffprobe -hide_banner -show_entries format=format_name,size -of default=noprint_wrappers=1 /tmp/b6-test.mkv
```

预期输出包含：

```text
codec_name=h264
codec_type=video
width=640
height=360
pix_fmt=yuv420p
codec_name=aac
format_name=mov,mp4,m4a,3gp,3g2,mj2
duration=2.000000
```

重封装后的 MKV 应报告 `format_name=matroska,webm`，`size` 与源接近——**编码未变、容器变了**，这就是 remux 的直接证据。

再验证硬解是否可用（无 GPU/无会话时会失败，属正常）：

```bash
vainfo 2>&1 | grep -E 'VAProfile|driver'
ffmpeg -hwaccels 2>/dev/null | tail -n +2
```

## 失败模式

| 现象 | 根因 | 处置 |
| ------------------------------ | ------------------------------------------ | ------------------------------------------------------ |
| 播放器打开即报「不支持的格式」 | 容器或编码不被目标设备支持 | `ffprobe` 确认编码；先 `-c copy` 换容器，再考虑转码 |
| 硬解开启后黑屏/花屏 | 驱动不支持该 profile 或色彩转换失败 | 关硬解（`--hwdec=no`）对比，确认后选 `auto-safe` |
| 只有声音没有画面 | 视频编码无解码器 | 装对应解码器或转码为 H.264 |
| 音画不同步 | 可变帧率、时间戳错误、容器索引损坏 | 用 `ffmpeg -i` 看流时长，重封装或重编码 |
| 10-bit/HDR 发灰或过曝 | 色彩空间未正确传递/映射 | 用支持 HDR 的渲染路径，或显式 tone mapping |
| 转码后体积反而更大 | 码率/预设选错 | 用 CRF 而非固定码率，按内容调 preset |
| 字幕乱码或不同步 | 字幕编码/帧率与视频不匹配 | 转字幕编码，按帧率校正偏移 |
| 播放 4K 卡顿但 CPU 不高 | 硬解没生效或在软解 4:4:4 | `mpv` 的 `i` 统计页确认实际解码路径 |

## 验证与回滚

```bash
ffprobe -hide_banner -show_streams -show_format file.mkv | head -40
ffmpeg -hwaccels
vainfo 2>/dev/null | grep -c VAProfile
mpv --no-config --hwdec=no --frames=1 file.mkv 2>&1 | tail -5
```

- `ffprobe` 的 `codec_name`/`pix_fmt`/`duration` 是判断「文件本身」的事实依据。
- `mpv` 播放时按 `i` 打开统计页，能看到 `VO`、`hwdec` 与实际解码器；这是「硬解到底有没有生效」的最直接证据。
- 对比「软解 vs 硬解」的 CPU 占用，比看日志更直观。

回滚：

- 转码前保留原文件，输出写新文件名，**不要原地覆盖**。
- 硬解配置改坏时，用 `--no-config` 启动排除配置影响。
- 驱动/解码器变更后无法播放，回退驱动包或改用软件解码先恢复可用。

## 取舍边界

- **mpv vs VLC**：要画质、脚本化、精确控制选 mpv；要开箱即用、偶尔播放选 VLC。两者可共存。
- **硬解 vs 软解**：硬解省电省 CPU，但受 profile 与驱动限制；软解兼容性最好，代价是功耗与发热。笔记本优先硬解，服务器转码看 CPU 余量。
- **H.264 vs H.265/AV1**：分发兼容优先 H.264；存储/带宽优先 H.265/AV1，但要确认播放端支持。
- **remux vs transcode**：能 remux 就不 transcode；转码只在编码不被支持或需要降码率时做。
- **CRF vs 固定码率**：CRF 按画质目标分配码率，通常更优；固定码率适合有严格带宽上限的流媒体。
- **HDR 直通 vs tone mapping**：显示设备支持 HDR 就直通；SDR 屏幕必须 tone mapping，否则要么灰要么过曝。

## 小结

- 视频四层：容器、视频编码、音频编码、字幕；先分清再排障。
- remux 只换容器（`-c copy`），transcode 重编码；优先 remux。
- mpv 强在画质与配置，VLC 强在易用，ffmpeg 是分析与处理的事实标准。
- 硬解走 VA-API/NVDEC，`auto-safe` 比 `auto` 稳；`mpv` 的 `i` 统计页能确认实际路径。
- 10-bit/HDR 与特殊 profile 常导致硬解失败，回退软解是正常策略。
- 验证以 `ffprobe` 与播放器统计为准，不看文件名后缀。

## 练习

1. 生成与探测：按正文生成 2 秒测试视频，记录 `codec_name`、`pix_fmt`、`duration` 三项实际值。
2. 无损重封装：把 MP4 转成 MKV（`-c copy`），比较两个文件的 `size` 与 `format_name`，解释为什么耗时很短。
3. 编码对比：用 `libx264` 与 `libx265` 各编一次同一素材（短片段），比较体积与耗时，说明兼容性取舍。
4. 硬解判定：在有 GPU 的机器上用 `mpv` 播放并打开统计页，记录 `hwdec` 实际值；再 `--hwdec=no` 对比 CPU 占用。
5. 失败注入：用 `ffmpeg` 生成一个 10-bit 视频，在只支持 8-bit 硬解的路径上播放，观察回退行为。
6. 转码决策：给定「老电视只支持 H.264/AAC、原文件是 HEVC/Opus」，写出 remux 与 transcode 的正确顺序。
