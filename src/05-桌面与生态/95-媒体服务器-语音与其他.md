# 第 95 章 媒体服务器、语音与其他

这一章开始进入「按类别讲应用」的部分。每个类别只讲**这一类应用的共性、2–3 个代表、以及选型边界**，不铺软件清单。媒体服务器与语音工具的共同点是：**它们都是「本机 + 服务端 + 客户端」的三段结构**，桌面只是客户端之一，真正的复杂度在服务端。

> 本章目标：能说出媒体服务器「库 → 元数据 → 转码 → 客户端」的四段管线；能按免费/开源自建、音乐轻量、低延迟语音三种需求选择代表应用；知道媒体库权限、硬件转码、反向代理与 TLS 分别由哪一章负责；会用包查询与端口/进程检查验证部署；能识别「库扫不到」「转码占满 CPU」「直接暴露公网」三类问题。
> 对应 Wiki：[List of applications/Multimedia](https://wiki.archlinux.org/title/List_of_applications/Multimedia)、[List of applications/Internet](https://wiki.archlinux.org/title/List_of_applications/Internet)、[Jellyfin](https://wiki.archlinux.org/title/Jellyfin)

## 四段管线

| 段 | 做什么 | 失败表现 |
| ---------------- | ------------------------------------------------ | ------------------------------ |
| 媒体库 | 扫描目录、识别文件名、读取内嵌元数据 | 扫不到文件、名字混乱 |
| 元数据 | 联网刮削海报、简介、字幕 | 刮错、封面空白、请求被限流 |
| 转码 | 按客户端能力实时转换编码/码率 | CPU 占满、播放卡顿 |
| 客户端 | 浏览器、手机、电视 App 拉流 | 能登录但播不了 |

任何一段出问题都表现为「打不开视频」，所以要按段排查，而不是只看服务是否 `active`。

## 三类代表

| 类别 | 代表 | 定位 | 部署形态 |
| -------------- | -------------- | ------------------------------------------ | ------------------------------ |
| 综合媒体库 | Jellyfin | 开源、无订阅、插件与硬件转码 | `jellyfin-server` 官方包，或容器 |
| 音乐库 | Navidrome | 轻量、Subsonic API、适合纯音乐 | `navidrome` 官方包，或容器 |
| 低延迟语音 | Mumble | 自建、低延迟、适合游戏/团队语音 | `mumble-server` 官方包 |
| 去中心聊天 | Element | Matrix 客户端，聊天为主、可音视频 | 客户端官方包，服务端另部署 |

三个代表应用的取舍：

- **Jellyfin**：完全开源、无账号绑定，适合家庭媒体库；刮削与客户端生态不如商业方案成熟，硬件转码要自己调（第 82、90 章）。
- **Navidrome**：资源占用低、只做音乐，Subsonic 兼容客户端多；不处理视频与复杂元数据。
- **Mumble**：延迟低、自建简单，适合固定团队；界面与功能不如现代语音平台丰富。

## 转码与直连：先看客户端能力

「能不能播」取决于客户端解码能力，而不是服务端心情：

| 客户端 | 常见能力 | 建议策略 |
| ---------------- | ------------------------------------------------ | ------------------------------ |
| 桌面浏览器 | 依赖浏览器内置解码器，H.264/AAC 最稳 | 优先直连；异常编码才转码 |
| 手机 App | 硬解主流编码，字幕/音轨支持因 App 而异 | 直连为主，字幕用外挂 |
| 电视/盒子 | 硬件解码强，但对容器与音轨挑剔 | 先 `ffprobe` 看源（第 90 章），再决定是否转码 |
| 老旧设备 | 只支持低码率 H.264 | 单独设转码策略，别拖累全局 |

直连省 CPU、画质无损；转码兼容性最好但吃资源。**判断顺序是「源编码 → 客户端能力 → 网络带宽」**，三步都过才谈画质设置。

## 账号、密钥与设备权限

- 媒体服务器的 API key、管理员密码等同于「整个媒体库的读写权」，放配置文件时权限收紧到服务账号（第 77 章的最小权限思路）。
- 硬件转码需要访问 `/dev/dri/renderD128`；裸机部署时服务账号要加入 `render` 组，容器部署要给 `--device /dev/dri`，否则转码会静默回落到 CPU。
- 反向代理层的认证与服务自身认证是两套：反代挡在门外，服务内仍有账号体系；**不要用反代认证替代服务认证**，否则内网直连即绕过。

## 部署边界：不要在本章重造

媒体服务器看起来是「装个包」，实际涉及四个已有章节的职责：

- **进程托管**：`systemctl enable --now jellyfin`，单元写法见第 63 章；
- **容器化**：镜像、卷、端口映射见第 71–73 章，本章只给「什么时候该用容器」的判断；
- **反向代理与 TLS**：域名、证书、`proxy_pass` 见第 64–65 章；
- **存储布局**：媒体目录与挂载见第 18–23 章，权限见第 7 章，备份见第 40 章。

服务端放在**内网**、用反向代理暴露必要端口，是最小安全基线；**不要把媒体服务器的管理端口直接映射到公网**，也不要关掉认证来「方便电视访问」。

## 可复现实验：包与服务的事实

```bash
pacman -Si jellyfin-server | grep -E 'Repository|Version|Depends On' | head -4
pacman -Si navidrome | grep -E 'Repository|Version' | head -2
pacman -Si mumble | grep -E 'Repository|Version' | head -2
systemctl status jellyfin --no-pager | head -8
ss -tlnp 2>/dev/null | grep -E '8096|4533|64738'
ls -l /dev/dri 2>/dev/null || echo "无 /dev/dri（无 GPU 或未加载驱动）"
pacman -Ql jellyfin-server 2>/dev/null | grep -E '/bin/|systemd/system' | head -6
```

本机核验结果：`jellyfin-server`、`navidrome`、`mumble`、`element-desktop` 都在官方仓库；`plex-media-server` 不在官方仓库（需 AUR 或厂商渠道）；服务未安装时 `systemctl status` 报 `could not be found`，`ss` 没有对应端口。**「包在仓库里」与「服务在跑」是两件事**，两者都要验证。

端口参考：Jellyfin 默认 8096（HTTP），Navidrome 默认 4533，Mumble 默认 64738（TCP/UDP）。端口只是默认值，部署时按实际配置核对。

## 失败模式

| 现象 | 根因 | 处置 |
| ------------------------------ | ------------------------------------------ | ------------------------------------------------------ |
| 库扫描不到文件 | 目录权限、挂载未生效、路径写错 | 用服务账号 `ls` 目标目录，核对容器卷映射 |
| 文件名识别混乱 | 命名不符合刮削规则/元数据缺失 | 按 `剧名/季/集` 规范命名，或手工修正 |
| 刮削请求失败/限流 | 元数据源不可达或频率过高 | 换元数据源、降低并发，检查网络与 DNS |
| 播放卡顿且 CPU 100% | 实时转码，客户端不支持原编码 | 开硬件转码（第 82 章）或选直连播放 |
| 手机外网连不上 | 只监听 `127.0.0.1` 或端口未放行 | 反代暴露 HTTPS（第 64–65 章），不要裸映射管理口 |
| 电视能登录但播不了 | 客户端不支持容器/编码 | 转码或换客户端；先 `ffprobe` 确认源编码（第 90 章） |
| 服务启动即退出 | 数据目录不可写/端口被占 | `journalctl -u` 看报错，`ss` 查端口占用 |
| 公网暴露后被扫描/入侵 | 直接映射端口且弱认证 | 收回端口，走反代 + 强认证 + 更新 |

## 验证与回滚

```bash
systemctl is-active jellyfin
ss -tlnp | grep 8096
curl -fsS http://127.0.0.1:8096/health 2>/dev/null || echo "健康端点不可达"
journalctl -u jellyfin -b --no-pager | tail -20
```

`is-active` 只说明进程在；端口监听说明网络层通；健康端点/登录页说明应用层可用；日志说明启动阶段有没有隐藏错误。三项都过，再谈媒体库扫描与播放。

回滚：

```bash
sudo systemctl disable --now jellyfin
sudo pacman -Rns jellyfin-server
sudo rm -rf /var/lib/jellyfin # 确认后；媒体文件不要删
```

删除服务包不会删媒体文件，但**配置与数据库在 `/var/lib/jellyfin`**，先备份再删；容器部署则 `podman rm -f` 加卷清理（第 72 章）。

## 取舍边界

- **裸机 vs 容器**：单机、要硬件转码与直接访问设备时裸机简单；多服务、要隔离与易迁移时用容器（第 71–73 章）。
- **Jellyfin vs Plex**：要开源与无订阅选 Jellyfin；要成熟客户端与自动转码体验选 Plex，代价是专有与账号体系。
- **综合库 vs 纯音乐**：视频+音乐用 Jellyfin；只要音乐用 Navidrome，资源占用低得多。
- **自建语音 vs 平台**：固定团队、在意数据主权用 Mumble 自建；临时沟通用现成平台更省事。
- **直连播放 vs 转码**：客户端支持源编码就直连，省 CPU；不支持才转码，并尽量用硬件转码。
- **内网 vs 公网**：默认只在内网；必须公网时走反代、TLS、强认证与限流，不直接暴露管理端口。

## 小结

- 媒体服务四段：库、元数据、转码、客户端；按段排障。
- 代表：Jellyfin 综合、Navidrome 音乐、Mumble 语音、Element 聊天。
- 进程托管看第 63 章，容器看第 71–73 章，反代与 TLS 看第 64–65 章，存储看第 18–23 章，权限与备份看第 7、40 章。
- 包在官方仓库不等于服务在跑，`systemctl` + `ss` + 健康端点三层验证。
- 默认内网部署，公网必须经过反代与认证，不裸映射管理端口。
