# 第 92 章 打印与扫描

第 88 章给了打印与扫描的最小闭环；这一章讲**CUPS 的内部结构与排障**。打印是桌面里最容易「看起来配好了但就是不出纸」的部分：队列状态、过滤器、后端、PPD 四层任何一层出错，表现都只是「任务卡住」。把层次拆开，才能用 `lpstat` 与日志定位到具体环节。

> 本章目标：能说出 CUPS 的调度器、队列、过滤器、后端、PPD/IPP 五个部件；理解 IPP Everywhere/AirPrint 为什么能免驱；会用 `lpadmin` 建队列、`lpstat` 查状态、`cancel`/`cupsenable` 处理卡单；知道 `/var/log/cups/error_log` 与调试日志的开启方式；理解 SANE 的 `sane-find-scanner`/`scanimage` 链路与 `sane-airscan` 的适用场景；能识别「队列暂停」「过滤器缺失」「扫描仪权限不足」三类问题。
> 对应 Wiki：[CUPS](https://wiki.archlinux.org/title/CUPS)、[Printing](https://wiki.archlinux.org/title/Printing)、[SANE](https://wiki.archlinux.org/title/SANE)、[Scanner](https://wiki.archlinux.org/title/Scanner)

## CUPS 的五个部件

| 部件 | 作用 | 出问题时的表现 |
| -------------------- | ------------------------------------------------ | ------------------------------ |
| `cupsd` 调度器 | 接收任务、排序、调用过滤器与后端 | 整个打印系统不响应 |
| 队列（queue） | 一台逻辑打印机，带状态与默认设置 | `lpstat` 显示 `disabled` |
| 过滤器链 | 把文档格式转成打印机认识的格式 | 任务停在「processing」不动 |
| 后端（backend） | 真正把数据送到设备：`ipp`、`usb`、`socket` | 任务报「backend failed」 |
| PPD / IPP Everywhere | 描述设备能力（纸张、分辨率、色彩） | 选项缺失、纸张尺寸不对 |

`cupsd` 通过 `cups.socket` 按需启动，也可以常驻 `cups.service`；两者都指向同一个守护进程，**不要同时启用两套启动方式**。

## 免驱打印：IPP Everywhere 与 AirPrint

现代打印机大多支持 IPP Everywhere（AirPrint 是其苹果叫法）：设备自己描述能力，客户端不需要厂商 PPD：

```bash
lpinfo -v # 列出可用后端与发现的设备 URI
lpinfo -m | grep -i everywhere # 确认 everywhere 驱动存在
```

建队列：

```bash
sudo lpadmin -p Office -E \
  -v ipp://192.168.1.50/ipp/print \
  -m everywhere
lpstat -p Office -d
```

- `-p` 队列名，`-E` 表示启用并接受任务，`-v` 设备 URI，`-m everywhere` 使用 IPP Everywhere。
- 网络打印机优先写 `ipp://`；老设备只支持 `socket://`（RAW 9100）时，过滤器链可能无法转换格式，需要厂商 PPD。
- 只有 USB 接口、但只支持 IPP 的打印机，可用 `ipp-usb` 把它暴露成本地 IPP 设备。

厂商专用驱动（如某些激光机的 PPD）只在免驱不工作时才装；**装了厂商驱动并不自动更好**，它常带来版本绑定与升级问题。

## 队列状态与卡单处理

```bash
lpstat -t # 汇总：默认队列、各队列状态、排队任务
lpq -P Office # 查看某队列的任务
lpstat -o # 所有未完成任务
cancel -u "$USER" -a # 取消自己的全部任务（谨慎）
sudo cupsenable Office # 重新启用队列
sudo cupsaccept Office # 重新接受新任务
```

- `disabled` 表示队列被暂停（常见于缺纸、卡纸、后端失败后的自动停用）；`cupsenable` 恢复。
- `rejecting` 表示不接受新任务但可继续打印旧的；`cupsaccept` 恢复接收。
- 任务一直 `processing` 但不出纸，多半是过滤器或后端卡住；看日志而不是反复 `cancel`。

日志与调试：

```bash
sudo tail -n 50 /var/log/cups/error_log
sudo cupsctl --debug-logging # 临时提高日志级别
sudo cupsctl --no-debug-logging # 排查完关掉
```

`error_log` 会记录「哪个过滤器失败、哪个后端报错、返回码是多少」，这是定位「任务卡住」最直接的证据。调试日志会快速增长，排查后务必关闭。

## 扫描：SANE 链路

SANE 分「后端驱动」与「前端应用」两层：

```bash
sudo pacman -S sane sane-airscan
sane-find-scanner # 找 USB/SCSI 设备
scanimage -L # 列出 SANE 认识的设备
scanimage --format=png --resolution 300 -o /tmp/scan.png
```

- `sane-find-scanner` 只验证「总线上有没有设备」，不代表驱动可用；`scanimage -L` 才是「能不能用」。
- `sane-airscan` 支持 eSCL（AirScan）与 WSD，很多网络一体机不需要厂商驱动；本地 USB 设备则依赖具体 backend。
- 权限问题常见：USB 扫描仪需要 udev 规则或 `scanner`/`lp` 组权限，加入组后要重新登录。
- 网络扫描依赖 mDNS（5353）与 WSD 发现；防火墙挡住多播时，`scanimage -L` 看不到设备，但手动指定 `--device` 仍可能可用。

## 三个代表应用

- **CUPS**：打印调度器与队列管理，`lpadmin`/`lpstat`/`cancel` 是它的 CLI。
- **SANE + `scanimage`**：扫描的底层 API 与命令行前端，适合脚本化与排障。
- **Simple Scan**：GNOME 系图形扫描前端，底层仍走 SANE；适合日常扫描，不适合批量脚本。

## 可复现实验：只查状态，不打印

```bash
systemctl status cups --no-pager | head -8
systemctl status cups.socket --no-pager | head -8
lpstat -t 2>&1
lpinfo -v 2>&1 | head -10
lpinfo -m 2>/dev/null | grep -ci everywhere
scanimage -L 2>&1 | head -5
sane-find-scanner 2>&1 | tail -5
```

**预期**：没有配置打印机时，`lpstat -t` 会报 `no destinations added` 或只显示类信息；`lpinfo -v` 仍会列出 `direct`/`network` 后端，说明 CUPS 本身是通的；没有扫描仪时 `scanimage -L` 报 `No scanners were identified`，这是设备问题不是 SANE 坏了。**区分「服务没起」与「没有设备」是排障第一步**。

## 失败模式

| 现象 | 根因 | 处置 |
| ------------------------------ | ------------------------------------------ | ------------------------------------------------------ |
| `lpstat` 报 `No destinations added` | 没建队列 | `lpadmin` 建队列，或先在 `localhost:631` 添加 |
| 队列 `disabled`，新任务不打印 | 缺纸/卡纸/后端失败后自动暂停 | 修硬件后 `cupsenable` |
| 任务 `processing` 长时间不动 | 过滤器缺失或后端卡住 | 看 `error_log`，确认过滤器与 URI |
| 报 `backend failed` | URI 错、设备离线、网络不通 | `lpinfo -v` 核对 URI，`ping`/`ipptool` 测连通 |
| 打印内容乱码/半页 | PPD 与设备不匹配 | 换 `everywhere` 或正确厂商 PPD |
| 纸张尺寸/双面选项缺失 | PPD 能力描述不全 | `lpoptions -p <队列> -l` 查看，换驱动 |
| `scanimage -L` 找不到扫描仪 | backend 缺失或权限不足 | 装对应 backend，检查 udev/`scanner` 组 |
| 网络扫描仪时有时无 | mDNS/WSD 被防火墙挡住 | 放行 5353/WS-Discovery，或手动指定设备 |
| USB 打印机换口后失效 | URI 绑定旧总线路径 | 重新 `lpinfo -v` 获取新 URI，更新队列 |
| 调试日志撑满磁盘 | 忘记关 `--debug-logging` | `cupsctl --no-debug-logging`，清理日志 |

## 验证与回滚

打印的验证要走到「出纸」才算完成：

```bash
lp -d Office /usr/share/cups/data/testprint # 打印测试页
lpstat -o Office # 观察任务状态
sudo tail -n 30 /var/log/cups/error_log
```

测试页能出，说明队列、过滤器、后端、PPD 四层全通；只到 `processing` 就停，按日志定位过滤器/后端。扫描的验证是「能出图」：

```bash
scanimage -L
scanimage --format=png --resolution 100 -o /tmp/scan-test.png
file /tmp/scan-test.png
```

回滚：

```bash
sudo lpadmin -x Office # 删除队列
sudo systemctl disable --now cups.service # 若改用 socket 激活
sudo systemctl enable --now cups.socket
sudo cp /etc/cups/cupsd.conf.bak /etc/cups/cupsd.conf # 恢复配置
sudo systemctl restart cups
```

删除队列前记录 `lpstat -p` 与 `lpoptions -l`，便于重建；`cupsd.conf` 改前备份，改坏后 CUPS 可能直接不启动。

## 取舍边界

- **`cups.socket` vs `cups.service`**：偶尔打印用 socket 激活省资源；打印频繁或要即时响应用常驻服务。只选一种。
- **IPP Everywhere vs 厂商 PPD**：免驱优先，升级稳定；厂商驱动只在免驱不支持时用，并接受其版本绑定。
- **本机 CUPS vs 打印服务器**：单机直连最简单；多机共享把 CUPS 放一台常开主机，其他机器指向它的 IPP URI。
- **SANE 通用后端 vs 厂商工具**：`sane-airscan` 覆盖多数网络一体机；特殊功能（胶片、双面批量）可能仍需厂商工具。
- **网络打印 vs USB 直连**：网络打印免去线缆与位置限制，但依赖网络与发现协议；USB 稳定但要处理 URI 变化。
- **调试日志 vs 性能**：调试日志定位快但会快速膨胀；生产环境默认关闭，排查时短开。

## 小结

- CUPS 五部件：调度器、队列、过滤器、后端、PPD/IPP；卡单先判断卡在哪一层。
- IPP Everywhere/AirPrint 可免驱；`lpadmin -m everywhere` 是现代首选。
- `lpstat -t` 看全局，`lpq` 看队列，`error_log` 看根因；`cupsenable`/`cupsaccept` 恢复队列。
- SANE 分 backend 与前端，`sane-find-scanner` 只证明总线有设备，`scanimage -L` 才证明可用。
- 网络扫描依赖 mDNS/WSD 与权限，`sane-airscan` 能覆盖大量一体机。
- 验证打印看「出纸」，验证扫描看「出图」，不看命令返回码。
