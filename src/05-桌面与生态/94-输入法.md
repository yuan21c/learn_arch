# 第 94 章 输入法

第 88 章给了 Fcitx5 的最小安装与自启；这一章讲**输入法为什么在某些应用里不工作**。中文输入法是最典型的「分层故障」：引擎、框架、应用接入方式三层，任何一层没对上，表现都是「打不出字」或「候选框不跟随」。把这三层拆开，比反复重装输入法有效得多。

> 本章目标：能说出输入法引擎、框架、应用接入三层及各自代表；理解 X11 的 XIM/immodule 与 Wayland 的 `text-input` 协议差别；能写出 GTK/Qt 需要的环境变量并说明为什么要放在会话级；能按桌面环境在 Fcitx5 与 IBus 之间选择；知道 Rime 的方案文件放在哪、部署失败怎么查；会用 `fcitx5-diagnose`、`fcitx5-remote` 与环境变量验证链路；能识别「候选框不出现」「变量没进会话」「两个框架打架」三类问题。
> 对应 Wiki：[Input method](https://wiki.archlinux.org/title/Input_method)、[Fcitx5](https://wiki.archlinux.org/title/Fcitx5)、[IBus](https://wiki.archlinux.org/title/IBus)、[Rime](https://wiki.archlinux.org/title/Rime)

## 三层结构

| 层 | 作用 | 例子 |
| -------------- | ------------------------------------------------ | ------------------------------------------ |
| 引擎 | 把按键转成候选字/词 | Rime、拼音、五笔、注音 |
| 框架 | 管理引擎、候选窗、热键、状态 | Fcitx5、IBus |
| 应用接入 | 让应用把按键交给框架，并接收候选窗位置 | GTK/Qt immodule、XIM、Wayland `text-input` |

装「输入法」其实是装这三层的组合：`fcitx5` 是框架，`fcitx5-rime` 是引擎插件，`fcitx5-gtk`/`fcitx5-qt` 是应用接入模块。**只装框架不装接入模块，GTK/Qt 应用就不会走输入法**。

## X11 与 Wayland 的接入差异

| 会话 | 接入方式 | 需要什么 | 典型问题 |
| ---------- | ------------------------------ | ------------------------------------------ | ------------------------------ |
| X11 | XIM、GTK/Qt immodule | `XMODIFIERS`、`GTK_IM_MODULE`、`QT_IM_MODULE` | 变量缺失、只对部分工具包生效 |
| Wayland | `text-input-v3` 协议 + immodule | 合成器支持协议、框架支持 Wayland | 合成器不支持、候选框位置错 |
| XWayland | 沿用 X11 的 immodule/XIM | 与 X11 相同 | 只有 XWayland 程序能输入 |

Wayland 下**不是所有合成器都完整实现 `text-input`**：KDE/GNOME 支持较好，部分 wlroots 合成器需要额外协议或插件。这就是「同一个 Fcitx5，在 Plasma 能用、换到某个平铺合成器就失效」的原因（第 84 章）。

## 环境变量矩阵

X11 与传统工具包依赖这几个变量：

```bash
export GTK_IM_MODULE=fcitx
export QT_IM_MODULE=fcitx
export XMODIFIERS=@im=fcitx
```

- `GTK_IM_MODULE` 影响 GTK3/GTK4；`QT_IM_MODULE` 影响 Qt5/Qt6；`XMODIFIERS` 影响 XIM 与部分老程序。
- 这些变量**必须在会话启动时就有**；只在终端 `export` 后从启动器打开的应用读不到。
- 持久化写 `~/.config/environment.d/im.conf`（systemd 用户管理器在登录时读入并导入会话），X11 会话可同时写 `~/.xprofile`；系统级可写 `/etc/environment`，但会影响所有用户。变量该写哪里的完整对照表见 [第 88 章](88-多媒体打印与日常主题.md) §输入法。

```ini
# ~/.config/environment.d/im.conf
GTK_IM_MODULE=fcitx
QT_IM_MODULE=fcitx
XMODIFIERS=@im=fcitx
```

改完要**重新登录**才对所有新启动的应用生效；`systemctl --user import-environment` 只影响当前用户管理器，不能替代重新登录。

## Fcitx5 与 IBus

| 维度 | Fcitx5 | IBus |
| ------------------ | ------------------------------ | ------------------------------ |
| 生态与引擎 | Rime、拼音、五笔等插件丰富 | Rime、拼音，引擎也不少 |
| Wayland 支持 | 较好，配合合成器 | GNOME 集成更直接 |
| 配置方式 | 图形配置 + 文本 | 图形配置 + `ibus-setup` |
| 与桌面集成 | KDE 友好 | GNOME 默认 |
| 诊断工具 | `fcitx5-diagnose` | `ibus-setup`/日志 |

选择原则：**GNOME 用户优先 IBus**（少一层适配）；**KDE/其他桌面或需要 Rime 高级方案优先 Fcitx5**。两者**绝对不要同时运行**——同时装可以，但同时自启会导致热键与候选窗互相抢。

## Rime：方案与部署

Rime 是引擎，方案（schema）决定输入习惯：

```bash
sudo pacman -S fcitx5-rime # 或 ibus-rime
ls ~/.local/share/fcitx5/rime/
```

- 用户方案与配置在 `~/.local/share/fcitx5/rime/`（IBus 版本路径不同）。
- `default.custom.yaml` 用来选默认方案与候选数量；改完要在输入法界面「重新部署」，或重启框架。
- 部署失败常表现为「方案列表为空」或「候选不出字」；先看 Rime 日志与 `fcitx5-diagnose` 的输出，不要急着重装。
- 词库与个人习惯文件可备份；迁移机器时把 `rime/` 目录整体带走即可。

## 可复现实验：链路的证据

```bash
pacman -Q fcitx5 fcitx5-rime fcitx5-gtk fcitx5-qt 2>&1
echo "GTK_IM_MODULE=$GTK_IM_MODULE"
echo "QT_IM_MODULE=$QT_IM_MODULE"
echo "XMODIFIERS=$XMODIFIERS"
fcitx5-diagnose 2>&1 | head -30
fcitx5-remote 2>&1
ls ~/.local/share/fcitx5/rime/ 2>&1
```

本机（未装输入法、SSH 会话）的实际结果：`pacman -Q` 报未安装，三个变量为空，`fcitx5-diagnose`/`fcitx5-remote` 不存在。**这说明「框架没装、变量没注入」，不是「输入法坏了」**。有图形会话时，`fcitx5-diagnose` 会逐项检查框架进程、immodule、XIM、Wayland 协议与环境变量，是最省事的诊断入口。

## 失败模式

| 现象 | 根因 | 处置 |
| ------------------------------ | ------------------------------------------ | ------------------------------------------------------ |
| 能切换但打不出候选 | 引擎/方案未加载或部署失败 | 查 Rime 部署与 `fcitx5-diagnose` 的引擎项 |
| 某些应用能输入、某些不能 | 缺对应工具包的 immodule | 装 `fcitx5-gtk`/`fcitx5-qt`，重启应用 |
| 所有应用都不能输入 | 环境变量没进会话 | 变量必须在图形会话的进程环境里可见：`systemctl --user show-environment` 或应用内 `env` 确认，再按第 88 章的矩阵选位置（`environment.d` 或 `~/.xprofile`） |
| 候选框固定在左上角 | Wayland 协议/合成器不支持光标定位 | 换合成器或接受降级；XWayland 程序另测 |
| 打字弹出两个候选框 | Fcitx5 与 IBus 同时运行 | 停用其中一个，删其自启项 |
| 热键冲突/切不过去 | 框架热键与应用热键重叠 | 在框架配置里改切换键 |
| GNOME 下 Fcitx5 时好时坏 | GNOME 自带 IBus 抢占 | 用 IBus，或彻底停用 IBus 并配置 GNOME 扩展 |
| Rime 方案列表为空 | 方案文件缺失或路径错 | 核对 `rime/` 目录与 `default.custom.yaml`，重新部署 |

## 验证与回滚

```bash
fcitx5-diagnose 2>/dev/null | grep -E 'Environment|Frontend|Addon' | head -20
fcitx5-remote # 查看/切换当前状态
systemctl --user status fcitx5 --no-pager | head -8
printenv | grep -E 'GTK_IM_MODULE|QT_IM_MODULE|XMODIFIERS'
```

诊断顺序：**框架进程在不在 → 变量在不在 → immodule 装没装 → 合成器协议支不支持**。四项都通过后仍有问题，才怀疑引擎或方案。

回滚：

```bash
rm ~/.config/autostart/fcitx5.desktop
rm ~/.config/environment.d/im.conf
systemctl --user disable --now fcitx5
```

删除变量文件后重新登录，应用会回到「无输入法」状态；想换框架时，先停旧框架再装新框架，不要两套并行。

## 取舍边界

- **Fcitx5 vs IBus**：GNOME 用 IBus 省适配；其他桌面或 Rime 深度用户用 Fcitx5。只选一个运行。
- **Rime vs 内置拼音**：Rime 可定制、可迁移，但要学方案配置；内置拼音开箱即用，定制弱。
- **系统级变量 vs 用户级**：多用户机器写 `environment.d` 更安全；`/etc/environment` 会影响所有用户与所有会话。
- **XIM vs immodule**：现代工具包走 immodule；只有老程序才需要 XIM，且 XIM 在新环境下问题更多。
- **Wayland 原生 vs XWayland**：原生协议体验更好但依赖合成器；XWayland 兼容性好但候选框定位可能退化。
- **自动启动 vs 手动**：自动启动省事；排障时先手动启动看日志，稳定后再加自启。

## 小结

- 输入法三层：引擎、框架、应用接入；缺一层就表现为「打不出字」。
- X11 靠 `XMODIFIERS`/`GTK_IM_MODULE`/`QT_IM_MODULE`，Wayland 靠 `text-input` 协议 + immodule。
- 变量必须在图形会话的进程环境里可见（`systemctl --user show-environment` 可查）；只在终端 `export` 无效，写哪里按第 88 章矩阵选。
- Fcitx5 与 IBus 只运行一个；GNOME 优先 IBus，其他桌面优先 Fcitx5。
- Rime 方案在用户数据目录，改完要重新部署；部署失败先看诊断与日志。
- 排障顺序：框架进程 → 变量 → immodule → 合成器协议 → 引擎。
