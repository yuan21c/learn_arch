# 第 6 章 权限管理

每个文件都归某个用户、属于某个组，权限位决定「谁能把它怎么样」。Linux 的权限模型简单到只有三组 `rwx`，却支撑起整个多用户系统的隔离。本章从逐列读懂 `ls -l` 开始，走完 `chmod/chown/umask`，再进入三个特殊位与 ACL，把「这个命令会不会被拒绝」讲到可以预判的程度。

> 本章目标：能逐列读懂 `ls -l` 的属主、属组与九位权限，说出 r/w/x 对文件与目录的不同含义；会用数字与符号模式 `chmod`，用 `chown/chgrp` 改归属并知道普通用户的边界；能用 `umask` 的屏蔽公式推算新建文件权限；掌握 SUID/SGID/Sticky 的机制与 `s/S/t/T` 读法；能从 `+` 标志识别 ACL，并知道其配置与 mask 规则在第 7 章展开。
> 对应 Wiki：[File permissions and attributes](https://wiki.archlinux.org/title/File_permissions_and_attributes)、[Access Control Lists](https://wiki.archlinux.org/title/Access_Control_Lists)

## 读懂 ls -l：属主、属组与九位

`ls -l` 的第一列把类型与权限合在一起：首字符是文件类型（第 3 章讲过，`-` 普通文件、`d` 目录），后面九位按 **属主（u）、属组（g）、其他（o）** 三组排列，每组固定 `rwx` 三个位置。实跑一条：

```text
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 80792 Jul 30 18:04 /usr/bin/passwd
```

逐列含义：`-` 普通文件；`rws r-x r-x` 属主可读可写可执行（`s` 占属主的 `x` 位，稍后讲）、属组与其他可读可执行；九位之后是链接数，再是属主与属组（本例都是 `root`），最后是大小与时间。r、w、x 在文件和目录上的含义完全不同，这是本章第一个必须记牢的表：

| 位 | 在文件上 | 在目录上 |
| --- | ------------ | ------------------------ |
| `r` | 读取内容 | 列出目录项（`ls`） |
| `w` | 修改内容 | 创建、删除、改名目录项 |
| `x` | 当作程序执行 | 进入目录、访问其中的条目 |

两个直接推论：删除或改名一个文件只看**所在目录**的 `w`（以及用 `x` 进入它的能力），与文件自身权限无关——第 5 章目录项一节说的就是这件事；而有 `w` 没 `x` 的目录（`-w-`）谁也无法真正往里放东西，因为够不到里面的条目。`w` 对目录的破坏力极大，Sticky 位一节会讲怎么收束它。

九位权限的数字写法：`r=4`、`w=2`、`x=1`，每组三位各自求和。常用的几组：`755`（自己全有、他人可进可读）、`644`（自己可读写、他人只读）、`600`（只有自己可读写）、`640`（自己读写、属组只读）。Linux 上几乎所有系统文件的权限都能被这张表解释。

## chmod：数字与符号模式

`chmod` 是改权限的唯一入口，两种写法等价（/tmp 演练）：

```bash
mkdir -p /tmp/p6 && cd /tmp/p6 && touch a.txt f1 f2
chmod 640 a.txt # 数字模式：rw-r-----
chmod u+x,g-w a.txt # 符号模式：对属主加 x、对属组去掉 w
ls -l a.txt # -rwxr----- 1 arch arch ...
```

符号模式的语法是「谁 ±= 权限」：`u/g/o/a`（属主/属组/其他/全部），`+`/`-`/`=`（增加/删除/精确设置）。**不写「谁」等价于 `a`，但会受 umask 屏蔽（umask 见下节）**——实测 umask 077 下 `chmod =r f1` 得 `-r--------`，而 `chmod a=r f2` 得 `-r--r--r--`。要分组精确赋值就把 `ugo` 写全：`chmod u=rx,go= file` 表示「属主可读执行、其他人一律清空」。

> **危险**：`chmod -R 777 目录` 会递归把整棵子树改成人人可写，常见于「先放开再收紧」的救火操作——一旦执行，敏感文件已经暴露过，收回权限也补不回信息泄露。递归改动一律先在 `/tmp` 演练，收紧的正确方向是 `chmod -R go-w 目录` 这类**减法**。

## chown 与 chgrp：改归属与普通用户的边界

`chown` 改属主，`chgrp` 改属组，`chown 用户:组 文件` 一次改两个（`用户:` 带冒号**同时改属主与属组**，属组变为该用户的登录组；`用户` 无冒号只改属主；`:组` 只改属组）。两者都可加 `-R`，也同样受危险提示约束。关键边界是：**改属主需要特权**。普通用户把自己的文件给别人，实跑直接被拒：

```bash
cd /tmp/p6 # 接上例
chown nobody a.txt
# chown: changing ownership of 'a.txt': Operation not permitted
chgrp wheel a.txt # 成功：wheel 是本用户所属组（Arch/RHEL 常用；Debian/Ubuntu 默认用 sudo 组，无 wheel）
chgrp root a.txt
# chgrp: changing group of 'a.txt': Operation not permitted
```

规则：`chown` 需要 root（等价于持有 CAP_CHOWN 能力）；`chgrp` 普通用户可用，但只能改成**自己所属的组**。把文件交给别的用户、或改到不属于自己的组，都要 `sudo`。这条边界保证了「我不能把我的文件塞给你、让你替我背锅」。

## umask：新建文件的默认权限

`umask` 是创建文件时的**屏蔽位**，公式只有两行：

- 新文件 = `666 & ~umask`（初始给全员读写，但绝不给执行位）
- 新目录 = `777 & ~umask`（目录必须有 `x` 才能进入）

bash 的 `umask` 显示为四位八进制，首位是特殊位（通常为 0），后三位与 `rwx` 一一对应。实测两种取值的结果：

```bash
umask # 0022
touch c.txt; ls -l c.txt # -rw-r--r--（666 & ~0022 = 644）
(umask 077; touch b.txt; mkdir d77; ls -ld b.txt d77)
# -rw------- b.txt drwx------ d77（600 / 700）
```

本机普通用户与 root 的默认 umask 都是 `0022`（bash 实测），所以家目录里新建的文件通常是 644、目录 755。umask 的取值是四位八进制——最高位留给特殊位，普通场景恒为 0，因此 bash 输出 `0022`，而 zsh 等会省略前导零显示 `022`；本书代码块按 bash 写法补足四位。临时改 umask 只影响当前 shell 及其子进程；想常驻写进 shell 启动文件（第 10 章）。注意 umask 只屏蔽九位 `rwx`——SUID 这类特殊位不会因 umask 出现，只能用 `chmod` 显式添加。

## 特殊位：SUID、SGID 与 Sticky

三位特殊位占据数字模式的最高位与权限显示的属主/属组/其他槽位：

| 特殊位 | 数字 | 加在文件上 | 加在目录上 |
| ------ | ---- | ------------------------------ | ----------------------------------------- |
| SUID | `4` | 执行期间以**文件属主**身份运行 | 无实际意义 |
| SGID | `2` | 执行期间以**文件属组**身份运行 | 新建条目继承目录的属组 |
| Sticky | `1` | 无实际意义 | 只有属主、目录属主和 root 能删除/改名条目 |

**SUID 是提权的标准化通道。** 普通用户读不了 `/etc/shadow`（实测 `cat /etc/shadow` 报 Permission denied），但 `passwd -S arch` 却能输出密码状态——因为 `/usr/bin/passwd` 带 SUID，执行的瞬间有效用户变成它的属主 root，于是可以读 shadow、写系统账号文件。`/usr/bin/su`、`/usr/bin/sudo` 同理。显示上，SUID 占属主的 `x` 位：属主槽位有 `x` 时是小写 `s`，无 `x` 时是大写 `S`（仅表示属主槽位不可执行，其他有 `x` 的主体仍可执行 实测）：

```bash
chmod u+s c.txt; ls -l c.txt # -rwSr--r--：SUID 已设但属主无 x；且三组都无 x，谁都执行不了，这才真正形同虚设
touch prog; chmod 4755 prog # 数字模式的最高位：4 = SUID（prog 为示例文件名）
```

三个特殊位的显示规则一致：各占对应主体的 `x` 槽位，**小写表示该槽位同时有 `x`，大写表示该槽位缺 `x`**——大写只影响这一槽位，其他主体的执行权、SGID 的属组继承与 Sticky 的删除保护仍生效（实测：`drwxr-Sr--` 中新建文件属组仍继承 wheel；`-rwSr-xr-x` 由 other 执行仍得 euid 0）。Sticky 的行为验证要用 `chmod 1777` 得到小写 `t`：大写 `T` 时 other 连 `x` 都没有，删除被拒是「进不去」而非 Sticky 在起作用：

| 特殊位 | 槽位 | 有 `x`（小写） | 无 `x`（大写） |
| ------ | --------- | -------------- | -------------- |
| SUID | 属主 `x` | `rws` | `rwS` |
| SGID | 属组 `x` | `r-s` | `r-S` |
| Sticky | other `x` | `rwt`（目录） | `rwT`（目录） |

**SGID 加在目录上更常用**：目录带 `g+s` 后，里面新建的文件自动继承目录的属组，团队共享目录不必每个文件手动 `chgrp`。实测：

```bash
mkdir sg && chgrp wheel sg && chmod 2775 sg
touch sg/inside.txt && ls -l sg/inside.txt
# -rw-r--r-- 1 arch wheel 0 ... inside.txt （属组跟随目录，而非创建者主组）
```

`/usr/bin/wall` 这类「以共享组身份写终端」的程序是 SGID 文件的典型（实测 `-rwxr-sr-x root tty`）。**Sticky** 则收束目录 `w` 的破坏力：`/tmp` 是 `drwxrwxrwt`，人人可建文件，但删不掉别人的——实测删除 root 在 `/tmp` 的文件报 `Operation not permitted`，这正是粘滞位在起作用。

> **危险**：给不可信的**二进制**加 SUID root 等于安装后门（解释型脚本上的 SUID 会被内核忽略，见第 7 章）；SUID 位只能加在你完全理解、且属主可信的二进制上。排查时用 `find /usr/bin -perm -4000` 列出全部 SUID 文件，来源不明的要深究。

## ACL 与文件能力：已独立成章

按名字精确授权（ACL）、mask 与默认 ACL 继承、file capabilities（`getcap/setcap`）内容较多，独立成章——见[第 7 章 权限深入：UID、ACL 与文件能力](07-权限深入-UID-ACL-与文件能力.md)。本章只需记住：`ls -l` 权限位后的 `+` 表示文件带 ACL；具名用户、具名组与属组的有效权限会被 ACL 的 mask 压低，属主与 other 不受影响。

## 扩展一眼：文件属性与 Capabilities

两处与 rwx 相邻的知识，够用即可：**文件属性**是文件系统层面的开关，`lsattr 文件` 查看（实测输出全为 `-`），典型的是不可修改位 `i`——设置后 root 也不能直接改写，只能先解除；设置用 `chattr`，需要 root 且依赖文件系统支持，以 [File permissions and attributes](https://wiki.archlinux.org/title/File_permissions_and_attributes) 为准。**Capabilities** 把「root 无所不能」拆成 `cap_net_raw`、`cap_setuid` 这样的单点能力，程序只申请需要的一小块，是 SUID 的现代化替代；普通用户的有效能力集为空（实测 `grep '^CapEff' /proc/self/status` 输出全 0），细节见 [Capabilities](https://wiki.archlinux.org/title/Capabilities)。

## 常见失败与验证

| 失败模式 | 原因 | 验证与回滚 |
| --- | --- | --- |
| `chmod -R 777` 越修越乱 | 递归把目录与文件一起放开，且丢失可执行位语义 | 先 `find 目录 -type d -exec chmod 755 {} +`、文件单独 644；改动前记录 `find -printf '%m %p\n' > modes.txt` |
| 目录能读却不能进 | 目录缺少 `x` 位，无法穿越 | `namei -l 路径` 逐级看权限 |
| 新文件权限与预期不符 | `umask` 与默认权限组合 | `umask`、`umask -S`，再用 `touch` 实测 |
| SUID 不生效 | 脚本被忽略、所在文件系统 `nosuid`、属主不是 root | `findmnt -T 文件 -o OPTIONS`、`stat -c '%A %U' 文件` |
| ACL 加了却不生效 | mask 截断、挂载不支持 ACL | `getfacl 文件` 看 `mask` 与 `#effective` |

**回滚**：改权限前保存原模式（`stat -c '%a %n' 文件` 或上面的 `find -printf`）；ACL 用 `getfacl -R 目录 > acl.bak`，恢复用 `setfacl --restore=acl.bak`。SUID/SGID 位不要对普通用户可写文件保留。

**取舍**：能用「属组 + 组权限」解决时，不要上 ACL；能用 ACL 精确授权时，不要用 777。SUID 适合少数必须提权的二进制，脚本与自写程序优先用 capabilities 或服务化管理（见第 7 章）。

## 小结

- `ls -l` 第一列 = 类型 + 属主/属组/其他三组 `rwx`；r/w/x 在文件与目录上含义不同，删除改名只看目录的 `w`。
- 数字模式 `r=4 w=2 x=1` 求和；符号模式「谁 ±= 权限」精确赋值用 `=` 写全 `ugo`；递归放开权限是危险动作。
- `chown` 需要特权，`chgrp` 只能改自己所属的组——普通用户的改归属边界就在这里。
- umask：文件 `666 & ~umask`、目录 `777 & ~umask`；只屏蔽九位，特殊位靠 `chmod`。
- SUID 让程序以属主身份运行（`passwd` 能读 shadow 的原因），SGID 目录让新条目继承属组，Sticky 让 `/tmp` 人人可写但删不掉别人的。
- ACL 的按名授权、mask 与默认 ACL 继承、file capabilities 都在第 7 章；本章只需认得 `+` 标志。

## 练习

1. 逐列解读系统文件的权限：

 ```bash
 ls -l /usr/bin/passwd /tmp
 ls -ld /tmp /var/tmp /home/arch
 ```

 说出每行的类型、九位权限、属主属组，并解释 `/tmp` 为什么人人可写却删不掉别人的文件。
2. 在 `/tmp/p6`（不存在就 `mkdir -p /tmp/p6`）里建 `t.txt`，依次跑 `chmod 640 t.txt`、`chmod u+x,g-r t.txt`、`chmod =rx t.txt`、`chmod u=rx,go= t.txt`。对比数字与符号两种写法的结果，解释最后两条对「谁」的处理差别（省略 who 受 umask 影响，写全 `ugo` 才是精确赋值）。
3. umask 推算练习：先 `umask` 记下默认值，用公式算出新文件与新目录的权限，再用 `(umask 077; touch /tmp/p6/secret; mkdir /tmp/p6/priv; ls -l /tmp/p6/secret /tmp/p6/priv)` 验证；最后 `chmod u+s /tmp/p6/secret; ls -l /tmp/p6/secret` 观察无 x 时的 `S` 显示。
4. ACL 观察：先 `setfacl -m u:nobody:r /tmp/p6/t.txt` 造一个 ACL 条目，再用 `ls -l` 观察权限位后的 `+`，解释它意味着什么（衔接第 7 章）；若用 `find /etc /usr -maxdepth 3 2>/dev/null` 配合 `ls -l` 找不到带 `+` 的文件，说明系统中无 ACL 条目。ACL 的完整实验在第 7 章练习。
5. 巡检与改归属体验：`find /usr/bin -maxdepth 1 -perm -4000` 列出 SUID 程序，用 `stat -c '%A %U %G %n' /usr/bin/su /usr/bin/wall /tmp` 对照 SUID、SGID（`wall` 属组 tty）与 Sticky 三种显示；先 `sudo chown :$(id -gn) t.txt`，再用 `sudo chown $(id -un):$(id -gn) t.txt` 还原，体会改归属需要特权。
