# 第 8 章 用户与用户组

多用户是 Linux 的出厂设定：账号决定你是谁，组决定你和谁共享资源，配置文件是这套体系的账本，`sudo` 是受控的越权通道。本章把三本账（`passwd/shadow/group`）、账号增删改的命令族、`su/sudo` 的原理、密码策略与 PAM 讲透——这是全书用户管理的权威侧，后面的 Arch 环境章只讲差异。

> 本章目标：能逐字段读懂 `/etc/passwd`、`/etc/shadow`、`/etc/group` 与 `getent` 输出；会用 `useradd/usermod/userdel/groupadd` 管理账号并避开 `-a`、`-r` 这类一键事故；能区分 `su` 与 `sudo` 的验证与授权原理，会用 `visudo`、`sudo -l` 查看与编辑策略；会用 `passwd -S`/`chage` 管理密码老化；能读懂 `/etc/pam.d` 服务文件的四类栈与控制位。
> 对应 Wiki：[Users and groups](https://wiki.archlinux.org/title/Users_and_groups)、[Sudo](https://wiki.archlinux.org/title/Sudo)、[PAM](https://wiki.archlinux.org/title/PAM)

## 三本账：passwd、shadow、group

系统判断「你是谁、属于谁」靠三份纯文本账本，`getent` 是读取它们的统一入口（实跑）：

```text
$ getent passwd arch
arch:x:1000:1000::/home/arch:/usr/bin/zsh
$ getent group wheel
wheel:x:998:arch
```

**`/etc/passwd` 七字段**：`名 : x : UID : GID : 备注(GECOS) : 家目录 : 登录 shell`。三个要点：密码位是 `x`，真正的口令在 shadow；**UID 才是用户的身份编号**，判定 root 看的是 UID 0 而不是名字；系统服务账号（`bin`、`http`、`nobody`…）的 shell 多是 `/usr/bin/nologin`，只能被程序使用、不能登录。GID 是该用户的**主组**——Arch 默认「私有组模型」，建用户时会同步建一个同名组。

**`/etc/shadow` 九字段**：`名 : 加密口令 : 上次改密 : 最短间隔 : 最长寿命 : 警告天数 : 停用天数 : 过期日 : 保留`。实跑 root 行（口令截断）：`root:$y$…:20486::::::`——`$y$` 是 yescrypt 哈希（含随机盐；算法因发行版而异，如 `$6$` 是 SHA-512，由 `/etc/login.defs` 的 `ENCRYPT_METHOD` 决定），`20486` 是距 1970-01-01 的改密天数。口令位以 `!` 或 `*` 开头表示该账号**无可用密码**（实测服务账号 `alpm:!*:` 即被锁死）。这本账普通用户根本读不到：实跑 `cat /etc/shadow` 直接 Permission denied——但 `passwd -S arch` 能查到自己的状态，为什么？因为 `passwd` 带 SUID，执行时是 root 身份（第 6 章的机制在这里派上用场）。

**`/etc/group` 四字段**：`组名 : x : GID : 成员表`。成员表列的是**补充组**成员（主组由 `passwd` 的 GID 字段决定）；`wheel:x:998:arch` 说明 arch 是 wheel 组成员——第 6 章的 `chgrp wheel` 能成功、`chgrp root` 被拒，答案就在这里。`getent group` 可以同样查另外两本账（`getent shadow` 需要 root 权限）；`getent` 走的是系统账号接口（`/etc/nsswitch.conf` 配置），本地文件之外的 LDAP 等目录服务也能查到。

## 命令行视角：id、whoami 与 groups

把自己翻译成数字与组列表（实跑）：

```text
$ id
uid=1000(arch) gid=1000(arch) groups=1000(arch),998(wheel),1001(docker)
$ whoami
arch
```

`id` 一次给出主 UID、主 GID 与全部补充组；`id -u`/`id -g` 只输出数字，`id -Gn` 输出组名列表（`arch wheel docker`）。`whoami` 就是 `id -un` 的简写——提示符里的用户名、`ls -l` 的属主列、进程的 Uid，最终都对到这套数字上。

## 账号的增删改：useradd、usermod、userdel

命令族的分工：`useradd`/`userdel` 建删账号，`groupadd`/`groupdel` 建删组，`usermod` 改既有账号。`useradd` 的常用选项（以 `--help` 实测为准）：`-m` 建家目录、`-s` 指定 shell、`-G` 加补充组、`-g` 指定主组、`-c` 备注、`-d` 指定家目录路径、`-D` 查看/改新建账号的默认值。完整生命周期实跑（需 sudo，临时用户演练）：

```bash
sudo useradd -m -s /bin/bash lab8user
sudo passwd lab8user # 跳过 passwd 才会留下锁定口令（!），此时 su/sudo 认证失败
getent passwd lab8user # lab8user:x:1001:1002::/home/lab8user:/bin/bash
sudo groupadd lab8grp
sudo usermod -aG lab8grp lab8user
id lab8user # groups=1002(lab8user),1003(lab8grp)
sudo usermod -l lab8new lab8user # 只改登录名：家目录与组名不变；移动家目录用 usermod -d /新路径 -m
sudo userdel -r lab8new # -r 一并删除家目录与邮件池
sudo groupdel lab8grp
```

`usermod` 的三个高频点：`-aG` 的 **`a`（append）不能少**——实测 `usermod -G wheel lab8user`（无 `-a`）会把补充组列表**整个替换**成 wheel，原有组全部丢失；`-L`/`-U` 锁定/解锁账号（shadow 口令前加 `!`）；`-s` 改登录 shell，效果上与普通用户自己跑 `chsh` 相同。改主组与家目录用 `-g`/`-d`，动已有账号的 UID、家目录属于高危操作。组管理的三个常用件：`groupmod -n 新名 旧名` 改组名、`gpasswd -a/-d 用户 组` 增删组成员、`newgrp 组` 临时切换有效组；新用户骨架在 `/etc/skel`（`useradd -m` 时复制进家目录），新建默认值在 `/etc/default/useradd`。

> **危险**：`userdel -r` 连同家目录整体删除，没有回收站；`usermod -G`（不带 `-a`）会清空目标用户的补充组——若对自己的账号执行，可能瞬间丢掉 `wheel` 组而失去 `sudo`。一切演练只用临时用户，做完 `userdel -r` 清场，并用 `getent passwd 用户名` 确认已消失。

## su 与 sudo：切换身份的两种原理

| | `su - 目标用户` | `sudo 命令` |
| ------------ | ------------------------------------------------ | ---------------------------------- |
| 验证谁的密码 | **目标用户**的（实测连 `su` 到自己都会先问密码） | **自己**的，按 `/etc/sudoers` 放行 |
| 授权粒度 | 拿到目标的全部身份 | 按命令、按可伪装的用户细化 |
| 留痕 | PAM/wtmp 记成功登录（`last`）；失败登录在 btmp（`lastb`，通常需 root） | journal 另记每次执行的命令 |

`su` 是「换人」：`su -` 等价 `su --login`（官方帮助原话 "A mere - implies -l"），会清环境、切到目标家目录、按登录 shell 重走启动文件（第 10 章）；不带 `-` 的 `su` 只做最小重置——`HOME`、`SHELL` 会切到目标用户（目标非 root 时 `USER`/`LOGNAME` 也一并改），其余变量大多保留，容易留下身份混淆的隐患；`su -m`（`--preserve-environment`）才真正保留整个环境，风险更高。向 root 提权时 `su -` 意味着**共享 root 密钥**——谁拿到谁就是 root，这正是 sudo 被发明的原因。

`sudo` 是「按条目放行的代理执行」：验证的是**你自己的**密码，能否执行、能以谁的身份执行，全部由 `/etc/sudoers` 说了算。默认模板里的授权行长这样（Arch 出厂时两行均被注释）：

```text
%wheel ALL=(ALL:ALL) ALL # wheel 组：任意命令，以任意用户:组身份，需输自己密码
%wheel ALL=(ALL:ALL) NOPASSWD: ALL # 同上但免密
```

解码规则：`%` 前缀 = 组；第一段 `ALL` = 来源主机；括号 = 以谁的身份（默认 root）；最后 = 允许的命令。本机两行都被启用（`sudo -l` 实测输出 `(ALL : ALL) ALL` 与 `NOPASSWD: ALL`），所以 wheel 组成员免密——这是个人实验机的 `NOPASSWD: ALL`，属第 9 章点名的高危形态，生产环境不要用；Arch 出厂两行均被注释。三个日常工具：`sudo -l` 列出自己的授权；`sudo -k` 作废免密缓存；`visudo` 是唯一正确的编辑入口——它带并发锁与语法检查，**语法错误不会被写入**（实测 `sudo visudo -c` 输出 `/etc/sudoers: parsed OK`）。sudoers 的完整语法、drop-in 文件与最小授权实践见第 9 章。

> **危险**：不要直接 `vim /etc/sudoers`——改坏一个字，系统上所有 `sudo` 立刻失灵——靠已登录的 root 会话或 `su -` 兜底。改之前先开一个保持登录的会话（或 root 终端）别关，改完立刻 `sudo visudo -c` 验证。

sudo 的每次执行都会进审计日志（`journalctl` 需要 systemd 为 PID 1，未以 systemd 启动时先按第 37 章验收），实跑可见 PAM 会话记录：`journalctl -t sudo -n 5` 显示 `pam_unix(sudo:session): session opened for user root(uid=0) by (uid=1000)`。另一个伏笔：`sudo -l` 的输出里有 `secure_path=…`——sudo 执行命令时会**重置成固定的 PATH**，第 10 章排查「sudo 里找不到刚装的命令」时会用到。

## 密码策略与账号老化

口令的时效信息全部存于 shadow 第 4-8 字段，查看与修改各有一套（实跑）：

```text
$ passwd -S arch
arch P 2026-02-02 -1 99999 7 -1
$ chage -l arch
Last password change : Feb 02, 2026
Password expires : Nov 17, 2299
Maximum number of days between password change : 99999
Number of days of warning before password expires : 7
```

`passwd -S` 第二字段的状态码：`P` 可用、`L` 已锁定、`NP` 无密码（实测锁定的服务账号 alpm 输出 `L`）；查**别人的**状态会被拒绝（实测报 "You may not view or modify password information"），要看就加 `sudo`。改自己的密码用 `passwd`，交互输入两次。

`chage` 管老化（选项以 `--help` 实测为准）：`-M` 最长寿命、`-m` 最短间隔、`-W` 过期警告天数、`-I` 过期后停用天数、`-E` 账号过期日（格式 `YYYY-MM-DD`）。多数发行版出厂**不强制过期**——新建账号的默认值在 `/etc/login.defs` 的 `PASS_MAX_DAYS` 等条目里配置，未配置时用工具内置默认（实测本机 chage -l：max 99999 天、警告 7 天，即密码永不过期）；企业策略则常由 PAM 统一下发。`usermod -L` 能在不动口令的情况下冻结账号（shadow 里原口令前加 `!`）。

## PAM：认证的插件化中枢（深讲）

登录、`su`、`sudo`、`passwd`、SSH 都要回答同一个问题「怎么证明你是你」。Linux 把答案做成可插拔模块，按**服务**分文件放在 `/etc/pam.d/`（实测有 `login`、`su`、`sudo`、`sshd`、`passwd` 等）——换验证方式只改配置，不动程序。每个文件就是一叠规则，每行 `类型 控制位 模块 [参数]`，四类栈各管一段：

| 类型 | 回答什么 | 常见模块 |
| ---------- | ----------------------------------- | ------------------------------ |
| `auth` | 这次请求者是不是本人（验密码） | `pam_unix.so`、`pam_wheel.so` |
| `account` | 这个账号本身可用吗（过期、时段） | `pam_unix.so`、`pam_time.so` |
| `password` | 修改口令时执行什么策略 | `pam_unix.so shadow` |
| `session` | 会话开通/关闭时做什么（限额、记录） | `pam_limits.so`、`pam_unix.so` |

实跑读 `/etc/pam.d/su`（节选）：

```text
auth sufficient pam_rootok.so # root 直接放行，不问密码
#auth required pam_wheel.so use_uid # 默认注释：取消注释 = 仅 wheel 组可 su
auth required pam_unix.so # 核对 /etc/shadow 里的口令
account required pam_unix.so
session required pam_limits.so # 应用 /etc/security/limits.conf 资源限额
password include system-auth # include：整段复用共享栈
```

控制位读法：`required` 必须成功（失败则本次认证最终失败）；`sufficient` 成功即放行、失败则继续往下走；`include` 把另一个文件整段拉进来——Arch 用 `system-auth` 汇总 `pam_unix`、`pam_faillock`（连续失败锁定）、`pam_env`、`pam_limits` 等公共模块，一处修改全站生效。这也解释了本章开头的伏笔：`passwd -S` 能读到 shadow，是因为 SUID 让它以 root 身份打开文件；而真正修改口令时的校验、锁定与老化策略，才由 PAM 各栈接手。

> **危险**：PAM 规则按顺序执行，写错 `auth` 行可能让 `su`、`sudo` 甚至登录全体失效。修改 `/etc/pam.d/` 前先 `cp` 备份、**保留一个已登录的会话不要退出**，改完用新会话验证能登录再收工。

## 更远的认证版图（精讲）

单机密码之外，认证世界还有这些方向，先认识入口、需要时再深挖：

| 方向 | Wiki 页面 | 一句话 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 全景总览 | [Identity management](https://wiki.archlinux.org/title/Identity_management) | 账号从单机到企业的地图 |
| 目录与单点登录 | [Kerberos](https://wiki.archlinux.org/title/Kerberos)、[LDAP authentication](https://wiki.archlinux.org/title/LDAP_authentication)、[SSSD](https://wiki.archlinux.org/title/SSSD)、[Keycloak](https://wiki.archlinux.org/title/Keycloak) | 集中存账号、一处登录处处通行 |
| 第二因子 | [Google Authenticator](https://wiki.archlinux.org/title/Google_Authenticator)、[Pam oath](https://wiki.archlinux.org/title/Pam_oath)、[WebAuthn](https://wiki.archlinux.org/title/WebAuthn) | 密码之外再要一次验证（经 PAM 接入） |
| 硬件令牌 | [OpenPGP](https://wiki.archlinux.org/title/OpenPGP)、[Smartcards](https://wiki.archlinux.org/title/Smartcards) | 智能卡、U 盾当钥匙 |
| 本地增强 | [Howdy](https://wiki.archlinux.org/title/Howdy)、[Vault](https://wiki.archlinux.org/title/Vault) | 人脸解锁、本地密钥保管 |

`sudo` 之外还有两个近亲值得一词：[Doas](https://wiki.archlinux.org/title/Doas) 是 OpenBSD 出品的极简替代品；[Polkit](https://wiki.archlinux.org/title/Polkit) 则是图形环境与桌面程序的授权框架（点「输密码」弹窗背后就是它），两者本书不展开，需要时见各自 Wiki。

### 认证技术图谱的补充

上面的表按「方向」分组，这里补三块容易在清单里出现、但不必逐项展开的内容：

**PAM 模块族**（都是把某种能力接进 PAM 栈，不是独立认证协议）：`pam_unix` 本地密码；`pam_faillock` 失败次数锁定；`pam_limits` 读取 `/etc/security/limits.conf`；`pam_mount` 登录时挂载；`pam_usb`、`pam_oath` 硬件/OTP；`pam_abl` 按失败行为封禁；`pam_autologin` 自动登录。配置入口在 `/etc/pam.d/`，改错会直接影响登录，务必保留一个已登录的 root 会话或救援环境。

**身份管理平台**：FreeIPA / Jans 提供「目录 + Kerberos + 证书」的一体化身份；Keycloak 偏 OIDC/SAML 单点登录；Vault 管密钥与短期凭据；SSSD 负责把 LDAP/Kerberos 接到本机 NSS/PAM。它们适合多机、多服务的统一账号，不适合单机桌面。

**硬件与生物识别**：OpenPGP card、PIV/智能卡、Mooltipass、WebAuthn 安全密钥、Howdy 人脸、各国 eID（如 Romanian eID）都属于「第二因子或免密码」路线；接入方式仍是 PAM 或应用层 WebAuthn，选型先看设备生态与恢复手段。

**资源限制**：`limits.conf` 通过 `pam_limits` 生效，限制的是登录会话能拿到的资源（进程数、打开文件数、内存锁定量），不是文件权限。验证用 `ulimit -a`，改完重新登录才生效。

**最小实验（以只读观察为主）**：

```bash
ls /etc/pam.d | head                    # 本机启用的 PAM 服务栈
grep -R 'pam_faillock' /etc/pam.d 2>/dev/null   # 是否启用失败锁定
ulimit -a                               # 当前会话的资源限制
sudo faillock --user "$USER"            # 失败计数（需 root；无记录时输出为空）
```

**失败模式**：改 `/etc/pam.d/` 前先 `cp -a /etc/pam.d /etc/pam.d.bak`，并保留一个已登录的 root 会话或救援环境——模块名拼错就可能让所有登录失败，回滚就是从救援环境恢复备份；`limits.conf` 只对经过 PAM 的登录会话生效，systemd 服务要在单元里写 `LimitNOFILE=` 之类；`pam_faillock` 的计数文件在 `/var/run/faillock`，重启会清空，排查锁定问题时先看这里。

**取舍与风险**：单机用本地密码 + `sudo` 足够；多机再上 LDAP/SSSD；高价值账户再加第二因子。任何 PAM/身份改造都要先准备「救援登录路径」，并用一个测试账户验证，再推广到管理账户。

## 小结

- 三本账：`passwd` 七字段（身份与 shell，UID 0 = root）、`shadow` 九字段（口令与老化，`!`/`*` = 无可用密码）、`group` 四字段（补充组成员表）；`getent` 是统一读取口。
- `id`/`whoami` 把当前身份翻译成 UID 与组；`chgrp` 能否成功，取决于你是否在目标组里。
- `useradd -m -s -G`、`usermod -aG`（`a` 不能少）、`userdel -r`（删家目录）——增删改只对临时用户演练。
- `su -` 换人并验证目标密码、共享全部身份；`sudo` 验证自己、按 `/etc/sudoers` 细粒度放行并留审计日志；`visudo` 是唯一编辑入口。
- 密码状态看 `passwd -S`，老化用 `chage -M/-m/-W/-I/-E`；出厂默认不强制过期。
- PAM 在 `/etc/pam.d/` 按服务组织 auth/account/password/session 四类栈，`required/sufficient/include` 决定走向；改配置必须保留退路。

## 练习

1. 读三本账并逐字段标注：`getent passwd arch root nobody`、`getent group wheel`、`sudo head -1 /etc/shadow`。对照本章表格说出每个字段含义，指出哪个账号是 root、哪个不能登录。
2. 查自己的身份与密码状态：`id`、`id -Gn`、`whoami`、`passwd -S`、`chage -l`；再跑 `passwd -S root` 观察拒绝信息，解释为什么查别人要 `sudo`。
3. 临时用户完整生命周期（需 sudo）：

 ```bash
 sudo useradd -m -s /bin/bash lab7x
 getent passwd lab7x
 sudo groupadd lab8grp2 && sudo usermod -aG lab8grp2 lab7x
 id lab7x # 注意主组 + 补充组的组合
 sudo usermod -G wheel lab7x && id lab7x # 对比：不带 -a 其余组被清掉
 sudo usermod -l lab7x2 lab7x && sudo usermod -G lab8grp2 lab7x2
 sudo userdel -r lab7x2 && sudo groupdel lab8grp2
 getent passwd lab7x2 # 应无输出
 ```

4. sudo 策略只读巡检：`sudo -l` 列出自己的授权并解读 who / where / whom / commands 四段与可选标签；`sudo visudo -c` 确认语法完好；`journalctl -t sudo -n 5 --no-pager` 找到 `session opened for user root` 那行审计记录。
5. PAM 只读观察：`ls /etc/pam.d`，然后 `cat /etc/pam.d/su`，逐行标出四类栈、控制位与 `include`；在 `/etc/pam.d/sudo` 里找到 `auth include system-auth`，说明改 `system-auth` 一处会影响哪些服务。
