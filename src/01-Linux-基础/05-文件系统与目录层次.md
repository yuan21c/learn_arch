# 第 5 章 文件系统与目录层次

会用 `cd` 之后，下一个问题是「这棵树长什么样」：每个目录各管什么、空间被谁吃掉、一块磁盘如何出现在 `/mnt/usb` 这种路径上。本章按标准目录层次逐个看过去，学会用 `df/du` 盘点空间，理解 inode 这本账，最后把「挂载」讲到概念清楚——足够你读懂本机的目录树，细节留给第二篇。

> 本章目标：能按 FHS 说出主要顶层目录的职责；会用 `df/du`（含 `-i`）盘点空间与 inode；能解释 inode 与文件名、目录项、硬链接的关系；理解挂载的含义并能读懂本机的挂载表。
> 对应 Wiki：[File systems](https://wiki.archlinux.org/title/File_systems)

## 单一树：一切从根开始

Linux 没有盘符。所有存储——本地磁盘、U 盘、网络共享、内存文件系统——都被**挂**到以 `/` 为根的同一棵树上，路径从根写起。一块没挂载的文件系统不在目录树里，但设备本身仍在 `/dev` 可见（`lsblk` 也能列出），只是无法通过路径访问——这是理解后面一切路径问题的前提。

「一切皆文件」随之而来：程序和数据在磁盘上，设备在 `/dev`，运行中的进程在 `/proc`，内核状态在 `/sys`——观察它们用的是同一套 `ls/cat/stat`，不需要为每类东西学一套工具。

## 标准目录层次（FHS）逐个看

文件系统层次标准（FHS）约定顶层目录的职责，主流发行版都遵循它：

| 目录 | 职责 |
| --------------- | --------------------------------------------------------------------------------- |
| `/` | 树根，其下就是全部 |
| `/bin` `/sbin` | 基本命令（现代发行版多已并入 `/usr`，目标为 `/usr/bin` 或 `/usr/sbin`，视发行版） |
| `/boot` | 内核、initramfs、引导器文件 |
| `/dev` | 设备文件：磁盘、终端、空设备等 |
| `/etc` | 系统与程序的**配置文件**（只放配置，不放程序） |
| `/home` | 各普通用户的个人目录 |
| `/lib` `/lib64` | 共享库与内核模块（同样多已并入 `/usr/lib`） |
| `/media` | 可移动介质的自动挂载点 |
| `/mnt` | 手工临时挂载点 |
| `/opt` | 第三方大型软件的独立安装位 |
| `/proc` `/sys` | 内核导出的虚拟文件系统（不是磁盘内容） |
| `/root` | root 用户的家目录 |
| `/run` | 运行期数据：PID 文件、套接字、锁 |
| `/srv` | 对外提供服务的数据（网站、FTP 内容） |
| `/tmp` | 临时文件，重启可清 |
| `/usr` | 程序、库、文档的主要位置（`/usr/bin`、`/usr/lib`…） |
| `/var` | 会变的数据：日志、队列、缓存 |

判断「东西该放哪」的口诀：包管理器装的程序进 `/usr`，**自编译/自装的进 `/usr/local`**，第三方整套软件进 `/opt`；配置进 `/etc`，日志/状态/缓存进 `/var`（`log`/`lib`/`cache`/`tmp` 各有分工），临时文件进 `/tmp`，自己的文件进 `/home`。`/run`、`/dev/shm` 这类是 tmpfs——数据在内存里，重启即失。两处实跑验证：

```bash
ls -ld /bin /var/run
# lrwxrwxrwx ... /bin -> usr/bin （usr 合并：/bin 只是链接）
# lrwxrwxrwx ... /var/run -> ../run （运行数据统一放 /run）
cat /etc/os-release | head -2 # os-release 世界可读；并非所有 /etc 文件都可读（如 /etc/shadow，见第 6 章）
```

`/proc`、`/sys` 的内容由内核即时生成，第 12 章会把它们作为窗口使用；在那之前，记住它们「看起来像目录、其实是内核接口」。

## df 与 du：空间与 inode 盘点

两个工具、两个视角：`df`（disk free）按**已挂载的文件系统**汇总，回答「每个盘还剩多少」；`du` 按**目录树**逐层累加，回答「谁把目录吃空了」。实跑输出：

```text
$ df -h /
Filesystem Size Used Avail Use% Mounted on
/dev/sdd 1007G 21G 936G 3% /

$ df -i /
Filesystem Inodes IUsed IFree IUse% Mounted on
/dev/sdd 67108864 312805 66796059 1% /
```

注意 `1007G - 21G ≠ 936G`：差额是 ext4 为 root 保留的块（默认约 5%；XFS/Btrfs 等其他文件系统不一定有保留块），`df` 的 Avail 已把它们排除。`-h` 是人类可读单位，`-i` 换成 inode 视角——磁盘没满也可能 inode 先耗尽，那时新建文件会报 No space left on device。

`du` 的常用形态：`du -sh 目录` 只给总计，`du -h --max-depth=1 目录` 分一层展开，先 `df -h` 定位满的文件系统，再用 `du` 钻进去找大头。`df` 与 `du` 对不上是常事，两个典型原因：有文件已被删除但仍被进程持有（占空间、不出现在 `du` 里），以及两者统计的挂载点范围不同（`du -x` 可限制在同文件系统内）。

## inode：文件系统的账本

每个文件在文件系统里有一条 **inode** 记录：权限、属主、大小、三个时间戳、数据块指针——唯独**没有文件名**。文件名存在所在目录的「目录项」里，目录项只做一件事：名字 → inode 号的对应。实跑观察（/tmp 演练）：

```bash
mkdir -p /tmp/t5 && dd if=/dev/zero of=/tmp/t5/big bs=1M count=5 # 布场
stat -c '%n inode=%i links=%h' /tmp/t5/big
# /tmp/t5/big inode=<本机值> links=1
ls -i /tmp/t5/big
# inode=<本机值> /tmp/t5/big（示例值，以本机为准）
```

这个设计直接推出三件你已经见过的事：

- 同一文件系统内 `mv` 改名只改目录项，inode 与数据不动——所以改名瞬间完成；跨文件系统是「复制 + 删除」（第 3 章）。
- 两个目录项指向同一 inode 就是硬链接（第 3 章），链接数正是 inode 的「标签计数」。
- 目录本身也是文件，内容是一张条目表；条目不能像文本一样直接写入，只能用 `mkdir/unlink/rename` 这类操作增删——能否增删取决于对该目录的 `w` 与 `x` 权限；root 通常凭 CAP_DAC_OVERRIDE 绕过检查（只读挂载、`chattr +i` 等除外，见第 6 章）。

inode 用尽与磁盘写满表现相同（No space left on device），用 `df -i` 才能区分。

## 挂载概念预热

**挂载**就是把一个文件系统接到树上的某个目录（挂载点）：接上之后，该目录显示的内容就是那个文件系统的内容；卸载后目录恢复原样。新分区、U 盘、ISO 镜像、网络共享，进入这棵树的方式都是挂载——没有盘符，只有「接到哪个目录」。

不执行任何写操作也能读懂本机挂载表（实跑）：

```text
$ findmnt -T /
TARGET SOURCE FSTYPE OPTIONS
/ /dev/sdd ext4 rw,relatime,discard,errors=remount-ro,data=ordered

$ findmnt -T /tmp
TARGET SOURCE FSTYPE OPTIONS
/tmp tmpfs tmpfs rw,nosuid,nodev,inode64
```

`findmnt -T 路径` 反查「这个路径属于哪个文件系统」；`/proc/self/mounts` 是内核视角的完整挂载表。表里除了块设备上的文件系统，还有 `proc`、`sysfs`、`tmpfs` 这类由内核或内存生成的伪文件系统——它们不占磁盘，也不该被备份或格式化。至于挂载的另一半——`mount`/`umount` 命令、`/etc/fstab` 开机自动挂载、文件系统格式化与分区——全部留给第二篇第 18 章，那时你会有完整的动手链路。

## 其他文件系统速览（精讲）

ext4 是默认答案，但不是唯一答案。遇到新盘、闪存、备份盘或网络目录时，先看文件系统的定位：

| 文件系统 | 一句话定位 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| ext3 | ext4 的前身，向后兼容 | 老系统、老镜像 | 无 ext4 的延迟分配与校验特性 |
| F2FS | 面向闪存（NAND）设计，带垃圾回收 | eMMC、UFS、部分 SSD | 工具与恢复生态不如 ext4 |
| bcachefs | 新一代 CoW，校验、快照、压缩 | 想统一「校验 + 快照」的盘 | 内核 6.7 起合入（实验性），`bcachefs-tools` 在官方仓库；生产使用前按当前内核与工具版本核实 |
| NILFS2 | 日志结构，连续快照 | 需要频繁快照的备份盘 | 生态小，修复工具少 |
| JFS | 老牌日志文件系统，轻量 | 兼容旧系统 | 已不再是主流选择 |
| autofs | 按需自动挂载 | 网络共享、可移动介质 | 需要配置映射，排障链路更长 |
| davfs2 | 把 WebDAV 挂成本地目录 | 网盘、远程文档 | 用户态实现，性能与离线行为受限 |
| BeeGFS | 并行分布式文件系统 | HPC、多节点共享 | 部署与运维成本高 |

**扩展属性（xattr）**：ACL、SELinux 标签、文件能力都存放在扩展属性里，不是文件名或权限位的一部分。查看用 `getfattr -d 文件`（`attr` 包）；复制时要保留 xattr，否则 ACL/能力会丢，`cp -a` 与 `rsync -X` 才会带上。

**常见失败**：`mkfs.f2fs: command not found` 说明 `f2fs-tools` 未安装；`mount: unknown filesystem type` 说明内核未带该驱动；`mount: wrong fs type` 多半是 `-o loop` 拼错或镜像根本没格式化。先用 `lsblk -f` 与 `findmnt -T` 确认对象，再重建镜像——不要在真盘上靠试错确认参数。

**验证方式（不碰真实数据）**：用回环文件演练新文件系统，避免在真盘上格式化：

```bash
truncate -s 512M /tmp/fstest.img
mkfs.f2fs /tmp/fstest.img          # 工具属于 f2fs-tools；未安装时先查仓库
mkdir -p /tmp/fstest && sudo mount -o loop /tmp/fstest.img /tmp/fstest
findmnt -T /tmp/fstest
sudo umount /tmp/fstest && rm -f /tmp/fstest.img
```

**取舍边界**：默认装 ext4；闪存设备可评估 F2FS；需要快照与校验再评估 bcachefs，但先确认你的内核与工具版本支持，并在测试盘上验证恢复流程。任何新文件系统，先问「坏了怎么修、数据怎么取回」，再问性能。

## 小结

- 一棵以 `/` 为根的树容纳一切存储；磁盘只有挂载后才在树上存在。
- FHS 规定顶层目录职责：`/usr` 放程序、`/etc` 放配置、`/var` 放变化的数据、`/tmp` 放临时文件；`/bin`、`/var/run` 这类路径常是符号链接。
- `df` 看文件系统整体（含 inode），`du` 看目录明细；`Avail` 与 `Size - Used` 的差是保留块。
- inode 存元数据不存文件名；文件名是目录里的标签——改名、硬链接、链接数都由此解释。
- 挂载把文件系统接到目录树；`findmnt -T` 与 `/proc/self/mounts` 是只读观察入口。

本篇接下来的第 6、7 章讲权限、第 8 章讲用户与组、第 10 章讲环境变量，第 11 章会做一个把它们与本章目录知识串起来的综合实验；而挂载、`fstab` 与文件系统管理的完整内容在第二篇第 18 章展开——树的形状你已经知道了，接下来给树上的文件加上规则。

## 练习

1. 运行 `ls /`，对照本章的表标出每个顶层目录的职责；再 `ls -ld /bin /sbin /lib /var/run` 验证哪些是符号链接。
2. 运行 `df -h /` 与 `df -i /`，记下容量、已用百分比与 inode 使用率，解释 `Size - Used` 为什么大于 `Avail`。
3. 造一个大文件并用 `du` 定位它：

 ```bash
 mkdir -p /tmp/t5 && dd if=/dev/zero of=/tmp/t5/big bs=1M count=5
 du -h --max-depth=1 /tmp/t5
 stat -c '%n inode=%i links=%h' /tmp/t5/big
 ```

4. 用 `findmnt -T /`、`findmnt -T /tmp` 与 `head -3 /proc/self/mounts` 三处交叉验证，说出根文件系统与 tmpfs 的类型分别是什么。
5. 在 `/tmp/t5` 里给 `big` 建一个硬链接与一个符号链接，用 `ls -li` 观察 inode 与链接数，对照本章「目录项 → inode」的模型解释结果。
