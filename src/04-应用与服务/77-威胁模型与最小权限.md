# 第 77 章 威胁模型与最小权限

第 76 章给的是「基线加固清单」；这一章讲「为什么这些项值得做、先做哪一项」。方法是威胁模型：先列资产与对手，再算攻击面与影响，最后才谈控制措施。没有威胁模型的加固，容易把时间花在低风险项上，却漏掉真正会出事的入口。

> 本章目标：能用「资产—对手—攻击面—影响」四步写出一个可执行的威胁模型；会用 STRIDE 给威胁分类；能盘点到监听端口、启用服务、SUID 文件、capabilities 四类攻击面；理解 capabilities、专用用户、sudo 规则三种最小权限手段；知道会话锁、x11vnc、微码、PRoot 各自的安全含义；能识别「模型太大无法落地」「把 PRoot 当沙箱」两类问题。
> 对应 Wiki：[Security](https://wiki.archlinux.org/title/Security)、[Microcode](https://wiki.archlinux.org/title/Microcode)、[PRoot](https://wiki.archlinux.org/title/PRoot)、[X11vnc](https://wiki.archlinux.org/title/X11vnc)

## 威胁模型四步

不要从「有哪些加固项」开始，从「什么东西值得保护」开始：

| 步骤 | 要回答的问题 | 输出 |
| ------------ | ------------------------------------ | -------------------------------------- |
| 资产 | 丢了什么最痛：数据、密钥、身份、可用性 | 3–5 项，按影响排序 |
| 对手 | 谁会来：脚本小子、同网段用户、内部误操作、供应链 | 每类对手的能力与动机 |
| 攻击面 | 从哪进：端口、服务、账号、USB、浏览器、依赖 | 可枚举的入口清单 |
| 影响 | 成功一次会怎样：泄露、篡改、勒索、停机 | 可能性 × 影响，决定优先级 |

个人工作站的一个小模型：资产是 SSH 私钥、浏览器会话、代码仓库；对手是「拿到同网段的人」与「恶意依赖包」；攻击面是公网暴露的端口、过宽的 sudo、未锁屏的会话；影响最高的是私钥泄露。这个模型会直接把优先级指向「收窄端口 + 收紧 sudo + 自动锁屏」，而不是先去调内核参数。

**STRIDE** 是给威胁分类的检查表：伪造（Spoofing）、篡改（Tampering）、否认（Repudiation）、信息泄露（Information disclosure）、拒绝服务（DoS）、提权（Elevation of privilege）。逐项问「这条攻击面对应哪一类」，比泛泛写「加强安全」有用。

## 攻击面盘点

四条只读命令就能画出大部分入口：

```bash
ss -tulpn
systemctl list-unit-files --state=enabled
sudo find / -xdev -perm -4000 -type f 2>/dev/null
sudo getcap -r / 2>/dev/null
```

- **监听端口**：`0.0.0.0`/`[::]` 是对全网，`127.0.0.1`/`[::1]` 是仅本机；先区分，再决定是否要防火墙。
- **启用服务**：每个 `enabled` 都是一段长期运行的代码；不用的服务 `disable --now`，比事后加固便宜。
- **SUID 文件**：任何 SUID root 程序都是提权面；对照包管理器确认归属，陌生 SUID 要查来源。
- **capabilities**：比 SUID 细，但仍要逐条看；`getcap -r /` 输出为空是好事，不代表系统没有特权程序（root 服务仍以 root 跑）。

盘点结果要落到「保留 / 收窄 / 移除」三列，并写上与业务的关系；只列不管的清单没有意义。

## 最小权限的三种手段

**1）专用用户与服务账号**：应用不要以 root 跑，也不要复用你的登录用户。系统级服务用 `User=`/`Group=` 指定专用账号，数据目录只给该账号读写（第 63 章）。

**2）capabilities 代替 root**：需要绑低端口、发原始包时，只给对应能力：

```bash
sudo setcap cap_net_bind_service+ep /usr/local/bin/myserver
getcap /usr/local/bin/myserver
```

`getcap` 的输出就是「文件 + 能力 + 生效位」，例如 `cap_net_raw=ep`；要核对当前进程的能力，另用 `capsh --print`。

`cap_net_bind_service` 允许监听 1024 以下端口，不再需要整段 root。能力是「进程级」的，二进制被替换后要重新设置；升级脚本要记得保留或重设。

**3）sudo 规则收窄**：`sudoers` 里避免 `ALL=(ALL) NOPASSWD: ALL`；按命令、按参数、按用户授权，并用 `sudo -l -U 用户` 复核实际权限。`NOPASSWD` 只给「必须无人值守」的具体命令。

**4）会话与远程屏幕**：本地会话要能自动锁：

```bash
loginctl lock-session
loginctl list-sessions
loginctl show-session "$XDG_SESSION_ID" -p LockedHint
```

桌面环境另有自己的锁屏（swaylock、hyprlock 等），`loginctl` 是统一入口。**x11vnc** 把整个 X 会话暴露给远程：必须用 `-localhost` 只监听回环，再通过 SSH 隧道访问，并设置 `-rfbauth` 密码文件；它不会替你锁屏，配置不当等于多开一个远程操作入口。

## 微码与 PRoot 的安全含义

**微码（microcode）**：CPU 的部分漏洞靠微码更新缓解。安装 `intel-ucode` 或 `amd-ucode`，让 mkinitcpio 打进 initramfs（早期加载），重启后用内核日志验证：

```bash
pacman -Qs ucode
sudo journalctl -k -b | grep -i microcode
```

看到 `microcode: updated early` 之类的行，说明早期加载生效。微码更新通常不可回滚，升级前保留一个可启动的旧内核/initramfs 作为退路。

**PRoot**：用 ptrace 拦截系统调用、在用户态模拟 `chroot`/`bind`，不需要 root，常用于在受限环境里跑别的发行版 rootfs：

```bash
# proot 在 AUR（官方仓库未收录），安装前确认维护者与来源
proot -r /tmp/rootfs -0 -b /proc -b /dev -w / /bin/sh
```

`-0` 是「假 root」，`-b` 绑定目录。它**不是安全边界**：内核没有隔离，进程仍共享宿主内核与 UID 映射；只适合构建、兼容性测试，不能用来运行不可信程序。需要隔离时用容器（第 71 章）或 VM（第 74 章）。

## 失败模式

- **威胁模型太大**：写成「防止所有黑客」，没有资产、对手与优先级，最后无法落地。控制在一页、3–5 个资产。
- **只做清单不做决策**：端口、服务、SUID 列了一堆，没有「保留/收窄/移除」的结论，下次盘点还是原样。
- **SUID 遗留**：老工具装完留下 SUID root，没人认领；按包归属排查，陌生项先禁用再调查。
- **能力给多了**：为了省事给 `cap_sys_admin`，等价于半个 root；只给业务必需的最小能力。
- **`NOPASSWD` 通配**：`ALL` 或带通配符的命令让提权面失控；按具体命令授权。
- **锁屏不自动**：只手动锁，离开工位就裸奔；配置空闲自动锁并验证 `LockedHint`。
- **x11vnc 无认证/监听全网**：等于把桌面交给同网段；必须 `-localhost` + 密码 + SSH 隧道。
- **微码没加载**：`journalctl -k` 里没有任何 microcode 行，却以为已经更新；装包不等于生效。
- **把 PRoot 当沙箱**：用它跑不可信程序，内核漏洞照样穿透；PRoot 只解决路径与 rootfs 兼容。
- **模型不更新**：系统加了新服务、新端口，威胁模型还是去年的；变更时同步更新并定期复盘。

## 验证与回滚

最小权限的验证是「改前能做什么、改后还能做什么」：

```bash
sudo -l
getcap -r / 2>/dev/null
ss -tulpn
systemctl list-unit-files --state=enabled
loginctl show-session "$XDG_SESSION_ID" -p LockedHint
```

- **能力回滚**：`sudo setcap -r /usr/local/bin/myserver` 移除能力；若程序因此不能绑低端口，改用反代或调整端口。
- **SUID 回滚**：确认归属后用 `pacman -S <包>` 重装恢复原始权限，不要手工 `chmod +s` 猜。
- **服务收窄回滚**：`systemctl enable --now <服务>` 恢复；改 `User=` 前备份 unit，按第 63 章的 drop-in 回滚。
- **锁屏/x11vnc 回滚**：停掉 x11vnc 服务并移除自启；锁屏配置改回原值。
- **微码回滚**：微码本身通常不可回退；保留旧内核与旧 initramfs，出问题时从引导菜单回退。

每次变更都记录「改了什么、为什么、如何验证、如何回滚」；没有回滚路径的权限变更不要做。

## 取舍边界

- **最小权限 vs 可用性**：权限收得越紧，配置与排障越麻烦；按资产价值决定强度，个人实验机不必照搬生产基线。
- **capabilities vs root vs sudo**：长期服务用专用用户 + 最小能力；交互式运维用 sudo 具体命令；不要为了省事让服务以 root 跑。
- **SUID vs capabilities**：SUID 兼容老程序但权限粗；capabilities 更细但要求文件系统支持与升级维护。
- **锁屏 vs 远程访问**：自动锁屏是基线；远程屏幕共享必须叠加认证、加密与来源限制，不能以「反正有锁屏」为由放松。
- **x11vnc vs SSH 转发 vs 其他远程桌面**：x11vnc 简单但暴露整个会话；SSH X11 转发只传单个客户端；需要完整桌面时选带认证与加密的方案。
- **微码：安全 vs 稳定性**：微码修复漏洞，也可能带来性能变化或极少数兼容问题；安全优先，但保留回退内核。
- **PRoot vs 容器 vs VM**：PRoot 只做 rootfs 兼容；容器提供命名空间隔离；VM 提供内核级隔离。按「是否运行不可信代码」选。

## 小结

- 威胁模型四步：资产、对手、攻击面、影响；STRIDE 用来给威胁分类。
- 攻击面盘点看四样：监听端口、启用服务、SUID、capabilities；盘点后要有「保留/收窄/移除」结论。
- 最小权限三手段：专用用户、capabilities、收窄 sudo；会话锁与远程屏幕是同一问题的两面。
- 微码要确认「早期加载」生效，而不只是装了包；微码通常不可回滚。
- PRoot 是 rootfs 兼容工具，不是安全边界；不可信代码用容器或 VM。
- 每次权限变更都要有验证方法与回滚路径。

## 练习

1. 四步模型：为你的工作站写一页威胁模型（3 个资产、2 类对手、攻击面清单、影响排序），给出前三项行动。
2. 攻击面盘点：跑正文四条只读命令，把结果分成「保留/收窄/移除」，至少写一条具体动作。
3. 能力实验：复制一个二进制到 `/tmp`，`setcap cap_net_raw+ep` 后以普通用户运行，再 `setcap -r` 移除；解释为什么这比 SUID 更细。
4. sudo 审计：`sudo -l` 列出你的授权，找出任何 `NOPASSWD` 或通配符，写出收窄后的规则（不实际改）。
5. 锁屏验证：`loginctl lock-session` 后查 `LockedHint`，再配置空闲自动锁；说明 x11vnc 为什么必须 `-localhost`。
6. 微码检查：`journalctl -k -b | grep -i microcode`，判断是否早期加载；没有输出时写出排查顺序。
7. PRoot 边界：若已从 AUR 安装 proot，用一个 rootfs 跑 `proot -r … -0 /bin/sh`，在容器内执行 `uname -a`，说明它为什么仍共享宿主内核。
