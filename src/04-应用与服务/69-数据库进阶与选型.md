# 第 69 章 数据库进阶与选型

第 67、68 章把 MariaDB 与 PostgreSQL 跑了起来。这一章不再教某一个数据库的命令，而是回答「该用哪一类」：从嵌入式到缓存、文档、宽列、搜索与时序，每一类都有明确的擅长与不擅长。选错类型的代价，通常不是性能差一点，而是数据模型与一致性语义从第一天就拧着来。

> 本章目标：能用「数据模型、一致性、读写比、规模、运维成本」五个问题筛掉不合适的数据库；能说清关系型、键值缓存、文档、宽列、搜索、时序、嵌入式六类的边界；会用 SQLite 完成建库、WAL、在线备份与完整性校验；知道客户端（DBeaver、ODBC）与 Java 测试库（H2）的定位；能识别「拿缓存当主库」「拿搜索库当主库」两类高风险用法。
> 对应 Wiki：[SQLite](https://wiki.archlinux.org/title/SQLite)、[Valkey](https://wiki.archlinux.org/title/Valkey)、[Memcached](https://wiki.archlinux.org/title/Memcached)、[Open Database Connectivity](https://wiki.archlinux.org/title/Open_Database_Connectivity)、[Elasticsearch](https://wiki.archlinux.org/title/Elasticsearch)

## 选型先问五个问题

不要从「哪个数据库最流行」开始，从数据与访问方式开始：

| 问题 | 影响 | 典型答案 |
| ---------------------- | ---------------------------------------- | ------------------------------------------ |
| 数据是什么形状 | 强结构表格 vs 松散文档 vs 键值 vs 时序点 | 结构化 → 关系型；半结构 → 文档；时序 → 时序库 |
| 需要什么一致性 | 强事务 vs 最终一致 vs 只读缓存 | 钱与订单 → 关系型强事务；计数/Feed → 最终一致 |
| 读写比例与延迟 | 写多 vs 读多，毫秒级 vs 秒级可接受 | 读多 → 缓存/搜索；写多 → 宽列/时序 |
| 规模上限 | 单机 GB vs 集群 TB/PB | 单机装得下就别上分布式 |
| 谁来运维 | 有专职 DBA vs 一个人兼 | 没人运维 → 托管或嵌入式，越简单越好 |

五个问题里只要有一个答案指向「强事务 + 关系查询」，就先用第 67/68 章的关系型数据库；多数业务在 GB 级根本用不到分布式。**选型的反面不是「性能不够」，而是「为了想象中的规模引入不必要的复杂度」**。

## 六类存储的边界

| 类别 | 代表 | 擅长 | 不擅长 |
| ------------- | ------------------------------------ | ---------------------------------------- | ---------------------------------------- |
| 关系型 | MariaDB、PostgreSQL | 事务、约束、复杂查询、成熟备份 | 超大规模水平扩展、半结构化文档 |
| 嵌入式 | SQLite、H2 | 零服务、单文件、测试与桌面应用 | 多机共享、高并发写、网络文件系统 |
| 键值缓存 | Valkey、Memcached | 亚毫秒读、会话、计数器、限流 | 作为唯一数据源、复杂查询 |
| 文档 | MongoDB、CouchDB、RethinkDB | 松散 schema、嵌套结构、快速迭代 | 跨文档强事务、复杂 join |
| 宽列 | Cassandra | 写入吞吐、多数据中心、无单点 | 临时查询、强一致读、小规模部署 |
| 搜索 | Elasticsearch、OpenSearch | 全文检索、聚合、近实时索引 | 作为主数据源、事务更新 |
| 时序 | InfluxDB、TimescaleDB、TICK | 按时间聚合、降采样、保留策略 | 复杂关系、频繁随机更新 |

- **缓存不是数据库**：Valkey 提供持久化与复制，但它的定位是「加速」；主数据仍在关系型里，缓存丢了要能从主库重建。Memcached 更纯粹：多线程、无持久化、只有简单键值。
- **文档库的 schema-on-read 是双刃剑**：字段可以随时加，但约束要写进应用层；跨文档事务能力有限，适合「一个聚合根一文档」的模型。
- **宽列库按查询建表**：Cassandra 的 partition key 决定数据落在哪，先想查询再建表；用关系型思维做临时查询会非常痛苦。
- **搜索库是索引，不是账本**：Elasticsearch/OpenSearch 的写入先进 translog 再 refresh（默认 1 秒可见），适合检索与聚合；权威数据要落在关系型或对象存储，再同步进索引。Elasticsearch 与 OpenSearch 的许可证不同，选型时要连同许可一起评估。
- **时序库按时间分区**：InfluxDB 与 TICK（Telegraf + InfluxDB + Chronograf + Kapacitor）适合指标、日志计数与降采样；关系型也能存时序，但时间范围聚合与保留策略要自己实现。
- **H2 是测试工具**：Java 生态里常用它做内存库/文件库的单元测试，不要把它当成生产数据库。

## SQLite：被低估的默认选项

SQLite 不是「玩具」：它没有服务进程，数据库就是一个文件，读性能极高，写入串行但足够多数单机应用。适用边界：单机、读多写少、并发写不高、文件在本地磁盘（不要放网络文件系统）。

```bash
sudo pacman -S sqlite
sqlite3 /tmp/lab.db <<'SQL'
PRAGMA journal_mode=WAL;
CREATE TABLE notes(id INTEGER PRIMARY KEY, body TEXT NOT NULL);
INSERT INTO notes(body) VALUES ('first'), ('second');
.backup '/tmp/lab-backup.db'
PRAGMA integrity_check;
SQL
sqlite3 /tmp/lab-backup.db 'SELECT COUNT(*) FROM notes;'
```

四个要点：

- **WAL 模式**：`journal_mode=WAL` 让读不阻塞写、写不阻塞读，但同一时刻仍只有一个写者；并发写要靠应用层排队或 `busy_timeout`。
- **在线备份用 `.backup`**：直接 `cp` 主文件在 WAL 活跃时可能拿到不一致快照；`.backup` 走 SQLite 的在线备份 API。
- **完整性校验**：`PRAGMA integrity_check;` 返回 `ok` 才算文件没坏；备份后对新文件再跑一次。
- **迁移即文件**：备份、复制、归档都是文件操作，但要注意 `-wal`/`-shm` 伴随文件；用 `.backup` 或先 `PRAGMA wal_checkpoint(TRUNCATE);`。

## 客户端与互操作

- **DBeaver** 是通用 GUI 客户端，通过 JDBC 连多种数据库；适合临时查询、看表结构、导出结果，不适合作为生产自动化的一部分。
- **ODBC** 是跨语言/跨进程的标准接口：`unixodbc` 提供驱动管理器，`/etc/odbc.ini` 配数据源，`isql` 做连通性测试。应用用 ODBC 时，排障顺序是「驱动是否安装 → DSN 是否指向正确库 → 认证是否通过」。
- **连接方式的选择**：同机优先 Unix socket（少一层 TCP、权限更直接）；跨机才用 TCP，并配 TLS 与来源限制（第 67、68 章）。

## 一个组合示例：博客 + 搜索 + 缓存

以「个人博客」为例，把六类存储落到职责上：

| 存储 | 角色 | 权威数据 | 丢了怎么办 |
| ------------- | ------------------------------ | ---------------- | ------------------------------ |
| PostgreSQL | 文章、用户、评论 | 是 | 从 dump/PITR 恢复（第 68 章） |
| SQLite | 本地草稿、离线索引 | 部分是 | 文件备份即可，冲突以主库为准 |
| Valkey | 热门文章、会话 | 否 | 清空后从主库重建 |
| OpenSearch | 全文检索 | 否 | 从主库全量回灌 |
| 对象存储/文件 | 图片与附件 | 是 | 从备份恢复，数据库只存路径 |
| 时序库（可选） | 访问指标 | 否 | 接受丢失或从访问日志重算 |

写入路径是「主库先落盘 → 通过 outbox/CDC 同步索引 → 缓存按需回填」。读路径是「缓存命中直接返回；未命中查主库并回填；搜索走索引」。**每一条非权威存储都写明重建来源**，这张表就是故障时的操作顺序。

这套组合的代价是四套组件的运维；如果博客每天只有几百访问，PostgreSQL 全文检索 + 文件缓存就够，不要为了「架构完整」而上搜索集群。选型的终点不是组件数量，而是「每个组件都有明确的、可重建的职责」。

## 失败模式

- **拿缓存当唯一数据源**：Valkey/Memcached 重启或驱逐后数据消失，业务直接归零。缓存必须可重建，主库才是真相。
- **拿搜索库当账本**：索引 refresh 有延迟、mapping 变更代价高、删库重建要回灌；把订单只写进 Elasticsearch 是灾难模板。
- **SQLite 放在 NFS/共享盘**：文件锁语义不可靠，可能损坏数据库；SQLite 的官方建议是本地文件系统。
- **并发写没排队**：多进程同时写 SQLite 会报 `database is locked`；加 `busy_timeout` 或把写收口到单进程。
- **文档库当关系库用**：频繁跨集合 join、强事务更新，会把优势用成劣势；该换回关系型。
- **宽列库按关系模型建表**：没有按查询设计 partition key，后期只能重建表并回灌。
- **时序数据永不降采样**：原始点无限增长，磁盘与查询一起崩；要设保留策略与降采样。
- **备份只覆盖主库**：缓存、搜索索引、时序库各自有重建路径，但关系型主库必须独立可恢复。

## 验证与回滚

选型验证不靠压测口号，靠三个可复现动作：

```bash
sqlite3 /tmp/lab.db 'PRAGMA journal_mode; PRAGMA integrity_check;'
sqlite3 /tmp/lab.db ".backup '/tmp/lab-verify.db'"
sqlite3 /tmp/lab-verify.db 'SELECT COUNT(*) FROM notes;'
```

- **写入—备份—恢复**：造数据、在线备份、从备份读回，行数一致才算备份可用。
- **并发写演练**：开两个 `sqlite3` 会话同时写，观察 `database is locked`；再加 `PRAGMA busy_timeout=5000;` 看是否等待成功。
- **缓存失效演练**：清空缓存键后，确认应用能从主库重建；重建不了说明缓存被当成了主库。

回滚策略按类别不同：关系型回到 dump（第 67/68 章）；搜索索引删除后从主库回灌；缓存直接清空重建；时序库按保留策略回退到快照。**任何一类库的「回滚」都要先问「权威数据在哪」**。

## 取舍边界

- **先用关系型，除非有明确理由**：事务、约束、备份、人才储备都成熟；NoSQL 的扩展性优势在中小规模通常用不上。
- **SQLite vs 客户端/服务器数据库**：单机、单进程或低并发写 → SQLite；多用户、远程连接、高并发写 → MariaDB/PostgreSQL。
- **Valkey vs Memcached**：需要数据结构、持久化、复制 → Valkey；只要简单键值、多线程吞吐 → Memcached。
- **文档 vs 关系型**：聚合根天然是一个文档、schema 频繁变 → 文档库；跨实体关系与强事务 → 关系型。
- **搜索库 vs 数据库全文索引**：数据量小、查询简单 → PostgreSQL 全文检索足够；需要分词、聚合、相关性调优 → 专用搜索库，但要接受「索引与主库同步」的运维成本。
- **自建 vs 托管**：没有专职运维时，托管数据库买的是备份、监控与升级；自建买的是控制权与成本。
- **规模阈值**：单机装得下就不要分布式；分布式带来的分区、复制、一致性问题是长期成本，不是一次部署成本。

## 小结

- 选型从「数据形状、一致性、读写比、规模、运维」五个问题开始，不从流行度开始。
- 关系型是默认答案；缓存、文档、宽列、搜索、时序各自解决特定问题，也各自有明确边界。
- 缓存与搜索索引都不是权威数据源；主库必须独立可备份、可恢复。
- SQLite 适合单机低并发写；WAL 改善并发，`.backup` 做在线备份，`integrity_check` 验证完整性。
- 客户端工具（DBeaver、ODBC、H2）各有定位，不要把测试库或 GUI 工具当成生产方案。

## 练习

1. 五问演练：为一个「个人博客 + 评论 + 全文搜索」设计存储组合，用五个问题说明主库、缓存、搜索索引各自负责什么。
2. SQLite 实验：按正文建库、开 WAL、插入数据、`.backup`，再对备份跑 `integrity_check` 与 `COUNT(*)`；删除原库后用备份恢复。
3. 并发写：开两个会话同时写同一张表，记录 `database is locked`；加 `PRAGMA busy_timeout=5000;` 再试，解释差异。
4. 缓存边界：用 Valkey 或 Memcached（容器或本机均可）缓存一个查询结果，手动清空后验证应用能从主库重建；写出「缓存不可用时降级」的伪代码。
5. 搜索同步：说明把一张表同步到 Elasticsearch/OpenSearch 的三种方式（双写、事务日志订阅、定时全量），各写一条风险。
6. 读文档：对比 SQLite、Valkey、MongoDB 的官方文档，各找出一条「不适合作为主库」的明确说明并摘录。
