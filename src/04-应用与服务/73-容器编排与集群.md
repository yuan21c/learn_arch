# 第 73 章 容器编排与集群

单机 `compose` 能管几个容器，但管不了「某台机器挂了，把 Pod 挪到另一台」「滚动升级时流量不中断」「谁负责服务发现」。这些是编排器的职责。本章以 Kubernetes 为主线讲「声明式 + 控制器循环」的心智模型，同时给出 Minikube、Nomad、OpenShift 的定位，最后用 `podman play kube` 在本机演练一份 Pod YAML——不需要真集群也能理解对象关系。

> 本章目标：能说清编排器解决的四个问题（调度、自愈、滚动升级、服务发现）；能区分 Pod、Deployment、Service、Ingress、ConfigMap/Secret 的职责；能写出带 readinessProbe 与资源 requests/limits 的 Deployment；会用 `kubectl get/describe/logs/events` 与 `rollout status/undo` 排障与回滚；知道 Minikube、kind、k3s、Nomad、OpenShift 的适用边界；能用 `podman play kube` 在本机验证 Pod YAML。
> 对应 Wiki：[Kubernetes](https://wiki.archlinux.org/title/Kubernetes)、[Minikube](https://wiki.archlinux.org/title/Minikube)、[Nomad](https://wiki.archlinux.org/title/Nomad)、[OpenShift](https://wiki.archlinux.org/title/OpenShift)

## 编排器解决的四个问题

| 问题 | 没有编排器 | 编排器提供 |
| -------------- | ------------------------------ | ---------------------------------------- |
| 调度 | 手工决定容器跑在哪台 | 按资源请求与约束自动放置 |
| 自愈 | 进程挂了靠 systemd 拉 | 副本数不足时重建，节点失联时迁移 |
| 升级 | 停旧起新，有停机窗口 | 滚动/灰度，按就绪探针控制节奏 |
| 服务发现 | 写死 IP 与端口 | Service/负载均衡把后端变化对调用方隐藏 |

如果只在一台机器上跑一个容器，systemd + compose 就够了（第 63、71 章）；引入编排器的前提是「多实例、多机器、需要不停机升级」至少占一条。

## Kubernetes 的心智模型

Kubernetes 是「声明式」的：你写「我要 2 个副本、镜像 v1、端口 80」，控制器循环不断把现实拉向声明。核心对象：

- **Pod**：最小调度单位，一个或多个共享网络/存储的容器；通常一个 Pod 一个主容器。
- **Deployment**：管理 Pod 副本与滚动更新，维护 ReplicaSet 历史，支持 `rollout undo`。
- **Service**：给一组 Pod 一个稳定的虚拟 IP/域名与负载均衡；靠 label selector 找后端。
- **Ingress**：七层入口，把域名/路径路由到 Service（需要 Ingress Controller）。
- **ConfigMap / Secret**：配置与敏感数据注入；Secret 默认只是 base64，不等于加密。
- **PersistentVolumeClaim**：向存储类申请持久卷，Pod 删除后数据仍在。

一个最小 Deployment（`/tmp/web.yaml`）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
        - name: web
          image: nginx:alpine
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet: {path: /, port: 80}
            initialDelaySeconds: 3
          resources:
            requests: {cpu: 10m, memory: 32Mi}
            limits: {cpu: 100m, memory: 128Mi}
```

`requests` 决定调度，`limits` 决定上限；只写 `limits` 不写 `requests` 会让调度器按默认值放置，容易出现资源挤兑。`readinessProbe` 决定「什么时候接流量」，没有它，滚动更新会把请求打到还没启动完的副本。

## 本地集群与替代编排器

| 工具 | 形态 | 适合 | 代价 |
| ------------- | ------------------------------------ | ------------------------------ | ------------------------------ |
| Minikube | 单机起一个（可多节点的）K8s | 学习、验证清单 | 需要驱动（容器或虚拟化），占资源 |
| kind | 用容器跑 K8s 节点 | CI、快速重建 | 与宿主网络/存储边界要理解 |
| k3s | 轻量 K8s 发行版 | 边缘、单机小集群 | 部分组件被裁剪 |
| Nomad | 通用调度器（容器/非容器） | 不想背 K8s 复杂度、混合负载 | 生态与资料少于 K8s |
| OpenShift | 企业级 K8s 发行版 | 需要路由、SCC、Operator 的团队 | 组件重、学习与资源成本高 |

Minikube 的最短路径：

```bash
minikube start --driver=docker
kubectl get nodes
kubectl apply -f /tmp/web.yaml
kubectl rollout status deployment/web
minikube status
```

`--driver=docker` 要求 Docker 守护进程可用；没有容器驱动时改用虚拟化驱动（第 74 章）。`kubectl` 的上下文由 Minikube 自动配置，切回其他集群前先 `kubectl config current-context` 确认。

## 在本机演练 Pod YAML

没有集群也能验证对象关系：`podman play kube` 会把 Kubernetes Pod YAML 翻译成本地 Pod。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab-pod
spec:
  containers:
    - name: web
      image: docker.io/library/nginx:alpine
      ports:
        - containerPort: 80
          hostPort: 8080
```

```bash
podman play kube /tmp/lab-pod.yaml
podman pod ps
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
podman play kube --down /tmp/lab-pod.yaml
```

这条路径能验证「Pod 内容器共享网络、端口映射、生命周期一起管理」，但**不验证调度、副本、滚动更新**——那些需要真集群。把它当「清单语法与容器关系」的本地检查，不要当成 K8s 的替代品。

## 失败模式

- **Pod 一直 `Pending`**：资源请求超过节点可分配量，或节点亲和/污点不满足；`kubectl describe pod` 的 Events 会写原因。
- **`ImagePullBackOff`**：镜像名/标签写错、私有仓库缺 `imagePullSecret`、网络到 registry 不通。
- **`CrashLoopBackOff`**：容器启动即退；`kubectl logs --previous` 看上一次容器日志，通常是配置/环境变量/权限。
- **Service 没有 Endpoints**：selector 与 Pod label 不匹配，或 Pod 未 Ready；`kubectl get endpoints` 一看便知。
- **滚动更新卡住**：新副本 readiness 一直不通过，旧副本不敢下；先修探针或回滚。
- **PVC 一直 Pending**：没有可用 StorageClass/动态供应器；`kubectl describe pvc` 看事件。
- **Secret 当加密用**：默认只是 base64，能读 Secret 的人就能解出明文；敏感数据要配合加密或外部密钥管理（第 80 章）。
- **资源只写 limits**：调度器不知道真实需求，节点过载时先被驱逐；requests/limits 成对写。
- **`kubectl` 打错集群**：多上下文并存时误操作生产；命令前先看 `current-context`，危险操作加 `--context`。
- **单节点 etcd 没有备份**：集群状态丢了，对象定义与证书一起没；etcd 快照要纳入备份演练。

## 验证与回滚

排障按「对象 → 事件 → 日志 → 端点」四层：

```bash
kubectl get deploy,pods,svc -o wide
kubectl describe pod -l app=web
kubectl logs deploy/web --tail=50
kubectl get events --sort-by=.lastTimestamp | tail -20
kubectl get endpoints web
```

升级与回滚用 Deployment 的历史：

```bash
kubectl set image deployment/web web=nginx:1.27-alpine
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web
```

`rollout undo` 回退的是 Pod 模板，不回退数据库结构；有状态变更仍要按第 70 章的「扩展 → 双写 → 收缩」设计。回滚后验证：`kubectl get pods` 全部 Ready、`endpoints` 有地址、`curl` 通过、日志无新错误。

本机 `podman play kube` 的回滚就是 `--down` 后重新 apply 旧 YAML；真集群则保留上一版清单与镜像 digest，必要时 `kubectl apply` 旧清单。

## 取舍边界

- **compose vs Kubernetes**：单机、少量容器、个人项目 → compose；多机、需要自愈与不停机升级 → 编排器。别为了简历上写 K8s 而给单机博客上集群。
- **Kubernetes vs Nomad**：需要成熟生态、广泛托管支持、丰富 Operator → K8s；负载混合（容器 + 非容器）、想少背概念 → Nomad。
- **Minikube vs kind vs k3s**：学习与验证 → Minikube；CI 里快速起停 → kind；边缘/轻量生产 → k3s。三者都不是「生产级高可用集群」的完整替代。
- **自建 vs 托管**：自建买控制权与成本，托管买升级、备份与 SLA；没有专职运维时，托管通常更划算。
- **OpenShift vs 原生 K8s**：需要企业支持、内置路由/SCC/Operator 流水线 → OpenShift；只需要标准 API 与轻量组件 → 原生或 k3s。
- **有状态负载上不上集群**：数据库上 K8s 需要 Operator、PVC、备份与恢复演练；没有这些能力时，托管数据库或独立部署更稳。
- **`podman play kube` 的边界**：适合本地验证清单与 Pod 关系；不提供调度、副本控制与滚动升级，不要用它替代集群。

## 小结

- 编排器解决调度、自愈、滚动升级、服务发现；单机单容器不需要它。
- Kubernetes 是声明式 + 控制器循环；Pod 是最小单位，Deployment 管副本与历史，Service 管稳定入口。
- `requests` 决定调度、`limits` 决定上限；readinessProbe 决定何时接流量。
- 排障顺序：对象状态 → Events → 日志 → Endpoints。
- 回滚用 `rollout undo` 或旧清单/digest；数据库变更要单独设计兼容与回退。
- Minikube/kind/k3s 各有定位；`podman play kube` 只能做本地清单验证。

## 练习

1. 本机 Pod：用正文的 Pod YAML 执行 `podman play kube`，`curl` 验证 8080，再 `--down` 清理；解释 Pod 内容器共享了什么。
2. Minikube：`minikube start --driver=docker`，apply Deployment，`kubectl get pods -w` 观察两个副本；删一个 Pod，看控制器如何补回。
3. 探针实验：把 readinessProbe 的路径改成一个 404 路径，`kubectl rollout status` 会卡住；改回后恢复，记录行为差异。
4. 资源实验：只写 `limits` 不写 `requests`，`kubectl describe pod` 看调度结果；再补 `requests` 对比。
5. 回滚演练：`kubectl set image` 到一个不存在的 tag，观察 `ImagePullBackOff`，再 `rollout undo` 恢复。
6. 选型结论：为「单机个人项目」「公司多机微服务」「边缘小集群」三个场景各选一个方案，写两条理由与一条代价。
