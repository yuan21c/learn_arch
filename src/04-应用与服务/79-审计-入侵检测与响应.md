# 第 79 章 审计、入侵检测与响应

第 78 章让「篡改可发现」；本章让「行为可追溯、事件可响应」。三件事依次递进：**日志留存**（发生了什么）、**审计与入侵检测**（谁做了什么、是否异常）、**响应流程**（出事时先做什么）。很多系统不是没有日志，而是日志重启即丢、出事第一反应是重启清现场——后者会让证据一起消失。

> 本章目标：能配置 journald 持久化并区分 journald/rsyslog/syslog-ng 的分工；会用 logrotate 的 `-d` 预演与 `postrotate` 重载；知道 auditd 的 watch 规则、`ausearch`/`aureport` 的用法与性能代价；能区分网络 IDS（Suricata/Snort）与主机 IDS（AIDE/CrowdSec/fail2ban）；会按「准备—识别—遏制—清除—恢复—复盘」处理事件并保留证据；能识别「日志不持久」「重启毁证据」「审计规则过宽」三类问题。
> 对应 Wiki：[Systemd/Journal](https://wiki.archlinux.org/title/Systemd/Journal)、[Audit framework](https://wiki.archlinux.org/title/Audit_framework)、[Logrotate](https://wiki.archlinux.org/title/Logrotate)、[Fail2ban](https://wiki.archlinux.org/title/Fail2ban)、[CrowdSec](https://wiki.archlinux.org/title/CrowdSec)、[AIDE](https://wiki.archlinux.org/title/AIDE)

## 日志：先保证「留得下、看得懂、转得走」

| 组件 | 作用 | 关键配置 |
| -------------- | ---------------------------------------- | ------------------------------------------ |
| journald | 收集内核/服务/标准输出日志，结构化存储 | `Storage=persistent`、`SystemMaxUse=` |
| rsyslog | 传统 syslog 转发、格式化、写远端 | `/etc/rsyslog.conf`、`*.* @@host:514` |
| syslog-ng | 另一套转发/过滤引擎 | `/etc/syslog-ng/syslog-ng.conf` |
| logrotate | 按大小/时间切分、压缩、删除旧日志 | `/etc/logrotate.d/`、`postrotate` |
| logwatch | 定期汇总日志并邮件报告 | 定时任务 + 规则 |

journald 默认可能只把日志放在 `/run`，重启即丢。要留存就显式持久化：

```bash
sudo mkdir -p /var/log/journal
sudo systemctl restart systemd-journald
journalctl --disk-usage
journalctl -b -1 -p err --no-pager | tail -20
```

`Storage=persistent` 或 `auto` 会写到 `/var/log/journal`；`SystemMaxUse=` 限制总量，避免日志吃满磁盘。需要把日志送到另一台机器时，journald 可用 `ForwardToSyslog=yes` 交给 rsyslog，再由 rsyslog 转发；也可以让 rsyslog/syslog-ng 直接读 journal。

logrotate 的错误配置有两类典型后果：把正在写的日志删掉（进程仍持有已删除的 fd，磁盘不释放），或切分后没通知服务重开文件。`postrotate` 里 `systemctl reload <服务>` 或发信号，就是为这件事。

## 审计：谁改了什么

auditd 在内核层记录系统调用与文件访问，适合「关键文件被谁改、谁执行了敏感命令」：

```bash
sudo pacman -S audit
sudo systemctl enable --now auditd
sudo auditctl -w /etc/ssh/sshd_config -p wa -k ssh_config
sudo auditctl -l
sudo ausearch -k ssh_config
sudo aureport -f -i | tail -20
```

- `-w` 监视路径，`-p wa` 表示写与属性变更，`-k` 是检索键。
- `ausearch -k` 按键查事件，`aureport` 做汇总；时间线排障时先对时（NTP）再查。
- 规则越多、路径越热，开销越大；只盯关键文件与敏感目录，不要对 `/` 全量开 `execve` 审计。
- `auditctl -W <路径> -p wa -k <键>` 可移除单条 watch；`auditctl -D` 清空全部规则，属于破坏性操作，先导出规则再考虑。

## 入侵检测：网络、主机与行为

- **网络 IDS**：Suricata/Snort 按规则匹配流量，适合有镜像端口或网关流量的场景；单机可以用 `tshark` 做小范围验证（第 78 章）。
- **主机 IDS/文件完整性**：AIDE 对文件树做基线哈希，定期比对；基线要在「干净状态」生成，且存放在只读介质或远端。
- **行为型封禁**：fail2ban 读日志匹配失败登录并封 IP；CrowdSec 汇总行为信号并共享决策。两者都需要正确的日志后端（如 `backend=systemd`）与封禁动作（如 `banaction=nftables`）。
- **进程/资源监控**：Monit 能在进程消失或资源越线时告警/重启；systemd 的 `OnFailure=` 可触发单元。它们是「可用性监控」，不是入侵检测，别混为一谈。

## 事件响应：六步与证据顺序

1. **准备**：留出带外通道、备份、联系人清单、日志集中存储；没有准备，事件现场只能靠临场发挥。
2. **识别**：确认是否真是事件（误报很常见），记录时间、来源、影响范围。
3. **遏制**：隔离受影响主机/账号/网段，但**先保留证据**；能拔网线就不要急着重启。
4. **清除**：删恶意文件、改凭据、补漏洞；每步记录命令与时间。
5. **恢复**：从可信备份恢复，验证服务与完整性，再逐步接回网络。
6. **复盘**：写时间线、根因、改进项与责任人；没有复盘的响应等于没发生。

**证据顺序按「易失性」从高到低**：内存/进程/网络连接 → 临时文件 → 磁盘日志 → 备份/离线介质。重启会清掉前三类，所以「先采集再重启」。采集时记录哈希与时间，保证证据链可追溯。

## 失败模式

- **日志不持久**：`/var/log/journal` 不存在或 `Storage=volatile`，重启后什么也查不到。
- **logrotate 删了活动日志**：`copytruncate` 与追加写竞争，或没有 `postrotate` 重载，服务继续写已删除的 inode，磁盘空间不释放。
- **审计规则过宽**：对全盘 `execve`/所有写操作开审计，日志洪水 + 性能下降，最后只能整段关掉。
- **auditd 没启用**：规则写在文件里但服务没跑，`auditctl -l` 为空。
- **IDS 没有基线**：AIDE 基线在已被污染的系统上生成，之后所有异常都被当成正常。
- **fail2ban 不封**：`enabled=false`、日志后端不对、`banaction` 与防火墙不匹配；`fail2ban-client status` 能看到 jail 是否真的在跑。
- **告警疲劳**：所有日志都告警，真正的信号被淹没；按影响分级并设抑制窗口。
- **重启毁证据**：出事第一反应 `reboot`，内存、连接、临时文件全没了。
- **时间不同步**：多机日志时间线对不上，无法判断先后；NTP/chrony 要作为基础设施。
- **日志只存本地**：攻击者拿到 root 后先清日志；关键日志要转发到另一台主机或只写介质。

## 验证与回滚

日志与审计的验证要看「实际留存、实际规则、实际封禁」：

```bash
journalctl --disk-usage
ls -ld /var/log/journal
journalctl -b -1 -p err --no-pager | tail -10
sudo auditctl -l
sudo ausearch -k ssh_config -ts today | tail -20
sudo fail2ban-client status 2>/dev/null || echo "未安装 fail2ban"
sudo monit summary 2>/dev/null || echo "未安装 monit"
```

logrotate 用 `-d` 预演，不实际切分：

```bash
sudo logrotate -d /etc/logrotate.d/nginx
```

输出会列出「会切哪个文件、执行哪些脚本、是否报错」。确认后再 `-f` 强制执行一次；改坏配置就恢复备份。

回滚：

- **journald**：`Storage=` 改回原值并重启 `systemd-journald`；已写入的日志文件保留。
- **logrotate**：恢复 `/etc/logrotate.d/` 下的备份；已切分的日志按需合并或保留。
- **auditd**：`auditctl -W` 移除单条规则；`auditctl -D` 清空全部规则前先 `auditctl -l > /tmp/audit.rules.bak`。
- **fail2ban/CrowdSec**：`fail2ban-client stop` 或停服务，清空封禁决策；确认不会误封管理 IP。
- **事件响应**：遏制动作要可逆（隔离而非删除），恢复前验证备份完整性与哈希。

## 取舍边界

- **journald vs rsyslog/syslog-ng**：journald 结构化、按服务检索方便；rsyslog 转发与格式化生态成熟。常见组合是 journald 本地留存 + rsyslog 转发远端。
- **审计覆盖 vs 性能**：只盯关键路径与敏感命令；全量审计的日志量与开销通常不可接受。
- **IDS vs 预防**：IDS 发现，不是阻止；阻断要靠防火墙/IPS/封禁动作，且要防误封。
- **本地留存 vs 集中存储**：本地方便排障，集中存储防篡改；重要系统两者都要。
- **保留期 vs 磁盘**：按合规与排障需求定保留期，配 `SystemMaxUse`/logrotate 上限；无限保留等于迟早磁盘满。
- **fail2ban vs CrowdSec vs 仅密钥**：密钥登录已大幅降低暴力破解价值；封禁工具是缓解层，别用它替代认证加固。
- **Monit vs systemd**：systemd 管进程生命周期，Monit 做跨服务/资源检查与告警；别用 Monit 重复实现 systemd 的重启。
- **现场响应 vs 关机取证**：关机保「磁盘证据」，但丢「内存证据」；先采集易失数据，再决定是否关机。

## 小结

- 日志先解决「持久化、轮转、转发」三件事，再谈分析。
- auditd 盯关键文件与敏感命令；规则越宽，开销与噪音越大。
- 网络 IDS、主机完整性、行为封禁各管一段；基线要在干净状态生成。
- 事件响应六步：准备、识别、遏制、清除、恢复、复盘；证据按易失性从高到低采集。
- 重启会毁掉内存与连接证据；先采集再重启。
- 日志要能「留得下、看得懂、转得走」，否则审计与响应都是空谈。

## 练习

1. 持久化检查：`ls -ld /var/log/journal`、`journalctl --disk-usage`、`journalctl -b -1`；若没有上一次启动日志，说明如何开启持久化。
2. logrotate 预演：在 `/tmp/loglab` 建一个日志与配置，`logrotate -d` 看计划，再 `-f` 执行，检查切分与压缩结果。
3. 审计规则：在 `auditd` 可用时给 `/tmp/auditlab` 加 watch，触发一次写，`ausearch -k` 找到事件，再 `auditctl -W` 移除（不可用时写出手动步骤）。
4. 封禁检查：若装了 fail2ban，`fail2ban-client status` 看 jail 与当前封禁；说明日志后端与 `banaction` 如何影响生效。
5. 证据顺序：模拟「怀疑主机被入侵」，列出你会先采集的五类易失数据与对应命令，再说明什么情况下才关机。
6. 时间线：用 `journalctl` 与 `ausearch` 各取一条事件，按时间排序，说明 NTP 不同步会带来什么误判。
7. 保留策略：为一个每天 2 GB 日志的服务设计保留期与磁盘上限，写出 journald 与 logrotate 的具体参数。
