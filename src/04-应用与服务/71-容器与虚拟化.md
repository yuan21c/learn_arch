# 第 71 章 容器基础

第 63–68 章把服务直接跑在系统上。真实项目里还有两种打包方式：**容器**（应用 + 依赖一起走）与**虚拟机**（完整操作系统）。本章讲在 Arch（VM 或真机）上怎么用它们，以及各自会在哪里失灵；需要嵌套虚拟化或硬件直通的部分会单独标注。

> 本章目标：能说清容器与虚拟机的唯一关键差别及其后果；会用 Docker 或 Podman 运行、进入、看日志、挂载数据卷；能用 compose 描述多容器应用；知道容器共享宿主内核带来的三个边界（内核模块、cgroups/systemd、网络）；了解 libvirt/QEMU 的定位与「虚拟机里默认拿不到 `/dev/kvm`」的原因。
> 对应 Wiki：[Docker](https://wiki.archlinux.org/title/Docker)、[Podman](https://wiki.archlinux.org/title/Podman)、[Libvirt](https://wiki.archlinux.org/title/Libvirt)

## 容器与虚拟机：只差一件事

| 维度 | 容器 | 虚拟机 |
| ------------ | -------------------------------- | ---------------------------- |
| 内核 | **共享宿主内核** | 各自跑一个完整内核 |
| 隔离边界 | 命名空间 + cgroups + 安全模块 | 硬件虚拟化（VT-x/AMD-V） |
| 启动时间 | 毫秒到秒 | 数十秒 |
| 能跑的系统 | 与宿主同内核（Linux 跑 Linux） | 任意操作系统 |
| 内核相关操作 | 受限（模块、`sysctl`、部分特权） | 完全自由 |
| 典型用途 | 应用分发、环境一致 | 异构系统、内核实验、完整隔离 |

这一条差别解释了两类常见困惑：容器里 `uname -r` 显示的是宿主内核（不是镜像的）；容器里 `modprobe` 或改内核参数通常失败（不是权限没给对）。

## Docker：最普及的路径



```bash
sudo pacman -S docker docker-compose docker-buildx # compose、buildx 均为独立包；Docker 29 的 docker build 由 buildx 提供
sudo systemctl enable --now docker
sudo docker run --rm hello-world
docker compose version # 验证插件可用，否则报 'compose' is not a docker command
```

不想每次都敲 `sudo` 就把用户加进 `docker` 组（`sudo usermod -aG docker "$USER"`，重新登录后生效）；不加组则所有 `docker` 命令都带 `sudo`——二选一，别混着来。

镜像的最小心智模型：镜像是**只读分层**的堆叠，容器在其上加一层可写层；`docker build` 按 `Dockerfile` 逐行产出层，`docker push/pull` 与 registry（如 Docker Hub）交换层。

日常命令只需六个：

```bash
docker ps -a # 容器列表（含已退出）
docker images # 镜像列表
docker run -d --name web -p 8080:80 nginx
docker logs -f web # 跟日志
docker exec -it web sh # 进容器
docker rm -f web && docker rmi nginx
```

四个必须理解的参数：

- `-p 宿主端口:容器端口`：把容器端口映射出来。`-p 127.0.0.1:8080:80` 只绑回环，比 `-p 8080:80`（默认绑 `0.0.0.0`）安全；
- `-v 宿主路径:容器路径`：数据卷或绑定挂载。**容器删了，卷里的数据还在；没挂卷的数据跟着容器一起没**；
- `--name`：给容器起名，后续 `logs`/`exec`/`rm` 都用它；
- `-d`：后台运行（对应第 63 章的前台运行原则：应用进程不要自己 daemonize）。

`docker` 组等于 root：组内用户能挂载宿主目录、能起特权容器——**这是提权，不是权限细化**。个人开发机可接受，多人机器应改用 rootless（下一节）。

## Podman：无守护进程的替代

Podman 的命令与 Docker 几乎一一对应，差别在架构：**没有常驻守护进程**，默认以普通用户 rootless 运行。

```bash
sudo pacman -S podman
podman run --rm hello-world
podman ps -a
```

三个好处：不需要 root 守护进程（攻击面小）、rootless 下容器内的 root 映射到宿主的普通用户、可以用 Quadlet 把容器变成第 63 章那样的 systemd 单元。旧命令 `podman generate systemd` 已停止开发（仍可用），现在写 `.container` 文件放 `~/.config/containers/systemd/`：

```ini
# ~/.config/containers/systemd/web.container
[Container]
Image=docker.io/library/nginx:alpine
PublishPort=127.0.0.1:8080:80

[Service]
Restart=always

[Install]
WantedBy=default.target
```

`systemctl --user daemon-reload` 后即可 `systemctl --user enable --now web`；要让它在你未登录时也开机自启，还需 `loginctl enable-linger "$USER"`。

代价也要知道：rootless 容器只能绑定 1024 以上的端口（要 80/443 得靠反代或 `net.ipv4.ip_unprivileged_port_start`）；部分存储驱动与网络模式需要额外配置；与 Docker 的 compose 文件虽基本通用，但总有边角差异。

## compose：多容器应用

一个 Web + 数据库的最小 `compose.yaml`：

```yaml
services:
 app:
 image: nginx:alpine
 ports:
 - "127.0.0.1:8080:80"
 volumes:
 - ./site:/usr/share/nginx/html:ro
 depends_on:
 db:
 condition: service_healthy # 等 db 真正就绪，而非仅已启动

 db:
 image: postgres:16-alpine
 environment:
 POSTGRES_PASSWORD: example
 healthcheck:
 test: ["CMD-SHELL", "pg_isready -U postgres"]
 interval: 5s
 timeout: 3s
 retries: 10
 volumes:
 - pgdata:/var/lib/postgresql/data

volumes:
 pgdata:
```

```bash
docker compose up -d # 或 podman-compose up -d
docker compose ps
docker compose logs -f app
docker compose down # 不带 -v 保留卷
```

`podman-compose` 不在 `podman` 包里，是独立包，需另装（`sudo pacman -S podman-compose`）；等价命令为 `podman-compose up -d`。

`depends_on` 只保证**启动顺序**，不保证数据库就绪；上面用 `healthcheck` + `condition: service_healthy` 补上「就绪」语义——把 condition 退回普通写法，就能看到 app 在 db 未就绪时先行启动（换成会连库的应用即报连接失败，这正是「顺序 ≠ 就绪」）。

> **危险**：`docker compose down -v` 会**连数据卷一起删除**，数据库数据瞬间清零。执行前 `docker volume ls` 确认哪些卷会被删，重要数据先 `pg_dump`/备份；只想停服务就用不带 `-v` 的 `down`。

## 沙箱：容器之外的第三条路

不是所有隔离都需要镜像与运行时。**bubblewrap** 与 **firejail** 用命名空间 + seccomp 把单个进程关进笼子，常用于桌面应用与不可信文件：

```bash
sudo pacman -S bubblewrap firejail
bwrap --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp bash
firejail --net=none --private=/tmp/fj bash
firejail --list
```

- `bwrap` 只做一件事：用参数拼出可见的目录与命名空间；Flatpak 底层就用它。上面的命令把根目录只读挂载、给独立的 `/tmp`、隐藏网络，进程仍能读系统文件但写不出去。
- `firejail` 带现成 profile（`/etc/firejail/`），适合直接套在浏览器、下载工具上；`--net=none` 断网、`--private` 给临时家目录。
- 二者都**不是**容器：没有镜像、没有 registry、没有编排；隔离强度弱于虚拟机，强于普通用户权限。需要完整内核隔离时回到虚拟机（第 74 章）。

## 容器的三个边界

1. **内核是共享的**：容器与宿主共用内核，容器内 `uname -r` 显示的是宿主内核；需要特定内核模块或内核版本的功能（如某些 eBPF、`nf_tables` 高级特性）可能不可用。
2. **依赖 cgroups 与 systemd**：rootless Podman 需要 cgroups v2 与 systemd 用户会话；系统未以 systemd 启动时（第 37 章）会直接失败。
3. **网络多一层**：VM 默认 NAT 时，容器端口要经「容器 → VM → 物理网络」两层地址转换；`-p 127.0.0.1:8080:80` 只绑回环，`-p 8080:80` 才对外监听，能否从宿主访问取决于 VM 的网络模式。

另外，绑定挂载跨文件系统时 I/O 很慢（权限语义也可能不同），代码目录建议放在 Linux 原生文件系统里。

## libvirt/QEMU：完整虚拟化

（需要真机，或已开启嵌套虚拟化并暴露 `/dev/kvm` 的 VM）

```bash
sudo pacman -S libvirt qemu-full virt-manager dnsmasq
sudo systemctl enable --now libvirtd
sudo usermod -aG libvirt "$USER" # 重新登录后生效
sudo virsh net-start default; sudo virsh net-autostart default # 默认 NAT 常为 inactive，不启动 VM 拿不到 IP
sudo virsh net-list --all # 预期：default active 且 autostart yes
```
`default` 网络依赖 `dnsmasq` 提供 DHCP/DNS；防火墙后端按 Arch Wiki 选择 `iptables-nft` 或 `nftables`，不要同时装互相冲突的 iptables 变体。

- **QEMU** 是模拟器/虚拟化器本体，`-enable-kvm` 才走向硬件加速；
- **libvirt** 是管理层（守护进程 + API + 存储/网络抽象），`virsh` 与图形化的 `virt-manager` 都通过它操作；它自带一个名为 `default` 的 NAT 网络（`virsh net-list --all` 查看），虚拟机默认从这里拿 IP，对外访问走宿主 NAT。
- 没有 `/dev/kvm` 时一切退化为纯软件模拟，慢到不可用——这是判断「能不能在这台机器上跑虚拟机」的第一条命令：

```bash
ls -l /dev/kvm
```

## 失败模式

容器「跑不起来」通常不是镜像坏了，而是权限、端口、数据与就绪四件事：

- **`docker` 组用户等于 root**：能把宿主 `/` 挂进容器、能起特权容器。个人机可接受，多人机改用 rootless Podman，而不是给更多人加组。
- **`-p 8080:80` 把服务暴露到所有网卡**：默认绑 `0.0.0.0`，同网段可直接访问。只给本机用就写 `127.0.0.1:8080:80`，并用 `ss -tlnp` 复核。
- **删容器后数据没了**：没挂卷，可写层随容器删除。数据库、上传目录一律用命名卷或绑定挂载，并在删除前 `docker volume ls`。
- **`docker compose down -v` 清空数据库**：`-v` 连卷一起删。停服务只用 `down`，删卷单独决策并先备份。
- **容器里 `modprobe`/`sysctl` 失败**：共享宿主内核，不是权限没给对；需要内核能力的 workload 应放虚拟机或特权模式（后者有代价）。
- **rootless 绑 80 失败**：非特权用户不能监听 1024 以下端口。用反代转发，或调整 `net.ipv4.ip_unprivileged_port_start`（系统级改动）。
- **rootless 直接起不来**：缺 cgroups v2 或 systemd 用户会话；`systemctl --user status` 与 `ls /sys/fs/cgroup` 先确认。
- **compose 起来了但应用连不上库**：`depends_on` 只保证顺序，不保证就绪；补 `healthcheck` + `condition: service_healthy`。

## 验证与回滚

容器的验证要落到「进程、端口、数据、日志」四项：

```bash
docker ps -a
ss -tlnp | grep 8080
docker inspect -f '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' web
docker logs --tail 20 web
docker compose config >/dev/null && echo "compose 语法 OK"
```

数据持久化用「删容器不删卷」验证：

```bash
docker run -d --name labdb -e POSTGRES_PASSWORD=example -v labdata:/var/lib/postgresql/data postgres:16-alpine
# 写入数据后
docker rm -f labdb
docker run -d --name labdb2 -e POSTGRES_PASSWORD=example -v labdata:/var/lib/postgresql/data postgres:16-alpine
```

回滚的原则是「先停、保留卷、再决定是否删」：

```bash
docker compose down          # 停服务，保留卷
docker compose down -v       # 仅在确认数据可丢时执行
docker volume ls
docker volume rm <卷名>      # 最后一步，且先确认无容器引用
```

镜像升级出问题时，回退到上一个 tag 重新 `up -d`；不要用 `docker system prune -a` 做「清理」，它会连同未使用的镜像与网络一起删掉。

## 取舍边界

- **容器 vs 虚拟机**：要秒级启动、环境一致、应用分发用容器；要异构系统、内核实验、强隔离用虚拟机（第 74 章）。
- **Docker vs Podman**：Docker 生态与 compose 最成熟；Podman 无守护进程、rootless 默认、可交给 systemd/Quadlet，适合更在意攻击面的单机。
- **compose vs systemd 单元**：开发与多容器编排用 compose；单机长期运行、要与系统服务同生命周期，用 Quadlet 生成 systemd 单元（第 63 章）。
- **命名卷 vs 绑定挂载**：命名卷由运行时管理、跨容器复用方便；绑定挂载便于直接改代码，但跨文件系统 I/O 慢、权限语义不同。
- **rootless vs rootful**：rootless 更安全，代价是低端口、部分网络/存储模式受限；需要精细网络或特权能力时再选 rootful。
- **镜像瘦身 vs 可调试**：`alpine`/distroless 体积小、攻击面小，但排障工具少；生产镜像可另建 `-debug` 变体，而不是把工具塞进正式镜像。
- **沙箱 vs 容器 vs 虚拟机**：单进程、桌面应用用 bubblewrap/firejail；应用分发用容器；完整隔离用虚拟机，三者按隔离强度递增、按启动成本递增。

## 小结

- 容器与虚拟机只差「是否共享内核」；这条差别决定了启动速度、隔离强度与内核相关操作是否可用。
- Docker：`run/ps/logs/exec/rm` 六个命令覆盖日常；`-p` 绑定地址与 `-v` 数据卷是最容易出事的两个参数。
- `docker` 组等价 root；多人环境用 rootless Podman，并可交给 systemd 托管。
- compose 的 `depends_on` 只管顺序不管就绪；`down -v` 会删数据卷。
- 容器的三个边界：共享内核、依赖 cgroups/systemd、网络多一层；跨文件系统的绑定挂载很慢。
- libvirt/QEMU 需要 `/dev/kvm`；普通虚拟机默认拿不到，实验请在真机或开启嵌套虚拟化的环境做。

## 练习

1. 最小容器：跑 `nginx:alpine`，用 `-p 127.0.0.1:8080:80` 绑定回环，`curl` 验证；再改成 `-p 8080:80`，用 `ss -tlnp` 看绑定地址的变化。
2. 数据持久化：用命名卷跑一次数据库，写入数据后 `rm -f` 容器，重新起一个挂同一卷，验证数据还在；再试不挂卷的版本，确认数据消失。
3. 进容器：`docker exec -it <容器> sh` 后运行 `uname -r` 与 `cat /etc/os-release`，解释为什么内核版本是宿主的、发行版是镜像的。
4. compose：用正文的 yaml 起两个容器，`docker compose logs` 观察 app 被推迟到 db 健康后才启动；再把 `condition: service_healthy` 改回普通 `depends_on`，对比启动顺序差异，并解释「顺序 ≠ 就绪」。
5. 内核边界：在容器里尝试 `modprobe dummy` 与 `sysctl -w net.ipv4.ip_forward=1`，记录失败信息，并解释这是隔离设计还是权限问题。
6. 虚拟化能力检查：`ls -l /dev/kvm` 与 `grep -Ec '(vmx|svm)' /proc/cpuinfo` 各是什么结果？据此判断这台机器能否跑硬件加速的虚拟机。
