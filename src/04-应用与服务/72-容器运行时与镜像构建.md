# 第 72 章 容器运行时与镜像构建

第 71 章会「用」容器；这一章讲容器从哪来：镜像怎么分层、Dockerfile/Containerfile 怎么写、构建缓存为什么失效、rootless 构建需要什么前提。还会把「系统容器」与「镜像工具」放到一张地图上——nspawn、distrobox、LXD/Incus、Kata、mkosi 各有各的边界，不要拿一个工具硬套所有场景。

> 本章目标：能说清 OCI 镜像/运行时的分工（引擎、运行时、构建器）；会写多阶段 Containerfile 并用 `.dockerignore`、非 root 用户、版本锁定缩小镜像与攻击面；能用 Podman/Buildah 做 rootless 构建并读懂 `history`；知道系统容器（nspawn、distrobox、toolbox、LXD/Incus）与 VM 型容器（Kata、CRI-O）的适用边界；能识别「密钥进层」「缓存被 `COPY . .` 打穿」「`latest` 漂移」三类问题。
> 对应 Wiki：[Docker](https://wiki.archlinux.org/title/Docker)、[Podman](https://wiki.archlinux.org/title/Podman)、[Buildah](https://wiki.archlinux.org/title/Buildah)、[Systemd-nspawn](https://wiki.archlinux.org/title/Systemd-nspawn)、[Distrobox](https://wiki.archlinux.org/title/Distrobox)、[LXD](https://wiki.archlinux.org/title/LXD)

## 镜像、运行时与引擎：三层分工

| 层 | 职责 | 常见实现 |
| -------------- | ---------------------------------------- | ------------------------------------ |
| 镜像格式 | 分层 tar + 配置 JSON + manifest，按 digest 寻址 | OCI Image Spec |
| 运行时 | 真正创建命名空间、挂载、启动进程 | runc、crun |
| 容器引擎 | 拉镜像、管生命周期、网络与卷 | Docker、Podman、containerd |
| 构建器 | 按指令产出镜像层 | BuildKit、Buildah、buildx |
| 编排运行时 | 按 CRI 接口为集群启动 Pod | CRI-O、containerd |

一句话：**镜像是「文件系统 + 配置」的只读堆叠，容器是它在运行时加的一层可写层**。`docker`/`podman` 是引擎，`runc`/`crun` 才是最终 `clone()` 出进程的那一层。理解这层分工，才能在报错时判断是「引擎拉不到镜像」还是「运行时起不来进程」。

## Containerfile：从能跑到可维护

一个最小但合格的多阶段示例（放在 `/tmp/lab/Containerfile`）：

```dockerfile
FROM alpine:3 AS build
RUN apk add --no-cache gcc musl-dev
WORKDIR /src
COPY hello.c .
RUN gcc -static -O2 -o /hello hello.c

FROM alpine:3
RUN adduser -D -u 10001 app
USER 10001
COPY --from=build /hello /usr/local/bin/hello
ENTRYPOINT ["/usr/local/bin/hello"]
```

```bash
podman build -t lab-hello:v1 -f /tmp/lab/Containerfile /tmp/lab
podman run --rm lab-hello:v1
podman history lab-hello:v1
```

四个要点：

- **多阶段**：编译工具链留在 `build` 阶段，最终镜像只带静态产物；体积与漏洞面一起下降。
- **非 root**：`USER 10001` 之后，容器内默认不是 root；只在需要绑定低端口或改系统目录时才保留 root，并用能力收窄。
- **执行形式**：`ENTRYPOINT ["/usr/local/bin/hello"]` 是 exec 形式，信号能直达进程；shell 形式会被 `/bin/sh -c` 包一层，`SIGTERM` 可能传不到。
- **`.dockerignore`**：构建上下文只送需要的文件；漏了它，`.git`、`node_modules`、本地密钥都会进上下文，既慢又可能泄密。

## 构建缓存与可重复性

每条 `RUN`/`COPY` 都会生成一层；**前面的层变了，后面的缓存全部失效**。因此顺序应该是「变化少的在前」：

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

反过来写 `COPY . .` 再装依赖，每次改一行代码都要重装全部依赖。另一个常见误区是把密钥当 `ARG`/`ENV`：`history` 里能看到构建参数，层里也可能残留文件；用 BuildKit 的 secret 挂载或运行时注入，不要写进镜像。

可重复性靠三件事：**基础镜像按 digest 锁定、依赖版本锁定、构建命令固定**。`alpine:3` 是方便的选择，生产镜像应记录 `alpine@sha256:…`；`podman build --no-cache` 可以验证「不靠旧缓存也能构建成功」。

## 系统容器与镜像工具

| 工具 | 是什么 | 适合 | 注意 |
| ---------------- | ------------------------------------ | ------------------------------ | ------------------------------ |
| `systemd-nspawn` | 用命名空间启动一个完整 systemd 系统容器 | 本机跑另一发行版的完整用户空间 | 需要容器内有 init/systemd；不是镜像分发格式 |
| Distrobox | 基于 Podman/Docker 的「深度集成」开发容器 | 在宿主发行版里用另一发行版的工具链 | 共享家目录与设备，隔离弱于 VM |
| Toolbox | 类似的开发容器工具（Fedora 生态） | 不可变系统上的开发环境 | 与 Distrobox 定位重叠，选一个 |
| LXD / Incus | 系统容器与轻量 VM 管理器 | 跑完整系统、批量管理 | Incus 是 LXD 的社区分支；命令高度相似 |
| Kata Containers | 每个容器跑在轻量 VM 里 | 需要强隔离的多租户 | 启动与资源开销高于 runc |
| CRI-O | Kubernetes 的 CRI 运行时 | 集群节点 | 面向 K8s，不单独当日常引擎 |
| mkosi | 构建 OS 镜像（systemd 工具） | 制作可启动的系统镜像 | 学习曲线陡，偏镜像工程 |
| cloud-init | 云镜像首次启动初始化 | 批量部署 VM | 只在首次启动跑；改配置要重建实例 |
| Vagrant | 声明式管理开发 VM | 团队统一开发环境 | 依赖 VirtualBox/libvirt 等 provider |
| User-mode Linux | 把 Linux 作为用户态进程运行 | 内核实验、特殊隔离 | 性能与生态有限，偏实验 |

这张表的用法是「按隔离强度与分发方式选」：要完整系统但共享宿主内核 → nspawn/Incus 系统容器；要和宿主无缝混用工具 → Distrobox；要硬件级隔离 → Kata 或第 74 章的 VM；要产出可启动镜像 → mkosi/cloud-init。

## 失败模式

- **`COPY` 报文件找不到**：构建上下文路径写错，或文件被 `.dockerignore` 排除；`podman build` 的最后一个参数是上下文目录，不是 Containerfile 路径。
- **改一行代码重装所有依赖**：`COPY . .` 写在依赖安装之前，缓存被打穿；调整指令顺序。
- **密钥进了镜像**：`ARG`/`ENV`/`COPY .env` 都会留在层或配置里；`podman history --no-trunc` 能直接看到。发现后必须重建镜像，删层不等于删历史。
- **容器以 root 运行**：基础镜像默认 root，忘了 `USER`；用 `podman inspect --format '{{.Config.User}}'` 复核。
- **`latest` 漂移**：今天和下周拉到的不是同一镜像；生产用 digest 或不可变 tag。
- **`exec format error`**：在 x86 宿主上跑了 arm64 镜像；构建时用 `--platform` 明确目标架构。
- **rootless 构建失败**：`/etc/subuid`、`/etc/subgid` 未配置或 `newuidmap` 缺失；先 `podman info` 看 rootless 状态。
- **nspawn/Distrobox 起不来**：容器内没有 systemd，或宿主 cgroups 不满足；系统容器不是「随便一个镜像」都能跑。
- **Kata/CRI-O 装了却不会用**：它们面向 K8s/CRI，不是日常 `run` 的替代品；单机开发用 Podman 就够。

## 验证与回滚

构建产物的验证要落到「历史、用户、运行、架构」四项：

```bash
podman history --no-trunc lab-hello:v1
podman inspect --format 'User={{.Config.User}} Arch={{.Architecture}}' lab-hello:v1
podman run --rm lab-hello:v1 id
podman run --rm --platform linux/amd64 lab-hello:v1 uname -m
podman image inspect --format '{{.Digest}}' lab-hello:v1
```

`history` 看每层做了什么、有没有可疑的大文件；`Config.User` 看是否非 root；`run id` 验证实际身份；`--platform` 验证架构。回滚靠「保留旧 tag/digest」：

```bash
podman tag lab-hello:v1 lab-hello:previous
# 新版本出问题时
podman run --rm lab-hello:previous
podman tag lab-hello:previous lab-hello:current
```

镜像仓库里更稳的做法是按 digest 回滚（`image@sha256:…`），因为 tag 可以被覆盖而 digest 不会。删除镜像前先确认没有容器引用：`podman ps -a --filter ancestor=lab-hello:v1`。

## 取舍边界

- **Docker vs Podman vs Buildah**：Docker 生态与 compose 最顺；Podman 无守护进程、rootless 默认；Buildah 专做构建、可脚本化。三者产出的镜像都遵循 OCI，混用要看团队习惯而非技术优劣。
- **单阶段 vs 多阶段**：单阶段简单、调试方便；多阶段体积小、攻击面小，但构建文件更复杂。生产镜像优先多阶段。
- **精简基础镜像 vs 可调试**：`alpine`/distroless 小，但排障工具少；需要现场排查时另建 `-debug` 变体，不要往正式镜像里塞工具。
- **系统容器 vs 应用容器**：要完整 systemd、包管理器、多进程 → nspawn/Incus；只跑一个应用 → 应用容器。把数据库塞进系统容器通常不如直接用应用容器或宿主机服务。
- **Distrobox vs VM**：共享家目录、即开即用 → Distrobox；需要独立内核、强隔离 → VM（第 74 章）。
- **Kata vs runc**：多租户、不可信负载 → Kata 的 VM 隔离值得开销；单机自用 → runc/crun 足够。
- **本地构建 vs CI 构建**：本地快、便于调试；CI 可复现、可签名、可多架构。生产发布应在 CI 里按 digest 构建并留存 provenance。

## 小结

- OCI 把「镜像格式、运行时、引擎、构建器」分开；报错时先判断在哪一层。
- Containerfile 的顺序决定缓存命中；依赖安装放在源码复制之前。
- 多阶段、非 root、exec 形式、`.dockerignore`、版本/digest 锁定是可维护镜像的五条基线。
- 密钥不要进 `ARG`/`ENV`/镜像层；`history` 能看见，删层删不掉历史。
- 系统容器（nspawn、Distrobox、LXD/Incus）与 VM 型容器（Kata）各有隔离与分发边界。
- 回滚靠旧 tag/digest，不靠「重新构建一次应该差不多」。

## 练习

1. 多阶段构建：用正文的 Containerfile 构建并运行，比较单阶段版本与多阶段的镜像大小（`podman images`）。
2. 缓存实验：先 `COPY . .` 再装依赖，改一行源码重建，记录耗时；调整顺序后再改，比较缓存命中。
3. 非 root 验证：故意去掉 `USER`，用 `podman run --rm image id` 看到 uid=0；加回 `USER 10001` 再验证。
4. 密钥检查：用一个 `ARG TOKEN=secret` 构建，`podman history --no-trunc` 找出它；改用运行时环境变量或 secret 挂载。
5. 架构验证：构建一个 `--platform linux/arm64` 的镜像，在 x86 宿主上运行，记录 `exec format error`，再用 QEMU 模拟或换架构解释。
6. 系统容器：用 `systemd-nspawn` 或 Distrobox 起一个最小环境，说明它与应用容器的隔离差异；卸载/删除时确认没有残留挂载。
