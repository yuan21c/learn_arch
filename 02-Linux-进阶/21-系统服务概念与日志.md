# 第 21 章 系统服务概念与日志

一个长期运行的程序——Web 服务器、数据库、定时备份——和你在终端里敲的命令有本质区别：它没有终端、没人盯着、要在开机时自动起来、崩了要能自己恢复、出了事要留下证据。管这些事的东西叫**服务管理器**（supervisor），留下的证据叫**日志**。本章讲这两件事的通用概念；systemd 的具体命令在篇三第 32-34 章。

> 本章目标：能说清守护进程与交互程序的差别，以及为什么「自己 `&` 一下」不算部署服务；理解服务管理器要解决的五个问题；能区分「启用」与「启动」、进程活着与服务的健康；掌握日志的级别、来源与轮转，会用 `journalctl` 与 `/var/log` 定位问题；知道日志为什么要考虑容量、权限与隐私。
> 对应 Wiki：[Systemd](https://wiki.archlinux.org/title/Systemd)、[Systemd/Journal](https://wiki.archlinux.org/title/Systemd/Journal)

## 守护进程：没有终端的程序

守护进程（daemon）是脱离终端在后台长期运行的程序。它和交互程序的差别不在「在不在后台」，而在**生命周期由谁负责**：

| 对比 | 交互程序 | 守护进程 |
| --- | --- | --- |
| 控制终端 | 有，`Ctrl-C` 即结束 | 无，挂断终端不影响它 |
| 标准输入输出 | 终端 | 通常接到日志或 `/dev/null` |
| 生命周期 | 你退出就结束 | 开机自起、崩溃自恢复 |
| 状态查询 | 看屏幕输出 | 查服务状态与日志 |

历史上守护进程会自己做「两次 `fork` + `setsid`」来脱离终端；现代做法正相反：**程序保持前台运行，把「后台化」交给服务管理器**。理由很实际——自己 `fork` 到后台的程序，管理器就看不到它的主进程，无法判断它是否还健康，也无法收集它的输出。这就是「用 `nohup app &` 部署服务」必然出问题的原因：进程在，但没人管它；进程死了，没人知道。

## 服务管理器要解决的五个问题

1. **启动时机**：网络就绪之后再起 Web 服务，数据库就绪之后再起应用；
2. **依赖顺序**：A 依赖 B，B 没起来就不该启动 A；
3. **失败处理**：崩了要不要重启、重启几次后放弃、失败如何告警；
4. **日志收集**：把服务的标准输出与错误收进统一的日志系统；
5. **资源与权限**：以哪个用户跑、能用多少内存与 CPU、能给哪些权限。

从 SysV 的启动脚本到今天的 systemd，变的只是配置方式，这五个问题一直没变。systemd 的答案是「单元（unit）」：一个单元描述一种资源，服务是 `service`，定时任务是 `timer`，套接字激活是 `socket`，一组单元的组合是 `target`，挂载点是 `mount`。这个模型的好处是依赖关系可以声明（`After=`、`Requires=`），而不是靠脚本里的 `sleep 5`。

有两个概念必须分清：

- **启动（start）**：现在把它跑起来，重启后不一定；
- **启用（enable）**：设置开机自启，现在不一定跑。

所以「服务没开机自启」和「服务现在没跑」是两个独立问题，命令也不同。新手最常犯的错是只 `start` 没 `enable`，重启后「配置丢了」。

还有一个更隐蔽的区分：**进程活着 ≠ 服务健康**。进程可能卡死、可能在无限重启循环里。好的服务管理器会记录「失败」状态，好的服务本身会提供健康检查端点。部署时要看的是「服务状态 + 最近日志」，而不是 `ps` 里有没有那个 PID。

## 日志：三层来源

Linux 的日志来自三个地方，各有各的用途：

| 来源 | 内容 | 查看方式 |
| --- | --- | --- |
| 内核环形缓冲区 | 硬件探测、驱动、内核报错 | `dmesg` |
| 服务标准输出/错误 | 应用自己打印的东西 | `journalctl -u <服务>` |
| 传统日志文件 | 应用按自己的格式写到 `/var/log` | `tail -f`、`grep` |

传统 syslog 的模型是「设施（facility）+ 级别（severity）」：`kern`、`auth`、`daemon`、`cron` 是设施，级别从高到低是 `emerg`、`alert`、`crit`、`err`、`warning`、`notice`、`info`、`debug`。今天 journald 仍然沿用这套级别，用 `-p` 过滤：

```bash
journalctl -p err -b            # 本次启动的错误及以上
journalctl -u sshd --since "1 hour ago"
journalctl -f                   # 实时跟随（类似 tail -f）
journalctl --disk-usage         # 日志占用多少磁盘
```

journald 相比纯文本日志多了两样东西：**结构化字段**（每条日志带 `_PID`、`_COMM`、`_SYSTEMD_UNIT` 等元数据，可以精确过滤）和**自动轮转**（按时间与体积限额，不用手工配 `logrotate`）。代价是日志默认是二进制格式，必须用 `journalctl` 读，不能直接 `grep`。

## 轮转：不轮转会撑爆磁盘

日志是只增不减的，一张跑了一年的服务器能把 `/var` 写满。轮转（rotation）解决三件事：按大小或时间切分、压缩旧文件、删除过期文件。传统工具是 `logrotate`，配置在 `/etc/logrotate.d/`；journald 则在 `/etc/systemd/journald.conf` 里用 `SystemMaxUse`、`MaxRetentionSec` 控制。

```bash
sudo du -sh /var/log            # 谁在占空间
sudo journalctl --vacuum-size=500M   # 只保留 500M 日志
```

> **危险**：`--vacuum-size`/`--vacuum-time` 会**永久删除**旧日志，事后无法回溯历史故障。执行前确认可丢弃的时间段，需要留存的先 `journalctl --since ... > backup.log` 导出。

磁盘写满的后果不只是「不能写日志」：服务写不了临时文件会崩，数据库会拒绝写入，甚至无法登录（`/var` 满时 `sudo` 都可能失败）。所以「日志占了多少」应该是巡检项之一。

## 日志的另外三件事

- **时间**：日志时间戳依赖系统时钟。时钟错了，日志时间线就乱了，跨机器关联也无从谈起（第 20 章末尾的 `timedatectl`）。
- **权限与隐私**：日志里常有 IP、用户名、路径，甚至误打出来的令牌与密码。`/var/log` 与 journal 的默认权限是受限的，不要把日志文件随手 `chmod 644`，也不要直接贴到公开渠道。
- **集中式收集**：单机日志在机器挂掉时就没了。生产环境通常把日志送到中央收集器（如 journald 的 `ForwardToSyslog`、或专门的日志系统），这一步的取舍是「多一个组件」与「事后能查」之间的权衡。

## 排查一个起不来的服务

顺序固定，别跳步：

1. **看状态**：服务管理器的状态输出会给出退出码与最后一次失败原因；
2. **看日志**：`journalctl -u <服务> -b --no-pager`，重点看最后 30 行与第一个错误；
3. **验证配置**：多数服务有 `-t`/`--test`/`configtest` 之类的语法检查，先验证再重启；
4. **看依赖**：端口被占（第 18 章的 `ss`）、目录权限、环境变量、上游服务未就绪；
5. **手工前台跑一次**：用服务的用户身份、在前台启动，错误会直接打到终端——这是最快的一步，也最容易被跳过。

一个常见误判：看到 `Active: failed` 就以为服务代码有问题，实际是「端口被占用」或「配置目录权限不对」。日志的第一条错误通常不是根因，**最早的那条**往往才是。

## 小结

- 守护进程的关键不是「在后台」，而是生命周期由服务管理器负责；`nohup app &` 不是部署。
- 服务管理器解决五件事：启动时机、依赖顺序、失败处理、日志收集、资源与权限。
- `start` 与 `enable` 是两件事；进程活着不等于服务健康。
- 日志三个来源：内核（`dmesg`）、服务输出（`journalctl -u`）、传统文件（`/var/log`）；级别从 `emerg` 到 `debug`。
- 轮转必须配，否则 `/var` 会被写满；journald 用 `SystemMaxUse`，传统日志用 `logrotate`。
- 排障顺序：状态 → 日志 → 配置验证 → 依赖 → 前台手工跑；找**最早**的错误而不是最后一条。

## 练习

1. 前台与后台（环境：WSL）：用 `python3 -m http.server 8000` 前台起一次，`Ctrl-C` 结束；再用 `nohup … &` 起一次，`ps` 找到 PID 后 `kill -9`，说明为什么这两种方式都「不算服务」。
2. 日志三来源（环境：WSL）：分别运行 `dmesg | tail -5`、`journalctl -b -p err --no-pager | tail -10`、`ls -l /var/log` 并 `tail -5` 其中一个文件，说出三者内容与格式的差别。
3. 日志占用（环境：WSL）：`journalctl --disk-usage` 与 `du -sh /var/log` 各跑一次，比较数字；再用 `tail -100 某日志 | grep -i error` 练习按关键字过滤。
4. 服务失败的定位（环境：VM）：写一个必然失败的测试服务（命令写 `/bin/false`），`enable` 并 `start`，用状态输出、`journalctl -u`、`systemctl --failed` 三种方式定位失败原因，记录各自给出的信息。
5. 端口冲突（环境：WSL）：先起 `python3 -m http.server 8000`，再起第二个同端口实例，观察报错；用 `ss -tlnp | grep 8000` 确认占用者，说明日志里第一条错误与根因的关系。
6. 轮转策略（环境：VM）：查看 `/etc/logrotate.d/` 里任一配置，说出它的切分周期、保留份数与压缩策略；再读 `journald.conf` 中的 `SystemMaxUse` 默认值，解释两者管的对象不同。
