# 第 13 章 进程管理

第 12 章把进程讲成了概念：带 PID 的运行实例、随生随灭的 `/proc/PID` 目录。现在把它变成日常操作——谁在跑、跑了多久、占多少 CPU、怎么停、怎么让它排队。这一章的所有命令都在同一个观察面上工作：内核维护的进程表；`ps`/`top` 读它，`kill` 改它，`nice` 调它的调度权重。

> 本章目标：能用 `ps` 的多套选项看清进程与进程树，读懂 `STAT` 状态码；理解前台、后台与作业控制（`&`、`Ctrl-Z`、`jobs`、`bg`、`fg`、`disown`）的区别；掌握信号机制与 `kill` 的正确用法，知道为什么优先 `TERM` 而不是 `KILL`；会用 `nice`/`renice` 调整调度优先级；能识别僵尸进程与孤儿进程。
> 对应 Wiki：[Improving performance](https://wiki.archlinux.org/title/Improving_performance)、[Core utilities](https://wiki.archlinux.org/title/Core_utilities)

## 进程表：ps 的三套写法

Linux 的 `ps` 同时兼容三种历史风格，选项前缀决定风格——不加前缀是 BSD 风格，加 `-` 是 UNIX 风格，加 `--` 是 GNU 长选项。日常最常用的两条（环境：WSL，实跑）：

```bash
ps aux | head -5      # BSD：所有进程，含无终端进程（a=所有用户，u=用户视角，x=含无终端）
ps -ef | head -5      # UNIX：所有进程，-e 全部，-f 完整格式
```

| 列                 | 含义                                              |
| ------------------ | ------------------------------------------------- |
| `PID` / `PPID`     | 进程号 / 父进程号                                 |
| `STAT`             | 状态码，见下节                                    |
| `NI`               | nice 值，影响调度权重（见「优先级」一节）         |
| `%CPU` / `%MEM`    | 自进程启动以来的 CPU / 内存占比                   |
| `TIME` / `ELAPSED` | 累计消耗的 CPU 时间 / 从启动到现在的墙钟时间      |
| `TTY`              | 关联终端；`?` 表示没有终端（守护进程、后台任务）  |
| `COMMAND` / `CMD`  | 命令行；BSD 风格截断长命令，要完整看用 `ps auxww` |

BSD 与 UNIX 风格的关键差异：`ps aux` 的 `%CPU` 是**平均占用**（总 CPU 时间 ÷ 存活时间），新启动的进程数字可能偏高；要看**此刻**谁在吃 CPU，用 `top` 而不是 `ps`。要挑列、按列排序，用 `-o`（环境：WSL）：

```bash
ps -eo pid,ppid,stat,ni,pcpu,pmem,cmd --sort=-pcpu | head -8
```

## 状态码 STAT：一个字母加几个后缀

`STAT` 的第一位是进程状态，取自内核的 `task_state`：

| 码  | 状态                  | 说明                                                   |
| --- | --------------------- | ------------------------------------------------------ |
| `R` | Running / Runnable    | 正在 CPU 上跑，或在运行队列里等 CPU                    |
| `S` | Interruptible Sleep   | 可中断睡眠，最常见——等输入、等定时器、等网络           |
| `D` | Uninterruptible Sleep | 不可中断睡眠，通常在等磁盘 I/O；`kill -9` 也要等它返回 |
| `T` | Stopped               | 被信号暂停（`Ctrl-Z` 或 `SIGSTOP`）                    |
| `Z` | Zombie                | 已退出但父进程尚未回收                                 |
| `I` | Idle                  | 内核线程的空闲态                                       |

后缀修饰第一位：`s` 是会话首进程（session leader），`+` 在前台进程组，`l` 有多线程，`<` 高优先级，`N` 低优先级。所以 `Ss` 是「可中断睡眠的会话首进程」，`R+` 是「正在前台跑」。用 `ps -eo stat,cmd | grep -E '^(D|Z)'` 可以快速找出卡在 I/O 或没被回收的进程。

## 进程树：谁生了谁

进程的亲子关系构成一棵树，根是 PID 1。看树用 `pstree`（环境：WSL）：

```bash
pstree -p | head -20      # -p 标出每个进程的 PID
```

父子关系解释了很多现象：终端里跑的命令都是 shell 的子进程，所以关掉终端，前台任务会收到 `SIGHUP`（挂断）；反过来，父进程先死，子进程会被 PID 1 收养，成为**孤儿进程**，继续运行而不受影响——这就是 `nohup` 与 `disown` 能保住任务的原理（见作业控制）。

## top 与 htop：动态视图

`ps` 是快照，`top` 是每秒刷新的仪表盘（环境：WSL）：

```bash
top           # 默认按 CPU 排序，q 退出
```

`top` 的交互键值得记：`P` 按 CPU 排序、`M` 按内存排序、`T` 按运行时间排序、`1` 展开每个逻辑 CPU、`c` 显示完整命令行、`H` 按线程显示、`k` 直接发信号（输入 PID 和信号号）、`q` 退出。表头里的 `load average` 三个数字与 `/proc/loadavg` 同源（第 12 章），判据仍是「是否持续超过逻辑 CPU 数」。`htop` 是更好用的替代品，带颜色、可鼠标操作、支持过滤（`F4`）与树形视图（`F5`），Arch 下装 `htop` 即可。

## 前台、后台与作业控制

shell 的**作业**（job）是一组进程，用 `%N` 编号管理。三条操作构成完整的作业控制（环境：WSL）：

```bash
sleep 300 &            # 放进后台，shell 立刻返回提示符，并打印 [1] PID
jobs -l                # 列出本 shell 的作业：作业号、PID、状态、命令
fg %1                  # 把 1 号作业调回前台
```

前台进程按 `Ctrl-Z` 会被 `SIGTSTP` 暂停（状态变 `T`），此时可以二选一：

```bash
bg %1                  # 让暂停的作业在后台继续跑
kill %1                # 直接给整个作业发信号
```

几个容易被混淆的点：

- `Ctrl-Z` 是**挂起**不是结束，被挂起的进程仍占内存，必须 `bg` 或 `kill` 处理；
- `Ctrl-C` 发 `SIGINT`，只对**前台进程组**有效，后台任务不受影响；
- 后台任务的输出仍会打到终端；要让它在退出终端后继续跑，用 `nohup 命令 &`（忽略 `SIGHUP`，输出改写到 `nohup.out`），或者对已启动的任务 `disown %1`（从 shell 的作业表里摘掉，退出时不再发 `SIGHUP`）；
- 作业控制是终端交互功能，**脚本里不可用**——脚本没有前台进程组的概念。

## 信号：与进程对话的协议

信号是内核投递给进程的异步通知，进程可以对多数信号注册处理函数。`kill` 的名字会误导——它只是「发信号」，最常见的用途才是终止。列出全部信号（环境：WSL）：

```bash
kill -l                # 列出编号与名称
```

日常只需记住这几个：

| 信号      | 编号 | 含义与行为                                             |
| --------- | ---- | ------------------------------------------------------ |
| `SIGHUP`  | 1    | 挂断；终端关闭时发给前台进程组，守护进程常借它重读配置 |
| `SIGINT`  | 2    | 中断，即 `Ctrl-C`                                      |
| `SIGQUIT` | 3    | 退出并转储核心（`Ctrl-\`），用于抓 core dump           |
| `SIGTERM` | 15   | **默认终止信号**，可被捕获，进程能先保存状态再退出     |
| `SIGKILL` | 9    | 强制杀死，**不可捕获、不可忽略**，进程没有收尾机会     |
| `SIGSTOP` | 19   | 强制暂停，同样不可捕获                                 |
| `SIGCONT` | 18   | 恢复被暂停的进程                                       |

正确顺序是先礼后兵（环境：WSL，`/tmp` 演练）：

```bash
sleep 300 & pid=$!
kill -TERM $pid        # 先请求退出
sleep 1; ps -p $pid    # 若还在，说明它不理会 TERM
kill -KILL $pid        # 再强制
kill -0 $pid; echo $?  # 只探测存在性，不投递信号：0 存在，1 不存在
```

**为什么避免直接 `-9`**：`KILL` 让进程跳过清理——临时文件残留、锁文件不释放、数据库事务未提交。对 `D` 状态的进程 `-9` 也无效，它要等内核把 I/O 做完。按名字发信号更省事：`pkill -TERM nginx`、`pgrep -a nginx`（`-a` 显示命令行），`killall` 按精确进程名匹配但各家实现不同，脚本里优先 `pgrep`/`pkill`。

## 优先级：nice 与调度权重

Linux 的普通调度策略是 CFS，权重由 **nice 值**决定：范围 `-20`（最优先）到 `19`（最不优先），默认 `0`。`top` 里的 `PR` 是「优先级」，与 nice 的关系是 `PR = 20 + NI`（普通进程）。

```bash
nice -n 10 tar -czf big.tar.gz big/     # 以 nice 10 启动，让出 CPU
renice -n 5 -p 1234                     # 改已运行进程的 nice 值
```

两条规则：**只有 root 能把 nice 值调低**（提高优先级），任何用户都能把自己的进程调高；nice 值不改变进程能拿到多少内存或 I/O，只影响 CPU 时间的分配顺序——磁盘 I/O 的优先级由 cgroup 的 `io.weight` 控制，属于容器与 systemd 的范畴（第 46 章）。

## 僵尸与孤儿

- **僵尸（Z）**：子进程已退出，父进程还没 `wait()` 取走退出码。僵尸不占 CPU 和内存（只剩一个进程表项），但会占 PID。**僵尸不能被杀**——它已经死了；要么等父进程回收，要么杀掉父进程让它被 PID 1 收养后立刻回收。
- **孤儿**：父进程先退出，子进程还活着，被 PID 1 收养。孤儿本身完全正常，不是故障。两者共同点：都说明父进程对子进程的生命周期管理有缺口。

排查僵尸（环境：WSL）：

```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
```

若看到了，先找它的 `PPID` 是谁——问题在父进程没有正确处理 `SIGCHLD`，修应用，而不是反复 `kill -9`。

## 一键排查的顺序

遇到「机器变慢」时按这个顺序走，避免上来就 `kill`：

1. `uptime` 看负载与 CPU 核数是否匹配，`top` 按 `P`/`M`/`1` 分别看 CPU、内存与单核；
2. `ps -eo stat,pid,cmd | grep '^D'` 查是否有进程卡在 I/O——这是「负载高但 CPU 空闲」的典型原因；
3. `free -h` 看内存与 swap，`vmstat 1` 看 `si/so` 是否在换页；
4. 定位到具体进程后再决定 `renice` 还是 `kill -TERM`；服务类进程不要手工 `kill`，交给 systemd（第 32-34 章）。

## 小结

- `ps` 有三套选项风格；`STAT` 第一位是状态（`R/S/D/T/Z`），后缀标会话、前台、多线程与优先级。
- 作业控制只对交互式 shell 有效：`&` 后台、`Ctrl-Z` 挂起、`jobs` 查看、`bg`/`fg` 切换、`disown` 脱离；`nohup` 抗挂断。
- 信号是异步通知；`TERM`（15）可捕获、`KILL`（9）不可捕获，先 `TERM` 后 `KILL`，`D` 状态杀不掉。
- nice 值 `-20..19` 调 CPU 权重，只有 root 能提高优先级；它不管内存与 I/O。
- 僵尸是父进程未回收，杀不掉；孤儿是父进程先死，本身正常。
- 排查变慢的顺序：负载 → CPU → I/O 等待 → 内存/swap → 定位进程 → 决定手段。

## 练习

1. 三套写法对照（环境：WSL）：分别运行 `ps aux | head`、`ps -ef | head`、`ps -eo pid,ppid,stat,ni,pcpu,cmd --sort=-pcpu | head`，说出三种输出的列差异，并解释为什么 `%CPU` 不等于「此刻的占用」。
2. 状态码辨认（环境：WSL）：制造三种状态——`sleep 300 &`（`S`）、`sleep 300` 后按 `Ctrl-Z`（`T`）、`dd if=/dev/zero of=/tmp/f bs=1M count=200` 同时另一终端 `ps`（可能见到 `D` 或 `R`）。用 `ps -o stat,cmd -p PID` 逐个确认，并说明 `Ss`、`R+` 的含义。
3. 作业控制全流程（环境：WSL）：`sleep 300 &` 记下作业号与 PID；`jobs -l` 查看；`fg %1` 调回前台后 `Ctrl-Z` 挂起；`bg %1` 恢复后台；最后 `kill %1` 结束并 `jobs` 确认消失。
4. 信号实验（环境：WSL，`/tmp` 演练）：启动一个会写文件的循环脚本，先 `kill -TERM` 观察它是否有机会清理临时文件，再启动同样脚本用 `kill -KILL`，对比残留。写一段话说明为什么生产环境默认先 `TERM`。
5. 优先级对照（环境：WSL）：同时启动两个相同的 CPU 密集任务，一个 `nice -n 19`，一个默认，用 `top` 观察 `NI`/`PR`/`%CPU` 的差别；再用 `renice` 把默认那个调成 `19`，观察变化。
6. 僵尸复现与回收（环境：WSL，`/tmp` 演练）：写一个父进程 `fork` 后不 `wait` 的脚本，用 `ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'` 找到 `Z` 状态子进程，验证 `kill -9` 无效；结束父进程后确认僵尸消失。
