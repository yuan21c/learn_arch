# 第 15 章 软件安装的通用概念

前面四章讲的是「系统怎么跑」，从这一章起转向「系统上装什么、怎么装」。不管你用 apt、dnf、pacman 还是 brew，底层的选择只有三类：**用发行版的二进制包**、**从源码编译**、**跑在容器里**。这一章只讲这三条路的通用原理与取舍，不涉及任何发行版的具体命令——pacman 的细节留给第 24-26 章。

> 本章目标：能说清包管理器的六项职责与「依赖」的三种含义；理解二进制包、源码编译、容器三种安装方式的代价与适用场景；知道动态链接库为何会导致「装的时候好好的，升级后跑不起来」；理解仓库、镜像与签名组成的信任链；能判断什么时候该用语言级包管理器而不是系统包管理器。
> 对应 Wiki：[Pacman](https://wiki.archlinux.org/title/Pacman)、[System maintenance](https://wiki.archlinux.org/title/System_maintenance)

## 三条路，不是三十条

| 方式 | 装的是什么 | 优点 | 代价 |
| --- | --- | --- | --- |
| 二进制包 | 别人替你编译好的程序 + 元数据 | 快、可查询、可卸载、自动处理依赖 | 版本受仓库限制，可能有裁剪 |
| 源码编译 | 你自己按本机参数生成的可执行文件 | 可用最新版、可改编译选项 | 慢、依赖要自己解决、无统一卸载记录 |
| 容器镜像 | 应用 + 它的整套用户态依赖 | 环境一致、隔离、易分发 | 多一层运行时、共享内核、数据持久化要另配 |

三者并不互斥。一台开发机上同时存在系统包（编辑器、编译器）、源码装的工具（某个最新版 CLI）、容器里的服务（数据库）是常态。关键是知道**谁在管它的生死**——升级、卸载、安全更新分别由哪套机制负责。

## 包管理器到底在管什么

一个包管理器不是「下载器」，它至少要负责六件事：

1. **依赖解析**：把「A 需要 B ≥ 2.0，B 需要 C」展开成一组合法的安装集合；
2. **下载与校验**：从仓库取包，校验哈希与签名；
3. **文件登记**：记录「这个包装了哪些文件」，卸载与冲突检测都靠它；
4. **事务**：一组包的安装要么全成功要么全回退，避免装到一半的系统；
5. **升级与回滚**：知道新旧版本的差异，能降级；
6. **数据库**：维护「已安装什么版本」的本地记录。

这六件事解释了为什么「手动解压 tar.gz 到 /usr/local」不算安装——第 3 项和第 6 项都没有，于是不会有任何工具知道它的存在。这也是源码安装最常见的事故来源：删不干净、升级被覆盖、与其他包冲突。

### 「依赖」的三种含义

- **运行时依赖**：程序跑起来必须有的库或数据，缺了立刻报 `error while loading shared libraries`；
- **构建时依赖**：只在编译阶段需要（编译器、头文件），产物不需要它们；
- **可选依赖**：不装也能跑，只是少某个功能（如 `curl` 的 HTTP/2 支持）。

包管理器的元数据把这三类分开记录。降级、裁剪系统时，最容易踩的坑是只看了运行时依赖，忘了构建时依赖——或者反过来，把构建时依赖留在了生产机上。

## 二进制包：仓库、镜像与信任链

二进制包来自**仓库**（repository），仓库通过**镜像**（mirror）分发，每个包带**签名**。三者构成一条信任链：

```text
开发者签名包 → 仓库索引（含校验和）→ 镜像同步 → 你的机器用本地信任的公钥验证
```

因此三件事必须记住：镜像只是加速，**不改变内容**（内容由签名保证）；换镜像不会让包变得更可信或更不可信；而**导入未知公钥**等于把信任链的根换掉——这是很多「装不上，网上说要先加个 key」教程最危险的地方。

仓库通常分层：官方核心仓库（稳定、经过审核）、社区/额外仓库（数量多、审核较松）、第三方仓库（如某些软件的官方源）、以及 AUR 这类「打包脚本集合」而非二进制仓库（第 32 章）。

## 版本与 ABI：为什么升级会弄坏东西

程序依赖的不是「库的名字」，而是库的**二进制接口（ABI）**。动态链接的程序在运行时才去找 `.so` 文件：

```bash
ldd /usr/bin/ls          # 列出运行时依赖的共享库
file /usr/bin/ls         # 看它是动态链接还是静态链接
```

两类发行版策略由此分叉：**固定版本发行版**（Debian、RHEL 系）倾向于「大版本内不升 ABI」，所以能长期稳定；**滚动发行版**（Arch、Gentoo）持续升级，因此要求**整系统一起升**——单独升级一个库而不同步升级依赖它的程序，就会出现「昨天还好，今天启动就报找不到符号」。第 24 章讲的「不能部分升级」正是这条原理的纪律化表达。

这也解释了为什么很多项目发布**静态链接**的二进制（把所有依赖打进一个文件）：牺牲体积换「拷过去就能跑」，代价是库的安全更新要等发布者重新编译。

## 源码编译：三步与它的代价

传统 GNU 项目的安装是三步（环境：WSL，`/tmp` 演练）：

```bash
./configure --prefix=/usr/local     # 检查环境、生成 Makefile
make -j$(nproc)                     # 编译
sudo make install                   # 复制到 prefix 下
```

这看起来简单，代价却分散在细节里：`configure` 失败通常意味着缺构建时依赖；`--prefix` 决定了文件落在 `/usr/local`（本地覆盖）还是 `/usr`（系统目录，会与包管理器打架）；`make install` 不做任何登记，卸载只能靠 `make uninstall`（很多项目根本不提供）或对照 `install_manifest.txt` 手工删。

打包者做的事，正是把这三步放进受控环境：指定 `DESTDIR` 安装到临时目录、只收集需要的文件、生成元数据。所以**「自己编译」和「打一个包」的区别不是技术难度，而是有没有登记与可复现性**。

## 容器：把依赖一起打包

容器镜像里装的是应用 + 它的用户态依赖（库、解释器、配置），运行在宿主内核上。与虚拟机的关键差别只有一条：**容器共享宿主内核**，虚拟机跑自己的内核。这条差别带来两个后果：容器启动快、开销小；但容器里的内核相关行为（模块、`sysctl`、某些特权操作）受宿主限制。

在 WSL 上这条差别会被放大一层——容器跑在 WSL 的轻量虚拟机上，而 WSL 虚拟机又共享 Windows 的内核接口，涉及 `systemd`、网络模式与内核模块的场景要特别验证（第 45 章）。

## 语言级包管理器：边界在哪

`pip`、`npm`、`cargo`、`go install` 也能装软件，但它们管的是**某个语言生态的库与工具**，与服务系统包管理器有两处冲突：

- **同一个东西两份**：系统包管理器装了 `python-requests`，`pip install requests` 又装一份到用户目录，版本不同、导入路径不同，排障时极难分辨；
- **绕过系统信任与文件登记**：`pip install` 装的东西不在包管理器数据库里，系统升级不会管它，卸载也容易残留。

工程上的共识是：**系统级组件用系统包管理器；项目依赖用项目级隔离环境**（`venv`、`node_modules`、`Cargo.toml`），不要往系统 Python 里 `pip install`。新版发行版甚至用 `externally-managed-environment` 错误直接阻止这种行为，这不是刁难，而是保护。

## 怎么选：一张决策表

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 系统工具、库、桌面软件 | 发行版仓库 | 有签名、有依赖解析、可随系统升级 |
| 仓库里没有、但有人打包 | AUR / 第三方打包 | 仍享受登记与卸载（第 30-32 章） |
| 需要最新版或特殊编译选项 | 源码编译 | 接受「自己负责升级与卸载」 |
| 服务端应用、需要环境一致 | 容器 | 依赖随镜像走，宿主保持干净 |
| 项目依赖 | 语言级隔离环境 | 不污染系统，版本随项目锁定 |

还有一条常被忽略的原则：**安装来源越少，系统越可维护**。每多一种来源，就多一套升级路径与一套排障知识。

## 小结

- 三条路：二进制包（快、有登记）、源码（灵活、无登记）、容器（环境一致、共享内核）。
- 包管理器六职责：依赖解析、下载校验、文件登记、事务、升级回滚、本地数据库；「手动解压」缺的是登记与数据库。
- 依赖分运行时、构建时、可选三类；只看一类就会在裁剪或降级时出事。
- 信任链是「签名 → 索引 → 镜像」；镜像只加速，导入未知公钥才是真正的风险。
- 程序依赖 ABI 而非库名，滚动发行版必须整系统升级；静态链接换来可移植、牺牲安全更新。
- 语言级包管理器管项目依赖，系统组件交给系统包管理器。

## 练习

1. 依赖观察（环境：WSL）：`ldd /usr/bin/ls` 与 `file /usr/bin/ls` 各跑一次，说明 `ls` 是动态还是静态链接；再找一个静态链接的程序（提示：`go` 或 `busybox` 编译产物）做对比。
2. 源码安装演练（环境：WSL，`/tmp` 演练）：下载一个用 Autotools 的小项目（或用 `hello` 示例），走 `configure --prefix=/tmp/prefix`、`make`、`make install`，然后用 `find /tmp/prefix -type f` 列出它装了哪些文件，并回答「如果现在要卸载，你打算怎么做」。
3. 登记与否的差别（环境：WSL）：分别用系统包管理器安装一个小工具（如 `tree`）与源码安装同一个程序，各用「查询它属于谁」的命令对比——说出为什么一个能查、一个查不到。
4. 容器与虚拟机的边界（环境：WSL，若已装 Docker/Podman）：运行 `docker run --rm alpine uname -r` 与 `uname -r` 对比内核版本，解释为什么容器里看到的是宿主内核。
5. 语言级包管理器边界（环境：WSL）：`python3 -m venv /tmp/venv && /tmp/venv/bin/pip install requests`，对比系统 Python 是否受影响；再解释为什么不该直接 `sudo pip install`。
6. 决策练习（环境：无）：为四个场景各选一条路并说明理由——(a) 需要 `htop`；(b) 某个仓库没有的最新版 CLI 工具；(c) 团队共享的 PostgreSQL；(d) 项目依赖 `requests`。
