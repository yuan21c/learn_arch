# 第 20 章 系统启动概念

按下电源键到出现登录提示符，中间发生了什么？这条链条不长——五个阶段——但每一环都能让系统起不来。本章只讲**通用流程与每一环的职责**，让你在遇到「开机黑屏」「卡在某个提示」「进不去系统」时知道该看哪里；Arch 特有的引导器配置、`mkinitcpio` 与内核参数细节，留给第 41 章。

> 本章目标：能按顺序说出固件、引导器、内核与 initramfs、init、用户空间五个阶段各自做什么；理解 UEFI 与 BIOS 的差别、ESP 的作用与 Secure Boot 的影响；知道 initramfs 为什么必须存在；会用 `dmesg` 与 `journalctl -b` 定位是哪个阶段出了问题；理解引导参数与救援目标（rescue/emergency）的用途。
> 对应 Wiki：[Arch boot process](https://wiki.archlinux.org/title/Arch_boot_process)、[Systemd](https://wiki.archlinux.org/title/Systemd)

## 五个阶段

```text
固件(UEFI/BIOS) → 引导器(GRUB/systemd-boot) → 内核 + initramfs → init(PID 1) → 用户空间(服务与登录)
```

| 阶段 | 谁在跑 | 职责 | 失败表现 |
| --- | --- | --- | --- |
| 固件 | 主板上的 UEFI/BIOS | 自检、初始化硬件、按启动顺序找引导程序 | 无输出、进固件设置、找不到启动设备 |
| 引导器 | GRUB、systemd-boot、rEFInd | 选内核、加载内核与 initramfs、传引导参数 | 出现 `grub>` 提示、菜单后黑屏 |
| 内核 | Linux 内核 + initramfs | 初始化硬件与驱动、挂载真正的根文件系统 | `Kernel panic`、卡在 `Waiting for root device` |
| init | systemd（PID 1） | 挂载其余文件系统、启动服务、管理进程树 | 停在 `A start job is running…`、进紧急模式 |
| 用户空间 | 各服务、登录管理器 | 提供登录界面与业务服务 | 能登录但服务异常、图形界面起不来 |

排查的第一原则是**先定位阶段**：屏幕上有内核日志说明已过引导器；能进 `journalctl` 说明 init 已经起来。

## 固件：UEFI 与 BIOS

固件的任务是找到「下一段代码」。两代标准差别很大：

| 对比 | 传统 BIOS | UEFI |
| --- | --- | --- |
| 启动方式 | 读磁盘第一个扇区（MBR）的引导代码 | 从 FAT32 的 **ESP**（EFI 系统分区）加载 `.efi` 程序 |
| 分区表 | MBR | GPT（也兼容 MBR） |
| 启动项 | 靠磁盘顺序 | NVRAM 里的启动项（可用 `efibootmgr` 查看） |
| 安全启动 | 无 | Secure Boot：只允许签名过的引导程序与内核 |

ESP 是一个独立的小分区（通常 512 MiB-1 GiB，FAT32；多内核或 UKI 给 1 GiB），每个操作系统的引导程序各占一个目录（如 `/boot/EFI/...`）。它能被多个系统共享，这是双系统共存的基础。**Secure Boot** 打开时，未签名的引导程序与内核会被拒绝——这不是故障，而是策略；处理方式有签名、用 shim，或关闭 Secure Boot（三条路线见第 42 章）。

如果开机直接进了固件设置界面，先查两件事：启动顺序里有没有你的系统盘，以及 ESP 里的 `.efi` 文件是否还在。

## 引导器：不只是「选择菜单」

引导器的核心工作有三件：**加载内核**、**加载 initramfs**、**传递引导参数**。菜单只是外壳。

- **GRUB**：功能最全，支持 BIOS 与 UEFI、多系统、脚本化配置；代价是配置生成逻辑复杂，改错了不易察觉。
- **systemd-boot**：只支持 UEFI，配置就是几个文本文件，简洁；功能也相应少。
- **rEFInd**：自动探测多个系统，适合多系统桌面。

引导参数是排障的重要抓手，常见的几类：

| 参数 | 作用 |
| --- | --- |
| `root=UUID=…` | 告诉内核真正的根文件系统在哪 |
| `ro` / `rw` | 以只读还是读写方式挂载根 |
| `quiet` | 少打印内核日志（排障时应去掉） |
| `nomodeset` | 禁用 KMS、退回基本显示/控制台（不是「能进图形」），先救急再装/换驱动 |
| `systemd.unit=rescue.target` | 引导到单用户式的救援目标 |

参数在引导菜单里通常可以临时编辑（按 `e`），这一次生效、不改配置——这是救急最常用的手段。

## 内核与 initramfs

内核被加载后要做两件事：初始化硬件（加载驱动）、挂载根文件系统并启动第一个用户空间程序。难点在第二步：**要挂载根文件系统，需要先有存储驱动**（SATA/NVMe、LVM、加密卷），而这些驱动往往在模块里，不在内核本体中。于是有了 **initramfs**：一个被打包进内存的小型根文件系统，里面带着挂载真正根所需的驱动与脚本。

```text
内核启动 → 解压 initramfs 到内存 → 执行其中的 init → 加载存储驱动、解锁 LUKS、激活 LVM
        → 找到并挂载真正的根 → switch_root 切换过去 → 执行真正的 init（PID 1）
```

所以「改了内核或存储相关配置后忘了重建 initramfs」是经典事故：内核升级了，initramfs 里还是旧模块，于是卡在 `Waiting for root device` 或直接 kernel panic。反过来，`根文件系统挂载失败` 类报错，第一嫌疑人也总是 initramfs 里缺驱动。

内核日志存在环形缓冲区里，随时可查：

```bash
dmesg | head -50          # 本次启动的内核日志开头
dmesg -T | tail -30       # 带时间戳看最近的硬件/驱动事件
```

`dmesg` 只覆盖内核与驱动；服务层的日志要看 journal（见第 21 章）。

## init：PID 1 的职责

内核挂载根之后，执行的第一个用户空间程序就是 PID 1。今天绝大多数发行版用 **systemd** 担任这个角色。它作为 PID 1 的职责有四类：

1. **挂载文件系统**：按 `/etc/fstab` 挂载剩余文件系统（第 16 章）；
2. **启动服务**：按依赖关系拉起各个单元（unit），并处理失败与重启；
3. **收养孤儿**：任何父进程死掉的进程都会被它接管（第 13 章）；
4. **关机与重启**：接收 `reboot`/`poweroff`，按依赖顺序停止服务、卸载文件系统、同步磁盘。

systemd 用**目标（target）**组织启动阶段，常见的有 `multi-user.target`（多用户命令行）与 `graphical.target`（图形界面）。它取代了传统 SysV 的 runlevel，但你可以粗略对应：runlevel 3 ≈ multi-user，runlevel 5 ≈ graphical。第 32-34 章会详细讲单元、依赖与目标。

## 启动失败怎么查

按阶段对症：

| 现象 | 先查 |
| --- | --- |
| 完全无输出 / 直接进固件 | 启动顺序、ESP 里的 `.efi` 文件、Secure Boot |
| 卡在引导器提示符 | 引导配置是否指向正确的内核与 initramfs |
| `Kernel panic` / `Waiting for root device` | 引导参数 `root=`、initramfs 是否含存储驱动 |
| 卡在某个 job 或进 emergency mode | `journalctl -xb` 看哪个单元失败 |

```bash
journalctl -b            # 本次启动的全部日志
journalctl -b -1         # 上一次启动（排查「上次为什么没起来」）
journalctl -xb -p err    # 本次启动的错误级别日志
systemctl --failed       # 失败的单元列表
```

还有两个「进门」的方式：**rescue.target**（单用户救援：挂载全部文件系统、只保留最基本服务）与 **emergency.target**（只有根文件系统与最基本的 shell，连 `/etc/fstab` 都不完整挂载）。它们的用途不同：rescue 适合修配置，emergency 适合修文件系统与 fstab——注意 emergency 下根通常是**只读**挂载，先 `mount -o remount,rw /` 才能改，改完 `mount -a` 验证（第 16 章）。进入方式一般是临时编辑引导参数加 `systemd.unit=…`。

排障时另一个常用手段是**只读挂载根**：以 `ro` 引导、或从 live 环境挂载磁盘，避免在故障系统上继续写入。这一点在第 38-40 章的维护与排障里会展开。

## 关机、重启与时钟

关机不是「断电」，也有顺序：通知所有进程（`SIGTERM` → 等待 → `SIGKILL`）、停止服务、卸载文件系统、`sync` 落盘、最后断电。直接拔电源跳过全部步骤，代价是文件系统不一致（下次开机 `fsck`）与数据丢失。

系统有两条时间：**RTC（硬件时钟）** 与 **系统时钟**。开机时从 RTC 读一次，之后由 NTP 校准（`chrony`、`systemd-timesyncd` 等）。两者不一致会表现为日志时间错乱、TLS 证书校验失败、`make` 认为文件来自未来。排查时先看 `timedatectl`（通用工具），再决定是改时区还是改同步源。

## 小结

- 五阶段：固件 → 引导器 → 内核 + initramfs → init → 用户空间；排障第一步是定位阶段。
- UEFI 从 ESP 的 `.efi` 加载，启动项在 NVRAM；Secure Boot 会拒绝未签名的引导程序与内核。
- 引导器三件事：加载内核、加载 initramfs、传参；`root=`、`nomodeset`、`systemd.unit=` 是救急三招。
- initramfs 的存在理由是「挂载根之前需要存储驱动」；改了内核或存储配置必须重建它。
- PID 1 四项职责：挂载、启动服务、收养孤儿、关机；目标（target）替代 runlevel。
- 启动失败先按现象定位阶段，再用 `journalctl -b`/`-b -1` 与 `systemctl --failed` 找具体单元。

## 练习

1. 阶段辨认（环境：WSL）：运行 `dmesg | head -20`，指出哪些行属于「硬件探测」、哪些属于「驱动加载」；再运行 `journalctl -b | head -20`，说明为什么 WSL 里的启动日志与裸机差别很大。
2. 启动项侦察（环境：VM）：在虚拟机里查 ESP 的内容（`lsblk -f` 找 FAT32 分区，挂载后 `find` 出 `.efi` 文件），记录引导程序的位置与文件名；再用固件工具列出启动项。
3. 引导参数实验（环境：VM）：临时在引导菜单里加 `systemd.unit=rescue.target` 启动一次，登录后 `systemctl get-default` 与 `systemctl --failed` 各看一次；重启正常进入，确认没有改到持久配置。
4. 上一次启动（环境：VM）：制造一次「服务启动失败」（写一个必然失败的测试单元），重启后分别用 `journalctl -b -1` 与 `systemctl --failed` 找到它，说出两者的信息差异。
5. initramfs 的作用（环境：VM，只读观察）：列出 initramfs 里包含的内核模块，说明为什么存储驱动必须在里面；再回答「如果根分区用了 LVM + 加密，initramfs 还需要装什么」。
6. 关机流程（环境：VM）：对一个写日志的循环脚本执行 `systemctl reboot`，观察它是否收到 `SIGTERM` 并有机会清理；对比直接强制断电（虚拟机关电源）后文件系统是否需要 `fsck`。
