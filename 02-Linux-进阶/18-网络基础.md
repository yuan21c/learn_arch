# 第 18 章 网络基础

网络问题的特点是：报错信息往往只有一行（`Connection refused`、`Temporary failure in name resolution`），而可能的原因横跨网卡、IP、路由、DNS、端口、防火墙六层。这一章不追求把 TCP/IP 讲全，而是给你一套**分层排查的顺序**和每层对应的命令；学会用它们定位问题，比记住所有协议头有用得多。

> 本章目标：能用 `ip` 查看与临时修改地址、链路与路由；用 `ss` 找出谁在监听哪个端口；会用 `ping`、`dig`、`curl` 分层验证连通性；理解 DNS 解析链路与常见记录类型；能配置 SSH 密钥登录、`~/.ssh/config` 与端口转发；理解 nftables 的表/链/规则模型并写出最小可用规则集。
> 对应 Wiki：[Network configuration](https://wiki.archlinux.org/title/Network_configuration)、[Domain name resolution](https://wiki.archlinux.org/title/Domain_name_resolution)、[OpenSSH](https://wiki.archlinux.org/title/OpenSSH)、[Nftables](https://wiki.archlinux.org/title/Nftables)

## 五分钟网络最小集

后面所有命令都站在五个概念上，先用一张表备齐：

| 概念      | 是什么                                     | 看它的命令                  |
| --------- | ------------------------------------------ | --------------------------- |
| IP 地址   | 机器在网络中的门牌，IPv4 形如 `192.0.2.10` | `ip -br addr`               |
| 掩码/前缀 | `/24` = 255.255.255.0，决定谁算同网段      | `ip -br addr` 里的 `/24`    |
| 默认网关  | 出本网段的下一跳路由器                     | `ip route` 的 `default via` |
| 端口      | 进程的门牌，一台机器 65535 个              | `ss -tlnp`                  |
| DNS       | 域名 → IP 的翻译服务                       | `dig +short <域名>`         |

示例地址用 `192.0.2.0/24`、`203.0.113.0/24` 这类**文档保留段**（RFC 5737），不与真实地址冲突；`10.x`、`172.16-31.x`、`192.168.x` 是私网段（RFC 1918），WSL2 的 NAT 地址就落在其中。

## 分层排查：先定层，再动手

遇到「连不上」，按这个顺序走，每层用一个命令确认，确认通过才进下一层：

| 层     | 问题                         | 命令                                                            |
| ------ | ---------------------------- | --------------------------------------------------------------- |
| 1 链路 | 网卡起来了吗？有 IP 吗？     | `ip -br link`、`ip -br addr`                                    |
| 2 路由 | 知道往哪走吗？有默认网关吗？ | `ip route`                                                      |
| 3 连通 | 对端 IP 可达吗？             | `ping -c 4 <IP>`                                                |
| 4 名称 | 域名能解析成 IP 吗？         | `dig +short <域名>`、`getent hosts <域名>`                      |
| 5 端口 | 目标端口开着吗？             | `ss -tlnp`（本机）、`nc -zv <IP> <端口>`（`openbsd-netcat` 包） |
| 6 应用 | 服务真的在跑吗？怎么回应的？ | `curl -v`、`journalctl -u <unit>`                               |

### ip：地址、链路与路由

`ip` 取代了旧的 `ifconfig`/`route`/`arp`，一套命令管全部（环境：WSL，只读）：

```bash
ip -br link          # 链路：网卡名、状态 UP/DOWN、MAC
ip -br addr          # 地址：每个网卡的 IPv4/IPv6
ip route             # 路由表：default via ... 就是默认网关
ip neigh             # ARP/邻居表：同网段 IP 与 MAC 的对应
```

WSL2 默认是 NAT 模式：一个 `eth0` 拿到 `172.x` 私有地址，网关是 Windows 侧的虚拟网桥，外界访问要经过端口转发。新版 Windows 提供 mirrored 模式，让 WSL 与主机共享网络栈——模式不同，排查时的现象也不同（第 40 章讲 WSL 特有问题）。

临时改地址与路由（重启或网络服务重载后失效，持久化配置留给第 45 章）：

```bash
sudo ip addr add 192.0.2.10/24 dev eth0
sudo ip route add default via 192.0.2.1
sudo ip link set eth0 up
```

### ss：谁在监听

服务「没起来」和「起来了但没监听」是两件事。`ss` 直接读内核的 socket 表（环境：WSL，`-p` 需 root 才能看别人的进程）：

```bash
ss -tulpn            # t=TCP u=UDP l=LISTEN p=进程 n=数字端口
ss -tan state established   # 已建立的连接
sudo ss -tlnp 'sport = :22' # 只看 22 端口
```

输出里的 `0.0.0.0:80` 表示监听所有 IPv4 地址，`127.0.0.1:5432` 表示**只**监听本机回环——这是「本机能连、外部连不上」最常见的原因。`[::]:443` 是 IPv6 通配，双栈时通常也接受 IPv4。

## DNS：名字怎么变成地址

解析是一条链：`/etc/nsswitch.conf` 决定顺序（通常是 `files` 再 `dns`），`files` 指 `/etc/hosts`，`dns` 指 `resolv.conf` 里列出的服务器；Arch 上 `resolv.conf` 常由 `systemd-resolved` 或 NetworkManager 生成，**不要手改**（`resolvectl` 的用法见第 39-40 章）。

```bash
cat /etc/hosts                    # 本地静态映射，优先级高于 DNS
cat /etc/resolv.conf              # nameserver 列表
getent hosts archlinux.org        # 走完整 nsswitch 链路，最能代表程序看到的结果
dig +short archlinux.org A        # 直接问 DNS 服务器
dig archlinux.org MX              # 查邮件记录
dig @1.1.1.1 archlinux.org        # 指定服务器，用于对比本地 DNS 是否有问题
```

常见记录类型：`A`（IPv4）、`AAAA`（IPv6）、`CNAME`（别名）、`MX`（邮件）、`TXT`（校验与策略）、`NS`（权威服务器）。`dig` 的 `ANSWER SECTION` 里每个记录带 TTL（秒），表示缓存还能留多久；改完解析不生效，先看 TTL 而不是怀疑配置。`dig` 由 `bind` 包提供，最小系统可能没装。

`getent hosts` 与 `dig` 的结果不一致时，问题多半在 `/etc/hosts` 或 `nsswitch.conf`，而不是 DNS 服务器。

## SSH：远程登录的默认答案

SSH 是加密的远程 shell，也是所有远程运维的地基。密钥登录比密码登录安全且免交互（环境：WSL）：

```bash
ssh-keygen -t ed25519 -C "you@host"     # 生成 ~/.ssh/id_ed25519 与 .pub
ssh-copy-id user@server                 # 把公钥追加到对端 ~/.ssh/authorized_keys
ssh user@server                         # 首次连接会要求确认主机指纹，存入 known_hosts
```

权限是硬要求，但两端各管一段：**服务端**的 `~/.ssh` 与 `authorized_keys` 只要不是「组/其他人可写」就能过 sshd 的 StrictModes 检查（`700`/`600` 是稳妥写法）；**客户端**的私钥若对其他人可读（如 `755`），`ssh` 会拒绝使用并报 `bad permissions`——这是私钥侧的检查，别和 sshd 混为一谈。

`~/.ssh/config` 让长命令变成别名：

```text
Host prod
  HostName 203.0.113.10
  User deploy
  Port 2222
  IdentityFile ~/.ssh/id_ed25519
  ServerAliveInterval 60
```

客户端加固要点：`known_hosts` 里的指纹变化意味着**可能有人中间人**，先核实再删；`StrictHostKeyChecking=no` 不要写进配置。

服务端 `/etc/ssh/sshd_config` 的最小加固（WSL 默认没有 sshd：`sudo pacman -S openssh` 后 `sudo systemctl enable --now sshd`；改完 `systemctl restart sshd`，**先开一个新会话验证能登录，再关旧会话**）：

```text
Port 2222                # 与防火墙放行端口（SSH_PORT）保持一致
PermitRootLogin prohibit-password
PasswordAuthentication no
AllowUsers deploy
```

### 端口转发与文件传输

SSH 能当隧道用，三个方向：

```bash
ssh -L 8080:localhost:80 user@server    # 本地转发：本机 8080 → 服务器 80
ssh -R 9000:localhost:3000 user@server  # 远程转发：服务器 9000 → 本机 3000
ssh -D 1080 user@server                 # 动态转发：本机 1080 起一个 SOCKS 代理
```

文件传输优先 `rsync -avz --progress src/ user@server:/dst/`（可断点续传、只传差异），临时拷贝用 `scp`（其协议已弃用，但用法仍在）。

## 防火墙：nftables 的模型

Arch 默认推荐 nftables（`iptables-nft` 是它的兼容层）。模型只有三层：**表**（按协议族分，`inet` 同时管 IPv4/IPv6）→ **链**（挂在哪个钩子上，`input`/`forward`/`output`）→ **规则**（匹配 + 动作）。查看当前规则（环境：WSL 需 root，且 WSL 内核可能未加载相关模块）：

```bash
sudo nft list ruleset
sudo nft list tables
```

> **危险**：防火墙规则写错会立刻切断正在进行的 SSH。动手前保留一个已登录会话、准备控制台或快照退路；放行的端口必须与 `sshd_config` 的 `Port` 一致（下文用 `SSH_PORT` 表示）。

一个最小可用的入站策略——**先建宽松策略的链，规则全部就位后最后一步才收紧 `policy drop`**；链创建瞬间就 `drop` 的话，已登录 SSH 的回包会被立即丢弃：

```bash
SSH_PORT=2222                       # 与 sshd_config 的 Port 保持一致
sudo nft add table inet filter
sudo nft add chain inet filter input '{ type filter hook input priority 0; policy accept; }'
sudo nft add rule inet filter input ct state established,related accept
sudo nft add rule inet filter input iif lo accept
sudo nft add rule inet filter input tcp dport $SSH_PORT accept
sudo nft add rule inet filter input icmp type echo-request accept
sudo nft add rule inet filter input icmpv6 type '{ echo-request, destination-unreachable, packet-too-big, time-exceeded, parameter-problem, nd-router-advert, nd-neighbor-solicit, nd-neighbor-advert }' accept   # IPv6 邻居发现必须放行
sudo nft 'add chain inet filter input { policy drop; }'   # 规则齐了再收紧
```

顺序即语义：规则自上而下匹配，`policy drop` 在链尾兜底；`ct state established,related accept` 必须在前，否则回包也被丢。更稳的姿势是整份规则写进 `/etc/nftables.conf`，先 `sudo nft -c -f` 预检、再 `sudo nft -f` 原子加载，并启用 `nftables.service` 持久化。第 53 章会把它放进完整的安全加固流程。

## 小结

- 排查分层：链路 → 路由 → 连通 → 名称 → 端口 → 应用；每层一个命令，确认再往下。
- `ip -br addr`/`ip route` 看地址与网关；`ss -tulpn` 看监听，`0.0.0.0` 与 `127.0.0.1` 的区别决定「外部能不能连」。
- 解析链路是 `nsswitch.conf` → `/etc/hosts` → `resolv.conf` 里的 DNS；`getent hosts` 代表程序真实看到的结果。
- SSH 三件事：密钥（`ed25519`）、权限（`700`/`600`）、`~/.ssh/config`；隧道分 `-L`/`-R`/`-D`。
- nftables 三层：表 → 链（含钩子与 `policy`）→ 规则；先放行 `established,related`，最后 `drop` 兜底。

## 练习

1. 分层自查（环境：WSL）：依次运行 `ip -br link`、`ip -br addr`、`ip route`、`ping -c 4 <默认网关>`、`dig +short archlinux.org`、`ss -tulpn`，把输出对应到六层排查表的每一层，说明 WSL 的 NAT 模式在路由表上留下了什么特征。
2. 监听与可达（环境：WSL）：用 `python3 -m http.server 8000 --bind 127.0.0.1` 起一个服务，`ss -tlnp` 确认它只监听回环；再用 `--bind 0.0.0.0` 重启一次，比较两次 `ss` 输出的地址列，并解释对「外部能否访问」的影响。
3. DNS 对照（环境：WSL）：对同一域名分别运行 `getent hosts`、`dig +short`、`dig @1.1.1.1 +short`，若结果不一致，按 `nsswitch.conf` → `/etc/hosts` → `resolv.conf` 的顺序定位原因；再在 `/etc/hosts` 里临时加一条映射（需 root）验证它的优先级。
4. SSH 密钥与配置（环境：VM，或在 WSL 装 openssh 起 sshd）：生成密钥、`ssh-copy-id` 到本地测试账号，配置 `~/.ssh/config` 别名并验证免密登录。再做两个独立实验：客户端侧 `chmod 755 ~/.ssh/id_ed25519` 后连接，观察 `ssh` 报 `bad permissions` 并修复；服务端侧 `chmod g+w ~/.ssh/authorized_keys` 后连接，观察 sshd 拒绝并修复。
5. 端口转发（环境：VM）：用 `ssh -L 8080:localhost:80` 把远端 Web 服务映射到本机 8080，`curl -I localhost:8080` 验证；说明这与直接 `curl` 远端 IP 的区别。
6. nftables 最小策略（环境：VM，**保留一个已登录会话**）：按正文顺序建表、建宽松链、加四条放行规则，最后收紧 `policy drop`；`nft list ruleset` 核对顺序；再用 `nc -zv` 验证 `SSH_PORT` 仍可连、其他端口被拒，最后清理规则。
