# 第 11 章 管道、重定向与权限综合实验

前几章分头讲了路径与通配（第 2 章）、文件与 `find`（第 3 章）、文本流水线（第 4 章）、目录与 inode（第 5 章）、权限（第 6 章）、账号（第 8 章），但真实任务从不用单章知识——总是「先找到、再加工、改权限、落盘验收」的组合拳。本章给出可复用的套路，用三个递进场景热身，最后用一个完整实验把 2-8 章拧成一条流水线。

> 本章目标：能把「定位 → 加工 → 授权 → 验证」串成可重复的命令链；会用 `find/file/stat` 联合文本工具产出分析报告；会用 `find -perm` 做权限巡检并用 chmod/ACL 整改；理解每步的退出码与产物，养成先预览后落地的习惯；独立完成一次覆盖第 2-8 章的综合实验。
> 对应 Wiki：[Core utilities](https://wiki.archlinux.org/title/Core_utilities)、[Category:Commands](https://wiki.archlinux.org/title/Category%3ACommands)

## 组合套路：一条流水线的四个工位

把常见任务拆成四个工位，每个工位只用对应章节的工具：

| 工位 | 要回答的问题         | 主要工具                                 | 来源          |
| ---- | -------------------- | ---------------------------------------- | ------------- |
| 定位 | 东西在哪、是什么     | 通配符、`cd/pwd`、`find`、`file`、`stat` | 第 2、3、5 章 |
| 加工 | 数据长什么样         | 管道、`grep/cut/sort/uniq/awk`、重定向   | 第 4 章       |
| 授权 | 谁能看、谁能改       | `chmod/chgrp/umask`、ACL                 | 第 6、8 章    |
| 验证 | 结果对不对、留没留档 | `ls -l`、`getfacl`、`$?`、报告文件       | 全部          |

三条纪律贯穿始终：**每步只做一件事**，管道才接得起来；**先看屏幕再落盘**——重定向 `>` 会清空目标，先跑不带 `>` 的版本确认输出；**关键步骤查 `$?`**，别让上一步的失败静默混进下一步。所有演练只在自己的 `/tmp/lab9` 里进行，动系统目录前先 `ls` 核对路径。

## 场景一：从日志到统计报告

组合第 2 章的通配与引号、第 4 章的流水线（环境：WSL，/tmp 演练）：

```bash
mkdir -p /tmp/lab9 && cd /tmp/lab9
printf 'web INFO start\nweb ERROR timeout\ndb INFO ready\nweb ERROR retry\ndb ERROR lock\n' > app.log
grep -c ERROR app.log                      # 3，有匹配时退出码 0
grep ERROR app.log > err.txt               # 重定向落盘
cut -d' ' -f2 app.log | sort | uniq -c     # 3 ERROR、2 INFO：按级别统计（文本序 E 在 I 前）
wc -l *.log                                # 通配符一次统计全部日志
```

报告类任务的收尾动作是**落盘再复核**：`xxx > report.txt` 之后补一句 `wc -l report.txt`（或 `head report.txt`），确认产物非空、行数合理——空报告和报错报告是流水线最常见的两种「假成功」。

## 场景二：权限与文件巡检

定位加授权工具的组合（环境：WSL，实跑）：

```bash
find /usr/bin -maxdepth 1 -perm -4000        # SUID 巡检：passwd、sudo、su…
find . -name '*.log' -exec stat -c '%n %a %U' {} \;   # 名称+数字权限+属主一次取全
find . -type f -perm -0002                    # 找出人人可写的文件（当前应无输出）
```

三个细节：`stat -c %a` 输出数字权限（如 `644`），比解读 `ls -l` 字符串快；`-perm -4000` 的含义是「SUID 位必须置位」，`-perm -0002` 同理盯 other 可写——第 6 章说过，目录的 other 可写加无 Sticky 等于人人可删；巡检要**成对出现**：先 `find` 列出问题文件，整改（`chmod go-w`、`chmod u-s`）后再跑一遍确认清零。

## 场景三：组共享目录与报告归档

授权从「给谁」出发，先看身份再动权限（环境：WSL，实跑）：

```bash
id -Gn                                    # 自己在哪些组里（示例用户名请换成 $(id -un)）
getent group wheel                         # wheel:x:998:arch
mkdir -p shared && chgrp wheel shared && chmod 2775 shared   # SGID 组共享目录
chmod 600 app.log                          # 敏感产物只留属主
ls -l app.log shared                       # 用输出验证，而不是相信记忆
```

这条链把第 6、8 章接通了：`chgrp` 能否成功取决于 `getent group` 里的成员表；`2775` = SGID + 组可写 + 他人可读可进；需要给**组外**的特定用户开权限时，用第 6 章的 `setfacl -m u:名:rw 文件`，比把文件塞进某个组更精确。

## 断点排查：链子在哪里断的

流水线一旦变长，失败会以「静默」的形式出现——前半截没报错、后半截输出为空，报告却已经生成。两个通用手法：**拆链**（把管道从中间截断，逐段单独运行，看数据在哪一段消失）和**读退出码**（每段后 `echo $?`，`1` 往往是「没匹配」，`2` 是命令本身出错）。常见断点对照：

| 症状                 | 断点在哪                    | 处置                                  |
| -------------------- | --------------------------- | ------------------------------------- |
| `command not found`  | 名字没进 PATH（第 10 章）    | `command -v` 确认；补路径或全路径执行 |
| `Permission denied`  | 权限位或属主不对（第 6 章） | `ls -l` 看三件套；需要时 `sudo`       |
| `find`/`grep` 无输出 | 条件太严或路径敲错          | `pwd` 核对起始路径，逐个放宽条件      |
| 报告文件是空的       | `>` 先清空、命令后失败      | 先跑不带 `>` 的版本看输出             |
| 数字顺序奇怪         | 忘了 `sort -n`（第 4 章）   | 文本序与数字序是两回事                |

排查的顺序也有讲究：先看**报错文本**（stderr 不进管道，往往直接指出断点），再看 `$?`，最后才拆管道——多数断链在第一步就现形。

## 小结

- 组合拳四工位：定位（2/3/5 章）→ 加工（4 章）→ 授权（6/8 章）→ 验证（全部）。
- 三条纪律：一步一事、先看后落盘（`>` 会清空）、关键步查 `$?`。
- `stat -c %n %a %U` 一次取「名字+数字权限+属主」；`find -perm -4000/-0002` 是权限巡检的标准问句。
- 授权前先 `id`/`getent group` 看身份；组共享用 SGID 目录，指定人用 ACL，敏感产物 `chmod 600`。
- 巡检要成对：发现问题 → 整改 → 复跑确认清零。

## 练习

综合实验：为「小组日志归档」搭一条完整流水线，每步都留下可验证的产物（环境：WSL，需 sudo 的步骤已标出；`blkid`、`ss -p` 这类读系统状态的命令要 root；全部在 `/tmp/lab9` 内，不碰系统文件）。

1. **布场**（第 2 章，环境：WSL）：`mkdir -p /tmp/lab9/team && cd /tmp/lab9`，用 `pwd` 确认位置；`touch team/.keep app.log` 后 `ls -la` 看见隐藏文件。

2. **造数据**（第 4 章，环境：WSL）：

   ```bash
   printf 'web INFO start\nweb ERROR timeout\ndb INFO ready\nweb ERROR retry\ndb ERROR lock\n' > app.log
   seq 1 30 > team/nums.txt
   ```

3. **分析出报告**（第 4 章，环境：WSL）：`grep -c ERROR app.log; echo $?` 记录计数与退出码；`cut -d' ' -f2 app.log | sort | uniq -c` 按级别统计；把统计结果重定向进 `report.txt`，再用 `wc -l report.txt` 复核非空。

4. **定位与判型**（第 3、5 章，环境：WSL）：`find /tmp/lab9 -name '*.txt'` 找出全部文本文件；对 `app.log` 跑 `file app.log` 与 `stat -c '%n type=%F size=%s inode=%i' app.log`，回答它是什么类型、多大、inode 号多少。

5. **权限整改**（第 6 章，环境：WSL）：`chmod 600 app.log report.txt` 收紧报告；`chgrp wheel team && chmod 2775 team` 让归档目录进入组共享模式，然后 `touch team/after.txt && ls -l team`——对比创建在改组**前**的 `nums.txt` 与**后**的 `after.txt`，解释属组为何一个没变、一个变成了 `wheel`（注意：新条目继承的是**目录当前的属组**，所以先 `chgrp wheel` 才有 `wheel` 可继承，且只影响改组之后创建的文件）；`umask` 记下当前值，用第 6 章公式核对 `team/nums.txt` 的权限。

6. **组与身份验证**（第 8 章，环境：WSL）：`id -Gn` 与 `getent group wheel` 双向确认你在组里；`chgrp wheel report.txt` 无需 sudo 即成功，`sudo chown arch:arch report.txt` 则必须特权——对照两者体会边界并把属组还原；`setfacl -m u:nobody:r report.txt` 给指定用户加一条只读，`getfacl report.txt` 找出 `mask` 行，对照第 6 章说明它对具名条目的上限作用。

7. **复巡检**（第 3、6 章，环境：WSL）：`find /tmp/lab9 -type f -perm -0002` 应无输出；`find /tmp/lab9 -name '*.log' -exec ls -l {} \;` 逐个列出日志的最终权限；用 `ls -l /tmp/lab9 /tmp/lab9/team` 交卷，对照第 1 步确认每处改动都符合预期。

8. **自主加题**（环境：WSL）：在清场之前写一条命令，找出 `/tmp/lab9` 里「1 天内修改过且 other 可读」的文件（提示：`find /tmp/lab9 -type f -mtime -1 -perm -0004`），把结果**追加**到 `report.txt`——解释这一步为什么必须用 `>>` 而不是 `>`（第 4 章），并对照第 5、6 步说明为什么 `app.log` 不在结果里。

9. **清场**（环境：WSL）：`ls /tmp/lab9` 核对路径后再 `rm -rf /tmp/lab9`；`test -e /tmp/lab9; echo $?` 用退出码 1 确认已删干净（**危险**：`rm -rf` 前永远先 `ls` 看一眼路径）。
